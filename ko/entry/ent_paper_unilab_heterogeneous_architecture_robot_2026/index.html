UniLab: A Heterogeneous Architecture for Robot RL Beyond GPU-Dominant Paradigms

요약

Simulation-based RL for contemporary robot control is increasingly organized around GPU-resident simulation: physics, rollout collection, and learning are placed on a single GPU-centric execution path. Institutions per source list: THU、SJTU、SII、Motphys、DISCOVER Robotics、Dexmal.

출처

  • arXiv:2605.30313 UniLab: A Heterogeneous Architecture for Robot RL Beyond GPU-Dominant Paradigms
  • GitHub仓库 Robotics_Notebooks

개요

UniLab은 이기종 CPU-시뮬레이션/GPU-학습 로봇 RL 훈련 아키텍처를 제안하며, "효율적인 훈련은 GPU 상주 시뮬레이션이 필수"라는 커뮤니티의 암묵적 가정에 도전한다. 이 시스템은 MuJoCoUni와 MotrixSim이라는 두 개의 CPU 물리 백엔드를 통합 런타임과 조정하여 PPO, SAC, TD3, APPO 등의 알고리즘에서 3–10배의 종단 간 훈련 효율성 향상을 달성하고, Apple macOS, AMD ROCm, Intel XPU 크로스 플랫폼 배포를 지원한다.

그것이 바꾸는 것

이 논문이 실제로 바꾸는 것은 로봇 RL 훈련 시스템의 "하드웨어 역할 분담"에 대한 사고 모델이다. 커뮤니티의 기본 설정(Isaac Gym, Isaac Lab, Genesis 등)은 물리 시뮬레이션, 롤아웃 수집, 정책 학습을 모두 단일 GPU 실행 경로에 묶어두지만, 이는 엔지니어링 구현을 단순화하는 대신 고처리량 실험을 GPU 상주 소프트웨어 스택에 가둬버린다. 저자들은 로봇 RL이 폐루프 시스템이며, 종단 간 효율성은 물리 시뮬레이션이 실행되는 프로세서에 의해서만 결정되는 것이 아니라 시뮬레이션 처리량, 학습자 활용률, 수집기-학습자 동기화, 데이터 이동 및 버퍼 오버헤드의 결합 최적화에 달려 있다고 지적한다. GPU 커널은 규칙적이고 밀집되며 정적 형태의 실행에 능숙하지만, 동적 활성 접촉 집합, 희소 상호작용, 충돌 처리, 폐쇄 사슬 제약과 같은 접촉이 풍부한 연산은 오히려 GPU 시뮬레이션의 취약 지점이다.

따라서 UniLab은 문제를 "시뮬레이션-학습 폐루프의 시스템 구성 문제"로 재정의한다: CPU는 대규모 배치 강체 시뮬레이션과 데이터 생성을 담당하고, GPU는 정책 및 가치 학습에 집중하며, 통합 런타임이 조정 비용을 최소화한다. 이러한 전환의 본질은 각 하드웨어에 역할이 있음을 인정하는 것이다—CPU의 유연성과 높은 코어 수는 병렬 환경 스테핑에 더 적합하고, GPU의 행렬 처리량은 밀집 학습 업데이트에 더 적합하다—단일 가속기가 모든 것을 처리하게 하는 대신. 논문은 통제된 단일 CPU/단일 GPU 설정에서 이러한 이기종 역할 분담이 실현 가능할 뿐만 아니라 벽시계 효율성에서 GPU 상주 패러다임과 견줄 수 있거나 능가할 수 있음을 증명한다.

방법 분해

아키텍처 개요

UniLab은 세 부분으로 구성된다: CPU 측 시뮬레이션 백엔드(MuJoCoUni, MotrixSim), GPU 측 학습자(PPO/APPO/SAC/TD3/FlashSAC), 통합 런타임(데이터 이동, 버퍼링, 스케줄링, 파라미터 동기화 조정).

수집-업데이트 타이밍

  • 동기 모드(표준 PPO): CPU 수집기가 고정 시야 롤아웃을 생성하고, GPU 학습자가 전체 업데이트를 수행하며, 둘은 교대로 진행된다.
  • 느슨한 결합 모드(APPO): 수집기는 고정 시야 롤아웃, 행동 정책 로그 확률, 부트스트랩 정보를 공유 링 버퍼에 쓰면서 동시에 CPU에서 다음 롤아웃을 스테핑한다; 학습자는 GPU에서 사용 가능한 롤아웃을 비우고 V-trace 보정과 PPO 스타일 업데이트를 수행한다. CPU 수집과 GPU 학습은 벽시계 시간에서 중첩되며, 파라미터 동기화는 롤아웃 경계에 가깝게 이루어진다.
  • 재생 모드(SAC/TD3/FlashSAC): 수집기는 전이 배치를 공유 재생 버퍼에 삽입하고, 학습자는 디바이스 배치에서 여러 업데이트를 수행한다. 최적화 경로는 한 틱 앞서 CPU 재생 패킹과 디바이스 전송을 요청하여 현재 학습자 업데이트와 중첩시킨다.

재생 경로 최적화(부록 A)

핵심 설계는 재생 경계를 재생 버퍼에서 샘플링 배치로 이동시키는 것이다: 1. 수집기는 CPU 액터 추론, 환경 스테핑, 재생 삽입을 수행한다. 2. 학습자가 다음 훈련 배치를 요청하면, 수집기는 CPU 재생 스냅샷에서 샘플링하여 두 개의 공유 패킷 슬롯 중 하나에 패킹한다. 3. CUDA에서 패킷 슬롯은 고정 호스트 메모리 소스로 등록되어 비동기 H2D 전송에 사용된다. 4. 학습자 측 백그라운드 H2D 제출 스레드는 학습자가 현재 핫 슬롯을 소비하는 동안 패킹된 배치를 콜드 GPU 배치 슬롯으로 전송한다.

런타임 추상화

통합 런타임은 동기 및 느슨한 결합 실행이 하나의 시스템 스택을 공유하도록 하며, 명시적 인터페이스를 통해 로봇 자산, 작업 구성, 시뮬레이션 백엔드, 학습 알고리즘을 연결한다. 공유 인터페이스는 시뮬레이터 백엔드와 학습자 가속기 백엔드를 분리하며, 학습자는 Apple macOS, AMD ROCm, Intel XPU에 매핑될 수 있다.

핵심 혁신

  1. 하드웨어 역할 분담의 재정의: GPU 상주 시뮬레이션을 요구하지 않고, "CPU가 대규모 시뮬레이션 데이터를 생성하고, GPU가 밀집 학습 업데이트를 수행하며, 런타임이 조정 비용을 최소화한다"는 원칙을 따른다. 이는 GPU 중심 패러다임에 대한 직접적인 도전이며, 통제된 실험으로 효율성이 견줄 수 있음을 증명한다.

  2. 이중 버퍼 재생 경로: 재생 경계를 버퍼에서 샘플링 배치로 이동시키고, 공유 패킷 슬롯과 백그라운드 H2D 제출 스레드를 통해 수집기 패킹과 학습자 업데이트의 벽시계 중첩을 구현한다. 부록 A 데이터에 따르면 이 최적화는 주기 시간을 211 ms에서 136 ms로, 수집기 정지를 103 ms에서 <1 ms로 줄이고 훈련 시간을 34.34% 단축한다.

  3. 크로스 플랫폼 이식성: 공유 인터페이스는 학습자를 Apple macOS, AMD ROCm, Intel XPU에 매핑할 수 있게 하여, GPU 상주 패러다임의 NVIDIA CUDA 생태계 종속을 깨뜨린다. 표 3은 M5 Max에서 PPO G1 Flip Tracking 훈련 시간이 16.8분으로, RTX 4090 + AMD 9950X3D의 16.4분과 견줄 만함을 보여준다.

통제 비교는 기본 Linux 하드웨어(RTX 4090 + AMD Ryzen 9 9950X3D + 64 GB)에서 수행되었으며, 작업은 사족, 바퀴형 사족, 휴머노이드, 손재주 조작을 포함한다.

부록 A 타임라인 통계(A100 머신): 이중 버퍼 경로는 주기 시간을 211 ms에서 136 ms로, 수집기 정지를 103 ms에서 <1 ms로, 복구 간격을 12.3 ms에서 2.9 ms로 줄인다; 500 반복 추적에서 훈련 시간이 107.50 s에서 70.58 s로 감소(-34.34%); 환경 스텝/초가 9.69k에서 15.05k로 증가. UniLab에서 학습자 측 재생 소비는 평균 0.23 ms, CPU 패킹 6.30 ms, GPU H2D 전송 3.13 ms로, 99.50%의 수집기 활동이 학습자 업데이트와 중첩된다.

느슨한 결합 훈련에서 APPO, SAC, FlashSAC는 3–10배의 종단 간 훈련 효율성 개선을 얻는다.

경계와 한계

논문은 GPU 상주 시뮬레이션이 구식이라고 명시적으로 주장하지 않는다: 시뮬레이터 처리량이 더 이상 지배적 병목이 아니거나, 더 큰 가속기로 풍부한 구성을 사용하거나, 전용 GPU 네이티브 스택이 이기종 실행보다 우수한 경우 GPU 시뮬레이션이 여전히 더 바람직할 수 있다. UniLab은 시뮬레이션이 지배적이고 시뮬레이션이 학습과 효과적으로 분리될 수 있을 때 가장 유리하다; 엄격한 동기 파이프라인이나 렌더링, 인식, 표현 학습이 지배하는 시각 워크로드는 이점이 적을 수 있다. 주장은 통제된 단일 CPU/단일 GPU 설정에서의 종단 간 훈련 효율성에 국한되며, 극단적 규모에서의 절대 최고 처리량을 다루지 않는다; 다중 GPU 또는 더 큰 분산 구성은 균형을 바꿀 수 있다. 현재 구현은 강체 로봇 제어에 초점을 맞추며, 변형 가능한 물체, 소프트 바디, 유체를 다루지 않는다. 작업 범위, 성능, 연산자 범위, 알고리즘 성숙도는 백엔드 간에 고르지 않다. 물리 의미론이 sim-to-sim 또는 sim-to-real 견고성에 미치는 영향에 대한 전용 실험은 수행되지 않았다. 추적은 완전한 인과 절제가 아니다. 학습자 업데이트 커널의 지속 시간도 두 추적에서 다르기 때문이다. G1 Box Tracking은 APPO에서 사용 불가; Go2 Arm Manip Loco는 MuJoCoUni에서만 사용 가능; Sharpa Inhand의 접촉 위치 채널은 현재 0이며, 백엔드 접촉 프레임 지원을 기다리고 있다.

엔지니어링 시사점

UniLab을 재현할 때 먼저 하드웨어 구성과 백엔드 선택을 확인하라: 기본 Linux 워크스테이션은 RTX 4090 + AMD Ryzen 9 9950X3D + 64 GB 4800 MT/s 메모리이고, 부록 A 추적 머신은 A100 80 GB + 듀얼 Intel Xeon Gold 5320 + 188 GiB 메모리이다. 가장 쉽게 함정에 빠지는 부분은 재생 경로 최적화이다—이중 버퍼 패킷 슬롯은 CUDA 고정 호스트 메모리와 백그라운드 H2D 제출 스레드에 의존하며, 고정 메모리 소스를 올바르게 등록하지 않으면 비동기 전송이 동기 복사로 퇴화하여 주기 시간이 136 ms가 아닌 211 ms 수준으로 돌아갈 수 있다. 또 다른 핵심 포인트는 작업 수준 하이퍼파라미터 오버라이드이다: PPO 기본 num_envs=4096, num_steps_per_env=24이지만, G1 모션 추적 작업은 1024로, Allegro는 16384로 올라가며, G1 Flip은 MuJoCoUni/MotrixSim에서 max_iterations가 각각 20000/30000이다—전역 기본값을 그대로 적용하면 비교 불가능한 결과가 나온다. 크로스 백엔드 이식 시 도메인 무작위화 차이에 주의하라: MotrixSim에서 G1 Walk Rough는 Kp/Kd 무작위화가 비활성화되고, Sharpa 중력 무작위화는 방향에만 국한되며, G1 Flip은 MotrixSim에서 앵커/엔드 이펙터 z 오차 임계값이 환경 기본값으로 되돌아간다. 하류 팀에게는 작은 작업(예: Go2 Joystick Flat, FlashSAC 1.1분)에서 이중 버퍼 경로가 작동하는지 먼저 검증한 후 G1 모션 추적과 같은 긴 훈련 작업으로 확장할 것을 권장한다.
