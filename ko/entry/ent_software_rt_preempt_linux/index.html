요약

Linux 커널 대부분을 선점 가능하게 만들어 결정적·저지연 실시간 동작을 제공하는 커널 패치 집합.

출처

  • Wiki extraction

개요

Linux RT-PREEMPT는 Linux 커널의 대부분을 선점 가능하게 만들고 인터럽트를 스레드화하는 커널 패치 세트로, 결정론적 저지연 실시간 동작을 제공하는 것을 목표로 하며, 현재 휴머노이드 로봇 메인 제어 컴퓨터의 실시간 코어를 위한 주류 솔루션입니다. Linux 생태계(드라이버, ROS 2, 컨테이너 도구 체인)를 완전히 보존하면서 최악의 경우 지연 시간을 밀리초 단위에서 수십 마이크로초 수준으로 낮춥니다. 실제로 바꾸는 것은 "Linux가 실시간이 될 수 있는가"가 아니라 "로봇 메인 제어가 AI와 제어를 동시에 실행할 수 있는가"입니다.

핵심 내용

무엇인가: 정확한 정의

Linux RT-PREEMPT(PREEMPT_RT라고도 함)는 표준 Linux 커널을 위한 패치 세트로, 커널 선점과 인터럽트 스레드화라는 두 가지 메커니즘을 통해 범용 Linux 커널을 하드 실시간 기능을 갖춘 운영 체제로 변환하는 것을 핵심 목표로 합니다. 독립적인 운영 체제가 아니라 메인라인 Linux 커널에 대한 지속적인 패치 흐름입니다. 커뮤니티가 장기간 유지 관리하며 실시간 기능을 점진적으로 메인라인에 통합합니다.

소프트웨어 계층 관점에서 Linux RT-PREEMPT는 하드웨어 위, 로봇 미들웨어(예: ROS 2) 아래에 위치하며 운영 체제 및 드라이버 계층에 속합니다. 휴머노이드 로봇의 전형적인 이기종 컴퓨팅 아키텍처에서 일반적으로 표준 Linux 코어, QNX 실시간 코어와 함께 사용됩니다. RT-PREEMPT 실시간 코어는 제어 루프를 실행하고, 표준 Linux 코어는 인식 및 AI 추론을 실행하며, 두 코어 간에는 공유 메모리 또는 결정론적 이더넷 채널을 통해 데이터를 교환합니다.

왜 존재하는가: 문제점과 역사적 위치

범용 운영 체제(예: 표준 Linux)는 하드 실시간용으로 설계되지 않았습니다. 커널의 비선점 영역, 인터럽트 처리 및 스케줄러의 비결정성은 제어할 수 없는 지연 스파이크를 유발할 수 있습니다. 휴머노이드 로봇은 타이밍 요구 사항이 매우 엄격합니다. 전신의 수십 개 액추에이터가 밀리초 주기로 폐루프를 형성하며, 안전 관련 기능(비상 정지, 토크 제한, 낙상 보호)은 결정론적 응답을 강제합니다. 제어 루프가 지연 스파이크를 겪으면 가벼운 경우 보행 품질에 영향을 주는 떨림이 발생하고, 심한 경우 불안정 또는 안전 사고로 이어질 수 있습니다.

RT-PREEMPT가 등장하기 전에는 엔지니어들이 두 가지 선택지 사이에서 딜레마에 빠졌습니다. QNX와 같은 상용 RTOS를 사용하여 생태계 풍부함을 희생하고 라이선스 비용을 부담하거나, 표준 Linux의 타이밍 불확실성을 감수하는 것이었습니다. Linux RT-PREEMPT의 역사적 위치는 바로 이 공백을 메우는 것입니다. 개발자가 Linux 생태계를 떠나지 않고도 하드 실시간에 가까운 결정론을 얻을 수 있게 하여 최악의 경우 지연 시간을 밀리초 단위에서 수십 마이크로초 수준으로 낮춥니다(공학적 판단). 실제로 바꾸는 것은 "Linux가 실시간이 될 수 있는가"가 아니라 "로봇 메인 제어가 AI와 제어를 동시에 실행할 수 있는가"입니다. 즉, 원래 두 개의 이기종 칩이 각각 담당하던 작업을 동일한 멀티코어 프로세서로 수렴시킵니다.

원리 분석

① 커널 선점: 비선점 영역 축소

표준 Linux 커널에는 많은 비선점 임계 영역(예: 스핀락으로 보호되는 코드 섹션)이 존재하며, 실시간 작업은 이러한 영역에서 스케줄링될 수 없습니다. RT-PREEMPT는 다음 수단을 통해 대부분의 임계 영역을 선점 가능하게 변환합니다.

  • 스핀락을 절전 가능한 뮤텍스(rtmutex)로 교체하여 고우선순위 작업이 락을 보유한 저우선순위 작업을 선점할 수 있게 합니다.
  • 우선순위 상속 프로토콜을 도입하여 우선순위 역전으로 인한 고우선순위 작업의 무한 차단을 방지합니다.
  • 커널 코드 경로 자체를 선점 가능하게 만들고, 인터럽트 핸들러를 스케줄러가 일시 중단할 수 있게 합니다.

② 인터럽트 스레드화: 인터럽트를 스케줄 가능한 엔터티로 변환

기존 Linux에서 인터럽트 핸들러(ISR)는 비선점 컨텍스트에서 실행되며 실행 시간을 제어할 수 없습니다. RT-PREEMPT는 인터럽트 핸들러를 커널 스레드(IRQ threads)로 변환하고 우선순위 속성을 부여하여 인터럽트 응답 시간을 예측 가능하게 만듭니다. 매우 높은 실시간 요구 사항이 있는 인터럽트(예: EtherCAT 동기 인터럽트)는 스레드화되지 않은 빠른 처리 경로로 유지될 수 있습니다.

③ 병행 엔지니어링 실무: 결정론은 패치만으로 주어지지 않음

RT-PREEMPT 패치 자체는 "가능성"만 제공하며, 엔지니어링 실무가 결정론을 실현합니다. 자료에 명시된 병행 수단은 다음과 같습니다.

  • CPU 격리(isolcpus): 실시간 작업이 바인딩된 CPU 코어를 범용 스케줄러에서 격리하여 일반 프로세스의 선점을 방지합니다.
  • 인터럽트 친화성 바인딩: 중요 인터럽트(예: EtherCAT 마스터 인터럽트)를 특정 CPU 코어에 바인딩하여 실시간 작업과 동일 코어 또는 다른 코어에 배포합니다.
  • 메모리 잠금(mlockall): 실시간 스레드의 페이지 스왑 인/아웃으로 인한 예측 불가능한 지연을 방지합니다.
  • 실시간 우선순위(SCHED_FIFO): 실시간 스레드에 고정 우선순위를 할당하여 일반 프로세스보다 우선적으로 스케줄링되도록 보장합니다.

전형적인 스케줄링 설계는 다음과 같습니다. EtherCAT 마스터와 전신 제어(WBC) 작업을 독립 CPU 코어에 바인딩하고, 최고 SCHED_FIFO 우선순위를 부여하며 메모리를 잠급니다. 정책 추론과 일반 프로세스는 나머지 코어를 공유하며 cgroups를 통해 선점 간섭을 제한합니다. 모든 실시간 스레드는 동적 메모리 할당과 비결정론적 시스템 호출을 비활성화합니다.

수평 비교

QNX와 비교: QNX는 상용 마이크로커널 RTOS로, 파일 시스템과 네트워크 스택이 모두 사용자 공간 서비스이며 커널은 최소 기능만 유지합니다. 드라이버 오류가 커널로 확산되지 않으며 기능 안전 인증 자격을 갖추고 있습니다. 대가는 생태계와 라이선스 비용입니다. RT-PREEMPT의 장점은 Linux 생태계(드라이버, ROS 2, 컨테이너 도구 체인)를 완전히 보존하는 것이고, 단점은 안전 인증을 자체 구축해야 한다는 것입니다. 전형적인 휴머노이드 로봇은 "QNX 또는 RT-PREEMPT 실시간 코어로 제어 실행 + 표준 Linux 코어로 인식 및 AI 실행"의 이기종 조합을 채택하며, 안전 관련 기능은 실시간 측에 강제로 배치됩니다.

Xenomai와 비교: Xenomai는 이중 커널 솔루션으로, 실시간 작업은 Cobalt 실시간 코어에서 실행되며 지연 시간이 마이크로초 수준까지 낮을 수 있지만 유지보수가 복잡합니다. RT-PREEMPT는 단일 커널 솔루션으로 유지보수 비용이 낮지만 지연 수준은 수십 마이크로초입니다. 둘 다 Linux 사용자 공간 생태계를 재사용하지만, Xenomai의 실시간 작업은 전용 API를 사용해야 하는 반면 RT-PREEMPT의 실시간 작업은 표준 POSIX 인터페이스를 직접 사용합니다.

Zephyr와 비교: Zephyr는 리소스가 제한된 임베디드 장치를 위한 오픈 소스 RTOS로, 센서 노드와 모터 컨트롤러에 자주 사용되며 생태계 풍부함이 낮습니다. RT-PREEMPT는 메인 제어 컴퓨터를 대상으로 하며, 둘의 설치 위치가 다르므로 일반적으로 동일한 로봇에 공존합니다. RT-PREEMPT는 메인 제어를 실행하고 Zephyr는 관절/센서 노드를 실행합니다.

누가 사용하는가·응용 사례

Linux RT-PREEMPT는 현재 휴머노이드 로봇 실시간 코어의 주류 솔루션으로, 프로토타입 검증, 학술 연구 및 초기 상용 제품에 널리 사용됩니다. 자료에 제시된 전형적인 배포 패턴:

  • 메인 제어 컴퓨터: RT-PREEMPT 실시간 코어가 EtherCAT 마스터와 WBC 작업을 담당하며, 독립 CPU 코어에 바인딩되고 최고 SCHED_FIFO 우선순위를 가지며 메모리를 잠급니다.
  • 이기종 조합: 표준 Linux 코어와 함께 사용되며, 실시간 코어는 제어를 실행하고 표준 코어는 인식 및 AI를 실행하며, 두 코어 간에는 공유 메모리 또는 결정론적 이더넷 채널을 통해 데이터를 교환합니다.
  • 안전 기능 구현: 비상 정지, 토크 제한, 낙상 보호 등 안전 관련 기능은 실시간 측에 강제로 배치됩니다.

병행 엔지니어링 실무에는 다음도 포함됩니다. 정책 추론과 일반 프로세스는 나머지 코어를 공유하며 cgroups를 통해 선점 간섭을 제한합니다. 모든 실시간 스레드는 동적 메모리 할당과 비결정론적 시스템 호출을 비활성화합니다.

한계와 경계

  1. 지연 수준의 상한: RT-PREEMPT의 스케줄링 지연은 수십 마이크로초 수준으로 Xenomai와 QNX의 마이크로초 수준보다 낮습니다. 마이크로초 수준의 결정론이 필요한 응용(예: 일부 안전 중요 제어 루프)에는 충분하지 않을 수 있습니다.
  2. 안전 인증 자체 구축 필요: QNX에 성숙한 인증 사례가 있는 것과 달리 RT-PREEMPT의 안전 인증 기반은 "자체 구축 필요"입니다. 즉, 기능 안전 표준(예: IEC 61508, ISO 13849)의 제약 하에서 RT-PREEMPT를 사용하려면 추가 인증 작업이 필요합니다.
  3. 결정론은 엔지니어링 실무에 의존: 패치 자체는 결정론을 보장하지 않으며, CPU 격리, 인터럽트 친화성 바인딩, 메모리 잠금 등의 병행 수단이 모두 필수입니다. 구성이 잘못되면 여전히 지연 스파이크가 발생할 수 있습니다.
  4. 실시간 스레드의 프로그래밍 제약: 모든 실시간 스레드는 동적 메모리 할당과 비결정론적 시스템 호출을 비활성화해야 하며, 이는 개발자의 프로그래밍 습관에 대한 요구 사항입니다.

일반적인 오해

  1. "RT-PREEMPT 패치를 적용하면 실시간이 된다" — 틀림. 패치는 "가능성"만 제공하며, CPU 격리, 인터럽트 친화성 바인딩, 메모리 잠금, SCHED_FIFO 우선순위 등의 엔지니어링 실무가 모두 필수입니다. 자료는 후자를 "병행 엔지니어링 실무"로 명시합니다.
  2. "RT-PREEMPT 지연이 QNX보다 낮다" — 틀림. 자료의 비교표에서 RT-PREEMPT의 스케줄링 지연 수준은 "수십 마이크로초"이고 QNX는 "마이크로초 수준"입니다. RT-PREEMPT의 장점은 생태계에 있으며 지연 절대값에 있지 않습니다.
  3. "RT-PREEMPT와 표준 Linux는 둘 중 하나만 선택해야 한다" — 틀림. 전형적인 배포는 이기종 조합입니다. RT-PREEMPT 실시간 코어는 제어를 실행하고 표준 Linux 코어는 인식 및 AI를 실행하며, 두 코어 간에는 공유 메모리 또는 결정론적 이더넷 채널을 통해 데이터를 교환합니다.
  4. "실시간 스레드는 동적 메모리 할당을 자유롭게 사용할 수 있다" — 틀림. 모든 실시간 스레드는 동적 메모리 할당과 비결정론적 시스템 호출을 비활성화해야 하며, 그렇지 않으면 예측 불가능한 지연이 발생합니다.

관련 지식

  • ent_software_ros_2_middleware_2024 — ROS 2 미들웨어는 RT-PREEMPT 위에서 실행되며, 게시/구독 통신의 결정론은 하위 운영 체제의 실시간 기능에 의존합니다.
  • ent_software_qnx — QNX는 RT-PREEMPT와 나란히 선택할 수 있는 실시간 운영 체제 옵션으로, 마이크로커널 아키텍처와 안전 인증 자격이 차별화된 장점입니다.
  • ent_paper_gutierrez_real_time_linux_communications_2018 — 이 연구는 PREEMPT-RT Linux에서 UDP 통신 실시간 성능을 평가하여 CPU/IRQ 격리가 지연 경계를 유지하는 데 효과적임을 검증했습니다.
