개요

CI/CD 및 시뮬레이션 테스트 체인(CI/CD and simulation test chain)은 휴머노이드 로봇 소프트웨어 미들웨어 및 시스템 통합 단계(P14)의 핵심 공정 노드로, GitLab CI, Docker, SIL/HIL 자동화 테스트 및 코드 커버리지 도구를 통해 코드 커밋부터 자동화 검증까지의 지속적 통합 파이프라인을 구축합니다. 이 공정이 실제로 바꾸는 것은 "테스트 도구의 수"가 아니라 "소프트웨어 품질 문제의 발견 시점"입니다. 즉, 회귀 결함을 메인 브랜치 통합 전에 차단하고, 전체 기계 연동 디버깅 때까지 노출되는 것을 방지합니다. 이 공정은 5개의 세부 하위 작업(P14.2.3.1~P14.2.3.5)으로 전개되며, 입력 정량화부터 하류 전달까지의 완전한 엔지니어링 폐루프를 포괄합니다.

핵심 내용

정의: 정확한 정의

CI/CD 및 시뮬레이션 테스트 체인은 지속적 통합(Continuous Integration), 지속적 전달(Continuous Delivery) 및 시뮬레이션 테스트(Simulation Testing) 를 긴밀하게 결합한 엔지니어링 방법론 체계입니다. 휴머노이드 로봇 개발 프로세스에서 이는 소프트웨어 미들웨어 및 시스템 통합 단계(P14) 내부에 위치하며, P14.2 워크팩의 3차 하위 작업으로 번호 P14.2.3으로 존재합니다.

핵심 구성은 4가지 기술 기둥으로 이루어집니다:

  • GitLab CI: 파이프라인 오케스트레이션 엔진으로, 코드 커밋부터 빌드, 테스트, 패키징까지의 자동화 프로세스를 정의합니다.
  • Docker: 환경 일관성을 보장하여 "내 컴퓨터에서는 실행된다"는 말이 파이프라인에서 더 이상 성립하지 않게 합니다.
  • SIL/HIL 자동화 테스트: 소프트웨어 인 더 루프(Software-in-the-Loop)와 하드웨어 인 더 루프(Hardware-in-the-Loop)의 2단계 테스트로, 각각 알고리즘 로직의 정확성과 컨트롤러 하드웨어 타이밍 동작을 검증합니다.
  • 코드 커버리지: 테스트가 코드 경로를 얼마나 덮는지 정량화하여 품질 게이트의 정량적 근거로 사용합니다.

이 공정의 완료 기준은 명확히 세 가지로 정의됩니다: CI 파이프라인이 안정적으로 운영되고, 자동 테스트 통과율이 사전 설정된 임계값에 도달하며, 커버리지 지표가 인수 요구사항을 충족해야 합니다.

존재 이유: 문제점과 역사적 위치

휴머노이드 로봇 소프트웨어 스택의 복잡성은 일반 임베디드 시스템을 훨씬 초과합니다. 상위 계층은 시각 인식, 경로 계획, 대규모 모델 추론 등의 AI 작업으로 10–100 Hz 주기로 실행됩니다. 하위 계층은 관절 제어 루프로 1 kHz 이상의 업데이트율이 필요합니다. 두 계층 사이는 미들웨어 통신으로 연결되며, 어느 한 계층의 회귀 결함도 전체 기계 이상을 유발할 수 있습니다.

CI/CD 및 시뮬레이션 테스트 체인이 없던 시대에는 소프트웨어 검증이 두 가지 비효율적인 수단에 의존했습니다: 수동 통합 — 개발자가 로컬에서 수동으로 코드를 병합하고 수동으로 테스트를 트리거하여 효율이 낮고 회귀 누락이 매우 쉬웠습니다. 전체 기계 실측 — 소프트웨어를 물리적 프로토타입에 배포하여 검증하는 방식으로 비용이 높고 주기가 길며 위험이 큽니다. 전형적인 문제 시나리오는 다음과 같습니다: 한 개발자가 통신 프로토콜의 한 필드를 수정했고, 로컬 컴파일과 단위 테스트는 통과했지만 메인 브랜치에 통합한 후 다른 모듈의 파싱 로직이 붕괴되는 경우 — 이러한 문제는 순수 수동 프로세스에서는 종종 전체 기계 연동 디버깅 때까지 발견되지 않습니다.

CI/CD 및 시뮬레이션 테스트 체인의 역사적 위치는 바로 검증 단계를 좌측 이동(Shift-Left) 시키는 것입니다: 코드가 메인 브랜치에 통합되기 전에 자동화 파이프라인을 통해 빌드, 정적 검사, 단위 테스트, SIL 시뮬레이션 테스트를 완료하고, 필요 시 HIL 하드웨어 인 더 루프 테스트를 트리거합니다. 이것이 실제로 바꾸는 것은 "테스트 위치"가 아니라 "결함 발견의 시간 분포"입니다 — 원래 통합 단계에 집중되었던 결함 폭발을 각 코드 커밋으로 분산시키는 것입니다.

원리 분석

① 파이프라인 곧 게이트: CI의 핵심 메커니즘

GitLab CI의 핵심은 파이프라인(Pipeline) 과 작업(Job) 의 계층 구조입니다. 한 번의 코드 푸시가 하나의 파이프라인을 트리거하며, 파이프라인은 여러 단계(Stage)가 직렬로 연결되고 각 단계는 여러 병렬 작업을 포함합니다. 전형적인 단계 구분은 다음과 같습니다:

\[ \text{Pipeline:} \quad \underbrace{\text{build}}_{\text{컴파일}} \rightarrow \underbrace{\text{static\_check}}_{\text{정적 검사}} \rightarrow \underbrace{\text{unit\_test}}_{\text{단위 테스트}} \rightarrow \underbrace{\text{sil\_test}}_{\text{소프트웨어 인 더 루프}} \rightarrow \underbrace{\text{coverage}}_{\text{커버리지 게이트}} \]

각 작업은 Docker 컨테이너에서 실행되며, 컨테이너 이미지는 컴파일 툴체인, 의존성 라이브러리 버전 및 시스템 환경을 고정합니다. 이는 환경 일관성이 이미지 불변성으로 보장됨을 의미합니다 — 동일한 코드는 언제, 어떤 러너에서 빌드하든 결과가 일치해야 합니다. 작업의 종료 코드(exit code)가 파이프라인 지속 여부를 결정합니다: 어떤 작업이 실패하면 후속 단계는 자동으로 건너뛰고 통합 요청이 차단됩니다.

② 2단계 시뮬레이션: SIL과 HIL의 역할 분담

SIL(Software-in-the-Loop)은 테스트 대상 소프트웨어를 호스트 또는 시뮬레이션 환경에서 직접 실행하며, 제어 대상은 순수 수학적 모델입니다. 이것이 검증하는 것은 알고리즘 로직의 정확성입니다 — 컨트롤러의 상태 머신 전환, 플래너의 경로 출력, 통신 프로토콜의 인코딩/디코딩이 설계와 일치하는지 여부입니다. SIL의 장점은 속도가 빠르고 비용이 낮으며 병렬화가 쉽다는 점이고, 단점은 실제 하드웨어 타이밍을 포함하지 않는다는 점입니다.

HIL(Hardware-in-the-Loop)은 실제 컨트롤러 하드웨어를 폐루프에 연결하며, 제어 대상은 실시간 시뮬레이터가 계산합니다. 이것이 검증하는 것은 타이밍 및 인터페이스 정확성입니다 — 제어 주기가 안정적인지, 버스 통신이 프레임을 손실하는지, 인터럽트 응답이 적시에 이루어지는지 여부입니다. HIL의 폐루프 구조는 다음과 같이 표현할 수 있습니다:

\[ \text{HIL 폐루프:}\quad \underbrace{\text{실제 컨트롤러}}_{\text{실제 하드웨어}} \;\xrightarrow{\text{제어 명령}}\; \underbrace{\text{실시간 시뮬레이터}}_{\text{가상 제어 대상}} \;\xrightarrow{\text{센서 피드백}}\; \text{실제 컨트롤러} \]

두 단계 시뮬레이션은 파이프라인에서 위치가 다릅니다: SIL은 일반 게이트로 매 커밋마다 실행됩니다. HIL은 실시간 시뮬레이터 리소스가 필요하므로 일반적으로 nightly 빌드 또는 핵심 마일스톤 시점에 트리거됩니다.

③ 커버리지를 품질 게이트로 사용

코드 커버리지(Code Coverage)는 테스트 실행이 덮는 코드 줄, 분기 또는 경로의 비율을 측정합니다. 이는 품질 게이트의 정량적 근거로 사용되어 "테스트는 통과했지만 많은 코드가 실행되지 않은" 거짓 양성을 방지합니다. 커버리지 지표는 일반적으로 테스트 통과율과 함께 완료 기준의 정량적 KPI를 구성합니다.

수평 비교

휴머노이드 로봇 소프트웨어 검증 체계에서 CI/CD 및 시뮬레이션 테스트 체인은 인접 검증 수단과 상호 보완 관계를 형성합니다:

CI/CD 및 시뮬레이션 테스트 체인의 고유 가치는 상위 3단계 검증을 자동화하고 파이프라인화하여, 매 코드 변경이 단위 테스트부터 SIL까지의 완전한 검증 체인을 트리거할 수 있게 한다는 점입니다. 순수 수동 테스트와 비교하여 실제로 바꾸는 것은 "테스트가 실행되는지 여부"가 아니라 "테스트 실행의 빈도와 결정성"입니다 — 수동 테스트는 시간 부족으로 건너뛸 수 있지만, 파이프라인은 무조건 실행합니다.

사용자·적용 사례

이 공정의 전형적인 적용 시나리오는 다음과 같습니다:

  • 휴머노이드 로봇 소프트웨어 팀: 운동 제어, 인식, 내비게이션 등의 알고리즘 모듈을 개발할 때 CI 파이프라인을 통해 매 통합이 기존 기능을 깨뜨리지 않도록 보장합니다. 전형적인 프로세스는: 개발자가 코드 푸시 → GitLab CI가 파이프라인 트리거 → Docker 컨테이너에서 컴파일 및 단위 테스트 완료 → SIL 시뮬레이션으로 제어 로직 검증 → 커버리지 검사 → 모두 통과한 후 메인 브랜치 통합 허용.
  • 미들웨어 및 드라이버 개발: 통신 프로토콜이나 드라이버 인터페이스를 수정할 때 SIL 테스트로 프로토콜 인코딩/디코딩 정확성을 검증하고, HIL 테스트로 실제 버스 타이밍을 검증합니다. 이는 "프로토콜은 바뀌었지만 드라이버가 따라가지 못하는" 전형적인 통합 사고를 방지합니다.
  • 다중 팀 협업 시나리오: 여러 팀(운동 제어, 인식, 내비게이션)이 동일한 코드 저장소를 공유할 때 CI 파이프라인은 통합 게이트 역할을 하여 어떤 팀의 변경도 다른 팀의 기능을 깨뜨리지 않도록 보장합니다. 평가 매트릭스와 정량적 점수는 후보 방안 사이에서 합리적인 선택을 하는 데 사용됩니다.

한계와 경계

CI/CD 및 시뮬레이션 테스트 체인은 만능이 아니며, 그 한계는 다음과 같습니다:

  • 연산 자원 제약: SIL 시뮬레이션, 특히 다중 관절 동역학 시뮬레이션은 상당한 연산 자원이 필요하며, 파이프라인 동시 실행 시 리소스 병목이 발생할 수 있습니다. 이는 말뭉치에서 명시적으로 나열된 핵심 제약 중 하나입니다.
  • 테스트 환경 유지 비용: Docker 이미지는 의존성 라이브러리 버전을 따라잡기 위해 지속적으로 업데이트해야 하며, HIL 실시간 시뮬레이터는 전문 유지보수가 필요합니다. 환경 유지 자체가 지속적 투자가 됩니다.
  • 시뮬레이션과 현실의 격차: SIL에서 제어 대상은 수학적 모델이며, 모델 정확도가 테스트 유효성에 직접 영향을 줍니다. HIL은 실제 하드웨어를 연결하지만 제어 대상은 여전히 시뮬레이션입니다. 시뮬레이션은 전체 기계 실측을 완전히 대체할 수 없으며, 시뮬레이션 테스트 통과 ≠ 실제 기계 동작 정확입니다.
  • 커버리지 지표의 한계: 높은 커버리지가 높은 테스트 품질을 보장하지 않습니다 — 테스트가 코드 줄을 덮었지만 핵심 경계 조건을 덮지 않았을 수 있습니다. 커버리지는 필요 조건이지 충분 조건이 아닙니다.

흔한 오해

  1. "CI/CD는 자동화 컴파일이다" — 틀림. 컴파일은 파이프라인의 한 단계일 뿐입니다. CI/CD의 핵심은 지속적 검증입니다: 매 커밋이 단위 테스트, SIL 시뮬레이션, 커버리지 검사를 포함한 완전한 테스트 체인을 트리거합니다. 자동화 컴파일은 첫 단계일 뿐이며, 자동화 검증이 목적입니다.
  2. "SIL 통과하면 실제 기계에 올려도 된다" — 틀림. SIL은 알고리즘 로직을 검증하며 실제 하드웨어 타이밍을 포함하지 않습니다. 컨트롤러는 실제 기계에서 버스 지연, 인터럽트 지터, 리소스 경쟁으로 인해 비정상 동작할 수 있습니다. SIL과 HIL은 상호 보완 관계이지 대체 관계가 아닙니다.
  3. "커버리지 100%면 테스트가 완비된 것이다" — 틀림. 커버리지는 코드 줄이 실행되었음을 나타낼 뿐, 단언(assertion)의 유효성을 나타내지 않습니다. 모든 코드 줄을 덮었지만 단언이 모두 비어 있는 테스트 스위트는 커버리지 100%여도 가치가 없습니다. 커버리지 지표는 단언 품질, 경계 조건 커버리지와 함께 고려해야 합니다.
  4. "Docker가 모든 환경 문제를 해결한다" — 틀림. Docker는 빌드 환경의 일관성을 보장하지만 실행 환경의 일관성은 보장하지 않습니다. HIL 테스트는 실제 하드웨어를 포함하며, 그 동작은 물리적 요인의 영향을 받아 컨테이너화할 수 없습니다. Docker가 해결하는 것은 "빌드 의존성" 문제이지 "하드웨어 동작" 문제가 아닙니다.
