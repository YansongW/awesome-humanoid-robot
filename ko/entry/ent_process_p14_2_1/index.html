출처

개요

데이터 기록 및 재생(Data recording and playback)은 소프트웨어 미들웨어 및 시스템 통합 단계(P14)에서 도구 체인 및 DevOps 작업 패키지(P14.2)에 속하는 핵심 공정 노드로, 그 핵심 임무는 rosbag2, 구조화 로그, 데이터 레이크 및 데이터 버전 관리 등의 도구를 활용하여 로봇 실행 과정에서의 센서 스트림, 제어 명령 및 시스템 상태를 완전히 캡처하고 구조화된 방식으로 저장하여, 이후 문제 재현, 모델 훈련 및 성능 분석을 가능하게 하는 것입니다. 이는 데이터 저장 자체를 바꾸는 것이 아니라, 전체 개발 프로세스를 "문제 발생 시 현장 재현"에서 "언제든지 임의의 과거 현장으로 복귀할 수 있는" 엔지니어링 추적 가능성으로 전환하는 데 진정한 의미가 있습니다.

핵심 내용

무엇인가: 정확한 정의

데이터 기록 및 재생은 로봇 소프트웨어 개발에서 기본적인 엔지니어링 역량으로, 시스템 실행 중 다중 소스 이기종 데이터(관절 상태, IMU 판독값, 카메라 이미지, 제어 명령, 로그 이벤트 등)를 지속적으로 수집하고, 타임스탬프를 인덱스로 사용하여 동기화 저장하며, 사후에 필요에 따라 이러한 데이터 스트림을 정밀하게 재생하여 개발자가 실제 하드웨어 환경에서 벗어나 시뮬레이션이나 오프라인 분석에서 당시의 시스템 동작을 복원할 수 있게 하는 것을 의미합니다.

WBS V3의 공정 분해에서 이 노드(P14.2.1)는 아래로 다섯 개의 4단계 하위 작업으로 확장됩니다: P14.2.1.1 입력 정리 및 목표 정량화, P14.2.1.2 방안/방법 설계, P14.2.1.3 구현/프로토타입/시제품 제작, P14.2.1.4 검증 및 문제 폐루프, P14.2.1.5 문서 출력 및 하류 인계. 각 하위 작업은 통일된 엔지니어링 작업 템플릿을 따르며, 요구사항부터 인도까지 각 단계마다 명확한 검수 기준과 책임 소재가 보장됩니다.

원리 분해

① 시간 동기화: 다중 소스 데이터 정렬의 기초

휴머노이드 로봇은 일반적으로 수십 개의 센서를 탑재하며, 각 센서는 고유한 샘플링 주파수와 클록 소스를 가집니다. 데이터 기록 시스템은 각 데이터에 통일된 타임스탬프를 부여하고, 재생 시 시간 축을 기준으로 모든 데이터 스트림을 정렬해야 합니다. rosbag2는 ROS의 /clock 메커니즘과 TF 트리를 결합하여 다중 센서 데이터의 하드웨어 시간 동기화를 구현합니다. 호스트 간 데이터 수집의 경우 PTP(정밀 시간 프로토콜) 또는 NTP를 사용한 클록 동기화에 의존하며, 동기화 정밀도는 재생 시 데이터 연관의 정확성에 직접적인 영향을 미칩니다.

② 저장 아키텍처: 링 버퍼에서 데이터 레이크까지

실시간 기록은 매우 낮은 쓰기 지연을 요구하는 반면, 장기 저장은 용량 확장성을 요구합니다. 엔지니어링에서는 일반적으로 2단계 아키텍처를 채택합니다: 프런트엔드는 링 버퍼를 사용하여 메모리에 최근 데이터를 임시 저장하여 "충돌 직전 마지막 N초"의 현장 보존 요구를 충족합니다; 백엔드는 비동기 쓰기를 통해 데이터를 분산 저장소 또는 데이터 레이크에 디스크로 기록하여 장기 보관 및 일괄 분석 요구를 충족합니다. 두 단계 간의 데이터 이동은 백그라운드 스레드가 수행하여 실시간 수집 경로를 차단하지 않도록 합니다.

③ 재생 메커니즘: 시간 축 기반의 결정적 재연

재생의 핵심 과제는 결정성입니다 — 매번 재생 시 완전히 동일한 데이터 시퀀스를 생성해야 문제 재현이 보장됩니다. 이를 위해 재생기는 기록 시의 타임스탬프를 기준으로 비율을 조정하거나 원래 속도로 가상 클록을 진행시키며, 모든 구독자는 가상 클록에 따라 데이터를 소비합니다. 시뮬레이션 환경과 연동해야 하는 시나리오의 경우, 재생기는 "스텝 모드"도 지원합니다 — 외부 트리거 신호를 받을 때마다 한 프레임의 데이터를 진행시켜 프레임별 상태 변화를 검사하기 쉽게 합니다.

핵심 매개변수 및 사양

매개변수 일반 사양 설명
기록 대역폭 직접 확인 필요 센서 수와 해상도에 따라 달라지며, 다중 카메라 시스템은 수백 MB/s에 달할 수 있음

사용자·응용 사례

P14.2.1의 공정 정의에서 이 노드의 응용은 소프트웨어 미들웨어 및 시스템 통합 단계 전체에 걸쳐 있습니다. 대표적인 사용 시나리오는 다음과 같습니다:

  • 문제 재현: 로봇 현장에서 낙상, 떨림 또는 통신 타임아웃 등의 이상이 발생하면 개발자는 데이터 레이크에서 결함 시간 창의 데이터를 불러와 시뮬레이션 환경에서 재생하여 인식 지연, 제어 매개변수 또는 통신 패킷 손실 중 무엇이 원인인지 파악합니다.
  • 모델 훈련: 실제 실행에서 기록된 센서 데이터와 인간 시연 데이터를 훈련 세트로 정리하여 강화 학습 정책 또는 모방 학습 모델의 오프라인 훈련 및 평가에 사용합니다.
  • 성능 분석: 과거 데이터를 재생하여 동일한 입력에서 서로 다른 버전의 알고리즘 출력 차이를 비교하고, 성능 저하 또는 개선 폭을 정량화하여 버전 반복 결정을 지원합니다.

한계 및 경계

데이터 기록 및 재생은 만능이 아니며, 핵심 한계는 "무엇이 발생했는가"를 기록할 뿐 "왜 발생했는가"는 기록하지 않는다는 점입니다. 재생은 센서 입력과 시스템 출력만 복원할 수 있으며, 하드웨어 수준의 물리적 과정(모터 온도 변화, 기계적 마모 등)은 복원할 수 없습니다. 또한 이 노드는 세 가지 핵심 제약에 의해 제한됩니다: 저장 용량 — 장시간 실행 시 방대한 데이터가 생성되므로 계층적 저장 및 만료 정책을 설계해야 합니다; 대역폭 — 고주파 센서 데이터의 실시간 쓰기는 시스템 병목이 될 수 있어 수집 측에서 다운샘플링 또는 압축이 필요합니다; 프라이버시 — 로봇이 공공 또는 가정 환경에 배포된 경우 기록된 이미지와 오디오가 프라이버시 규정 문제를 야기할 수 있으므로 기록 전에 비식별화 처리가 필요합니다.

일반적인 오해

  1. "많이 기록할수록 좋다" — 틀림. 무차별적으로 모든 토픽을 기록하면 저장 공간과 대역폭이 빠르게 소진되고 후속 검색도 어려워집니다. 올바른 방법은 문제 영역에 따라 핵심 토픽을 선택하고 합리적인 샘플링률과 압축 전략을 설계하는 것입니다.
  2. "재생 데이터는 실제 실행과 동일하다" — 틀림. 재생은 데이터 수준의 입력과 출력만 복원할 수 있으며, 하드웨어 타이밍, 인터럽트 지연 등의 물리적 특성은 복원할 수 없습니다. 실시간성에 의존하는 문제의 경우 재생 결과는 참고용일 뿐 실제 기기 검증을 대체할 수 없습니다.
  3. "데이터 기록은 사후 대응이다" — 틀림. 데이터 기록 방안은 시스템 설계 단계에서 아키텍처에 포함되어야 하며, 토픽 명명 규칙, 타임스탬프 전략, 저장 용량 계획 등을 포함합니다. 사후에 추가 기록하면 핵심 데이터가 없어 문제를 파악하지 못하는 경우가 많습니다.
