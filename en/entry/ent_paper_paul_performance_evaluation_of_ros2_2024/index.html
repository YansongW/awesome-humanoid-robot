Summary

This paper empirically evaluates same-domain and cross-domain ROS2-DDS communication latency across Eclipse Cyclone DDS, eProsima Fast-DDS, and RTI Connext DDS using heterogeneous physical devices and multiple data types.

Sources

  • Performance Evaluation of ROS2-DDS middleware implementations facilitating Cooperative Driving in Autonomous Vehicle

概述

本文系统评估了 ROS2-Humble 下三种主流 DDS 实现（Eclipse Cyclone DDS、eProsima Fast-DDS、RTI-Connext DDS）在同域与跨域通信场景中的端到端延迟性能，覆盖 Binary、String、IMU 三种数据类型及有线和无线两种介质。核心贡献在于首次针对跨域桥接场景给出可复现的基准数据，并揭示了不同 DDS 实现在跨域无线通信中的显著性能分化。

它改变了什么

这项工作的真正价值在于把 ROS2 性能评估从「同域理想环境」拉到了「跨域真实部署」的维度。过去的研究几乎都默认所有节点在同一 DDS 域内通信，但实际自动驾驶系统中，由于 DDS 域参与者数量上限（RTI-Connext 4.1e 及以下仅 58 个，4.2e 及以上 120 个），以及单参与者占用双端口的限制，跨域通信是不可避免的工程现实。作者敏锐地抓住了这个被忽视的痛点——当开发者被迫使用桥接服务（Zenoh-plugin-DDS、Integration Service、Routing Service）时，不同厂商 DDS 实现的性能差异可能远超同域场景，而此前没有任何公开数据能指导选型。

更关键的是，这项工作把评估基线推进到了 ROS2-Humble 版本。ROS2 的 DDS 抽象层和桥接实现迭代极快，旧版本结论往往在新版本中失效。作者选择 Humble 这个当时的最新 LTS 版本，意味着数据对当前工业部署有直接参考价值，而非停留在学术理想状态。

方法拆解

测量架构

  • 采用 ping-pong 往返时间（RTT） 方案规避分布式时钟同步难题：发布节点在 T1 打时间戳，订阅节点收到后作为中继回传，发布节点在 T2 收到回传，RTT = T2 - T1
  • 订阅节点记录中间处理时间：开始下载帧时打 T3，中继发布时打 T4，中间处理时间 = T4 - T3
  • 延迟计算：Latency = (RTT - 中间处理时间) / 2

实验矩阵

  • 跨域配置：发布者位于域 5，订阅者位于域 10，通过 binary_image 和 binary_image_relay 主题进行测试
  • 数据类型：Binary（自定义 BinaryFile，含 sensor_msgs/Image 和 float64 时间戳）、String（StringTimestamp）、IMU（标准 imu 消息）
  • 数据规模：Binary 从 33Kb 到 4Mb 共 9 档；String 从 0.004KB 到 2.675KB 共 4 档；IMU 固定大小
  • 发布频率：Binary 从 1 Hz 到 1000 Hz；String 和 IMU 从 10 Hz 到 1000 Hz

关键设计决策

  • 使用 Docker 容器 运行在 host 网络模式，引用 Felter et al. (2015) 论证容器开销可忽略，保证底层库一致性
  • 客户端库统一使用 rclpy（Python），避免 C++ 与 Python 客户端实现的性能差异干扰
  • QoS 策略固定为默认值：Durability=volatile，Reliability=reliable，History=keep last，队列大小=10
  • Binary 和 IMU 数据来自 ASL Dataset，但二进制文件大小单一，作者从互联网随机选取不同大小文件生成数据集，保证尺寸梯度覆盖

关键创新

  1. 首次系统评估跨域桥接场景：此前所有 ROS2-DDS 性能研究都聚焦同域通信，本文是第一个把「不同域 + 桥接服务」作为独立变量进行对照的实验。这个视角直接对应自动驾驶多车协同的真实部署约束，填补了工程选型的关键空白。

  2. 多维度参数空间的交叉设计：同时变化数据类型（Binary/String/IMU）、数据大小（33Kb 到 4Mb）、发布频率（1 Hz 到 1000 Hz）、通信介质（有线/无线）、DDS 实现（三种）五个维度，而非单变量扫描。这种设计能暴露交互效应——例如 Cyclone DDS 在无线跨域场景下 145KB 阈值处的延迟突增，只有在多维度交叉时才能被发现。

  3. 异构硬件平台验证：覆盖 x86_64 笔记本、ARM 嵌入式平台（Pi 3、Pi 4、Jetson Nano）共五类硬件，并用 Jetson Nano 连接 Realsense 相机做实时数据流验证。这使结论不仅适用于桌面级部署，也对车载嵌入式场景有直接参考意义。

实验与结果

关键结果汇总

场景 Eclipse Cyclone DDS eProsima Fast-DDS RTI-Connext DDS
无线跨域，Binary > 145KB 延迟突增 表现最差 性能差异较小
有线跨域，Binary 502KB vs 1MB 延迟特性一致 502KB 比 1MB 延迟更高 502KB 比 1MB 延迟更高
String/IMU 跨域 与同域表现相似 跨域表现最差 与同域表现相似
Jetson Nano 实时相机流 未明确 未明确 跨域表现更优

结果解读

  • eProsima Fast-DDS 在跨域场景全面落后：所有数据类型、有线和无线条件下均表现最差，说明其桥接实现（Integration Service）存在系统性性能瓶颈，而非特定数据类型的偶发问题
  • Cyclone DDS 的 145KB 无线阈值：文件大小超过 145KB 时延迟突增，但有线连接下延迟特性一致，暗示无线传输与 Cyclone 桥接的交互存在缓冲区或分片效率问题
  • RTI-Connext 的跨域一致性：同域与跨域性能差异最小，且 502KB 文件比 1MB 延迟更高的异常现象在 Fast-DDS 和 Connext 中同时出现，可能与 DDS 分段传输的阈值行为有关（论文未明确解释原因）
  • 整体结论：当前厂商 DDS 实现在跨域无线通信中尚不能满足硬实时要求，桥接服务的参与是主要性能损耗来源

边界与局限

  • QoS 策略未探索：所有实验固定默认 QoS（Reliability=reliable，History=keep last，队列大小=10），未测试不同 QoS 组合对跨域性能的影响，而实际自动驾驶系统常需调整 Deadline 和 Liveliness 策略
  • 未做节点压力测试：实验仅在单发布-单订阅的 ping-pong 模式下进行，未模拟多节点并发、系统负载和网络拥塞场景
  • 未进行移动节点实验：所有节点位置固定，未模拟车辆移动导致的网络拓扑变化和信号衰减
  • 未集成 5G 通信：无线实验基于普通 Wi-Fi，未覆盖 5G-V2X 场景
  • 未分析 ROS2 安全包影响：SROS2 等安全机制可能显著增加延迟，但未纳入评估
  • 502KB 延迟异常未解释：作者承认无法解释 502KB 文件比 1MB 延迟更高的原因
  • 未开发 ML 推荐框架：作者提及计划基于机器学习构建 DDS 选型推荐系统，但未实现

工程启示

  • 优先核对桥接服务版本：跨域性能差异很大程度上取决于桥接实现（Zenoh-plugin-DDS、Integration Service、Routing Service）的版本和配置，复现实验前务必锁定与论文一致的桥接版本
  • 警惕 145KB 阈值：如果使用 Cyclone DDS 做无线跨域通信，数据帧大小应避开 145KB 附近区域，否则延迟会突增；建议实测确认该阈值在目标硬件上的具体位置
  • eProsima Fast-DDS 慎用于跨域：如果系统必须跨域通信，且对延迟敏感，Fast-DDS 应作为最后选择；优先考虑 RTI-Connext（跨域一致性最好）或 Cyclone（有线场景表现稳定）
  • 502KB 异常需实测验证：502KB 比 1MB 延迟更高的现象在两种 DDS 中复现，但原因未明；如果业务数据量恰好在 500KB 量级，建议在目标平台上实测确认是否触发该异常
  • Docker 部署可行但需验证：作者用 Docker 抽象底层库并引用文献论证开销可忽略，但实际部署时仍需在目标硬件上对比容器与裸机性能，特别是 ARM 平台
  • rclpy 与 rclcpp 差异未覆盖：实验全部使用 Python 客户端，C++ 客户端的延迟特性可能不同；C++ 为主的系统需谨慎外推结论
