Overview

Data Collection and Data Pipelines is a roadmap process node numbered P12.2.2 within the VLA / WAM / AI algorithm integration phase (P12). It is of the method type, belongs to the domain 07_ai_models_algorithms, and operates at the intelligence value chain level. It defines the complete engineering pipeline from raw data acquisition to deliverable training datasets, encompassing four major methodological tools—teleoperation, simulation data, internet videos, and data cleaning and augmentation—as well as five standardized process actions: input review, solution design, prototype implementation, result verification, and documentation delivery. What it truly changes is not how data volume is accumulated, but rather how data transforms from "collected material" into "acceptable, traceable, and reproducible engineering assets."

Content

What It Is: Precise Definition

Data Collection and Data Pipelines (P12.2.2) is the process node responsible for data-side engineering in VLA/WAM model development. It is not a specific dataset, but rather a set of procedural specifications that convert raw data into high-quality training corpora. In WBS V3, this node expands into five third-level subtasks: P12.2.2.1 Input Review and Target Quantification, P12.2.2.2 Solution/Method Design, P12.2.2.3 Modeling/Simulation and Prototype Implementation, P12.2.2.4 Simulation Result Verification and Optimization, and P12.2.2.5 Documentation Output and Downstream Delivery.

Each subtask follows a unified four-level key action template, forming a closed loop of "Review → Design → Implement → Verify → Deliver." The method toolbox explicitly includes four categories: Teleoperation, Simulation Data, Internet Videos, and Data Cleaning and Augmentation. These four methods correspond respectively to real physical interaction data, virtual environment-generated data, human behavior prior data, and data quality governance measures.

Why It Exists: Pain Points and Historical Positioning

VLA/WAM model training relies on high-quality, diverse robot data, which is the fundamental driver for this process node. In the productization of humanoid robots, the data side faces three structural contradictions:

First, data scarcity. Unlike internet text or image data, robot manipulation data cannot be obtained at scale through web crawling. Each real teleoperation collection session requires the full coordination of a physical robot, an operator, and scene setup, making the per-sample cost far higher than text annotation. While simulation data can be generated at scale, it suffers from the domain gap in sim-to-real transfer. Internet videos are abundant but lack robot-executable action labels and force feedback information.

Second, the quality-versus-scale trade-off. Insufficient data leads to poor model generalization, while excessive data introduces noise and redundancy. The data cleaning and augmentation stage exists precisely to maximize the information density of data under a limited budget, rather than simply pursuing quantity.

Third, engineering traceability. In laboratory settings, data collection is often "collect-and-use," lacking version management, quality checks, and requirement traceability. However, in product development processes, datasets must undergo version control, change management, and downstream dependency notifications just like software code. The five subtasks of P12.2.2 institutionalize this engineering discipline.

From a historical positioning perspective, this node sits in the middle of Phase P12: it receives sensor configuration and calibration information from the upstream perception stack (P12.1) as input, while providing data supply to downstream VLA model training (P12.2.3 and beyond). What it truly changes is not the degree of automation in data collection, but rather the transformation of data from "a researcher's personal asset" into "an organization's reusable engineering asset."

Principle Breakdown

① Input Review and Target Quantification (P12.2.2.1)

This subtask has three core actions: list all upstream input items and confirm versions, convert acceptance criteria into quantifiable KPIs, and establish task owners, milestones, and risk registers.

The upstream input list includes: sensor selection documentation from the perception stack, calibration parameters, scene definition files, and the overall requirements specification for Phase P12. Confirming versions matters because data collection must be bound to a specific version of the perception configuration; otherwise, the collected data cannot align with downstream model inputs. A typical approach to converting acceptance criteria into quantifiable KPIs is transforming "dataset quality is good" into measurable metrics such as "annotation accuracy ≥ [to be confirmed]%, invalid sample rate ≤ [to be confirmed]%, covered scene count ≥ [to be confirmed]." Establishing owners and milestones assigns responsibility to specific individuals, avoiding the situation where data work is "everyone's responsibility but no one's."

② Solution/Method Design (P12.2.2.2)

This subtask requires forming no fewer than 2 candidate solutions, establishing an evaluation matrix with quantitative scoring, organizing reviews, and freezing the chosen solution. Candidate solutions typically revolve around different combinations of the four data source categories:

Solution Dimension Teleoperation-Dominant Simulation-Dominant Hybrid Solution
Data Authenticity Highest Lower Medium
Collection Cost Highest Lowest Medium
Scene Coverage Limited Extensive Relatively Broad
Annotation Difficulty Lower (naturally has action labels) Medium (requires auto-annotation) Medium
Scale Ceiling Low (limited by physical machine hours) High (can be generated in parallel) Medium-High

The quantitative scoring in the evaluation matrix typically uses weighted scores across four dimensions: data quality, cost, time, and risk. The significance of reviewing and freezing the solution lies in the fact that once large-scale data collection begins, switching approaches midway would invalidate already-collected data; therefore, solution freezing is a critical risk control point.

③ Modeling/Simulation and Prototype Implementation (P12.2.2.3)

This subtask requires establishing simulation/mathematical models or prototype systems, executing computations or experiments, and recording key parameters and boundary conditions. For data pipelines, the "prototype" can be: a teleoperation collection system (including master hand, slave hand, and force feedback devices), a simulation data generator (domain randomization configuration based on a physics engine), or a data cleaning pipeline prototype. Key parameters include: collection frequency, resolution, force feedback sampling rate, scene lighting conditions, object material properties, etc. Boundary conditions include: robot joint limits, operational space range, sensor measurement ranges, etc.

④ Simulation Result Verification and Optimization (P12.2.2.4)

This subtask requires verifying the consistency between simulation results and theoretical/experimental data, identifying weak points, and iterating for optimization. Typical verification methods include: comparing distribution differences between simulation-generated data and a small amount of real teleoperation data; checking whether augmented samples maintain physical plausibility (e.g., objects do not penetrate, force feedback does not jump abruptly); and verifying whether cleaning rules mistakenly remove valid samples. After identifying weak points, the process enters an iterative loop: adjusting simulation parameters, optimizing augmentation strategies, and correcting cleaning rules.

⑤ Documentation Output and Downstream Delivery (P12.2.2.5)

This subtask requires outputting final reports/drawings/specifications, updating the ICD/BOM/SOP/requirement traceability chain, and completing formal delivery to downstream stages. Specific actions include: writing documentation according to templates with references to raw data, completing internal reviews and version control, and publishing and notifying downstream dependent parties. The "documentation" here is not just dataset descriptions, but also includes data collection SOPs (Standard Operating Procedures), data format specifications, quality inspection reports, and version change records. The requirement traceability chain ensures that every data requirement can be traced back to specific collection batches and cleaning rules.

Limitations and Boundaries

Data collection cost boundary. Teleoperation collection is constrained by the number of physical robots and operator hours, placing a hard upper limit on daily valid data volume. When a project requires millions of samples, a pure teleoperation approach is cost-infeasible and must rely on simulation data or internet videos as supplements. This is a constraint that must be quantified in the solution evaluation of P12.2.2.2.

Privacy and compliance boundary. Internet videos involve legal issues such as portrait rights, scene privacy, and platform terms of use. The data cleaning stage must include actions such as face blurring, scene desensitization, and source compliance review. This boundary should be reflected in the KPI settings of P12.2.2.1 as a hard requirement of "100% compliance rate."

Annotation quality boundary. Whether manual or automatic, annotation always carries an error rate. Annotation quality directly affects downstream model training performance, but excessively pursuing annotation accuracy significantly drives up costs. Engineering judgment: annotation accuracy targets are typically set between [to be confirmed]% and [to be confirmed]%, with specific values depending on task difficulty and model fault tolerance.

Simulation-to-real domain gap. Although simulation data is low-cost and large-scale, the approximate nature of physics engines causes distribution deviations from the real world. The verification stage of P12.2.2.4 exists precisely to quantify and narrow this gap, but it cannot be completely eliminated. For force-sensitive tasks (such as precision assembly), the credibility of simulation data requires careful assessment.

Common Misconceptions

  1. "More data is always better" — Incorrect. Data scale is only one KPI; quality, diversity, and annotation accuracy are equally important. Blindly expanding data volume may introduce large amounts of redundant samples, diluting effective information density. The KPI settings in P12.2.2.1 should include both scale and quality metrics.

  2. "Simulation data can fully replace real data" — Incorrect. Simulation data has advantages in coverage and cost, but the sim-to-real gap always exists. Engineering judgment: for contact-rich manipulation tasks, the proportion of real data should not fall below [to be confirmed]%, otherwise model performance in real environments may degrade significantly.

  3. "Data cleaning is just filtering out bad samples" — Incorrect. Data cleaning also includes positive operations such as deduplication, alignment, annotation correction, and augmentation generation. The "record anomalies and deviations" action in P12.2.2.3 indicates that the cleaning process itself is an important feedback channel for discovering data issues and improving collection solutions.

  4. "The work ends once the dataset is delivered" — Incorrect. P12.2.2.5 requires "publishing and notifying downstream dependent parties," but downstream users may discover new data issues during use, necessitating version iterations. The data pipeline is a continuously operated system, not a one-time static deliverable.
