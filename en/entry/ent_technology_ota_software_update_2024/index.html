Overview

OTA (Over-the-Air) software update is a technical method for wirelessly deploying control policies, firmware, and system software to a deployed fleet of humanoid robots. What it truly changes is not just the software maintenance approach for a single robot, but the entire business model and security response mechanism of a robot product—shifting from "fixed at factory" to "continuous evolution."

The English name is OTA Software Update, and the Korean name is OTA Software Update.

In the taxonomy of entity types, technology is an Information Entity, corresponding to Chapter 7 and subsequent software chapters of this book. As a technology-type entity, OTA software update is not a specific algorithm but a systematic software delivery and lifecycle management mechanism—it describes the transmission, validation, and activation channel for software from the development environment to physical robots, rather than a single technical component.

Why It Exists: Pain Points and Historical Positioning

In the industrialization of humanoid robots, a long-standing pain point is: software defects and feature iterations cannot be efficiently resolved through physical contact. Unlike industrial robotic arms fixed beside production lines where engineers can perform on-site maintenance at any time, the target deployment scenarios for humanoid robots are distributed environments such as logistics warehouses, home services, and outdoor inspection. If every control policy update required recalling robots or dispatching engineers with debugging cables, maintenance costs would scale linearly with fleet size, completely undermining the theoretical total cost of ownership (TCO) advantage of humanoid robots.

From a historical perspective, OTA is not an original invention in the humanoid robot domain. It has been maturely deployed for years in consumer electronics (smartphones) and intelligent vehicles (pioneered at scale by Tesla). When the humanoid robot industry introduced it, it faced three unique challenges: real-time requirements for control policies are far higher than for infotainment systems (joint servo cycles are typically on the order of 1 kHz, specific values to be confirmed), safety-critical levels are higher (erroneous firmware could cause a robot to fall, injure people, or self-destruct), and heterogeneous computing architectures are more complex (real-time controllers, AI inference units, and communication middleware must be updated simultaneously). Therefore, OTA for humanoid robots is not a simple reuse of automotive solutions but requires redesigning validation and rollback mechanisms.

Principle Breakdown

① Update Package Construction: From Source Code to Delta Images

The first step of OTA is packaging the new firmware or control policy into a transmittable update package. For humanoid robots, update targets typically include three categories: firmware for real-time motion controllers (running on MCUs/DSPs), AI model weights (running on GPUs/NPUs), and system software and middleware (running on operating systems like Linux). To reduce transmitted data volume, delta update technology is commonly adopted in engineering—only the differences between old and new versions are transmitted, rather than the entire image. Delta algorithms (such as bsdiff) compute differences at the binary level, significantly reducing update package size.

② Transmission Channel: Dual-Channel Redundancy and Resumable Transfers

Update packages are transmitted to robots via wireless networks (Wi-Fi, 4G/5G, specific supported frequency bands to be confirmed). Since deployment environments for humanoid robots may have unstable networks, OTA systems are typically designed with dual-channel redundancy: the primary channel transmits the complete update package, and the backup channel takes over upon disconnection. The transport layer must support resumable transfers and checksum verification (e.g., SHA-256) to ensure data integrity. For fleet management, bandwidth scheduling must also be considered—avoiding network congestion caused by pushing large packages to hundreds of robots simultaneously.

③ Installation and Activation: A/B Partitions and Atomic Switching

This is the most critical safety mechanism in OTA. Modern OTA systems commonly adopt the A/B partition scheme: the robot's storage medium maintains two system partitions (A and B). While currently running on partition A, the new version is written to partition B; after writing completes, the bootloader switches the boot partition. This design ensures that if the new version fails to boot, the system can automatically roll back to the old partition, avoiding "bricking." For humanoid robots, control policy updates must also be executed while the robot is in a safe state (e.g., powered off or in controlled standing), preventing loss of control during the update process.

④ Validation and Canary Release: From Single Unit to Fleet

After the update package is installed, it must pass self-check validation procedures (such as joint response tests and sensor data verification) before being marked as "activation successful." For fleet deployment, the canary release strategy is adopted in engineering: first push the update to a small number of robots, observe operational data (such as failure rates, energy consumption, task success rates), and confirm no anomalies before gradually expanding the push scope. This strategy confines single-point failure risks to a controllable range.

OTA for humanoid robots is close to automotive in safety level, but validation conditions are more demanding—large-scale road testing in closed test fields, as done for vehicles, is not feasible; instead, it relies more on simulation validation and canary releases.

Who Uses It: Application Cases

OTA software update has been widely applied in prototype validation, academic research, and early commercial products of humanoid robots. Typical scenarios include:

  • Control policy iteration: OEMs push new gait control parameters or whole-body motion planning strategies to sold robots via OTA, optimizing walking stability and energy efficiency without recalls.
  • Security patches: After discovering firmware vulnerabilities in joint controllers, fix patches are rapidly pushed via OTA to shorten the vulnerability exposure window.
  • Feature unlocking: Advanced features (such as new manipulation skill packages) are pushed to specific customer fleets via OTA, enabling a software-defined functionality business model.
  • Data collection strategy updates: Adjusting the frequency and content of sensor data uploaded by robots, complementing the Fleet Data Flywheel to optimize model training data quality.

Limitations and Boundaries

OTA software update is not a panacea; its boundaries include:

  1. Dependence on physical safety: OTA can only update software, not fix hardware defects. If robot performance degrades due to mechanical wear or electronic component aging, software updates cannot resolve it.
  2. Network dependence: In deployment environments without network coverage (such as underground mines or remote outdoor areas), the OTA channel is unavailable, requiring local updates or manual intervention.
  3. Validation sufficiency: Simulation validation cannot fully cover the diversity of real physical environments. Canary releases reduce risk but cannot eliminate all unknown failure modes.
  4. Security attack surface: The OTA channel itself is a potential attack entry point. If encryption and signature mechanisms are compromised, attackers could inject malicious firmware to control robots. This requires continuous investment in security defenses.
  5. Availability loss during updates: Robots typically cannot perform tasks during installation and validation, and frequent updates reduce the effective working time of the fleet.

Common Misconceptions

  1. "OTA is just remote configuration changes"—Wrong. The core value of OTA lies in safely and reliably updating executable code (firmware, model weights), not simple parameter adjustments. Configuration changes are only the most superficial application of OTA.
  2. "OTA only requires good transmission"—Wrong. Transmission is just the first step; installation validation, rollback mechanisms, canary strategies, and security defenses together form a complete OTA system. The absence of any component can lead to fleet failures.
  3. "A/B partitions solve all update failure problems"—Wrong. A/B partitions only solve boot failure issues, not hidden faults where "the new version boots but behaves abnormally." The latter requires reliance on canary releases and runtime monitoring.
  4. "OTA is only a consideration for the mass production stage"—Wrong. The OTA channel should be established during the prototype validation stage; otherwise, software iteration efficiency for early test fleets will severely constrain development progress.
