# ZOZO's Contact Solver 🫶 A contact solver for physics-based simulations involving 👚 shells, 🪵 solids, 🪢 rods, 🧱 rigid bodies and ⏳ sand. Institutions per source list: Ryoichi Ando 等、ZOZO、Inc.（st-tech）.

Overview

The open-source contact solver maintained by Ryoichi Ando at ZOZO, Inc., designed for unified physics simulation of cloth, solids, rods, rigid bodies, and sand. Its core selling points are penetration-free contact resolution under GPU single precision and the "Elasticity-Inclusive Dynamic Stiffness" coupling of elasticity and contact. The project is open-sourced under the Apache 2.0 license, offering Docker, native Windows executables, a Blender plugin, and a JupyterLab frontend, along with an LLM-driven MCP server. It aims to maintain robustness and reproducibility in large-scale scenarios with over 180 million contacts.

What It Changes

What this project truly changes is not "yet another contact solver," but rather transforming "reproducible large-scale physics simulation" from an academic paper accessory into an auditable, deployable engineering artifact. In the past, papers on contact solvers often provided only algorithms and a few examples, requiring readers to set up environments, handle dependencies, and guess parameters for reproduction. Here, the author open-sources the solver, frontend, Docker images, AWS/GCP/vast.ai deployment scripts, and logging APIs, even providing the cost and frame time for each example on specific GPUs—effectively turning "experiments" into "product manuals."

More critically, it changes the relationship between "contact solvers" and "elasticity solvers." Traditional approaches treat them separately: solve elasticity first, then handle contact, iterating until convergence. Here, "Elasticity-Inclusive Dynamic Stiffness" means contact stiffness is not a post-hoc correction but directly enters the Jacobian of the elastic system, coupling contact and deformation within the same nonlinear solve. This directly addresses the long-standing problem of "clipping/snagging" in cloth simulation—not through post-detection, but by guaranteeing penetration-free behavior during the solve itself.

Method Breakdown

Solver Architecture

  • Both contact and elasticity solvers run on the GPU, entirely in single precision, without double precision—a trade-off for GPU memory bandwidth and compute, but numerical robustness is maintained through symbolic force Jacobians.
  • Deformable bodies use the Finite Element Method (FEM), supporting triangular (shell) and tetrahedral (volume) elements; rods and rigid bodies (based on Painless Differentiable Rotation Dynamics) are integrated as separate element types within the same framework.

Contact Resolution Pipeline

  • Contact resolution guarantees penetration-free behavior, with a strict upper bound on triangle strain (5% by default in examples, adjustable to 1%).
  • An explicit intersection check is performed at the end of each step, raising an error if intersections are detected—meaning that when tests pass, all steps are mathematically penetration-free.

Elasticity-Contact Coupling (Elasticity-Inclusive Dynamic Stiffness)

  • The paper does not explicitly provide the specific formula, but based on the project description, contact stiffness is incorporated into the dynamic stiffness matrix of the elastic system, rather than being treated as an external constraint iteratively.
  • Key design decision: the derivative of contact forces with respect to displacement (i.e., contact stiffness) is merged with the elastic stiffness matrix, forming a unified nonlinear system solved via Newton's method.

Frontend and API Design

  • The frontend API uses method chaining, with a single import (from frontend import App), creating triangles/tetrahedra within the pipeline (.triangulate() and .tetrahedralize()), and does not include mesh data—users must provide or download meshes themselves.
  • Provides logging query APIs, including time-per-frame, newton-steps, num-contact, max-sigma, for monitoring and debugging.

Deployment and Integration

  • Offers a Blender plugin (requires Blender 5+) and a JupyterLab frontend, both communicating with the same solver engine; supports remote GPU simulation (e.g., vast.ai).
  • Provides an MCP server allowing LLMs to drive simulation workflows via natural language—an attempt to integrate physics simulation into AI agent workflows.

Key Innovations

  1. Elasticity-Inclusive Dynamic Stiffness: Directly incorporates contact stiffness into the Jacobian of the elastic system, rather than iterating as an external constraint. This eliminates the slow convergence and residual penetration issues that can arise from traditional alternating "elasticity-then-contact" iterations, representing a substantive improvement in contact-deformation coupled solving.

  2. Single-Precision GPU Large-Scale Solving: Handles simulations with 8.2M vertices and 184.1M contacts on an RTX 4090 at 144.5 seconds per frame—this is not just algorithmic innovation but a demonstration of engineering capability. Single precision halves memory usage but requires symbolic Jacobians to compensate for precision loss, a combination rarely seen in public projects.

  3. Reproducibility as a First-Class Citizen: Provides precompiled Docker images, native Windows executables, AWS/GCP/vast.ai deployment scripts, GitHub Actions stress tests (10 consecutive runs with jitter), and cost/frame-time tables for each example—this changes the delivery standard for "paper code," allowing downstream users to directly evaluate whether adoption is worthwhile.

Boundaries and Limitations

  • The paper does not explicitly provide the specific formula derivation and convergence proof for Elasticity-Inclusive Dynamic Stiffness, with its mechanism inferred only from the project description.
  • The solver is offline by design, not real-time; large-scale examples (large-twist, large-five-twist, large-woven) are not included in GitHub Actions tests because they may take days to weeks to complete—meaning the stability of these examples has not undergone automated regression verification.
  • Supports only x86 architecture, not arm64; documentation and tutorial videos are "not polished enough," with the author welcoming community contributions.
  • Project maintenance is performed by a single part-time individual (Ryoichi Ando), so issue handling may be slow; direct pull requests are not accepted (due to copyright and licensing concerns), requiring submission via issues or forks.
  • The main branch updates frequently and may diverge from the paper; the paper's reference implementation is on the sigasia-2024 branch, which receives only maintenance updates and does not include the latest algorithmic changes—meaning reproducing paper results requires using that specific branch.

Engineering Insights

  • Check the branch first: If the goal is to reproduce paper results, be sure to use the sigasia-2024 branch, not the main branch—the main branch contains the latest algorithmic changes that may diverge from the paper.
  • Hardware selection: Large-scale simulations (>1M vertices) require an RTX 4090 or 5090; small-to-medium scale (<200K vertices) is sufficient with an RTX 3090, 4070, or 5070. Single precision halves VRAM requirements, but note the driver requirement of CUDA 12.8+.
  • Most common pitfall: Mesh data is not included in the project; users must create or download meshes themselves—meaning the "out-of-the-box" experience is interrupted at the mesh preparation stage. It is recommended to first run small examples like yarn or drape to verify the environment, then gradually scale up.
  • Cost estimation: AWS L4 instances cost approximately $1/hour, small examples cost \(0.01-\)0.39, and large-scale examples should be estimated using vast.ai costs for RTX 4090 (<$0.5/hour)—but the per-frame times for large examples (46-437 seconds) mean a 2,000-frame simulation requires 1-10 days, so budgets need advance planning.
  • Logging API is a debugging asset: Metrics such as time-per-frame, newton-steps, num-contact, and max-sigma should serve as acceptance criteria—if max-sigma exceeds the strain limit, contact stiffness or time step size needs adjustment.
