Overview

Linux RT-PREEMPT is a patch set that makes most of the Linux kernel preemptible and interrupt handling threaded, aiming to provide deterministic low-latency real-time behavior. It is currently the mainstream solution for the real-time core of humanoid robot main control computers. It fully preserves the Linux ecosystem (drivers, ROS 2, container toolchains), compressing worst-case latency from the millisecond range down to tens of microseconds. What it truly changes is not "whether Linux can be real-time," but "whether a robot's main controller can run both AI and control."

Content

What It Is: A Precise Definition

Linux RT-PREEMPT (also known as PREEMPT_RT) is a patch set for the standard Linux kernel. Its core goal is to transform the general-purpose Linux kernel into an operating system with hard real-time capabilities through two key mechanisms: kernel preemption and interrupt threading. It is not a standalone operating system but an ongoing stream of patches applied to the mainline Linux kernel—maintained by the community over the long term, with real-time features gradually being merged upstream.

From a software layering perspective, Linux RT-PREEMPT sits above the hardware and below robot middleware (such as ROS 2), belonging to the operating system and driver layer. In a typical heterogeneous computing architecture for humanoid robots, it is usually used alongside a standard Linux core and a QNX real-time core: the RT-PREEMPT real-time core runs control loops, the standard Linux core runs perception and AI inference, and the two cores exchange data via shared memory or deterministic Ethernet channels.

Why It Exists: Pain Points and Historical Positioning

General-purpose operating systems (such as standard Linux) are not designed for hard real-time: non-preemptible regions in the kernel, interrupt handling, and scheduler non-determinism introduce uncontrollable latency spikes. Humanoid robots impose extremely stringent timing requirements—dozens of actuators across the body close loops at millisecond-level cycles, and safety-critical functions (emergency stop, torque limiting, fall protection) mandate deterministic responses. If a control loop encounters a latency spike, the consequences range from jitter degrading gait quality to instability or even safety incidents.

Before RT-PREEMPT, engineers faced a dilemma: either use a commercial RTOS like QNX, sacrificing ecosystem richness and bearing licensing costs, or tolerate the timing non-determinism of standard Linux. The historical positioning of Linux RT-PREEMPT is precisely to fill this gap—it allows developers to achieve near-hard-real-time determinism without leaving the Linux ecosystem, compressing worst-case latency from the millisecond range down to tens of microseconds (engineering judgment). What it truly changes is not "whether Linux can be real-time," but "whether a robot's main controller can run both AI and control"—converging tasks that previously required two heterogeneous chips onto a single multi-core processor.

Principle Breakdown

① Kernel Preemption: Shrinking Non-Preemptible Regions

The standard Linux kernel contains numerous non-preemptible critical sections (such as code protected by spinlocks), within which real-time tasks cannot be scheduled. RT-PREEMPT converts the vast majority of these critical sections into preemptible ones through the following means:

  • Replacing spinlocks with sleepable mutexes (rtmutex), allowing higher-priority tasks to preempt lower-priority tasks holding the lock;
  • Introducing a priority inheritance protocol to prevent priority inversion from indefinitely blocking high-priority tasks;
  • Making kernel code paths themselves preemptible, allowing interrupt handlers to be suspended by the scheduler.

② Interrupt Threading: Turning Interrupts into Schedulable Entities

In traditional Linux, interrupt handlers (ISRs) run in a non-preemptible context, and their execution time is uncontrollable. RT-PREEMPT converts interrupt handlers into kernel threads (IRQ threads), assigning them priority attributes so that interrupt response times become predictable. Interrupts with extremely stringent hard real-time requirements (such as EtherCAT synchronization interrupts) can still be preserved as non-threaded fast-path handlers.

③ Supporting Engineering Practices: Determinism Is Not Given by the Patch Alone

The RT-PREEMPT patch itself only provides "possibility"; engineering practices deliver determinism. The supporting measures explicitly listed in the source material include:

  • CPU isolation (isolcpus): Isolating CPU cores bound to real-time tasks from the general scheduler to prevent preemption by ordinary processes;
  • Interrupt affinity binding: Binding critical interrupts (such as the EtherCAT master interrupt) to specific CPU cores, deployed on the same core as or a different core from real-time tasks;
  • Memory locking (mlockall): Preventing real-time threads from experiencing unpredictable latency due to page swapping;
  • Real-time priority (SCHED_FIFO): Assigning fixed priorities to real-time threads to ensure they are scheduled ahead of ordinary processes.

A typical scheduling design is: the EtherCAT master and whole-body control (WBC) tasks are bound to a dedicated CPU core with the highest SCHED_FIFO priority and locked memory; policy inference and ordinary processes share the remaining cores, with cgroups limiting their preemption interference; all real-time threads disable dynamic memory allocation and non-deterministic system calls.

Horizontal Comparison

Comparison with QNX: QNX is a commercial microkernel RTOS where the file system and network stack run as user-space services, the kernel retains only minimal functionality, driver failures do not propagate to the kernel, and it possesses functional safety certification credentials; the cost is ecosystem and licensing. RT-PREEMPT's advantage is fully preserving the Linux ecosystem (drivers, ROS 2, container toolchains), while its disadvantage is that safety certification must be self-built. A typical humanoid robot employs a heterogeneous combination of "QNX or RT-PREEMPT real-time core running control + standard Linux core running perception and AI," with safety-critical functions mandatorily placed on the real-time side.

Comparison with Xenomai: Xenomai is a dual-kernel solution where real-time tasks run on the Cobalt real-time core, achieving latency as low as the microsecond level, but with complex maintenance. RT-PREEMPT is a single-kernel solution with lower maintenance costs, but latency is on the order of tens of microseconds. Both reuse the Linux user-space ecosystem, but Xenomai's real-time tasks require a dedicated API, whereas RT-PREEMPT's real-time tasks directly use standard POSIX interfaces.

Comparison with Zephyr: Zephyr is an open-source RTOS for resource-constrained embedded devices, commonly used in sensor nodes and motor controllers, with low ecosystem richness. RT-PREEMPT targets main control computers; the two have different installation locations and typically coexist on the same robot—RT-PREEMPT runs the main controller, while Zephyr runs joint/sensor nodes.

Who Uses It: Application Cases

Linux RT-PREEMPT is the mainstream solution for the real-time core of humanoid robots, widely used in prototype validation, academic research, and early commercial products. Typical deployment patterns from the source material:

  • Main control computer: The RT-PREEMPT real-time core hosts the EtherCAT master and WBC tasks, bound to a dedicated CPU core with the highest SCHED_FIFO priority and locked memory;
  • Heterogeneous combination: Paired with a standard Linux core, the real-time core runs control, the standard core runs perception and AI, and the two cores exchange data via shared memory or deterministic Ethernet channels;
  • Safety function implementation: Safety-critical functions such as emergency stop, torque limiting, and fall protection are mandatorily placed on the real-time side.

Supporting engineering practices also include: policy inference and ordinary processes share the remaining cores, with cgroups limiting their preemption interference; all real-time threads disable dynamic memory allocation and non-deterministic system calls.

Limitations and Boundaries

  1. Latency magnitude ceiling: RT-PREEMPT's scheduling latency is on the order of tens of microseconds, lower than the microsecond-level of Xenomai and QNX. For applications requiring microsecond-level determinism (such as certain safety-critical control loops), it may be insufficient.
  2. Safety certification must be self-built: Unlike QNX, which has mature certification cases, RT-PREEMPT's safety certification basis is "requires self-building"—meaning that under functional safety standards (such as IEC 61508, ISO 13849), using RT-PREEMPT entails additional certification work.
  3. Determinism depends on engineering practices: The patch itself does not guarantee determinism; supporting measures such as CPU isolation, interrupt affinity binding, and memory locking are indispensable. Improper configuration can still result in latency spikes.
  4. Programming constraints for real-time threads: All real-time threads must disable dynamic memory allocation and non-deterministic system calls, imposing requirements on developers' programming habits.

Common Misconceptions

  1. "Applying the RT-PREEMPT patch makes it real-time"—Wrong. The patch only provides "possibility"; engineering practices such as CPU isolation, interrupt affinity binding, memory locking, and SCHED_FIFO priority are indispensable. The source material explicitly lists these as "supporting engineering practices."
  2. "RT-PREEMPT has lower latency than QNX"—Wrong. In the comparison table from the source material, RT-PREEMPT's scheduling latency magnitude is "tens of microseconds," while QNX is "microsecond-level." RT-PREEMPT's advantage lies in the ecosystem, not in absolute latency.
  3. "RT-PREEMPT and standard Linux are mutually exclusive"—Wrong. Typical deployment is a heterogeneous combination: the RT-PREEMPT real-time core runs control, the standard Linux core runs perception and AI, and the two cores exchange data via shared memory or deterministic Ethernet channels.
  4. "Real-time threads can freely use dynamic memory allocation"—Wrong. All real-time threads must disable dynamic memory allocation and non-deterministic system calls; otherwise, unpredictable latency will occur.
