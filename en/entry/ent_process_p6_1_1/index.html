Overview

The generation of URDF/SDF files is the first third-level subtask in Stage P6 (URDF modeling and kinematic verification) of the humanoid robot development process. Its core work is to convert CAD design data into standardized robot description files that can be correctly parsed by simulation, control, and planning toolchains. What it truly changes is not the "export file" action itself, but rather the establishment of a quantifiable and traceable engineering bridge between "design intent" and "algorithm executability" for the first time.

Content

What It Is: Engineering Translation from CAD to Computable Models

URDF (Unified Robot Description Format) is an XML format in the ROS ecosystem that describes a robot's kinematic and dynamic properties. It defines the robot's topological connections, joint types (revolute/prismatic/fixed), kinematic parameters (origin, axis, limits), and inertial properties through a tree structure of <link> and <joint> elements. SDF (Simulation Description Format) is the native format supported by the Gazebo simulation environment, extending URDF with physical properties (friction coefficients, damping, materials) and sensor model descriptions.

The specific task of this process node P6.1.1 is to use methods and tools such as ROS URDF, Xacro, SolidWorks/NX → URDF plugins, and inertial parameter verification to complete the conversion and validation from CAD models to URDF/SDF files. Its design reasoning logic requires: links, joints, inertia, collision bodies, and visual models must be fully consistent with CAD; mass properties come from P3.1.2/P3.1.3. Key constraints include coordinate system consistency, unit uniformity, and collision bodies must not be too dense. The completion criterion is correct loading in RViz/Gazebo/Isaac Sim without parsing errors.

Why It Exists: The "Translation Error" Pain Point Between Simulation and Real Hardware

Humanoid robots are typical "high-degree-of-freedom, strongly coupled, multi-constrained" systems. Directly importing CAD models into simulation environments presents three critical problems: First, CAD models contain a large amount of decorative geometry (fillets, threads, chamfers), and using them directly for collision detection causes computational explosion; second, coordinate systems in CAD assemblies are often defined for design convenience rather than kinematic conventions (such as D-H parameters or the right-hand rule specified by ROS REP 103), leading to confusion in joint axis directions; third, inertial parameters (mass, center of mass, inertia tensor) exported by CAD software default to the part coordinate system, while URDF requires the link coordinate system, and unit systems may be inconsistent (kg·m² vs g·mm²).

The existence of the URDF/SDF file generation process is precisely to eliminate these three layers of "translation error." What it truly changes is not the act of "drawing a robot model" itself, but rather establishing a quantifiable and traceable engineering bridge between "design intent" and "algorithm executability" for the first time. Without this step, subsequent kinematic verification, dynamic simulation, and control algorithm development would all be built on incorrect models, leading to the classic engineering disaster of "works in simulation, breaks on the real robot."

Principle Breakdown

① Tree Topology: The Mathematical Essence of URDF

URDF uses a tree structure to describe the robot, with each <joint> connecting a parent <link> and a child <link>. This structure corresponds to the kinematic transmission chain:

\[ T_{\text{child}}^{\text{parent}} = T_{\text{joint\_origin}} \cdot T_{\text{joint\_axis}}(\theta) \]

where \(T_{\text{joint\_origin}}\) is the fixed transformation of the joint coordinate system in the parent link coordinate system (defined by the <origin> tag), and \(T_{\text{joint\_axis}}(\theta)\) is the rotation about the joint axis or translation along the joint axis (defined by the <axis> and <limit> tags). The forward kinematics of the entire robot is the sequential multiplication of transformations from the tree root to the leaves.

② Xacro: Macro Programming Eliminates Repetition

Humanoid robots are left-right symmetric. If URDF were written by hand, the link definitions for the legs and arms would repeat for hundreds of lines. Xacro (XML Macros) defines reusable link templates through <xacro:macro>, combined with parameterization (such as leg_prefix, hip_yaw_offset) to achieve "define once, instantiate twice." This is not just code reuse but a guarantee of engineering consistency—modifying a parameter on the left leg automatically synchronizes the right leg, avoiding hidden "left-right asymmetry" errors.

③ Inertial Parameter Verification: The Lifeline of Dynamic Simulation

The <inertial> tag in URDF contains mass (mass), center of mass position (origin), and the inertia tensor (6 independent components of inertia). The SolidWorks/NX URDF plugins automatically export these parameters, but there are two common pitfalls: first, unit systems—CAD software defaults to g·mm², while URDF requires kg·m², with a conversion factor of \(10^{-9}\); second, coordinate systems—the inertia tensor exported by the plugin is based on the link origin, but if the origin definition in the CAD assembly is inconsistent with kinematic conventions, the inertia tensor must be manually rotated:

\[ I' = R \, I \, R^T \]

where \(R\) is the rotation matrix from the CAD coordinate system to the URDF link coordinate system. If this step is incorrect, the torque output of dynamic simulation will deviate significantly from the real robot.

Who Uses It · Application Cases

Case One: Full-Size Bipedal Humanoid Robot Development (This Process)

In the P6.1.1 process, the team obtains mass property data from P3.1.2/P3.1.3, uses the SolidWorks URDF plugin to export the initial model, then refactors the left-right symmetric leg links using Xacro, and finally loads and validates in RViz. Key actions include: listing all upstream input inventories and confirming versions, converting acceptance criteria into quantifiable KPIs, and establishing task owners, timelines, and risk registers.

Case Two: Open-Source Humanoid Robot Projects

Many open-source projects (such as those collected in the awesome-humanoid-robot repository) deliver URDF files as standard artifacts for global developers to download and simulate in Gazebo or visualize in RViz. These projects typically provide both URDF and SDF formats to accommodate different versions of ROS and Gazebo.

Limitations and Boundaries

① URDF's Tree Structure Limitation: URDF does not allow closed-loop structures (such as parallel mechanisms or closed-chain kinematics). If a humanoid robot includes parallel link mechanisms, SDF or other formats must be used instead. Engineering judgment: most bipedal humanoid robots use serial structures, so this limitation has limited impact.

② The Contradiction Between Collision Body Simplification and Realism: Collision bodies must not be too dense (otherwise computational load explodes), but excessive simplification leads to distorted collision detection in simulation (such as finger grasping). A trade-off between accuracy and performance is required; typically, finer collision bodies are used for end effectors and simplified geometry for the torso.

③ Static Assumption of Inertial Parameters: Inertial parameters in URDF are fixed values and cannot describe load variations (such as a robot holding a heavy object). For dynamic load scenarios, online compensation must be performed at the control layer rather than modifying the URDF.

Common Misconceptions

  1. "URDF can be used directly after export"—Wrong. URDF exported by CAD plugins almost inevitably requires manual adjustment: coordinate system rotation, unit conversion, collision body simplification, and joint limit calibration. Direct use will cause severe deviation between simulation and the real robot.

  2. "The finer the collision bodies, the better"—Wrong. Collision bodies must not be too dense, otherwise simulation computational load explodes and real-time performance cannot be guaranteed. The correct approach is: preserve details in the visual model, use simplified geometry for collision bodies, and only increase precision at critical interaction points (such as grippers).

  3. "Inertial parameters don't matter since simulation can't tell the difference"—Wrong. Inertial parameters directly determine the torque output of dynamic simulation. If mass properties are incorrect, control parameters tuned in simulation will inevitably fail when transferred to the real robot. Mass properties must come from the verification results of P3.1.2/P3.1.3.

  4. "URDF and SDF are interchangeable"—Partially wrong. URDF is the standard format for ROS, while SDF is the native format for Gazebo. URDF can be converted to SDF using the gz sdf tool, but SDF supports features that URDF does not (such as closed chains and sensor models). The format should be selected based on the target simulation environment.
