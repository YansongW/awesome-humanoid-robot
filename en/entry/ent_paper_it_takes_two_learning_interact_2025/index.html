Summary

It Takes Two: Learning Interactive Whole-Body Control Between Humanoid Robots is a 2025 work on loco-manipulation and whole-body-control for humanoid robots.

Sources

  • It Takes Two: Learning Interactive Whole-Body Control Between Humanoid Robots (arXiv)

概述

本文提出 CodeBotler 与 RoboEval 两个工具，前者通过 LLM 将自然语言任务描述转化为服务机器人可执行的 Python 嵌入式 DSL 程序，后者提供轻量级模拟器与时间逻辑评估基准，用于系统衡量 LLM 生成程序在动作排序与顺序正确性上的表现。作者在 16 个任务、5 种 LLM 上验证了该评估框架的有效性，并识别出三类典型失败模式。

它改变了什么

服务机器人编程长期被简化为“视觉运动策略”或“高层规划”，而真正决定任务成败的往往是动作的精确排序——例如“检查多少会议室没有标记”必须先遍历所有房间再汇总。现有代码生成基准（如数据处理函数）只适合输入-输出单元测试，无法捕捉这种时序依赖。本文改变了这一评估范式：不再问“程序最终输出对不对”，而是问“程序执行轨迹是否满足时间约束”。这迫使 LLM 生成程序不仅要“会调用技能”，还要“在正确的时间调用正确的技能”。

另一个被改变的认知是：验证程序逻辑不需要高保真 3D 模拟。作者用符号模拟器加时间逻辑检查替代了物理仿真，将评估成本从小时级降至秒级，同时保持了对逻辑错误的敏感度。这对实际部署意义重大——团队可以快速迭代提示词与模型，而不必为每个任务搭建仿真环境。

方法拆解

程序生成管线

  • 用户任务描述与提示前缀拼接，前缀包含 8 种技能定义（get_current_location、get_all_rooms、is_in_room、ask、pick、place、go_to）及少量示例程序。
  • 查询 LLM 生成 Python 程序，支持 OpenAI API、Google PaLM API、HuggingFace 模型（AutoModel 与 Text-Generation-Inference）。
  • 关键设计：get_current_location 与 get_all_rooms 动态查询世界状态，避免硬编码；is_in_room 调用零样本 VLM 做感知推理；ask 提供结构化多选接口，适配触摸屏或音频交互。

执行与部署

  • 程序通过 ROS Actionlib 作为客户端运行，遇到技能调用（如 go_to("lobby")）即向远程话题（如 /go_to_server）发布目标，由机器人端 action server 接收。
  • 该设计使 CodeBotler 与具体机器人平台解耦，可机载或外部运行。

评估框架

  • 模拟器接受世界状态 w 与程序 π，产生轨迹 r（技能序列及参数），记录所有 Python 错误与机器人执行错误。
  • 评估器检查轨迹 r 是否满足时间约束 c，约束以合取范式表达；引入 RoboEval 时间逻辑（RTL），从 LTL 派生，更易书写且可读性更好。
  • 基准含 16 个任务，每个任务 5 种不同措辞提示（测试鲁棒性），多个世界状态对应多个时间检查。

关键创新

  1. 时间逻辑作为评估核心：将 LTL 简化为 RTL，使非形式化用户任务（如“先检查所有房间再报告”）能精确表达为可自动验证的约束。这是首次将时序正确性作为服务机器人程序生成的首要评估维度，而非仅看最终结果。

  2. 符号模拟替代物理仿真：用 Python 解释器加技能符号模拟，在保证逻辑验证能力的同时将评估成本降低数个数量级。这使得大规模、多提示、多世界状态的鲁棒性测试成为可能，而高保真模拟下这类测试几乎不可行。

  3. 提示措辞鲁棒性测试：每个任务固定 5 种不同措辞，直接暴露 LLM 对自然语言微小变化的敏感性。这一设计在现有基准中罕见，但对实际部署至关重要——用户不会用固定模板描述任务。

实验与结果

评估了 GPT-4、GPT-3.5、PaLM2、CodeLLama、StarCoder 五种模型，覆盖 16 个任务（如 Get Drink、Halloween List、Mail Delivery 等）。图 5a 与 5b 为图片，具体数字未提取，但作者明确报告了以下关键结果：

指标 数值 说明
平均 pass@1（最佳模型） 0.99 论文未明确对应具体模型，但为所有任务平均
平均 pass@1（最差模型） 0.00 论文未明确对应具体模型，但为所有任务平均
失败模式：Python 运行时错误 0.40 占所有失败的比例
失败模式：执行不可行动作 0.04 占所有失败的比例
失败模式：满足任务要求错误 0.58 占所有失败的比例（由 0.40+0.04+0.58 计算，总和 1.02（由表内数值 0.75÷0.75 计算） 因四舍五入）

失败模式分类显示：满足任务要求错误（即程序能运行但顺序不对）占比最高，验证了时序正确性评估的必要性。作者引入简单拒绝采样程序后，机器人执行错误立即减少，但具体降幅论文未明确。

边界与局限

论文未明确列出作者承认的局限。从事实要点推断：未对真实机器人部署做定量评估，未讨论多机器人协同或动态环境干扰；模拟器假设世界状态完全可观测且技能执行无噪声，这在真实场景中不成立。基准任务规模有限（16 个），且提示措辞变化仅 5 种，可能不足以覆盖真实用户表达的多样性。硬件与计算资源未提及，复现时需自行配置。

工程启示

复现时先核对三处：一是 ROS Actionlib 话题命名是否与你的机器人接口一致（/go_to_server 等），不一致需修改 CodeBotler 客户端映射；二是 is_in_room 依赖的 VLM 服务是否可用，零样本推理延迟会直接影响端到端执行时间；三是提示前缀中的示例程序是否与你的技能集匹配，示例质量对 LLM 输出影响极大。

最容易踩坑的是时间约束的书写——RTL 虽比 LTL 易读，但合取范式中的时序依赖（如“先访问所有房间再检查标记”）容易写错，建议先用模拟器对单个任务做 10 次以上轨迹采样验证约束正确性。另外，拒绝采样虽能减少执行错误，但会降低 pass@1，需根据任务容忍度权衡。若下游团队要接入新技能，务必同步更新提示前缀中的技能定义与模拟器中的符号执行逻辑，否则会出现“程序能生成但模拟器无法执行”的脱节。
