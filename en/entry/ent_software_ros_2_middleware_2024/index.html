Overview

The ROS 2 middleware is a robotics software layer based on the DDS (Data Distribution Service) standard that implements publish/subscribe communication and real-time support. It sits between the operating system and robot applications, serving as the "nervous system" connecting perception, decision-making, and execution modules in humanoid robot systems. Through the RMW (ROS Middleware) abstraction layer, it shields differences in underlying DDS implementations, allowing developers to switch between different communication backends without modifying application code.

Content

What It Is: A Precise Definition

The ROS 2 middleware is the core software layer responsible for distributed communication within the ROS 2 (Robot Operating System 2) framework. It is built on the DDS standard established by OMG (Object Management Group) and employs publish-subscribe semantics: senders (publishers) and receivers (subscribers) are decoupled through topics, without needing to know of each other's existence. This design enables multiple computational nodes in a robot system—such as vision perception nodes, motion planning nodes, and joint control nodes—to collaborate in a loosely coupled manner.

From a software layering perspective, the ROS 2 middleware resides between the operating system (Linux, QNX, etc.) and robot applications, providing common services such as communication, data serialization, time synchronization, and service discovery. What it truly changes is not "what robots can do," but "how efficiently robot modules collaborate"—decomposing what were tightly coupled monolithic programs into distributed components that can be independently developed, deployed, and scaled.

Why It Exists: Pain Points and Historical Positioning

Before ROS 2, the communication mechanism of ROS 1 had fundamental limitations: its proprietary protocol based on TCPROS/UDPROS lacked real-time guarantees and could not meet the stringent deterministic communication requirements of humanoid robots. A typical bipedal robot might simultaneously run: multi-camera perception streams at tens of hertz, joint force control loops at kilohertz, high-level planning above ten hertz, as well as time synchronization, fault diagnosis, and logging across modules throughout the body. These traffic flows have vastly different requirements in bandwidth, latency, jitter, reliability, and security, which cannot be satisfied by a single network or protocol.

Another pain point of ROS 1 was the lack of security mechanisms—no built-in encryption, authentication, or access control, which was unacceptable in industrial and commercial scenarios. The DDS standard happened to provide a complete QoS (Quality of Service) policy framework, the DDS-Security specification, and mature commercial and open-source implementations. ROS 2's choice of DDS as the underlying communication standard essentially advanced robot communication from the "proprietary protocol era" to the "standardized industrial communication era."

Principle Breakdown

① Publish-Subscribe and the DDS Global Data Space

The core model of DDS is the "Global Data Space": all participants (DomainParticipants) join the same domain and publish and subscribe to data through topics. Each topic is associated with a data type; publishers write data, and subscribers receive it asynchronously. This model naturally supports one-to-many, many-to-one, and many-to-many communication topologies without requiring a central server.

② RMW Abstraction Layer: Shielding DDS Differences

ROS 2 shields differences in underlying DDS implementations through the RMW interface. rmw_fastrtps_cpp, rmw_cyclonedds_cpp, rmw_connextdds, and others are adapter layers for different DDS implementations. Switching RMW typically only requires setting the environment variable RMW_IMPLEMENTATION, with no need to modify application code. This design allows ROS 2 to run on open-source DDS or switch to commercial DDS to meet high-safety scenario requirements.

③ Composition and Zero-Copy: Breaking Through Performance Bottlenecks

For kilohertz-level joint force control loops, the copy overhead of traditional DDS network communication is unacceptable. ROS 2 provides the Composition mechanism—placing multiple nodes in the same process and using intra-process communication to bypass the DDS network layer, directly performing pointer passing for zero-copy data transfer. This mechanism reduces communication latency between nodes within the same computational unit by more than an order of magnitude (engineering judgment).

④ Real-Time Support: From "Best Effort" to "Deterministic"

The ROS 2 middleware provides differentiated services for various traffic types through QoS policies (such as BEST_EFFORT and RELIABLE reliability policies, and the DEADLINE deadline policy). For hard real-time traffic like joint force control, RELIABLE + high-priority QoS can be configured; for perception streams with large bandwidth and tolerance for loss, BEST_EFFORT can be configured. Combined with underlying deterministic buses (such as TSN, EtherCAT, CAN-FD), the ROS 2 middleware can simultaneously carry both soft and hard real-time traffic within the same system.

The core advantage of the ROS 2 middleware lies in "standardization + ecosystem": it is not just a communication layer, but the communication foundation for the entire ROS 2 ecosystem (ros2_control, MoveIt 2, Nav2, Behavior Trees). In contrast, although a custom communication layer can be deeply optimized for specific hardware, it cannot benefit from community-maintained algorithms and tools.

Who Uses It: Application Cases

The ROS 2 middleware has been widely applied in humanoid robot prototyping, academic research, and early commercial products. Typical scenarios include:

  • Academic research: University humanoid robot laboratories use ROS 2 + CycloneDDS to build full perception-planning-control stacks, leveraging the Composition mechanism to place vision and force control nodes in the same process for low-latency communication.
  • Commercial robotics: Fast DDS is used as the default RMW, leveraging its excellent shared memory support for same-machine zero-copy to meet kilohertz communication requirements of joint force control loops.
  • High-safety scenarios: Aerospace and automotive fields choose RTI Connext DDS, utilizing its complete DDS-Security for encryption and access control.

Limitations and Boundaries

  1. Real-time ceiling: The ROS 2 middleware itself does not provide hard real-time guarantees—it relies on the underlying operating system (such as QNX, PREEMPT_RT Linux) and deterministic buses (TSN, EtherCAT) to achieve this together. Pure software-level ROS 2 communication cannot meet microsecond-level deterministic requirements.
  2. DDS implementation differences: Although different DDS implementations follow the same standard, they differ significantly in performance, toolchains, and security features. Switching RMW does not require code changes, but performance characteristics may change dramatically and require revalidation.
  3. Resource overhead: The full feature set of DDS (service discovery, QoS management, security) incurs additional memory and CPU overhead, which can become a bottleneck on resource-constrained embedded controllers.
  4. Learning curve: The QoS policy framework of DDS is complex, and beginners can easily misconfigure it, leading to communication anomalies (e.g., a subscriber going offline under the RELIABLE policy causing the publisher to block).

Common Misconceptions

  1. "ROS 2 middleware = DDS"—Inaccurate. The ROS 2 middleware is the communication layer within the ROS 2 framework based on DDS, including proprietary mechanisms such as RMW abstraction, Composition, and message serialization; DDS is the underlying communication standard, and the relationship is one of inclusion, not equivalence.
  2. "Performance remains unchanged after switching RMW"—Incorrect. Different DDS implementations vary significantly in latency, throughput, and memory usage; performance must be revalidated after switching.
  3. "Zero-copy = faster in all scenarios"—Incorrect. Zero-copy (pointer passing) is only effective in Composition (same-process) scenarios; cross-process or cross-device communication still requires serialization and network transmission.
  4. "The ROS 2 middleware can guarantee hard real-time"—Incorrect. It provides QoS mechanisms and real-time support, but hard real-time guarantees require coordination between the operating system and the underlying bus; the ROS 2 middleware is only one part of the chain.
