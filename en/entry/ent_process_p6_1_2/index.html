Overview

The DH (Denavit-Hartenberg) parameter definition is a standardized method for robot kinematics modeling, describing the transformation relationships between adjacent link coordinate systems through four parameters (a, α, d, θ). This process node P6.1.2 belongs to the URDF modeling and kinematics verification stage. Its core task is to establish standard kinematic parameters for each kinematic chain and verify the consistency between forward kinematics code and the URDF model through analytical methods, Pinocchio/RBDL, symbolic computation, and other means, ultimately outputting the "DH Parameter Table" and ensuring comparison errors < 1e-6. What it truly changes is not the act of "writing a set of coordinate transformations" itself, but rather establishing, for the first time, a quantifiable and traceable engineering bridge between "mechanical design intent" and "algorithm executability."

Content

What It Is: A Standardized Translation from Mechanical Drawings to Mathematical Models

DH parameters are the minimal parameter set in robotics for describing the relative pose between adjacent links. For revolute joints, the four parameters are defined as: link length a (distance along the x-axis from zi-1 to zi), link twist α (angle of rotation about the x-axis from zi-1 to zi), link offset d (distance along the zi-1-axis from xi-1 to xi), and joint angle θ (angle of rotation about the zi-1-axis from xi-1 to xi). The homogeneous transformation matrix between adjacent link coordinate systems is:

\[ T_i^{i-1} = \begin{bmatrix} \cos\theta_i & -\sin\theta_i\cos\alpha_i & \sin\theta_i\sin\alpha_i & a_i\cos\theta_i \\ \sin\theta_i & \cos\theta_i\cos\alpha_i & -\cos\theta_i\sin\alpha_i & a_i\sin\theta_i \\ 0 & \sin\alpha_i & \cos\alpha_i & d_i \\ 0 & 0 & 0 & 1 \end{bmatrix} \]

The positioning of this process node P6.1.2 is: within the URDF modeling and kinematics verification stage, convert the coordinate system conventions from CAD designs into a standard DH parameter table, providing a unified kinematic foundation for subsequent inverse kinematics and controller implementation. It receives mass property data from upstream P3.1.2/P3.1.3 and structural design outputs from the P5 stage, and outputs the "DH Parameter Table" and forward kinematics code for use in P10 motion control algorithm development.

Why It Exists: The "Translation Error" Pain Point Between Simulation and Physical Robots

Humanoid robots are typical "high-degree-of-freedom, strongly coupled, multi-constraint" systems. Directly using coordinate system definitions from CAD models for kinematics calculations presents three critical problems: First, coordinate systems in CAD assemblies are often based on design convenience (such as aligning datum planes or mating constraints) rather than kinematic conventions (such as aligning joint rotation axes with the z-axis), leading to confusion in deriving transformation matrices. Second, different engineers may define coordinate systems differently for the same joint, and the lack of a unified standard causes inconsistency between upstream and downstream models. Third, although the <origin> and <axis> tags in URDF can describe joint transformations, their expression differs from DH parameters, and mixing them directly can easily introduce errors.

The existence of DH parameter definitions is precisely to solve the above problems. Through strict coordinate system establishment rules (z-axis along the joint axis, x-axis along the common perpendicular), it transforms arbitrary coordinate systems in mechanical design into a standardized four-parameter description. The core value brought by this standardization is: reproducibility — the same mechanical structure yields the same DH parameter table in the hands of different engineers; verifiability — forward kinematics calculation results can be numerically compared with URDF model outputs, with errors quantifiable to the < 1e-6 order of magnitude; portability — the DH parameter table can be directly used in inverse kinematics algorithms, dynamics calculations, and trajectory planning without re-derivation.

Principle Breakdown

① Coordinate System Establishment Rules: The Core Logic of the DH Convention

The first step in DH parameter definition is to establish a coordinate system for each joint. The rules are as follows: the zi-1-axis aligns with the rotation axis of joint i; the xi-axis aligns with the common perpendicular direction between zi-1 and zi, pointing from joint i to joint i+1; the yi-axis is determined by the right-hand rule. This rule ensures that the transformation between adjacent coordinate systems is determined solely by four parameters, with each parameter having clear geometric meaning. For humanoid robots, the rotation axes of major joints such as the hip, knee, and ankle are typically defined as z-axes to ensure the simplicity of the kinematic model.

② Forward Kinematics Chain Propagation: From Base to End Effector

Forward kinematics calculation is implemented through chain multiplication. For an n-degree-of-freedom manipulator, the transformation matrix of the end effector relative to the base is:

\[ T_n^0 = T_1^0 \cdot T_2^1 \cdots T_n^{n-1} \]

Each Tii-1 is obtained by substituting DH parameters into the homogeneous transformation matrix. In libraries such as Pinocchio/RBDL, this process is encapsulated as an efficient recursive algorithm that supports analytical derivative computation, facilitating subsequent Jacobian matrix derivation and inverse kinematics solving. Engineering judgment: for humanoid robots (typically 20-40 degrees of freedom), the computational cost of chain multiplication is within milliseconds, fully meeting real-time control requirements.

③ Comparison Verification with URDF: The Engineering Significance of Error < 1e-6

URDF uses <origin> (position and orientation) and <axis> (rotation axis) to describe joint transformations, which differ in expression from DH parameters but are mathematically equivalent. The verification method is: compute the end-effector pose using the forward kinematics code generated from the DH parameter table and the URDF model at the same joint angles, then compare the position and orientation errors between the two outputs. An error < 1e-6 means the two models are numerically identical and can be used interchangeably. This verification is the core acceptance criterion for P6.1.2.4 verification and issue closure.

Horizontal Comparison

DH Parameters vs. Native URDF Description: DH parameters are a compact mathematical expression suitable for derivation and computation; URDF's <origin>/<axis> are more intuitive and suitable for visualization and simulation. The two are mathematically equivalent, but DH parameters are more efficient in inverse kinematics and dynamics calculations. Engineering judgment: it is recommended to use DH parameters as the standard input for kinematics calculations and URDF as the standard for simulation and visualization, ensuring consistency between the two through verification.

Analytical Methods vs. Pinocchio/RBDL vs. Symbolic Computation: Analytical methods are suitable for simple chains (such as a single arm), with transparent derivation processes but prone to errors; Pinocchio/RBDL are suitable for complex multi-chain systems (such as humanoid robots), supporting efficient numerical computation and analytical derivatives; symbolic computation (such as SymPy) is suitable for verifying derivation correctness but has slow computation speed. The three are complementary, and P6.1.2.2 requires forming no fewer than 2 candidate solutions precisely to select the optimal tool for different scenarios.

Who Uses It · Application Cases

Case 1: Lower-limb kinematics modeling for humanoid robots. Taking the hip joint as an example, DH parameters for 3 revolute joints (flexion/extension, abduction/adduction, internal/external rotation) need to be defined. After building the model with Pinocchio, forward kinematics computes the end-effector foot position for gait planning and stability control. Verification with error < 1e-6 ensures consistency between simulation and physical robot.

Case 2: Dual-arm collaborative kinematics verification. The dual arms have a total of 14 degrees of freedom (7 per arm). Forward kinematics code is generated from the DH parameter table and compared with the URDF model for verification. Symbolic computation is used to derive the Jacobian matrix, and analytical methods are used to verify calculation results at key joint angles. The combination of the three ensures model correctness.

Case 3: Controller inverse kinematics implementation. The DH parameter table is directly input into inverse kinematics algorithms (such as analytical inverse solutions or numerical iteration) for mapping from joint space to task space. Consistency in coordinate system orientation conventions and joint zero-point definitions ensures that inverse kinematics results are physically realizable.

Limitations and Boundaries

Limitation 1: DH parameters are sensitive to the order of coordinate system establishment. If adjacent joint axes are parallel or nearly parallel, the common perpendicular definition may not be unique, leading to non-unique DH parameters. In such cases, additional conventions are required (such as selecting the shortest common perpendicular), increasing modeling complexity.

Limitation 2: Closed-loop structures cannot be directly described. DH parameters are applicable to open-chain structures. For parallel mechanisms (such as the closed-loop structure of a humanoid robot's legs), equivalent open-chain conversion with virtual joints is required first.

Limitation 3: Verification with error < 1e-6 only covers kinematics. This standard does not involve verification of dynamic parameters (mass, inertia tensor); the dynamic model requires separate calibration.

Boundary Description: This process node P6.1.2 is only responsible for DH parameter definition and kinematics verification. It does not involve inverse kinematics algorithm development (belonging to the downstream P10 stage) or dynamic parameter identification (belonging to other process nodes).

Common Misconceptions

  1. "DH parameters are just another way of writing URDF" — Incorrect. The two are mathematically equivalent but differ in expression. URDF's <origin> contains the full 6D pose, while DH parameters use only 4 parameters and imply coordinate system establishment rules. Direct conversion requires attention to coordinate system alignment.

  2. "Error < 1e-6 is simulation accuracy" — Inaccurate. This error is the numerical comparison error between the forward kinematics code generated from DH parameters and the URDF model, reflecting the consistency of the two mathematical expressions rather than the physical error between simulation and physical robot. Physical error also needs to consider joint clearance, flexible deformation, and other factors.

  3. "Once DH parameters are determined, they never need modification" — Incorrect. When mechanical design changes (such as joint position adjustments) or coordinate system conventions are updated, DH parameters must be modified accordingly. The "modify DH parameter definitions" in P6.1.2 precisely emphasizes this dynamic maintenance process.

  4. "Symbolic computation can replace numerical verification" — Incorrect. Symbolic computation is used to verify derivation correctness but cannot cover the numerical accuracy of all joint angle combinations. Numerical comparison verification across the full joint angle range must be performed using numerical libraries such as Pinocchio/RBDL.
