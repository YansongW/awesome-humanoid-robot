Summary

Robots are typically described in software by specification files (e.g., URDF, SDF, MJCF, USD) that encode only basic kinematic, dynamic, and geometric information. Institutions per source list: Yale、APOLLO Lab.

Overview

This paper proposes the Universal Robot Description Directory (URDD), a modular robot description directory independent of underlying specifications such as URDF/SDF/MJCF/USD, which precomputes derived information (DOF mappings, kinematic chains, collision geometry, etc.) into structured JSON/YAML modules to eliminate redundant derivation across frameworks. The authors implement conversion and visualization tools in Rust, validate conversion efficiency and code reuse benefits on five robot platforms, and demonstrate composition and web viewing capabilities.

What It Changes

Robot software stacks have long been constrained by "lowest common denominator" specifications like URDF: they only encode raw kinematics/dynamics/geometry, while every downstream system—simulation, planning, control—must independently re-derive derived data such as DOF counts, kinematic chains, and collision geometry. This is not a performance issue but an ecosystem fragmentation problem—each framework writes its own parsing and derivation logic, resulting in inconsistencies, maintenance burdens, and no cross-tool reuse. URDD fundamentally changes the answer to "where does derived data come from": no longer computed ad hoc by each consumer, but generated once upstream, stored in a standardized form, and consumed on demand. It deliberately avoids specification-level extensions like URDF+ or Extended URDF, because extending a single format inevitably breaks compatibility with existing parsers; URDD, as an independent directory, is generated from URDF but not constrained by its syntax, enabling it to serve heterogeneous frameworks such as PyKDL, Drake, and MuJoCo simultaneously without requiring them to modify their own parsing logic.

Method Breakdown

URDD adopts a hierarchical directory structure, with the root directory containing metadata (robot name, version) and subdirectories as independent modules, all stored in JSON/YAML. The core design is "modularity + precomputation," rather than extending a single file.

Module Categories and Key Modules

  • Structural Properties: Chain module (parent-child hierarchy, parent joint/child joint lists), Connections module (joint-link path sequences between arbitrary link pairs)
  • Numerical Mappings: DOF module (total degrees of freedom, bidirectional joint index ↔ DOF index mapping), Bounds module (per-DOF upper and lower limits)
  • Precomputed Geometry: Mesh module (raw .glb/.obj/.stl + convex hulls/convex decompositions, relative paths), Link Shapes module (oriented bounding boxes, bounding spheres, neural network representation of self-collision states, link distance statistics, safely skippable pairs)

Conversion Pipeline

Rust implementation parses URDF → generates all 15 modules → stores mesh files → automatically computes convex hulls/convex decompositions → supports batch processing of entire robot repositories, outputting self-contained directories.

Composition and Visualization

  • Composition: Supports concatenating multiple URDDs (e.g., gripper + arm + quadruped), with attachment points allowing any valid joint type (fixed/revolute/prismatic/floating)
  • Visualization: Rust/Bevy desktop client (real-time rendering, shape switching, hierarchy highlighting, collision skip-pair overlay); JavaScript/Three.js web client (no installation required, configuration space exploration)

Key Design Decisions

  • Modular directory avoids single-specification file extensions breaking existing parsers
  • Language-agnostic structured data is preferred over code generation paradigms (e.g., RobCoGen), allowing any framework to consume it directly
  • Modules can be independently added, removed, or marked obsolete, supporting backward compatibility and incremental evolution

Key Innovations

  1. Standardized Prepositioning of Derived Data: URDD unifies derived computations—DOF counting, kinematic chain paths, convex decompositions, etc.—that were previously scattered across framework-internal logic into reusable standardized modules. This is not a new algorithm but a "data contract" at the ecosystem level, whose value lies in eliminating duplicate implementations and inconsistencies across frameworks.
  2. Format Agnosticism: Independent of any underlying specification (URDF/SDF/MJCF/USD), generated from URDF but not constrained by its syntax. This enables URDD to serve as an intermediate representation for all downstream frameworks without requiring them to modify parsers—something specification-level extensions (URDF+, etc.) cannot achieve.
  3. Precomputed Geometry and Learned Representations: The Link Shapes module stores not only traditional bounding volumes but also neural network representations of self-collision states and link distance statistics, moving geometric reasoning from runtime to build time, providing ready-to-use data for collision detection and motion planning.

Boundaries and Limitations

  • Scalability Not Verified: The authors acknowledge that adding modules will increase URDD size and parsing overhead. Although current evaluations show lightweight performance, large-scale adoption requires management strategies (e.g., on-demand module generation), for which the paper does not provide concrete mechanisms.
  • Module Dependencies Not Defined: For example, Jacobian computation depends on Chain and DOF modules, but the paper does not specify inter-module dependency declarations or validation mechanisms.
  • What Was Not Done: No direct comparative experiments with URDF+ or Extended URDF; no deployment testing on real robot hardware; no conversion tools from SDF/MJCF/USD to URDD.
  • Learned Representation Data Not Disclosed: The training data volume, hyperparameters, and inference frequency of the self-collision state neural network are not mentioned.

Engineering Insights

  • Verify Module Completeness First: When reproducing, confirm whether all 15 modules are generated, especially DOF mappings and Connections paths—these are the foundation for downstream IK/Jacobians, and missing them can cause silent errors.
  • Size Inflation Is Expected Behavior: URDD without meshes is 2-3 orders of magnitude larger than URDF (e.g., H1 from 0.028MB to 25.8MB), and with meshes B1 reaches 109.8MB. If deploying in resource-constrained environments, generate only the required modules (e.g., skip convex decomposition for kinematics-only use).
  • Most Common Pitfall: The Mesh module relies on relative paths; directory structure must be preserved when moving. When composing multiple URDDs, the choice of attachment point joint type affects subsequent kinematics calculations, and floating joints require additional handling.
  • Code Reuse Benefits Are Clear: FK implementations drop from 315-3784 lines to 0, but only if downstream frameworks are willing to consume URDD rather than continuing to parse URDF—teams need to evaluate migration costs versus benefits.
  • Conversion Time Is Acceptable: The most complex platform (Orca hand, 55 links) takes 90.5 seconds, suitable for offline batch processing; if models need frequent updates, incremental conversion is recommended over full rebuilds.
