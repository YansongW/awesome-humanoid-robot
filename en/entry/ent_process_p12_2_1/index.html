Overview

VLA model selection and fine-tuning (P12.2.1) is the first level-3 sub-task under the "VLA and Manipulation Policy" work package in the humanoid robot product development lifecycle. It is classified as a method type, belonging to the domain 07_ai_models_algorithms, with a value chain level of intelligence. This process uses OpenVLA, RT-X, π0, Diffusion Policy, and self-developed models as the candidate method pool. Its core objective is to map vision-language instructions to robot actions and fine-tune them for the specific robot platform. What it truly changes is not the accuracy ceiling of a single model, but rather transforming "models that can run demos" into "engineering modules that can be quantitatively validated and traceably delivered."

Content

What It Is: Precise Definition

VLA (Vision-Language-Action) model selection and fine-tuning refers to, within humanoid robot manipulation policy development, selecting vision-language-action models from a candidate model pool that match the hardware and task requirements of the specific robot, and through data collection, simulation validation, and parameter tuning, enabling them to possess end-to-end manipulation capabilities that can execute natural language instructions. The completion criterion for this process is delivering an "end-to-end demo that can execute natural language instructions" and achieving the preset success rate metrics.

In the WBS V3 process decomposition, P12.2.1 is expanded into five level-4 key action groups: input organization and target quantification (P12.2.1.1), algorithm/control scheme design (P12.2.1.2), algorithm implementation and simulation validation (P12.2.1.3), algorithm tuning and performance validation (P12.2.1.4), and documentation output and downstream delivery (P12.2.1.5). Each action group follows the standardized engineering closed loop of "input → scheme → implementation → validation → delivery."

Why It Exists: Pain Points and Historical Positioning

Before VLA models entered the robotics domain, manipulation policy development had long been fragmented across two approaches: traditional motion planning methods relied on precise environment modeling and hand-designed reward functions, exhibiting weak generalization; while end-to-end imitation learning methods could fit demonstration data but struggled to understand natural language instructions and were extremely sensitive to hardware differences. VLA models attempt to unify these two approaches using "vision-language joint representations," but this brings new engineering pain points:

  • Model scale vs. compute contradiction: Mainstream VLA models have parameter counts in the billions, while humanoid robot platforms often only have consumer-grade GPUs. How to complete fine-tuning and inference under limited compute is the first hurdle in model selection.
  • Sim-to-real gap: Policies trained in simulation environments often suffer severe performance degradation when transferred to real robots due to visual feature drift, dynamics differences, and other factors.
  • Data efficiency bottleneck: Real robot demonstration data collection costs are extremely high, with annotation and cleaning of a single trajectory taking far longer than traditional CV datasets.
  • Safety constraints: Humanoid robots may manipulate objects involving humans or fragile items, so model output actions must satisfy hard safety boundaries such as joint limits and torque constraints.

The historical positioning of P12.2.1 in the process is precisely to build a quantifiable bridge between "model capability" and "engineering deliverability"—it is not responsible for inventing new models, but rather for "domesticating" existing models into product components that conform to the specific robot's constraints, are acceptable for validation, and are traceable.

Principle Breakdown

① Input Organization and Target Quantification (P12.2.1.1)

The essence of this action group is "translating vague completion criteria into measurable KPIs." Upstream inputs include: visual feature formats output by the perception stack, kinematic parameters of the robotic arm/dexterous hand, natural language instruction sets for task scenarios, and compute resource inventories. There are three key actions:

  1. List all upstream input inventories and confirm versions—to prevent fine-tuning failures caused by inconsistent sensor firmware or interface versions;
  2. Convert acceptance criteria into quantifiable KPIs—for example, "success rate ≥ 90% (based on 50 test trials)" or "single inference latency ≤ 100ms" (both are example values, subject to engineering judgment);
  3. Establish task owners, timelines, and risk registers—clarifying responsible parties and milestones, and registering risks (such as insufficient data or compute overruns) in advance.

② Algorithm/Control Scheme Design (P12.2.1.2)

This action group requires forming no fewer than 2 candidate schemes and establishing an evaluation matrix for quantitative scoring. Candidate schemes typically come from combinations of OpenVLA, RT-X, π0, Diffusion Policy, and self-developed models. Evaluation dimensions must include at least:

  • Stability: variance of output actions under identical inputs;
  • Real-time performance: end-to-end latency from visual input to action command;
  • Scalability: whether new task instructions can be adapted without retraining.

The quantitative scoring in the evaluation matrix must incorporate measured data from the specific robot platform (such as joint response bandwidth and visual frame rate), rather than relying solely on values reported in papers. The implementation path is ultimately frozen through organizational review.

③ Algorithm Implementation and Simulation Validation (P12.2.1.3)

Implement the algorithm in simulation environments or on offline data to validate functional correctness, real-time performance, and robustness. Key actions include: establishing models/prototypes and recording key parameters (such as learning rate, batch size, LoRA rank), executing simulation or prototype validation, and recording anomalies and deviations. The core value of this stage lies in "low-cost trial and error"—issues exposed in simulation (such as action sequence deviations or end-effector positioning errors) can be fixed without consuming real robot lifespan.

④ Algorithm Tuning and Performance Validation (P12.2.1.4)

Perform parameter tuning and boundary testing on the algorithm to validate whether performance meets metrics under typical/extreme operating conditions. Key actions include: formulating test/review plans and pass criteria, executing tests and recording raw data, and outputting issue lists and improvement measures. Boundary testing should cover scenarios such as: sudden illumination changes, occlusion, target object color distribution shifts from training data, and joints approaching limits.

⑤ Documentation Output and Downstream Delivery (P12.2.1.5)

Output final reports/drawings/specifications, update ICD/BOM/SOP/requirements traceability chains, and complete formal delivery to downstream stages. Key actions include: writing documentation per templates with references to raw data, completing internal review and version control, and publishing and notifying downstream dependent parties. This step ensures that the intellectual activity of "model fine-tuning" is solidified as organizational assets rather than remaining at the level of personal experience.

Horizontal Comparison

In VLA model selection, the core differences among candidate schemes manifest in two dimensions: "architecture design" and "data requirements":

  • OpenVLA: Extends action heads based on pre-trained vision-language models (such as Prismatic), using discretized action token prediction. Its strength is strong language understanding; its weakness is that action precision is limited by discretization granularity.
  • RT-X (Open X-Embodiment): Emphasizes large-scale cross-embodiment, cross-task data pre-training, achieving multi-robot transfer through unified action spaces. Its strength is strong generalization; its weakness is that fine-tuning requires adapting to the robot's action space definition.
  • π0 (π-zero): Uses flow matching to generate continuous action sequences, suitable for high-precision manipulation. Its strength is smooth action generation; its weakness is that training stability is sensitive to hyperparameters.
  • Diffusion Policy: Models action generation as a denoising diffusion process, excelling at multimodal action distribution modeling. Its strength is expressing multiple feasible policies; its weakness is higher inference latency.
  • Self-developed models: Customized for the specific robot platform, capable of deeply coupling kinematic constraints, but with the longest development cycles and greatest data requirements.

The key to model selection is not "which model is strongest," but rather "which model can achieve the KPIs at the lowest cost given the compute, data volume, and safety constraints." For example, under an 8GB VRAM limit, a 3.1B-parameter VLA model requires LoRA and quantization techniques to run (inferred from corpus data), in which case the parameter count of Diffusion Policy-type models may become a bottleneck.

Who Uses It: Application Cases

Case 1: Low-Cost Fine-Tuning on Resource-Constrained Platforms (from ent_paper_omaisan_towards_accessible_physical_ai_2025)

The research team executed a button-pressing task on a SO101 robotic arm, using 200 demonstration trajectories to fine-tune a 3.1B-parameter VLA model with LoRA, combined with quantization to compress VRAM requirements to 8GB. Key findings were: freezing the vision encoder performed better with low data volumes, avoiding overfitting; primary failure modes included visual feature drift, action sequence deviations, and end-effector positioning errors. This case demonstrates that "consumer-grade GPU + small demonstration datasets" can accomplish effective VLA fine-tuning.

Case 2: Human-Robot Collaborative Dual-Agent Fine-Tuning (from ent_paper_jin_dual_actor_fine_tuning_of_vla_2025)

This study proposed a collaborative framework between a primary agent (responsible for robust multi-task execution) and a fine-tuning agent (responsible for latent space adaptive adjustments), introducing a "dialogue-adjustment" mechanism that converts human physical interventions into semantic instructions. In real multi-task experiments, after 101 minutes of online fine-tuning, three basic tasks (grasping, placing, stacking) all achieved 100% success rates, while the standard supervised fine-tuning (SFT) baseline averaged only 67%; long-horizon tasks (12 consecutive manipulations) maintained a 50% success rate, significantly outperforming the pure reinforcement learning (RL) method's 12% success rate. Dual-robot collaborative training achieved a 2x efficiency improvement.

Case 3: Cross-Platform Data Collection and Policy Deployment (from ent_paper_nian_control_your_robot_a_unified_s_2025)

The Control Your Robot framework supports both teleoperation and trajectory playback control modes through standardized workflows (modular design, unified API, closed-loop architecture), enabling seamless integration from multimodal data collection to inference. Experiments on single-arm and dual-arm systems showed that policies trained on data collected via this framework closely matched expert demonstrations, providing high-quality data infrastructure for VLA fine-tuning.

Limitations and Boundaries

  1. Diminishing returns of data volume vs. performance: Training data volume is positively correlated with real-world performance, but with diminishing marginal returns (from ent_paper_omaisan_towards_accessible_physical_ai_2025). Blindly increasing data volume does not always linearly improve success rates.
  2. Trade-off of freezing the vision encoder: Freezing the vision encoder performs better with low data volumes but may limit the model's ability to adapt to novel visual features; fine-tuning the vision encoder requires more data and compute.
  3. Stability bottleneck in long-horizon tasks: Even after fine-tuning, success rates for long-horizon tasks (e.g., 12 consecutive manipulations) remain significantly lower than single-step tasks, with error accumulation issues not yet fundamentally resolved.
  4. Residual sim-to-real gap: Passing simulation validation does not equal successful real-world deployment; visual feature drift and dynamics differences still require iterative tuning on the real robot.
  5. Hard boundary of compute constraints: 8GB VRAM is a typical lower bound for current low-cost deployment, but fine-tuning and inference for larger models (e.g., 7B and above) still require higher-spec hardware.

Common Misconceptions

  1. "Model selection means picking the strongest model"—Wrong. The essence of model selection is "finding the optimal solution under constraints"; compute, data volume, and safety boundaries are all hard constraints. A 3.1B model can run on 8GB VRAM, but a 7B model may fail even to load.
  2. "Fine-tuning means full parameter retraining"—Wrong. Parameter-efficient fine-tuning methods like LoRA only update low-rank matrices, drastically reducing VRAM usage and training time, and perform better with small data volumes.
  3. "Passing simulation validation means it works in reality"—Wrong. Simulation environments cannot fully replicate real-world factors such as visual illumination changes, joint friction, and cable drag; a tuning cycle on the real robot must be reserved.
  4. "Success rate is the only KPI"—Wrong. Latency, stability, and scalability are equally important. A model with 95% success rate but 500ms inference latency (example value, engineering judgment) may be completely unusable in real-time manipulation scenarios.
  5. "Documentation output is formalism"—Wrong. The documentation deliverables in P12.2.1.5 (reports, ICD/BOM/SOP updates, requirements traceability chains) are key to ensuring the model is maintainable, reproducible, and auditable; models lacking documentation cannot be iterated upon in subsequent stages.
