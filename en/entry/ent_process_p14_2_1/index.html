Overview

Data recording and playback is a critical process node under the Toolchain and DevOps work package (P14.2) in the software middleware and system integration phase (P14) of the development lifecycle. Its core task is to leverage tools such as rosbag2, structured logging, data lakes, and data version management to fully capture and structurally store sensor streams, control commands, and system states during robot operation, enabling subsequent problem reproduction, model training, and performance analysis. What it truly changes is not data storage itself, but the engineering traceability capability of the entire development process—shifting from "reproducing issues on-site" to "being able to return to any historical state at any time."

Content

What It Is: Precise Definition

Data recording and playback is a foundational engineering capability in robot software development. It refers to the continuous acquisition of multi-source heterogeneous data during system operation (including joint states, IMU readings, camera images, control commands, log events, etc.), synchronized storage indexed by timestamps, and precise on-demand replay of these data streams afterward, allowing developers to decouple from real hardware environments and reconstruct system behavior in simulation or offline analysis.

In the WBS V3 work breakdown, this node (P14.2.1) expands downward into five level-4 subtasks: P14.2.1.1 Input Analysis and Target Quantification, P14.2.1.2 Solution/Method Design, P14.2.1.3 Implementation/Prototype/Sample Fabrication, P14.2.1.4 Verification and Issue Closure, and P14.2.1.5 Documentation Output and Downstream Delivery. Each subtask follows a unified engineering action template, ensuring clear acceptance criteria and accountability at every step from requirements to delivery.

Why It Exists: Pain Points and Historical Positioning

In the early stages of humanoid robot development, debugging often relied on "on-site reproduction"—running the robot again in the same scenario to observe whether the fault recurred. This approach has three fundamental flaws: Non-reproducibility—robot system states are affected by noise, wear, and environmental disturbances, so the same code may produce different results at different times; Inefficiency—each reproduction requires the full hardware platform and on-site environment, with iteration cycles measured in days; Non-traceability—even if a problem is reproduced, it is impossible to answer questions like "what exactly was the controller's intermediate variable during the last run."

The advent of data recording and playback shifted the debugging paradigm from "on-site reproduction" to "offline replay." After a fault occurs, developers can retrieve the complete data stream from the data lake, replay it frame by frame in a simulation environment, and observe the trajectory of every intermediate variable. This shift reduces problem localization time from days to hours and makes model training and performance regression analysis based on real data feasible.

Principle Breakdown

① Time Synchronization: The Foundation for Multi-Source Data Alignment

Humanoid robots typically carry dozens of sensors, each with its own sampling frequency and clock source. The data recording system must stamp each data item with a unified timestamp and align all data streams along the time axis during replay. rosbag2 leverages ROS's /clock mechanism in conjunction with the TF tree to achieve hardware time synchronization across multi-sensor data. For cross-host data acquisition, clock synchronization relies on PTP (Precision Time Protocol) or NTP, and synchronization precision directly affects the accuracy of data association during replay.

② Storage Architecture: From Ring Buffers to Data Lakes

Real-time recording demands extremely low write latency, while long-term storage requires scalable capacity. Engineering practice typically employs a two-tier architecture: the front end uses a ring buffer in memory to temporarily hold recent data, satisfying the "last N seconds before crash" on-site retention requirement; the back end asynchronously writes data to distributed storage or a data lake, satisfying long-term archiving and batch analysis needs. Data transfer between the two tiers is handled by background threads to avoid blocking the real-time acquisition path.

③ Replay Mechanism: Time-Axis-Driven Deterministic Reenactment

The core challenge of replay lies in determinism—each replay must produce an identical data sequence to ensure problem reproducibility. To achieve this, the replay engine uses the recorded timestamps as the reference, advancing the virtual clock at a scaled ratio or original speed, with all subscribers consuming data according to the virtual clock. For scenarios requiring integration with simulation environments, the replay engine also supports "step mode"—advancing one frame of data only upon receiving an external trigger signal, facilitating frame-by-frame inspection of state changes.

Who Uses It: Application Cases

In the process definition of P14.2.1, the application of this node spans the entire software middleware and system integration phase. Typical usage scenarios include:

  • Problem Reproduction: When anomalies such as falls, jitter, or communication timeouts occur on-site, developers retrieve data from the fault time window in the data lake, replay it in a simulation environment, and determine whether the issue stems from perception latency, control parameters, or communication packet loss.
  • Model Training: Real-world recorded sensor data and human demonstration data are organized into training sets for offline training and evaluation of reinforcement learning policies or imitation learning models.
  • Performance Analysis: By replaying historical data, the output differences of different algorithm versions under identical inputs are compared, quantifying performance degradation or improvement to support version iteration decisions.

Limitations and Boundaries

Data recording and playback is not a panacea; its core limitation is that it records "what happened," not "why it happened." Replay can only reconstruct sensor inputs and system outputs, not physical processes at the hardware level (such as motor temperature changes or mechanical wear). Additionally, this node is constrained by three key factors: Storage capacity—long-duration operation generates massive data, requiring tiered storage and expiration policies; Bandwidth—real-time writing of high-frequency sensor data can become a system bottleneck, necessitating downsampling or compression at the acquisition end; Privacy—if robots are deployed in public or home environments, recorded images and audio may raise privacy compliance concerns, requiring desensitization before recording.

Common Misconceptions

  1. "The more data recorded, the better"—Wrong. Indiscriminately recording all topics rapidly exhausts storage and bandwidth and makes subsequent retrieval difficult. The correct approach is to select key topics based on the problem domain and design reasonable sampling rates and compression strategies.
  2. "Replayed data is equivalent to real operation"—Wrong. Replay can only reconstruct data-level inputs and outputs, not hardware timing, interrupt latency, or other physical characteristics. For real-time-dependent issues, replay results serve only as a reference and cannot replace verification on actual hardware.
  3. "Data recording is a post-hoc remedy"—Wrong. Data recording solutions should be incorporated into the architecture during the system design phase, including topic naming conventions, timestamp strategies, and storage capacity planning. Retroactive recording often fails to localize problems due to missing critical data.
