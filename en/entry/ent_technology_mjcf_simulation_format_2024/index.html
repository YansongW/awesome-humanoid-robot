Overview

MJCF (MuJoCo Simulation Format) is the native modeling format of the MuJoCo physics engine, an XML-based language used to describe articulated rigid-body systems with contacts, actuators, and sensors. What it truly changes is not "how to describe robots," but "how to make simulation modeling as iterative as writing web pages"—through a CSS-like default mechanism, it lets users start from minimal models and refine them progressively, transforming modeling from a one-time engineering task into an interactive experiment.

Content

What It Is: Precise Definition

MJCF is MuJoCo's native model format, an XML-based language specifically designed to describe complex dynamical systems. It can express various model elements including contacts, actuators, and sensors, and uses a built-in compiler to convert model descriptions into simulation data structures.

Three distinguishing features of MJCF (source: MuJoCo official documentation, Modeling chapter):

  1. Scalability first: Allows users to start with small models and gradually add details, rather than building a complete system from the outset;
  2. CSS-style default mechanism: Inspired by Cascading Style Sheets (CSS) in HTML, it significantly reduces repetitive descriptions through default value settings;
  3. Compile-time computation: The built-in compiler automatically performs numerous complex compile-time calculations, positioning MJCF between a modeling format and a programming language.

Why It Exists: Pain Points and Historical Positioning

Before MJCF, robot simulation modeling faced a core contradiction: expressiveness and ease of use could not coexist. Modeling formats of general-purpose physics engines were either too low-level (requiring vertex-by-vertex geometry description) or lacked first-class support for robotics primitives such as joints, actuators, and sensors. Researchers were forced into a painful trade-off between "model fidelity" and "modeling efficiency."

MJCF's positioning is precisely to fill this gap. It draws on a core concept from web development—progressive enhancement: users can first define a simple model with only a torso and legs, get control algorithms running, and then gradually add details such as joint limits, contact friction, and sensor noise. This design philosophy makes MJCF a bridge connecting "rapid prototyping validation" with "high-fidelity simulation."

Principle Breakdown

① XML Tree Structure and Compilation Pipeline

An MJCF model is essentially an XML tree. The root node <mujoco> contains child nodes such as <worldbody> (world coordinate system and rigid-body tree), <actuator> (actuator definitions), and <sensor> (sensor definitions). The model file is processed by MuJoCo's built-in compiler, generating the efficient C data structure mjModel for use by the simulator.

② Default Mechanism: The "CSS" of Modeling

MJCF's most ingenious design is the <default> node—it allows users to set default parameters for a class of elements, with child nodes able to inherit or override them. For example:

<default>
    <joint type="hinge" damping="0.1"/>
    <geom friction="1.0" density="1000"/>
</default>

This declaration makes all subsequently defined joints default to a damping of 0.1, and all geometries default to a friction coefficient of 1.0 and density of 1000. This greatly reduces repetitive descriptions, keeping model files concise.

③ Compile-time Automatic Computation

MJCF's compiler automatically performs several computations, including: inertia parameter aggregation (deriving mass and inertia tensors from geometry density), kinematic tree topology construction, and contact pair filtering. This means users do not need to manually calculate link center-of-mass positions or moments of inertia—they only need to define geometry shapes and densities, and the compiler automatically completes the remaining work.

Key Parameters and Specifications

Core specification parameters of MJCF (source: MuJoCo official documentation, Modeling chapter):

Parameter/Feature Description
Model elements Bodies, joints, geoms, actuators, sensors, pairs, tendons, etc.
Default mechanism Supports <default> nodes, CSS-like cascading overrides
Compile-time computation Automatically derives inertia parameters, kinematic trees, contact filtering
External format support Can load URDF (via URDF extensions), MJZ compressed packages, OpenUSD models
Programmatic modeling Supports loading, editing, compiling, and saving models via the mjSpec API in C/C++ or Python

MJCF's core advantage lies in being tailor-made for the MuJoCo physics engine—contact models, actuator models, and sensor models are deeply coupled with the engine's solver, avoiding information loss during format conversion. URDF's advantage lies in its widespread adoption within the ROS ecosystem, but its expressiveness is relatively limited.

Who Uses It: Application Cases

MJCF has been widely applied in humanoid robot simulation modeling and algorithm validation (source: simulation platform list in corpus chapter-08):

  1. Unitree H1: Simulation models built on MJCF for motion control and reinforcement learning training (associated entity ent_robot_unitree_h1_humanoid_robot_2024);
  2. HumanoidBench: A whole-body locomotion and manipulation benchmark based on Unitree H1, providing over 40 tasks and relying on MuJoCo/MJCF as the underlying simulation environment (associated entity ent_benchmark_humanoidbench);
  3. ManiSkill: A unified benchmark for generalizable manipulation skills, using MuJoCo as the physics engine and MJCF to describe manipulation scenarios (associated entity ent_benchmark_maniskill);
  4. Academic research: In fields such as reinforcement learning, model predictive control (MPC), and whole-body control (WBC), MJCF is the standard choice for building digital twin models.

Limitations and Boundaries

MJCF is not a panacea, and its boundaries need to be clarified:

  1. Not a general-purpose programming language: MJCF lacks the expressive power of general-purpose programming languages; complex logic requires external scripts or the mjSpec API;
  2. Limited soft-body support: Although MuJoCo supports soft bodies to a certain extent, MJCF's ability to describe flexible materials is weaker than specialized finite element formats;
  3. Ecosystem binding: MJCF is MuJoCo's native format; migrating to other physics engines (such as Bullet, PhysX) requires conversion to URDF or SDF, which may lose some details;
  4. Learning curve: Although the default mechanism lowers the entry barrier, advanced features (such as contact pair filtering, compile-time computation) require a deep understanding of MuJoCo's internal mechanisms.

Common Misconceptions

  1. "MJCF is just another way of writing URDF"—Wrong. MJCF's default mechanism, compile-time computation, and first-class support for contacts/actuators/sensors far exceed URDF's expressive capabilities; URDF leans more toward kinematic description, while MJCF is deeply optimized for dynamics simulation.

  2. "MJCF can only be used with MuJoCo"—Partially correct. Although MJCF is MuJoCo's native format, it can be exported to URDF/SDF via conversion tools for use with other engines, though some physical details will be lost.

  3. "The more detailed the model, the better"—Engineering judgment: overly detailed models (e.g., modeling every bolt) significantly increase computational cost without necessarily improving simulation accuracy. MJCF's design philosophy is "progressive enhancement"—start with the minimal model that meets requirements and add details as needed.
