Summary

Imagine a robot learning locomotion skills from any single video, without labels or reward engineering. We introduce SDS ("See it. Do it. Sorted.").

Overview

SDS (See it, Do it, Sorted) is a quadruped robot skill synthesis pipeline proposed by the UCL team that automatically generates executable reward functions from a single video demonstration and trains diverse gait policies. The core contribution lies in using GPT-4o combined with grid-frame prompting (𝒢ᵥ) and SUS multi-agent decomposition to fully automate reward engineering, achieving zero-shot deployment on a real Unitree Go1 with DTW distances as low as 10⁻⁶.

What It Changes

Quadruped gait acquisition has long been constrained by MoCap, manual reward shaping, and phase-based scheduling controllers, each step relying on expert experience and being difficult to transfer. What SDS truly changes is liberating "reward design"—the core bottleneck—from manual iteration: it uses vision-language models to directly "watch" videos and produce executable code, shifting skill discovery from "expert tuning" to "data-driven generation." This is not merely a simplification of the toolchain; it means the boundary of skill diversity expands from "rewards humans can think of" to "motions videos can demonstrate," without requiring any additional task inputs (such as natural language instructions or segmentation masks)—a fundamental distinction from methods like Eureka and DrEureka.

Method Breakdown

Input Processing: Grid-Frame Prompting (𝒢ᵥ)

  • Adaptively samples n frames based on demonstration speed v (n=T/v, τ=T/n), with dense sampling at low speeds to capture fine motion details
  • Frames are arranged in an h×w grid (h=w=√n), preserving temporal consistency and reducing token budget
  • ViTPose++ keypoints augment the grid to suppress hallucinations (e.g., misidentifying a quadruped as a "floating bench")

Task Decomposition: SUS Prompting

  • Four GPT-4o agents divide labor: Task-Descriptor (describes the task), Gait-Analyzer (analyzes contact sequences), Task-Requirement (extracts key features), SUS-Prompt-Generator (compiles the final prompt)
  • Multi-stage decomposition is inspired by cognitive reasoning, transforming complex visual information into structured task descriptions

Training Pipeline (7-Step Closed Loop)

  1. Reward Generation: GPT-4o generates n=8 candidate reward functions (including sub-rewards and total reward), filtered via static and runtime validation for invalid code
  2. Parallel Training: 4000 parallel agents in IsaacGym, PPO optimization for 1000 iterations, 25Nm torque limits, sub-rewards recorded every 100 iterations
  3. Evaluation: Policies deployed for 1000 time steps, ViTPose++ extracts keypoints rendered as grid 𝒢ₛ, while binary contact sequences ℝ^{4×1000} are recorded and rendered as contact plots (CP)
  4. GPT-4o Scoring: Scores based on pose stability, gait periodicity, and trajectory following (0-10), summed to select the optimal RF*
  5. Reward Evolution: RF* serves as the seed, combined with training log feedback (positive reinforcement prompts on success, traceback diagnostics on failure) to generate the next generation of candidates, enabling gradient-free reward optimization

Key Design Decisions

  • n=8 is an empirically tuned result, balancing candidate diversity against hallucination/unexecutable code risk
  • Unbounded growth components are adaptively rescaled; zero-gradient terms are flagged as uninformative and potentially discarded
  • Reward components cover speed (Vel/FM), base height (BH), orientation (Or), contact patterns (CP), limb synchronization (LS), action smoothness (AS), and joint limits (DoFL)

Key Innovations

  1. Vision as Reward: For the first time, reward function generation is built entirely on video understanding, requiring no manual design or additional task inputs. GPT-4o directly extracts kinematic features from grid frames and converts them into executable code—more direct than text-video alignment approaches like RoboCLIP and VLM-RM, while avoiding the cross-embodiment generalization limits of morphology-specific VLMs (e.g., S3D).

  2. Closed-Loop Evolution Mechanism: Reward optimization is modeled as an iterative "generate-train-evaluate-feedback" loop, where GPT-4o continuously improves reward functions via PPO training logs (scalar statistics converted to natural language summaries) and code execution feedback (tracebacks). This is a new paradigm for gradient-free reward optimization—more robust than Eureka's single-shot generation, and it automatically discards uninformative reward components (e.g., retaining only FM and DoFL in Hop).

  3. Adaptive Grid Sampling: 𝒢ᵥ dynamically adjusts frame density based on demonstration speed—dense sampling at low speeds captures fine gait details (e.g., Pace's ℝ^{6×6} grid), while sparse sampling at high speeds preserves macroscopic dynamics (e.g., Bound's ℝ^{4×4} grid). This speed-aware visual encoding is more efficient than fixed-frame-rate sampling, and combined with ViTPose++ keypoint augmentation, significantly reduces visual hallucination risk.

Ablation Experiments

  • Removing either 𝒢ᵥ or SUS mechanism: 0% contact pattern alignment, DTW>150 (complete failure)
  • Without 𝒢ᵥ, computational cost increases ×16 (slower convergence)
  • Removing 𝒢ₛ: contact matching drops to 4%; removing CP: drops to 19%; removing both: 0%, DTW>100

Generalization Experiments

  • ANYmal-D (38kg, 25cm wide, 49cm tall, reversed knee joints) trained for Trot and Bound: average DTW 157×10⁻⁶, average contact matching 95%

Stability

  • Base height fluctuation variance: 3.6×10⁻⁵m (Pace) to 3.6×10⁻⁴m (Hop)
  • Adding ground friction (rough socks) shows no significant change (Wilcoxon test, p=0.07)
  • Overall average StS=1.77 (max 2) under 50-110N lateral pushes

Boundaries and Limitations

  • Relies on side-view demonstrations with clearly visible limbs; generalization to arbitrary viewpoints and occluded scenes is limited; short-legged or furry animals (e.g., Persian cats) have poor keypoint visibility, degrading tracking accuracy
  • Static or low-dynamic skills (e.g., horse rearing) achieve low imitation success due to limited temporal variation in demonstrations and reduced contact cue reliability
  • Validated only on flat terrain; diverse terrain properties and domain shifts are not addressed; assumes full simulator state access, with no exploration of onboard-sensing-only learning
  • Single-skill-per-SDS-training limits scalability; multi-skill integration is not implemented; only periodic motions are addressed, with no extension to non-periodic behaviors
  • Effectiveness on morphologically distinct platforms (e.g., humanoid robots) is untested; no validation in outdoor or unstructured environments
  • The paper does not specify: systematic analysis of how demonstration video quantity, quality, or diversity affects SDS performance

Engineering Insights

  • Priority for Reproduction: Reward functions must be compatible with the IsaacGym observation API (environment variables include boolean foot contacts ℝ⁴, joint angles and velocities ℝ¹²)—this is a prerequisite for GPT-4o-generated code to execute. It is recommended to first run the official prompt files (https://github.com/sdsreview/SDS_ANONYM/tree/main/SDS/prompts) for init_sds_system and sds_user, then adjust the n=8 candidate count.
  • Most Common Pitfall: The 𝒢ᵥ and SUS prompting mechanisms are both indispensable—ablations show complete failure if either is removed. If contact matching rates drop sharply during reproduction, first check whether ViTPose++ keypoint augmentation is active and whether grid frames are adaptively sampled by speed (dense at low speeds, sparse at high speeds).
  • Evaluation Metric Trap: DTW distance is sensitive to frame alignment; it is recommended to also report contact sequence matching rates (SDS achieves 96% on real-world Bound, 98% average). If DTW exceeds the 10⁻⁶ order, first check whether PPO training reached 1000 iterations with no reset events (Table 9 shows zero resets across all skills).
  • Hardware Requirements: Single-skill 1-day training requires an RTX-4090 with 4000 parallel agents. If compute is insufficient, reducing parallelism is possible but note convergence speed implications (without 𝒢ᵥ, computational cost increases ×16).
  • Guidance for Downstream Teams: Real deployment requires 50Hz inference frequency and onboard force sensors for contact data (smoothed via moving average filtering). For stability evaluation, the StS metric is recommended (StS=2−[clip(CoM_dist,0,1)+clip(|ω|,0,1)]), with a maximum of 2; SDS achieves a mean of 1.72 under 110N perturbations, serving as a robustness benchmark.
