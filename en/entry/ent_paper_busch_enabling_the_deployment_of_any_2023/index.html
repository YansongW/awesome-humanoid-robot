Summary

This paper proposes a microservice-based containerization workflow for ROS/ROS 2 robotic applications and releases an open-source tooling suite (docker-ros, docker-ros-ml-images, docker-run) that automates minimal Docker image builds, supplies ML-enabled base images, and simplifies container-driven development, with qualitative comparison and deployment on an automated driving research vehicle.

Sources

  • Enabling the Deployment of Any-Scale Robotic Applications in Microservice Architectures through Automated Containerization

概述

本文由德国亚琛工业大学汽车工程研究所（ika）提出，针对机器人应用从开发到大规模部署的复杂性，设计并开源了 docker-ros、docker-ros-ml-images 和 docker-run 三件套工具。核心贡献在于通过自动化多阶段容器化构建流程，将 ROS 应用打包为仅含二进制与运行时依赖的最小部署镜像，并集成 CI/CD 与多架构支持，为微服务化机器人系统提供了工程化基础。

它改变了什么

机器人软件长期停留在单体或松耦合节点阶段，ROS 的模块化设计虽降低了功能开发门槛，却未解决跨设备、跨平台的大规模互联部署问题。现有工具如 industrial_ci、action-ros-ci 和 ros_buildfarm 要么侧重 CI 测试，要么生成 Debian 包，均未将“构建最小可部署容器镜像”作为核心目标。这导致从开发环境到生产环境的转换依赖手工操作，OTA 更新与弹性伸缩难以自动化。

该工作真正改变的是将 Web 领域成熟的“构建-发布-运行”容器化范式引入机器人软件生命周期。它不再把容器视为运行环境的替代品，而是将其作为部署单元，通过分离开发镜像与部署镜像，在保证可复现性的同时显著降低镜像体积。这一转变使得机器人应用可以像 Netflix 微服务一样被编排、滚动更新和弹性扩展，而非停留在单机演示阶段。

方法拆解

构建流程（docker-ros）

  1. 基础镜像选择：接受任意 Ubuntu 镜像，若缺少 ROS 核心则自动安装，支持 amd64 与 arm64。
  2. 依赖解析：优先使用 rosdep 管理系统与 ROS 依赖；公共/私有代码仓库依赖通过 vcstool 拉取；复杂依赖回退至自定义 shell 脚本。
  3. 阶段分离：多阶段 Dockerfile 中，dependencies 阶段仅安装依赖，dependencies-install 阶段固化依赖层，dev 阶段添加源码，build 阶段编译目标包，run 阶段仅复制编译产物（ROS install space）与运行时依赖。
  4. 产物输出：开发镜像含源码与依赖，部署镜像仅含二进制，避免源码泄露并减小体积。

关键设计决策

  • 依赖层缓存：将依赖安装与源码编译分离，利用 Docker 层缓存加速迭代构建。
  • CI/CD 集成：提供 GitHub Actions 与 GitLab CI 模板，测试阶段通过集成 industrial_ci 实现，而非原生功能。
  • 运行时要求：仅依赖 OCI runtime（Docker 兼容），可由 docker-compose 或 Kubernetes 编排。

配套工具

  • docker-ros-ml-images：组合 ROS 发行版（noetic、foxy、humble、rolling）、ROS 组件（core 至 desktop-full）、ML 框架（CUDA、TensorFlow Python/C++、PyTorch Python/C++）与架构（amd64、arm64），构建超 100 个多架构镜像并发布至 DockerHub。
  • docker-run：封装官方 Docker CLI，自动处理 X11 转发、GPU 支持、权限管理、源码挂载与容器附加，支持插件扩展，区别于 rocker 的即时镜像构建方式。

关键创新

  1. 最小部署镜像的自动化生成：现有工具要么输出开发镜像（industrial_ci），要么输出 Debian 包（ros_buildfarm），docker-ros 首次将“仅含二进制与运行时依赖”作为默认构建目标，直接降低部署体积与攻击面。
  2. 依赖管理的分层策略：将 rosdep、vcstool 与自定义脚本按优先级组合，覆盖从系统包到私有仓库的完整依赖谱系，且不牺牲可复现性。
  3. 多架构与 ML 框架的一体化支持：docker-ros-ml-images 预构建超过 100 个组合镜像，免去用户自行配置 CUDA 与 ROS 的繁琐步骤，显著降低 GPU 机器人应用的容器化门槛。

实验与结果

论文未进行定量基准测试，仅引用文献 [40] 说明 Docker 对 CPU、GPU 和内存性能开销可忽略。启动开销实测约 1 s，多容器同时启动时开销增加，但仍在可接受范围。构建时间主要由依赖安装与源码编译主导，且与开发异步执行。磁盘空间方面，Docker 复用公共基础镜像层，多个 docker-ros 镜像共享底层 ROS 安装。

边界与局限

论文未在真实大规模 ITS 或车队场景中验证部署效果，也未与 snap 在大规模编排中的适用性做定量对比。实时性约束下的容器化性能表现未讨论，启动开销的具体上限与优化方案未给出。docker-ros 不支持文档生成（ros_buildfarm 支持），测试功能依赖集成 industrial_ci 而非原生实现。所有性能结论基于文献引用而非实测，论文未明确。

工程启示

复现时先核对基础镜像的 Ubuntu 版本与 ROS 发行版匹配性，docker-ros 对 Ubuntu 的依赖意味着 Debian 或 macOS 环境需自行调整。依赖管理优先使用 rosdep，私有仓库务必配置 vcstool 的认证信息，否则构建会在 dependencies 阶段失败。部署镜像仅含二进制，若应用需要动态加载 Python 模块或运行时生成代码，需在 run 阶段显式添加解释器与相关库。

集成 CI 时，测试阶段通过 industrial_ci 实现，需确保 CI 环境有 Docker 权限且网络可访问 rosdep 源。多架构镜像构建建议直接使用 docker-ros-ml-images 预构建产物，避免本地交叉编译的复杂性。启动开销约 1 s 对单节点可忽略，但若编排数十个容器，需评估 docker-compose 或 Kubernetes 的调度延迟。最易踩坑处在于自定义 shell 脚本依赖：脚本中的绝对路径与基础镜像的差异会导致构建失败，建议在脚本内显式设置工作目录。
