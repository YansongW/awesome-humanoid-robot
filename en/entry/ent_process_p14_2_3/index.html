Overview

The CI/CD and simulation test chain is a critical process node in the software middleware and system integration phase (P14) of humanoid robot development. It builds a continuous integration pipeline from code commit to automated verification through GitLab CI, Docker, SIL/HIL automated testing, and code coverage tools. What it truly changes is not "the number of testing tools," but "the timing of software quality issue discovery"—allowing regression defects to be intercepted before merging into the main branch, rather than surfacing only during full-system integration. This process unfolds across five third-level subtasks (P14.2.3.1 to P14.2.3.5), covering a complete engineering loop from input quantification to downstream delivery.

Content

What It Is: Precise Definition

The CI/CD and simulation test chain is an engineering methodology system that deeply couples Continuous Integration, Continuous Delivery, and Simulation Testing. In the humanoid robot development workflow, it resides within the software middleware and system integration phase (P14), existing as a third-level subtask of work package P14.2, numbered P14.2.3.

Its core composition includes four technical pillars:

  • GitLab CI: Serves as the pipeline orchestration engine, defining the automated flow from code commit to build, test, and packaging;
  • Docker: Provides environment consistency guarantees, ensuring that "it works on my machine" no longer holds in the pipeline;
  • SIL/HIL Automated Testing: Two levels of testing—Software-in-the-Loop and Hardware-in-the-Loop—which respectively validate algorithmic logic correctness and controller hardware timing behavior;
  • Code Coverage: Quantifies the extent to which tests cover code paths, serving as the quantitative basis for quality gates.

The completion criteria for this process are explicitly defined as three things: the CI pipeline runs stably, the automated test pass rate reaches the preset threshold, and coverage metrics meet acceptance requirements.

Why It Exists: Pain Points and Historical Positioning

The complexity of humanoid robot software stacks far exceeds that of ordinary embedded systems. The upper layer consists of AI tasks such as visual perception, path planning, and large model inference, running at 10–100 Hz; the lower layer is the joint control loop, requiring update rates above 1 kHz. The two layers communicate through middleware, and a regression defect in either layer can trigger anomalies across the entire machine.

In the era before CI/CD and simulation test chains, software verification relied on two inefficient methods: manual integration—developers manually merging code and triggering tests locally, which is inefficient and highly prone to missing regressions; and full-machine physical testing—deploying software to physical prototypes for verification, which is costly, slow, and risky. A typical pain point scenario: a developer modifies one field in a communication protocol, local compilation passes, unit tests pass, but after merging into the main branch, it causes parsing logic in other modules to crash—such issues in purely manual processes often go undetected until full-system integration.

The historical positioning of the CI/CD and simulation test chain is precisely to shift-left the verification stage: before code merges into the main branch, an automated pipeline completes builds, static checks, unit tests, and SIL simulation tests, triggering HIL hardware-in-the-loop tests when necessary. What it truly changes is not "where testing happens," but "the temporal distribution of defect discovery"—dispersing the defect outbreak originally concentrated in the integration phase across every code commit.

Principle Breakdown

① Pipeline as Gate: The Core Mechanism of CI

The core of GitLab CI is the hierarchical structure of Pipelines and Jobs. A code push triggers a pipeline, which consists of multiple sequential stages, each containing several parallel jobs. A typical stage division is as follows:

\[ \text{Pipeline:} \quad \underbrace{\text{build}}_{\text{Compilation}} \rightarrow \underbrace{\text{static\_check}}_{\text{Static Check}} \rightarrow \underbrace{\text{unit\_test}}_{\text{Unit Test}} \rightarrow \underbrace{\text{sil\_test}}_{\text{Software-in-the-Loop}} \rightarrow \underbrace{\text{coverage}}_{\text{Coverage Gate}} \]

Each job runs in a Docker container, where the container image locks in the compilation toolchain, dependency library versions, and system environment. This means environment consistency is guaranteed by image immutability—the same code built at any time on any runner should produce identical results. The job's exit code determines whether the pipeline continues: if any job fails, subsequent stages are automatically skipped, and the merge request is blocked.

② Two-Level Simulation: The Division of Labor Between SIL and HIL

SIL (Software-in-the-Loop) runs the software under test directly on the host machine or in a simulation environment, with the controlled object being a purely mathematical model. It validates algorithmic logic correctness—whether the controller's state machine transitions, the planner's path outputs, and the communication protocol's encoding/decoding match the design. SIL's advantages are speed, low cost, and ease of parallelization; its disadvantage is that it does not involve real hardware timing.

HIL (Hardware-in-the-Loop), by contrast, connects real controller hardware into the closed loop, with the controlled object solved by a real-time simulation machine. It validates timing and interface correctness—whether the control cycle is stable, whether bus communication drops frames, and whether interrupt responses are timely. The HIL closed-loop structure can be expressed as:

\[ \text{HIL Closed Loop:}\quad \underbrace{\text{Real Controller}}_{\text{Real Hardware}} \;\xrightarrow{\text{Control Commands}}\; \underbrace{\text{Real-Time Simulator}}_{\text{Virtual Controlled Object}} \;\xrightarrow{\text{Sensor Feedback}}\; \text{Real Controller} \]

The two simulation levels occupy different positions in the pipeline: SIL runs as a regular gate on every commit; HIL, requiring real-time simulator resources, is typically triggered on nightly builds or key milestone nodes.

③ Coverage as a Quality Gate

Code coverage measures the proportion of code lines, branches, or paths executed by tests. It serves as the quantitative basis for quality gates, preventing false positives where "tests pass but large amounts of code are never executed." Coverage metrics, together with test pass rates, typically constitute the quantitative KPIs in completion criteria.

Horizontal Comparison

Within the humanoid robot software verification system, the CI/CD and simulation test chain complements adjacent verification methods:

Verification Method Verification Target Environment Timing Cost
Unit testing Individual functions/modules Host machine Every commit Low
SIL simulation testing Algorithmic logic/multi-module integration Host machine/simulation environment Every commit Medium
HIL hardware-in-the-loop testing Controller hardware + timing Real-time simulator Nightly/milestones High
Full-machine physical testing Complete system Physical prototype Integration phase Extremely high

The unique value of the CI/CD and simulation test chain lies in automating and pipelining the first three levels of verification, enabling every code change to trigger a complete verification chain from unit to SIL. Compared to purely manual testing, what it truly changes is not "whether tests are executed," but "the frequency and determinism of test execution"—manual testing may be skipped due to time pressure, while the pipeline executes unconditionally.

Who Uses It: Application Cases

Typical application scenarios for this process include:

  • Humanoid robot software teams: When developing algorithm modules such as motion control, perception, and navigation, the CI pipeline ensures that each merge does not break existing functionality. The typical flow is: developer pushes code → GitLab CI triggers the pipeline → compilation and unit tests complete in Docker containers → SIL simulation validates control logic → coverage check → merge into the main branch is allowed only after all pass.
  • Middleware and driver development: When modifying communication protocols or driver interfaces, SIL tests validate protocol encoding/decoding correctness, and HIL tests validate real bus timing. This avoids the typical integration incident of "the protocol changed but the driver didn't keep up."
  • Multi-team collaboration scenarios: When multiple teams (motion control, perception, navigation) share the same code repository, the CI pipeline serves as a merge gate, ensuring that any team's changes do not break other teams' functionality. The evaluation matrix and quantitative scoring are used to make rational choices among candidate solutions.

Limitations and Boundaries

The CI/CD and simulation test chain is not a panacea; its limitations include:

  • Computational constraints: SIL simulation, especially multi-joint dynamics simulation, requires significant computational resources, and concurrent pipeline execution may create resource bottlenecks. This is one of the key constraints explicitly listed in the corpus.
  • Test environment maintenance costs: Docker images require continuous updates to track dependency library versions; HIL real-time simulators require specialized maintenance. Environment maintenance itself becomes a sustained investment.
  • The gap between simulation and reality: In SIL, the controlled object is a mathematical model, and model accuracy directly affects test validity; although HIL connects real hardware, the controlled object remains simulated. Simulation cannot fully replace full-machine physical testing—passing simulation tests ≠ correct real-machine behavior.
  • Limitations of coverage metrics: High coverage does not guarantee high test quality—tests may cover code lines but miss critical boundary conditions. Coverage is a necessary but not sufficient condition.

Common Misconceptions

  1. "CI/CD is just automated compilation"—Wrong. Compilation is only one stage of the pipeline. The core of CI/CD is continuous verification: every commit triggers a complete test chain, including unit tests, SIL simulation, and coverage checks. Automated compilation is only the first step; automated verification is the goal.
  2. "Passing SIL means ready for the real machine"—Wrong. SIL validates algorithmic logic and does not involve real hardware timing. Controllers may behave abnormally on real machines due to bus latency, interrupt jitter, and resource contention. SIL and HIL are complementary, not substitutive.
  3. "100% coverage means complete testing"—Wrong. Coverage only indicates that code lines were executed, not that assertions are effective. A test suite that covers all code lines but has entirely empty assertions is worthless even at 100% coverage. Coverage metrics must be considered together with assertion quality and boundary condition coverage.
  4. "Docker solves all environment problems"—Wrong. Docker guarantees consistency of the build environment, but not the runtime environment. HIL testing involves real hardware whose behavior is influenced by physical factors and cannot be containerized. Docker solves the "build dependency" problem, not the "hardware behavior" problem.
