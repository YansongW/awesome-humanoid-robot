Overview

The overall architecture and function allocation (P1.2.2) is a core process node in the system solution design phase of a humanoid robot project, belonging to the third-level subtask under the P1.2 system solution design work package within the requirements definition and system solution (Concept / Pre-A) phase. What it truly changes is not the act of drawing an architecture diagram, but the decision-making approach "from part stacking to system contracts"—before detailed design, it freezes the boundaries and interface relationships of the seven subsystems—motion, manipulation, perception, computing, energy, thermal management, and structure—into a traceable engineering baseline using functional decomposition, N² diagrams, and interface control document (ICD) drafts. This node is uniformly expanded into five fourth-level key actions: input review and target quantification, solution/method design, implementation/prototype/sample fabrication, verification and issue closure, and documentation output and downstream delivery.

Content

What It Is: Precise Definition

Overall architecture and function allocation is a process node under the P1.2 system solution design work package. Its input is the product specification and requirements baseline output by P1.1 requirements engineering, and its outputs are the system architecture diagram, function allocation table, and ICD draft. It answers three questions: what subsystems constitute the entire machine, what functions each subsystem undertakes, and how subsystems interact with each other.

The methods/tools for this node are explicitly defined as functional decomposition, N² diagrams, and interface control document (ICD) drafts. Functional decomposition breaks down the overall machine functions layer by layer into allocatable atomic functions; N² diagrams enumerate the interface relationships between subsystem pairs in matrix form; ICD drafts provide preliminary agreements on the electrical, mechanical, communication, thermal, and software attributes of each interface. Together, they form a complete chain of "architecture description—interface enumeration—contract solidification."

The design reasoning logic requires clarifying the boundaries of the seven subsystems: motion, manipulation, perception, computing, energy, thermal management, and structure. The key constraints are real-time performance, power consumption, cable count, and maintainability—these four constraints determine the topology of the architecture: real-time performance dictates the communication method between computing and actuation, power consumption determines the capacity and distribution of the energy subsystem, cable count determines the routing topology and connector selection, and maintainability determines the module partitioning granularity and quick-release structure design.

Why It Exists: Pain Points and Historical Positioning

In the early days of the humanoid robot industry, teams often skipped overall architecture design and went directly into subsystem detailed design. Mechanical engineers selected motors based on intuition, software engineers defined interfaces based on imagination, and only during integration did they discover insufficient joint peak torque, inadequate communication bandwidth, or substandard safety levels—rework costs escalated exponentially. The existence of the overall architecture and function allocation node is precisely to fix "who does what, and who talks to whom and how" with an architecture diagram and an ICD draft before detailed design.

From a process positioning perspective, P1.2.2 sits in the middle of P1.2 system solution design: upstream is the quantified requirements baseline output by P1.1 requirements engineering, and downstream are the detailed design tasks of each subsystem. It serves a "translation" function—translating requirements language into architecture language, turning "the robot must be able to lift a 10 kg object" into "the manipulation subsystem requires a 6-DOF arm, peak torque ≥ X N·m, and a communication cycle with the computing subsystem ≤ Y ms." If this translation is missing, all subsequent subsystem designs will operate in silos.

Principle Breakdown

① Functional Decomposition: From "Whole-Machine Capability" to "Atomic Functions"

Functional decomposition follows a three-layer progression of "goal—function—means." The first layer lists the goal capabilities the entire machine must achieve (e.g., walking, grasping, navigation); the second layer decomposes each goal capability into functions (e.g., walking decomposes into gait planning, joint servo control, posture balancing); the third layer assigns each function to a specific subsystem (e.g., gait planning belongs to the computing subsystem, joint servo control belongs to the motion subsystem). The granularity of decomposition follows the criterion that "one function belongs to only one subsystem," avoiding responsibility vacuums caused by ambiguous function ownership.

② N² Diagram: Exhaustive Enumeration and Conflict Discovery of Interface Relationships

An N² diagram is an N×N matrix, where N is the number of subsystems. Diagonal cells contain subsystem names, and off-diagonal cells contain interface descriptions between two subsystems. For seven subsystems, every off-diagonal cell (N×(N−1) cells) must be explicitly filled with "has interface" or "no interface." The value of this exhaustive process lies in the fact that it forces the design team to answer "whether there is actually interaction" for every subsystem pair, thereby discovering omitted interfaces at the drawing stage.

③ ICD Draft: Contractualization of Interface Attributes

The ICD draft defines five categories of attributes for each identified interface: electrical (voltage, current, signal type), mechanical (connector model, mounting dimensions, protection rating), communication (protocol, baud rate, cycle), thermal (heat flow direction, allowable temperature rise), and software (data format, invocation method). The word "draft" in ICD draft means that revisions are permitted during subsequent detailed design, but revisions must go through a change management process—this is precisely what "contract" means.

Horizontal Comparison

The relationship between the overall architecture and function allocation node and its adjacent nodes can be understood through the following table:

Comparison Dimension P1.1 Requirements Engineering P1.2.2 Overall Architecture and Function Allocation P1.2.3 Subsystem Detailed Design (Downstream)
Core question What the robot needs to do What parts constitute the robot and how they collaborate How each part is specifically implemented
Outputs Requirements specification, quantified KPIs System architecture diagram, function allocation table, ICD draft Detailed design drawings, calculation reports
Abstraction level Requirements layer (user language) Architecture layer (system language) Implementation layer (engineering language)
Change cost Low (modify documents) Medium (modify architecture diagram and ICD) High (modify drawings and code)

This comparison reveals a key rule: the change cost at the architecture layer is far lower than at the implementation layer. The purpose of P1.2.2 is to move high-cost changes as early as possible to the low-cost stage for resolution.

Who Uses It · Application Cases

This node applies to all humanoid robot product development projects adopting the WBS V3 process, especially teams transitioning from the concept stage to the Pre-A prototype stage. Typical application scenarios include:

  • Whole-machine solution review: During the Pre-A stage, teams use the system architecture diagram to present the technical roadmap to investors and management, use the function allocation table to explain the responsibility boundaries of each subsystem, and use the ICD draft to demonstrate that interface risks have been identified.
  • Cross-team collaboration kickoff: When mechanical, electrical, software, and algorithm teams start detailed design in parallel, the ICD draft serves as the "interface constitution" constraining each team's interface definitions, avoiding "interface disputes" during integration.
  • Supply chain selection input: The function allocation table clarifies the functional requirements of each subsystem, enabling the procurement team to issue quantified technical requirements to suppliers rather than vague "good performance."

Limitations and Boundaries

The limitation of this node is that architecture design cannot eliminate all integration risks. N² diagrams can only enumerate known interface relationships and cannot foresee emergent issues in dynamic interactions (such as electromagnetic interference, thermal coupling, or software deadlocks). The "draft" nature of the ICD draft means interfaces may be revised during detailed design, and the cascading impact of such revisions is difficult to fully predict at the architecture layer.

Boundary conditions include: this node does not involve specific component selection calculations (which belong to downstream detailed design); it does not involve the specific implementation of control algorithms (which belongs to software detailed design); it does not involve manufacturing process planning (which belongs to the process phase). It is only responsible for "defining boundaries and interfaces," not for "implementing the content within the boundaries."

Common Misconceptions

  1. "An architecture diagram is just drawing a block diagram"—Wrong. The system architecture diagram must correspond one-to-one with the function allocation table; every block must have a clear functional description and interface list; otherwise, it is merely a decorative picture.
  2. "The N² diagram only fills in cells with interfaces"—Wrong. The value of the N² diagram lies precisely in exhaustively filling all cells, including "no interface" cells. Only by explicitly confirming "no interface" can unexpected interactions during integration be avoided.
  3. "The ICD draft can wait until detailed design"—Wrong. The core value of the ICD draft is to expose interface conflicts early. If written only during detailed design, interface conflicts have already turned into rework costs.
  4. "The finer the function allocation table, the better"—Wrong. The granularity of function allocation is capped by "one function belongs to only one subsystem." Overly fine granularity leads to an explosion in the number of interfaces, increasing integration complexity instead.
