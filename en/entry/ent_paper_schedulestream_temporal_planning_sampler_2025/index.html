Summary

Bimanual and humanoid robots are appealing because of their human-like ability to leverage multiple arms to efficiently complete tasks. However, controlling multiple arms at once is computationally challenging due to the growth in the hybrid discrete-continuous action space. Institutions per source list: NVIDIA Research（Caelan Garrett）、University of Sydney（Fabio Ramos）.

Overview

ScheduleStream is a general-purpose planning and scheduling language built entirely on Python, proposed by the author team to overcome the limitation of traditional TAMP frameworks (such as PDDLStream) that only support sequential plans, directly supporting schedules where actions overlap asynchronously in time. Its core contribution lies in seamlessly integrating a declarative planning language with procedural Python programming, introducing continuous sampling operations (streams) to instantiate action parameters in infinite constant domains, and proposing the Eager Stream Scheduling algorithm to solve minimal makespan schedules.

What It Changes

What it truly changes is the "solution space shape" of TAMP problems. Previously, frameworks like PDDLStream output action sequences, implying the serial constraint of "one action completes, the next begins," which severely wastes parallel hardware capabilities in multi-arm coordination scenarios. ScheduleStream defines solutions as timestamped schedules τ, allowing actions to overlap, directly altering the combinatorial structure of the planning problem—from "arranging actions" to "arranging action start and end times on a timeline"—and introducing makespan as an optimization objective. Additionally, it bridges the gap between declarative languages (PDDL) and procedural languages (Python), allowing users to directly define predicates (such as collision detection) and samplers (such as trajectory planning) as Python functions, addressing PDDL's inability to express infinite continuous parameter spaces (such as SE(3) configurations).

Method Breakdown

Language Core: Functional State and Overloaded Operators

  • State is defined as assignments to functions, e.g., At(arm1)<=q1 indicates that arm 1's current configuration is q1. A variant of the closed-world assumption is adopted: undeclared functions evaluate to None, and undeclared predicates are False.
  • By overloading Python's <= (assignment) and == (test) operators, declarative modeling syntax is embedded into Python, making state updates and condition checks directly readable at the code level.

Action Models: Instantaneous and Durative

  • Instantaneous actions (e.g., pick): Similar to STRIPS, with preconditions (e.g., Kin(...), Attached("?obj")==None) and effects (e.g., Holding("?arm")<="?obj").
  • Durative actions (e.g., move): Extended with start conditions/effects, invariant conditions, end conditions/effects, and duration. For example, move's start effect is At("?arm")<="?t" (intermediate trajectory point), its end effect is At("?arm")<="?q2", and its duration is computed by the procedural function Duration("?t").

Streams as Continuous Samplers

  • Streams are an extension of PDDLStream, used to generate infinitely many continuous parameter values. For example, the grasps stream generates grasp poses, ik_qs generates inverse kinematics solutions, and motions plans trajectories.
  • Each stream has a conditional generator, invoked via next(grasps.gen(arm1)), returning a new constant or None. Stream outputs are added to the "stream plan" ψ, updating the initial state and inducing the next round of solving.

Eager Stream Scheduling Algorithm

  1. Solve a finite scheduling problem with the current constant set (subroutine schedule).
  2. If it fails, instantiate stream s ∈ 𝒮 as s(x), invoke the generator to produce a new constant y.
  3. If y is valid and unexplored, add the stream output predicate p(x,y) to ψ, update the initial state I, and re-solve.
  4. Repeat until a schedule is found or streams are exhausted.

Schedule Subroutine: From Sequential Plans to Schedules

  • Compile each durative action a into two instantaneous actions: a.start and a.end. Introduce the predicate Ongoing (action in progress) and the function Remaining (remaining time).
  • After solving a sequential plan π, construct the schedule by timestamps: upon encountering a.start, set start time T[a(x)] ← t; upon encountering a.end, compute Δt ← a(x).duration − (t − T[a(x)]), update t ← t + max(0, Δt), and record ⟨T[a(x)], a(x), t*⟩.

Key Innovations

  1. Solution space from sequences to schedules: This is a fundamental extension of the TAMP problem definition. Allowing action overlap means the planner must handle concurrency constraints (such as arm collision avoidance), not just sequential causal chains. This directly raises the throughput ceiling in multi-arm scenarios.
  2. Seamless fusion of declarative and procedural: By defining predicates (e.g., collision_cond) and durations (Duration) as Python functions, complex geometric computations (collision detection, inverse kinematics) can be directly embedded into planning logic, without needing to precompute all possible values with external tools as in PDDL. This is a practical upgrade of PDDLStream's "stream" concept.
  3. Eager stream instantiation strategy: Unlike PDDLStream's "sample-then-plan" approach, the Eager strategy generates new constants on demand only when solving fails, avoiding invalid sampling explosions, and is tightly coupled with the scheduling solver, converging faster to feasible schedules.

Boundaries and Limitations

  • No experimental validation provided: The paper excerpt completely lacks an experimental section, making it impossible to judge the method's feasibility, robustness, or computational efficiency on real robotic systems.
  • No optimality guarantees discussed: Eager Stream Scheduling is a greedy stream instantiation strategy; the paper does not explain its gap from optimal schedules, nor does it mention any pruning or heuristics to ensure solution quality.
  • No global optimization of resource conflicts: The scheduling subroutine is compiled from sequential planning and may fail to capture complex resource competition between actions (such as shared workspaces); the paper does not clearly state how such global constraints are handled.
  • Not explicitly addressed by the paper: The authors do not discuss sampling efficiency when scaling to high-dimensional continuous spaces (e.g., 7-DOF arms), adaptability to dynamic environments (moving obstacles), or integration with learning methods.

Engineering Insights

  • Verify core interfaces before reproduction: Focus on checking whether the overloading of <= and == operators is compatible with Python's object model, especially when function values are PyTorch tensors—the semantics of == need customization (tensor comparisons return tensors and must be converted to booleans).
  • Stream generator implementation is the biggest pitfall: next(s.gen(x)) must guarantee returning a valid constant or None within finite time, and the generator must not have state leakage (e.g., stale caches causing repeated outputs). It is recommended to maintain independent generator objects for each stream instance.
  • Carefully validate the scheduling subroutine's compilation logic: When compiling durative actions into start/end instantaneous actions, the update logic of the Remaining function is error-prone, especially when multiple actions run in parallel—the advancement of t* must be strictly processed in timestamp order.
  • Guidance for downstream teams: If the goal is multi-arm collaborative assembly, it is recommended to first use Problem 1 and 3 scenarios for unit testing to verify whether the scheduler correctly produces overlapping actions; if planning time is excessive, first check whether stream instantiation is too frequent (the Eager strategy may degenerate into exhaustive sampling on certain problems).
  • Be aware of closed-world assumption side effects: Undeclared functions evaluate to None, meaning any omitted state initialization will cause planning failure, and errors are hard to trace. It is recommended to explicitly initialize all potentially involved functions during modeling.
