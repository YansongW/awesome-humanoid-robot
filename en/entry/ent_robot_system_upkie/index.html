Summary

A fully open-source wheeled biped robot built from about 3,000 USD of off-the-shelf components plus 3D-printed parts, using mjbots quasi-direct-drive actuators and a Raspberry Pi 4, with Python-first software and out-of-the-box PID, MPC and reinforcement-learning balancing examples.

Overview

Upkie is a community-driven, fully open-source wheeled biped robot, with core author Stéphane Caron (Inria) among others. It is built on the mjbots open-source actuator ecosystem and comes in configurations such as Upkie Zero / Upkie Standard / 2026 hardware v2. The entire robot can be reproduced for about $3,000 in off-the-shelf components plus over 60 hours of 3D printing (per the official Hackaday account), with 6 degrees of freedom (3 per leg: hip, knee, driven wheel); height/weight have no official unified values (source: research archive upkie.md, same below). What it truly changes is not "how capable the robot is," but "how low the barrier is for individuals to learn balance control on real hardware."

Content

What It Is: Precise Definition

Upkie is a wheeled biped robot platform: two legs each with a driven wheel, maintaining balance via the wheels and handling uneven terrain via the legs. It is not a toy, nor a research prototype, but a reproducible complete system—from 3D-printed structural parts, mjbots actuator selection, Raspberry Pi main controller, to the Python software stack and three balance control examples, all open source and all self-buildable.

To determine whether a platform belongs to the Upkie ecosystem, look for three features:

  1. Wheeled-leg morphology: each leg ends in a driven wheel rather than a foot, simplifying the balance problem from "inverted pendulum + foot contact" to "inverted pendulum + wheel-ground contact";
  2. Quasi-direct-drive actuators: uses mjbots qdd100 quasi-direct-drive brushless servos, with open-source firmware and force control capability;
  3. Python-first: the software stack is primarily Python, with a Gymnasium standard interface, and the same code runs in both simulation and on the real robot.

Why It Exists: Pain Points and Historical Positioning

Before Upkie, individuals wanting to learn legged robot balance control faced an awkward gap. Pure walking bipeds (such as ToddlerBot, Berkeley Humanoid Lite) have high mechanical complexity and high crash costs, often tens of thousands of dollars; simulators (such as MuJoCo) are zero-cost, but "balance learned in simulation" and "balance on real hardware" are separated by modeling errors, actuator latency, and friction uncertainty. Upkie fills exactly this gap: the wheeled-leg morphology reduces the dimensionality of the balance problem, quasi-direct-drive actuators make force control transparent, the $3,000 cost makes it affordable for individuals, and over 60 hours of 3D printing makes the structural parts self-manufacturable. What it truly changes is not "what the robot can do," but "who is eligible to conduct balance control experiments on real hardware."

Principle Breakdown

① Wheeled-leg balance: from inverted pendulum to wheeled inverted pendulum

Upkie's balance is essentially a wheeled inverted pendulum problem. Unlike legged bipeds, the support point of a wheeled-leg robot is not discrete feet but continuous wheel-ground contact, so balance control simplifies from "gait planning + zero moment point (ZMP) adjustment" to "center of mass projection falling within the wheel-ground contact line." This simplification allows higher control frequencies, stronger robustness, and makes classical controllers like PID feasible on real hardware for the first time.

② Quasi-direct-drive actuators: the source of force control transparency

Upkie's hip and knee joints use mjbots qdd100 quasi-direct-drive actuators. The core feature of quasi-direct-drive is a low reduction ratio (typically 3:1–10:1), allowing external torque to "pass through" directly back to the motor side, so output torque can be estimated simply by measuring motor current:

\[ \tau_{\text{out}} \approx G \, k_t \, I_m - J_{\text{eq}} \ddot{\theta}_m \]

where \(G\) is the reduction ratio, \(k_t\) is the motor torque constant, \(I_m\) is the q-axis current, \(J_{\text{eq}}\) is the equivalent inertia, and \(\ddot{\theta}_m\) is the motor angular acceleration. The second term is the inertia compensation term. Due to the low reduction ratio, friction and backlash nonlinearities are also small, making this estimate sufficiently accurate for engineering purposes—this is the entire secret behind "force control without torque sensors" (source: quasi-direct-drive actuator technical documentation).

③ Software stack: frictionless migration from simulation to real hardware

Upkie's software stack centers on the upkie Python library, providing a Gymnasium environment where the same code controls both simulation (PyBullet) and the real robot. This means users can debug algorithms in simulation and then deploy directly to a Raspberry Pi 4 without rewriting any interface code. Three balance control paradigms are included out of the box: PID, MPC (qpmpc), and reinforcement learning (Stable-Baselines3), covering the full spectrum from classical control to modern learning.

Who Uses It · Application Cases

Upkie's primary user groups are individual learners, educational institutions, and open-source robotics enthusiasts. Typical application scenarios include:

  1. Balance control introduction: use the PID example to experience "wheeled inverted pendulum" balance tuning on real hardware and understand core feedback control concepts;
  2. MPC and reinforcement learning research: use qpmpc or Stable-Baselines3 examples to train policies in simulation, then deploy to the real robot to validate sim-to-real transfer;
  3. Robotics course teaching: as a low-cost experimental platform, allowing students to encounter sensor noise, actuator latency, and communication issues on real hardware;
  4. Community secondary development: modify structures or add sensors based on upkie/parts (CAD/printed parts) and upkie/upkie_description (URDF).

The GitHub repository upkie/upkie has 386 stars / 52 forks (snapshot as of 2026-07-01, still frequently updated), is listed in well-known collections such as awesome-open-source-robots, and has active community discussions on GitHub Discussions and the Matrix chat room.

Limitations and Boundaries

  1. Cannot walk: the wheeled-leg morphology determines that it can only "roll" over uneven terrain rather than "walk," and cannot climb steps or stairs;
  2. No official unified height/weight values: varies by configuration, and specific version parameters need to be confirmed independently;
  3. Limited payload capacity: desktop-class size, unsuitable for heavy loads or prolonged outdoor operation;
  4. Dependence on the mjbots ecosystem: actuators, drivers, and firmware all come from mjbots; if that ecosystem ceases maintenance, Upkie's supply chain will be affected;
  5. Reinforcement learning examples still require tuning for real-hardware deployment: although Stable-Baselines3 examples are provided, the sim-to-real gap (modeling errors, latency) still needs to be handled by users.

Common Misconceptions

  1. "Upkie is a toy"—Wrong. It is a complete robotics research platform that includes real-hardware force control, state estimation, and communication issues that cannot be experienced in simulation;
  2. "Wheeled-leg is simpler than legged, so it has no value"—Wrong. Wheeled-leg simplifies balance control but retains the core challenges of legged robots: joint force control, state estimation, and uneven terrain adaptation;
  3. "You get a complete robot for $3,000"—Inaccurate. The $3,000 is the cost of off-the-shelf components; it also requires over 60 hours of 3D printing time plus assembly and debugging, making the total time cost far greater than the monetary amount;
  4. "You must use Python"—Inaccurate. The software stack supports both Python and C++; Python is merely the default recommendation, and C++ users can equally develop and deploy.
