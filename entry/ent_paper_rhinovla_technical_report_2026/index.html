摘要

RhinoVLA 是一个面向边缘部署的视觉-语言-动作模型，由 Huixi AI 与 Huixi R1 边缘 SoC 协同设计。其核心贡献在于通过 token 高效的 Qwen3-VL 骨干网络和连续动作专家模块降低计算负担，并引入统一接口支持跨机器人学习。在 Huixi R1 上实现了 11.69 Hz 的端到端推理，满足 10 Hz 实时闭环控制需求。

概述

RhinoVLA是HuixiAI团队提出的面向边缘实时部署的视觉-语言-动作（VLA）模型，核心贡献在于系统性地解决了VLA在板载SoC上闭环推理的延迟瓶颈。作者通过Roofline分析定位MLP投影算子为延迟主因（占VLM延迟约74.7%），并针对Huixi R1平台设计了定制W8A16 GEMM内核（up_proj延迟从191μs降至113μs，1.69×加速）与三路并行视觉编码（34.52ms降至24.31ms），最终实现11.69Hz闭环频率，满足10Hz实时控制目标。架构上采用2.13B Qwen3-VL骨干加0.40B Action Expert的两模块分解，通过View Registry统一异构相机接口、72D物理槽位空间对齐跨机器人动作语义、机器人实例LoRA实现高效迁移；在LIBERO基准上平均成功率90.0%，Long套件82.4%超过π0（73.0%）9.4个百分点，真实机器人任务成功率与π0.5相当。

它改变了什么

RhinoVLA真正改变的，是VLA系统在边缘硬件上的“可行性边界”这一问题的定义方式。此前，π0.5、RDT等系统在Orin这类板载硬件上，5 Hz目标频率已逼近有效roofline上限，10 Hz实时闭环控制被普遍视为“算力不够”的硬约束。作者没有停留在“换更强芯片”或“压缩模型”的常规思路上，而是把问题重新拆解为两个可工程化攻克的子问题：一是VLM的视觉与上下文token数量直接决定GEMM主导算子的计算量——这是延迟的线性瓶颈；二是异构机器人数据在输入输出接口上的语义错配，导致跨机器人训练要么依赖笨重的独立输出头，要么牺牲统一动作契约。这两个问题在过往工作中常被当作“工程细节”一笔带过，但RhinoVLA将其提升为架构设计的核心约束。

更关键的是，作者对“实时”的定义做了实质性推进。他们不满足于在Orin上勉强跑通，而是基于Roofline分析明确指出：在40%计算利用率假设下，Orin的FP16有效吞吐约17.2 TFLOPS，π0.5的858.3 ms端到端延迟中，VLM Backbone占528.0 ms、Action Expert占257.0 ms，合计超90%——这意味着单纯优化算子或量化权重都只是“修修补补”，无法跨越10 Hz门槛。RhinoVLA的回应是双管齐下：架构上把视觉token从PaliGemma的256个压缩到64个（4×减少），同时用72D统一物理槽位空间+View Registry+实例LoRA的组合，把跨机器人训练从“每机器人一套接口”的泥潭中解放出来。这改变了问题的性质：实时部署不再是“在有限算力上榨取性能”的被动优化，而是“从模型架构和接口设计源头就为边缘硬件定制”的主动约束。作者甚至用W8A16而非W8A8量化，明确拒绝以精度换速度的捷径，说明他们追求的是在不牺牲任务成功率前提下的系统性提速——11.69 Hz的闭环频率和LIBERO Long套件82.4%的成功率（超过π0-FAST 22.2个百分点）证明了这条路走得通。

方法拆解

RhinoVLA 的方法核心是“两模块 VLA 分解 + 统一接口抽象 + 边缘部署优化”三层设计，下面按架构、接口、训练、部署四部分拆解。

架构：两模块分解，视觉 token 减负 4×

  • VLM 骨干：采用 2.13B 参数的 Qwen3-VL，224×224 输入下仅用 64 个合并视觉 token（PaliGemma-224 需 256 个），视觉 token 负担减少 4×。关键设计决策：用更少但信息密度更高的视觉 token，直接削减 GEMM 主导的投影算子计算量——当模型维度固定时，投影计算量随 token 数线性增长，这是延迟优化的首要杠杆。
  • Action Expert：0.40B 参数（π0.5 约 0.43B），基于 Qwen3-VL 接口重新设计，使用 Qwen 兼容 Transformer 组件。每个去噪步骤条件化于：Qwen3-VL 最后 18 层 KV 缓存、当前 72D 机器人状态、状态/动作掩码、带噪动作块、流匹配时间 t、机器人实例索引 r。动作侧推理路径为 18 层/1024 隐藏大小，GQA 分组 2 查询头共享 1 KV 头，头维度 128。

统一接口：View Registry + 72D 物理槽位空间

  • View Registry：预处理时将每个数据集相机字段映射到固定角色-模态词汇表（如 [head|rgb]、[left_wrist|rgb]、[head|depth]），标签插入图像内容前。设计理由：解耦相机身份与数据集特定图像顺序，使跨机器人训练时视觉输入格式统一。
  • 72D 物理槽位空间：每个槽位跨数据集有固定物理含义，状态和动作使用相同槽位定义。关键分配：D0–D6/D7–D13 为双臂规范关节（rad），D14–D15 平行夹爪（闭合比 [0,1]），D16–D47 双手主动 DoF（每手 16 槽，按 4-3-3-3-3 分配），D48–D50 头/颈 RPY，D51–D52 躯干，D55–D57 腰部 RPY，D58–D60 基座速度命令（m/s, m/s, rad/s），D61–D71 保留。设计决策：移动基座槽位定义为速度目标而非位置目标，因为速度命令更通用且可跨平台迁移；二进制掩码（状态掩码 m_s、动作掩码 m_a）指示当前样本存在的维度及有效监督维度，物理缺失的槽位从流匹配监督中排除。

训练：冻结骨干，LoRA 分实例

  • 预训练：Qwen3-VL 骨干冻结，联合优化 VLM LoRA、共享 Action Expert 和机器人实例 LoRA。批次采样用幂律平衡 p_i = N_i^0.43 / Σ_j N_j^0.43，防止大数据集主导。
  • 流匹配：构造 x_t = (1-t)a + tz，Action Expert 预测 v̂θ = f_θ(x_t, t, s, m_s, m_a, c_vlm, r)，流目标为 z - a。掩码流匹配损失： L_FM = Σ m_a(d) w(h,d) ||v̂θ(h,d) - (z(h,d) - a(h,d))||_2^2 / (Σ m_a(d) w(h,d) + ε) 其中 w(h,d) 为每槽位权重以平衡动作组。
  • 机器人实例 LoRA：放置在 Action Expert 每层 feed-forward 网络，注意力模块和最终动作投影保持共享；按 instance_id 硬路由选择单个适配器。选择 LoRA 而非独立输出头的理由：独立输出头会削弱统一 72D 动作契约，且引入机器人特定部署图，难以跨机器人复用推理内核。训练中基础 Action Expert 预测保持直接监督，适配器残差被正则化，防止实例 LoRA 接管完整动作生成。
  • 后训练/迁移：视觉-语言编码器（含预训练 VLM LoRA）冻结，大部分 Action Expert 参数冻结，仅更新目标机器人实例 LoRA。

部署优化（Huixi R1）

  • W8A16 GEMM 内核：将 Transformer 主要线性层 GEMM 分解为多个子矩阵任务，分布在八个计算核心；以内存通道感知方式重新组织离线权重布局，减少 DDR 通道争用。内核将权重加载、缩放转换和矩阵乘加组织为重叠流水线，避免两阶段“反量化-再计算”执行流。使用 per-channel 缩放。在 up_proj 上 W16A16 耗时 191 μs，定制 W8A16 降至 113 μs（1.69× 加速），达 50.6% 计算利用率。
  • 并行视觉编码：三张相机图像打包成单 batch 由视觉编码器处理，延迟从 34.52 ms 降至 24.31 ms。
  • 图级与调度级优化：激进算子融合（RMSNorm 权重/偏置保留在 SPM），细粒度算子任务调度按计算需求、SPM 使用和数据移动需求分配。

关键创新

RhinoVLA 的核心创新在于将“实时闭环部署”从论文的附属章节提升为架构设计的第一性约束，而非在训练完成后做工程修补。这体现在三个相互咬合的设计决策上。

第一，以算子级延迟剖析驱动架构选型，而非仅以精度论英雄。作者在 Orin 上对 π0.5 的剖析揭示了一个反直觉的事实：VLM Backbone 占端到端延迟的 61.5%（528.0 ms / 858.3 ms），而其中 MLP 投影算子（gate_proj、up_proj、down_proj）又占 VLM 延迟的 74.7%。这意味着传统 VLA 的瓶颈不在注意力，而在被忽视的线性层。RhinoVLA 据此将 VLM 骨干从 PaliGemma 换成 Qwen3-VL-2B，并将视觉 token 从 256 个压缩至 64 个（4× 减少），直接削减了与 token 数线性相关的 GEMM 计算量。这一选择使 VLM 推理路径参数从 2.92B 降至 2.13B，但更重要的是改变了计算密度分布，为后续内核优化创造了条件。

第二，用“物理槽位语义化”替代“数据集特定接口”，实现跨机器人零代码迁移。现有跨机器人方案多依赖输入输出适配层，但 RhinoVLA 定义了统一的 72D 物理槽位空间：每个槽位有固定物理含义（如 D0–D6 为臂 0 规范关节弧度），状态和动作共用同一槽位定义，并用二进制掩码标记有效维度。这不仅是数据格式统一，更关键的是将“机器人实例差异”从网络结构层面剥离——通过按 instance_id 硬路由的 LoRA 注入 Action Expert 的 feed-forward 层，而注意力与最终动作投影保持共享。选择 LoRA 而非独立输出头，是为了维持 72D 动作契约的完整性，避免引入机器人特定部署图，从而保证推理内核和硬件优化可跨机器人复用。

第三，定制 W8A16 GEMM 内核与并行视觉编码，将量化收益真正落地。作者识别出传统 INT8 量化的隐藏成本：GEMM 前将权重反量化回 FP16 会引入额外数据搬运和转换开销，可能抵消量化收益。为此设计了将权重加载、INT8-to-FP16 转换和 FP16 MAC 融合为重叠流水线的内核，并以内存通道感知方式重排离线权重布局以减少 DDR 争用。在 π0.5 的 up_proj 上，该内核将延迟从 191 μs 降至 113 μs（1.69× 加速），达到 50.6% 计算利用率。同时将三路相机图像打包为单 batch 并行编码，延迟从 34.52 ms 降至 24.31 ms。这两项优化使端到端频率从 5.84 Hz 提升至 11.69 Hz，首次在边缘 SoC 上满足 10 Hz 实时闭环目标，且 LIBERO Long 套件上 82.4% 的成功率超过 π0 达 9.4 个百分点——证明实时性并非以牺牲泛化精度为代价。

实验与结果

实验围绕三个层面展开：内核级优化、端到端部署效率、以及任务精度。作者先在 Huixi R1 上对 π0.5 VLM 骨干的延迟主导算子 up_proj 做内核级对比，W16A16 基线耗时 191 μs，定制 W8A16 GEMM 降至 113 μs，加速 1.69×，计算利用率达 50.6%。三路相机图像的 ViT 前向从顺序执行改为 batch 并行后，处理延迟由 34.52 ms 降至 24.31 ms。这两项优化直接支撑了端到端闭环频率从 5.84 Hz 提升至 11.69 Hz，跨过 10 Hz 实时控制门槛。

端到端延迟分解（Table 6）显示，Action Expert 占 42.9%（36.71 ms），是最大开销；Vision Encoder 占 28.4%（24.31 ms），VLM Backbone 占 24.3%（20.78 ms），其余 4.4%。值得注意的是，VLM Backbone 在 R1 上仅 20.78 ms，远低于 π0.5 在 Orin 上的 528.0 ms——这既来自 W8A16 与算子融合，也来自视觉 token 数从 256 减至 64 的 4× 削减。

LIBERO 基准上 RhinoVLA 平均 90.0%，与 π0.5 的 96.9% 有差距，但显著超过 π0（86.0%）、π0-FAST（85.5%）、SmolVLA（88.8%）等基线。在 Long 套件上 RhinoVLA 达 82.4%，分别超 π0 和 π0-FAST 9.4 和 22.2 个百分点，说明长程任务上的泛化优势明显。真实机器人评估中，Galbot G1 的 “Red bag to far bin” 任务 RhinoVLA 与 π0.5 均 100%；但 “Black fan to middle bin” 仅 40%、“White foam to near bin” 仅 20%，未见 π0.5 对照。AgiBot G2 三步序列任务 Seen 场景 58%，Unseen 场景 24%（π0.5 为 18%）；毛巾折叠 Seen 67%、Unseen 43%。实例 LoRA 消融显示，加入后 Masked FM Loss 从 0.0192 降至 0.0191，Arm MAE 从 0.0446 降至 0.0440，Gripper MAE 从 0.1064 降至 0.1056，增益有限但一致为正。

整体判断：RhinoVLA 的核心贡献在部署效率——以相近参数规模（VLM 2.13B + Action Expert 0.40B vs π0.5 的 2.92B + 0.43B）在边缘 SoC 上实现 11.69 Hz 闭环，代价是 LIBERO 平均成功率较 π0.5 低约 7 个百分点。作者将差距归因于训练配方的简化（仅用机器人轨迹，无多源联合训练），而非架构缺陷。

边界与局限

RhinoVLA的边界与局限首先体现在其评估范围上：LIBERO基准与真实机器人任务均集中于桌面拾放、折叠等短程操作，未覆盖长时程、高动态或重接触任务；且真实机器人评估样本量极小（如Black fan任务仅40%成功率、White foam仅20%），统计显著性存疑。论文未明确给出各任务尝试次数与方差，结论外推需谨慎。

跨机器人泛化的核心机制——72D槽位空间与View Registry——依赖严格的语义映射假设。作者明确承认预训练不监督腿/脚关节，源数据中出现即排除；被动或机械耦合关节不占槽位。这意味着对四足、人形或带复杂腿部机构的机器人，该框架当前无法直接适用，且论文未提出扩展方案。槽位D61–D71为保留位、无固定语义，实际泛化能力仅覆盖单臂/双臂+夹爪/灵巧手构型。

性能结论的边界条件同样关键：11.69 Hz闭环频率仅在Huixi R1特定SoC上实现，依赖定制W8A16 GEMM内核、SPM tiling与并行视觉编码三重优化。若迁移至其他边缘平台（如Orin），这些优化不可直接复用，且论文未报告在Orin上的端到端延迟。W8A16而非W8A8的取舍意味着INT8权重+FP16激活的内存带宽收益有限，在带宽更受限的平台上可能无法复现同等加速比。

训练策略上，VLM骨干完全冻结、仅训练LoRA与Action Expert，限制了视觉语言表征对机器人数据的适配能力。作者承认与π0.5的多源联合训练存在性能差距（LIBERO Long套件82.4% vs 92.4%），且未消融VLM LoRA单独贡献。此外，流匹配损失中的槽位权重w(h,d)设定细节未充分披露，其对手部精细动作与基座速度的平衡效果难以独立验证。

工程启示

复现RhinoVLA，第一优先级是核对视觉token压缩与KV cache接口：Qwen3-VL在224×224下仅用64个合并视觉token（PaliGemma-224为256个），且Action Expert条件化于VLM最后18层KV cache——这两处直接决定推理延迟与显存占用，任何改动都会破坏与预训练权重的对齐。最易踩坑的是72D物理槽位映射：论文强调“语义映射而非位置映射”，但实际实现中关节弧度、夹爪闭合比[0,1]、基座速度（m/s与rad/s）混用，且被动/机械耦合关节不占槽位——建议先写单元测试验证每个数据集的掩码正确性，再谈训练。第二个坑是W8A16量化：论文明确警告直接W8A8会明显降低成功率，只能量化权重、保留FP16激活，且需定制融合反量化与GEMM的内核（up_proj从191μs降至113μs），若用现成库的W8A8方案，性能与精度双输。第三个坑是实例LoRA的硬路由：按instance_id选择单个适配器，部署时需合并进基础权重，若误用软路由或多LoRA叠加，会破坏“基础Action Expert保持直接监督”的训练假设。下游团队若只做单机器人部署，可跳过View Registry与跨数据集采样（幂律p_i=N_i^0.43），但若追求多机器人复用，务必保留统一72D契约，否则推理内核无法跨平台共享。最后，LIBERO Long套件是RhinoVLA相对π0.5差距最小（82.4% vs 92.4%）但相对π0-FAST优势最大（+22.2%）的场景，建议作为验收基准；真实机器人成功率波动大（20%-100%），需按论文的严格成功定义（抓错/掉落即失败）复现评估，否则数字不可比。
