DeepInsight: A Unified Evaluation Infrastructure Across the Physical AI Stack

摘要

DeepInsight 是一个统一的评估基础设施，专为覆盖物理 AI 堆栈中跨越三个数量级差异的算子（从单次基础模型解码到全身控制的数千物理滴答）而设计。它由研究团队提出，核心贡献在于通过三个窄抽象（任务、资源和结果）在单一运行时上保留异构性，并实现跨层诊断。该基础设施已在人形机器人堆栈的三个层中部署，能够通过配置快速接入新基准，并支持近线性扩展。

概述

DeepInsight 是 XPENG Robotics 提出的统一评估基础设施，旨在覆盖 Physical AI 全栈——从单次解码（System 2 语义推理）到数千物理 tick 的全身控制（System 0），跨度超过三个数量级。其核心贡献在于通过任务、资源、结果三个抽象，将轨迹作为持久工件而非附带品，使跨层回归可在单一共享 trace 上定位，并在单节点 8×A100 上与最强开源基线保持竞争力（多模态 VQA 对齐 8/15 最接近参考值），同时实现近线性水平扩展（1→4 节点 4.00× 加速）。

它改变了什么

现有评估体系的最大问题不是缺工具，而是缺身份：System 2 的 lm-evaluation-harness、System 1 的 LIBERO 类 harness、System 0 的 Isaac Lab 各自为政，互不共享运行时或评分。这导致一个部署栈中，语义规划器的错误改变视觉运动策略的分布、策略犹豫改变稳定器运行状态——这些层间耦合故障在独立 harness 下根本无法诊断，因为每个 harness 只保留局部有效性，丢失了跨层回归所需的共享身份。DeepInsight 真正改变的是评估的优先级：传统管线保留聚合结果而丢弃轨迹，隐含假设是分数是产品、轨迹是附带品；DeepInsight 反转这一假设，让轨迹成为持久工件，聚合分数从轨迹计算而非替代轨迹存储。这使得回归出现一周后，解释它的轨迹仍在，钻取成为读操作而非重建操作。

另一个结构性改变是报告与评估的解耦。传统管线在评估管线内计算聚合，修改或扩展聚合路径需改动管线本身；DeepInsight 中报告器是独立注册组件，消费与上游子系统写入相同的记录格式，新增报告器是注册而非管线修改。这看似工程细节，实则改变了评估基础设施的演进方式——从"改管线"变成"加读取器"，从"推翻重来"变成"增量扩展"。

方法拆解

三个核心抽象（每个实现为一个不变量）

  • 任务抽象：环境暴露 reset(handle) 和 step(handle, action) 两方法接口；所有瞬态状态（数据集样本、对话、进行中结果、当前观测-动作对）存于每 episode 的 handle 上，环境本身无状态。关键决策：状态存于 handle 而非环境，使一个环境实例可服务任意多并发 episode，worker 不专属于某一 episode 形状。
  • 资源抽象：昂贵后端（LLM 推理和沙箱运行时）委托给各自控制平面，通过 acquire(kind, episode_id, constraints) 和 release(handle) 窄接口暴露；编排器保持异步和薄。推理平面（vLLM、vLLM-Omni、SGLang 异构引擎）和沙箱平面（预预热容器池 + 按需 OpenSandbox 容器）对编排器呈现相同形状。
  • 结果抽象：所有事件写入单一结构化记录，由层级身份元组 (run_id, suite_id, task_id, episode_id, epoch) 寻址，携带因果血缘 (event_id, parent_event_id)。

关键设计决策

  • 执行配置作为持久化工件：套件配置（任务是什么）与模板配置（如何运行）在启动时合并为单一快照，转储到磁盘用于重放，捕获所有实际应用的覆盖。
  • 判断与任务正交：评分器是独立注册组件，读取 trace 并输出结构化判断；报告分数是任务 × 判断的叉积，各自独立版本化。
  • 阶段获得独立并发预算：CPU-bound 和 I/O-bound 步骤即使共享相同步骤角色也分属不同队列，各有独立 worker 池和并发预算。
  • 缩放旋钮正交：每个独立瓶颈有一个缩放旋钮（编排器每阶段 worker 并发、推理平面连接池和副本数、沙箱平面部署/活跃并发/并行 rollout 上限），调一个不消耗另一个。
  • 沙箱平面两种部署模式：预预热容器池（HTTP 前端）服务无状态调用，按需 provisioner 租用 per-episode OpenSandbox 容器服务有状态工作负载；占据函数调用→容器→microVM→fullVM 隔离谱系的函数调用和容器两层。
  • 推理平面服务发现是客户端侧：引擎注册端点到目录，调用方传输层监视，请求直达所选副本无网关跳转；负载均衡策略可基于应用级路由键，包括有界负载一致哈希策略提供 KV 缓存亲和力。

三个结构性选择（支撑扩展性）

  • 异步流水线：从队列连续异步补充，对比同步 64-episode 批屏障。
  • 阶段解耦：每个阶段独立队列和 worker 池，对比全局耦合单池（按最受限阶段大小，此处为 sandbox 上限 14 workers）。
  • 水平扩展：eval-instance 数随硬件扩展（2/4/8 实例，TP=4 每个）。

关键创新

  1. 轨迹作为一等公民的持久化单位：每个事件按 schema 写入并持久化，聚合分数从轨迹计算而非替代轨迹存储。这使回归可追溯至构成事件，钻取成为读操作。这不是技术优化，而是评估哲学的倒转——传统框架把轨迹当调试工具，DeepInsight 把轨迹当产品本身。

  2. 跨频谱段的统一身份：从单次解码到全身控制，所有事件共享同一寻址方案 (run_id, suite_id, task_id, episode_id, epoch) 和因果血缘。这使得 System 2 的语义错误、System 1 的策略犹豫、System 0 的稳定器恢复行为可以在同一 trace 上定位起源——这是现有任何框架都无法做到的，因为它们的运行时和评分根本不共享。

  3. 资源抽象的对称性：推理平面和沙箱平面对编排器呈现相同形状，通过窄接口 acquire/release 暴露。这使编排器保持异步和薄，同时让每个平面独立优化（推理平面用有界负载一致哈希提供 KV 缓存亲和力，沙箱平面用预预热池 + 按需 provisioner 覆盖无状态/有状态工作负载）。对称抽象使阶段解耦成为可能，而阶段解耦是 3.31× 加速的结构性前提。

实验与结果

实验采用对照设置：在基础模型端，以 lm-evaluation-harness、OpenCompass、HELM、VLMEvalKit、lmms-eval、Inspect AI 等最强开源基线为参照，在相同硬件（单节点 8×A100）、推理后端与采样协议下对比基准保真度与吞吐量；在全身控制端，以 Isaac Lab 为参照，验证行为级诊断与全系统验证能力。评估算子差异与 episode 长度跨度均超过三个数量级（论文原文 "more than three orders of magnitude"），覆盖从单次解码步骤到数千物理 tick 的完整频谱。表 1 将 episode 长度分为 ≤ 1 step、2–50 steps、50–500 steps、≥ 500 physics ticks 四档；HELM 组织 42 个场景，VLMEvalKit 与 lmms-eval 各覆盖 80–100+ 视觉-语言基准。沙箱部署采用预预热容器池（无状态）与按需 OpenSandbox 容器（有状态）两种模式，覆盖 function-call → container → microVM → fullVM 四层隔离谱系中的函数调用层与容器层。

结果含义一：保真度是吞吐量对比的前提，DeepInsight 在保持参考量表的同时覆盖最广的模态集合。 在每张表中，DeepInsight 最接近 Ref. 的行数最多（文本 5/8 与 4/9、多模态 8.0/15、omni 4/5），被计时的系统产生可比分数而非以精度换速度。残余偏移是协议级而非基础设施级：LiveCodeBench 依赖未发布的参考沙箱/超时，Video-MME 与带字幕参考对比而所有开放运行使用无字幕——这些案例界定了对齐证据的边界而非削弱它。

结果含义二：吞吐量收益来自架构级机制而非段特定优化，且各扩展旋钮正交。 异步流水线消融中，批屏障下最慢 episode 将批次拉过中位数并使生成池在每批长尾中空闲，异步化后生成占用率从 54% 升至 89%，LLM 吞吐量从 1,547 增至 2,178 tokens/s（+41%，论文原文数值）；阶段解耦消融中，耦合池 98% 时间忙碌但花在错误资源上——生成被节流到 14 路饿死 GPU，解耦后同时以 14 路上限运行沙箱、以完整 128 路预算运行生成。水平扩展中，容量随硬件增长而无需重新调优编排器，1→4 节点全程 4.00× 加速，每次在约 1.5% 线性范围内，共享裁判配置从未成为瓶颈。

结果含义三：全系统验证揭示孤立模块评估不可见的集成缺口。 端到端回合成功率 60.4%，但子目标级报告显示任务意图识别 94.8%、工具序列有效 93.8%、用户目标选中 82.3%、用户到达 77.1%——高局部完成率不一定产生成功的系统级结果。失败归因中，System 1 执行占 42.1%（16/38），边界交接占 28.9%（11/38），System 2 推理占 18.4%（7/38），System 0 占 10.5%（4/38）。边界失败暴露了独立设计子系统之间关于状态、前置条件、时序与可执行性的假设缺口，这些在孤立评估各模块时不可见，但对最终系统结果影响显著。System 0 案例中，聚合赢家通过全局运动检查但失败于局部检查（髋关节动力学、接触姿态稳定性、上肢运动学均 Fail），这依赖每 tick 轨迹状态被保留并在单条 trace 上可查询，使发布阻塞的局部失败在原本获胜的分数背后仍可定位。

边界与局限

  • 对齐证据的边界：LiveCodeBench 依赖未发布的参考 sandbox/超时；Video-MME 与带字幕参考比较，而所有开放运行使用无字幕——这些情况界定而非削弱对齐证据。
  • System 1 和 System 0 是覆盖演示，非竞争性基准：这两层的定量深度留给未来工作；System 1 演示非原始基准环境下精确分数复现，而是统一基础设施上的覆盖和可扩展性。
  • 全系统研究使用一个代表性组合任务族：跨任务族的更广覆盖留给未来工作。
  • 多节点扩展无对等基线：对等框架不支持多节点执行，单独报告。
  • 所有 rollout 都是模拟的：sim-to-real 差距仍是面向硬件的策略的决定性不确定性；论文未明确提及训练配置、数据量、推理频率等细节。

工程启示

  • 先核对对齐协议再信分数：DeepInsight 在文本对齐上并非全面领先（Qwen3.6 文本 5/8 最接近 Ref.，但 GPQA-Diamond 上 83.38 低于 Inspect AI 的 86.03），多模态 VQA 对齐优势明显（8/15）。复现时先确认每个基准的采样 profile、judge 配置、字幕/无字幕协议是否与参考一致——Video-MME 的 7 个百分点差距可能来自协议差异而非框架能力。
  • 阶段解耦是最大的工程杠杆：3.31× 加速来自把生成并发（128）与 sandbox 上限（14）解耦。如果你的下游有类似瓶颈（如沙箱并发远低于生成并发），全局耦合单池会按最受限阶段大小拖垮整个管线——这是最容易踩坑也最容易修复的地方。
  • 轨迹持久化是诊断的前提：跨层回归定位（如 System 1 导航局部成功但违反下游前置条件）依赖单一共享 trace 和因果血缘。如果你要复现类似能力，先确保所有事件写入同一寻址方案，而不是为每层单独存日志——否则边界交接失败（28.9% 的失败占比）根本无法归因。
  • 资源抽象的形状对称性值得借鉴：推理平面和沙箱平面对编排器呈现相同 acquire/release 接口，使编排器保持薄和异步。如果你要构建类似系统，先定义窄接口，再让各平面内部优化（如 KV 缓存亲和力的负载均衡策略），而不是让编排器直接管理后端细节。
