概述

端侧 VLA 推理（On-Device VLA Inference）指将视觉-语言-动作模型直接部署在机器人内置的边缘计算设备上，而非卸载到边缘服务器或云端，以满足延迟、连接性和隐私约束。它真正改变的不是模型本身的精度，而是机器人对物理世界做出反应的速度上限——当控制闭环要求端到端推理延迟低于 20 ms 时，网络往返的代价已不可接受。

核心内容

是什么：准确定义

端侧 VLA 推理是一种部署范式，其核心约束在于"推理发生在机器人本体上"。与云端推理将输入数据上传、在远端算力上执行、再回传动作指令不同，端侧推理要求视觉编码器、语言编码器与动作解码器全部运行在机器人携带的计算硬件上——典型如 NVIDIA Jetson 系列嵌入式平台。

从系统架构看，端侧 VLA 推理处于感知与决策的交界处：它接收来自 egocentric 相机流的视觉观测、机器人状态（关节角度、IMU 数据）与自然语言指令，在机载计算单元上完成多模态融合与动作生成，输出直接馈入控制律计算模块。这一位置决定了它必须与实时操作系统（RTOS）、中间件序列化层和执行器驱动紧密耦合。

为什么存在：痛点与历史定位

在 VLA 模型出现之前，机器人控制的主流范式是"感知-规划-控制"三级流水线，每一级由独立模块承担，推理延迟的预算相对宽松。VLA 模型将视觉、语言与动作映射压缩进单一网络，虽然简化了策略设计，却引入了新的部署难题：参数量动辄数十亿的 Transformer 模型，其单次前向推理在通用硬件上需要数百毫秒，远超控制闭环的时序要求。

云端推理的诱惑在于算力无限，但物理定律不可回避：数据从机器人到云端再返回，即便在理想网络条件下也要消耗数十毫秒的传输时间，且伴随抖动（jitter）。对于需要 0.5–2 ms 硬实时周期的关节电流环和平衡控制，这种不确定性是致命的。端侧推理因此不是性能妥协，而是实时性约束下的必然选择——它真正改变的不是"模型能做什么"，而是"模型能在什么时间尺度内做出反应"。

原理拆解

① 延迟预算的分解：端侧推理的物理基础

端侧 VLA 推理的可行性取决于一个关键等式：端到端延迟必须小于控制闭环的周期要求。以 50 Hz 视觉闭环为例，其延迟预算可分解为：

\[ L_{\text{total}} = L_{\text{sensor}} + L_{\text{preprocess}} + L_{\text{inference}} + L_{\text{control}} + L_{\text{actuator}} \]

其中 \(L_{\text{inference}}\) 是 VLA 模型的前向推理时间。语料指出，50 Hz 视觉闭环要求端到端推理延迟低于 20 ms。若将推理放在云端，\(L_{\text{inference}}\) 本身可能降至 5 ms，但网络往返 \(L_{\text{network}}\) 会额外增加 20–100 ms（取决于链路质量），且抖动不可控。端侧推理以牺牲峰值算力为代价，换取延迟的可预测性——这是硬实时控制的前提。

② 部署链路：PyTorch → ONNX → TensorRT

语料给出了当前 NVIDIA Jetson 平台最主流的部署路径：PyTorch → ONNX → TensorRT。训练阶段使用的 PyTorch 模型包含动态图结构和大量算子，不适合直接在嵌入式 GPU 上运行。转换为 ONNX 中间表示后，TensorRT 会针对目标 GPU 架构进行层融合、精度校准与内核自动调优，生成高度优化的推理引擎。

量化是这条链路的关键环节：从 FP32 到 FP16 再到 INT8，每一步都在精度与速度之间权衡。语料强调，FP16 通常是延迟-功耗-精度的最佳平衡点，而 INT8 前必须做全量验证——感知误差可能直接转化为碰撞或跌倒。

③ 内存与调度：端侧推理的系统约束

端侧硬件资源有限，GPU 全局内存以事务（transaction）为单位访问，当同一 warp 的 32 个线程访问连续地址时，硬件可把多次访问合并为少量事务，显著提高有效带宽。占用率（occupancy）指每个 SM 上活跃 warp 数与最大 warp 数之比；高占用率有助于隐藏内存延迟，但过高可能导致寄存器/共享内存资源竞争。

在操作系统层面，通用 Linux 并非为硬实时设计。PREEMPT_RT 补丁使内核中大部分代码可抢占，中断也可线程化，提供数十微秒的调度延迟，是机器人主控的常见选择。端侧 VLA 推理任务通常运行在非实时的 Linux 用户态，但其输出必须通过实时内核调度器传递给控制任务——两个世界之间的交接延迟，同样是延迟预算的一部分。

横向对比

端侧推理、边缘服务器推理与云端推理构成三种部署选项，其差异集中在延迟、带宽与隐私三个维度：

维度 端侧推理 边缘服务器推理 云端推理
推理延迟 最低，无网络开销 低，但受局域网质量影响 高，受公网链路影响
延迟抖动 最小，可预测 中等 最大，不可控
算力上限 受功耗与散热约束 较高 几乎无限
隐私性 最高，数据不出本体 中等，数据出本体但不出本地 最低，数据上传至远端
适用场景 硬实时控制、隐私敏感任务 大规模地图构建、多机协同 训练、离线评估、非实时任务

语料指出，VLA-Perf 分析框架从部署视角考察了"推理应在何处执行——端侧、边缘服务器还是云端"，并强调硬件能力与网络性能共同决定端到端延迟。工程判断：对于人形机器人的平衡控制与灵巧操作，端侧推理是唯一满足硬实时约束的选项；而云端推理更适合模型迭代验证与跨场景泛化评估。

谁在用：应用案例

NVIDIA Isaac GR00T N1.6 是端侧 VLA 推理的典型实践。该模型是 multimodal vision-language-action 模型，整合 egocentric 相机流、机器人状态与自然语言指令为统一策略表示，通过世界模型（如 NVIDIA Cosmos Reason）将高层指令分解为基于场景理解的逐步动作计划。其 sim-to-real 流水线在 NVIDIA Isaac Lab 中完成全身强化学习训练，部署时依托 Jetson 平台实现端侧推理。

VLA-Perf 基准研究（arXiv:2602.18397）系统考察了 VLA 推理性能全景，从模型设计视角分析模型缩放、架构选择、长上下文视频输入、异步推理与双系统模型流水线对推理性能的影响，并从部署视角分析端侧、边缘与云端的执行位置选择。该研究提炼了 15 项关键结论，为端侧 VLA 推理的工程实践提供了量化依据。

局限与边界

端侧 VLA 推理的边界首先来自算力天花板。嵌入式 GPU/NPU 的算力受功耗与散热约束，无法运行最大规模的 VLA 模型——语料明确将功耗列为约束而非副作用。这意味着模型缩放（model scaling）在端侧存在硬上限，超出后必须依赖模型蒸馏或量化压缩。

其次，端侧推理不解决模型本身的推理效率问题。VLA 模型的 Transformer 堆叠结构导致深层计算冗余，早期退出机制（如 DeeAD 框架）与自适应剪枝（如 AutoPrune）是互补的优化手段，但它们的有效性取决于任务复杂度分布——对于复杂度恒定的任务，自适应策略的收益有限。

最后，端侧推理与实时控制之间的接口仍是工程难点。VLA 推理运行在 Linux 用户态，而关节控制需要硬实时周期，两个世界之间的数据交接延迟与调度抖动，构成了端到端延迟中不可忽略的组成部分。

常见误区

  1. "端侧推理就是模型压缩"——错。量化与蒸馏是端侧部署的使能技术，但端侧推理的本质是部署位置的选择。一个未压缩的小模型在端侧运行，同样是端侧推理；一个 INT8 量化的大模型若部署在云端，则属于云端推理。

  2. "端侧推理延迟一定低于云端"——不必然。对于单次推理，云端高端 GPU 的算力可能使 \(L_{\text{inference}}\) 远低于端侧；端侧的优势在于消除网络延迟 \(L_{\text{network}}\) 与抖动，使总延迟可预测。若任务对延迟不敏感（如离线数据分析），云端推理反而更优。

  3. "FP16 量化没有精度损失"——需谨慎。FP16 相比 FP32 的精度损失通常可接受，但 INT8 量化可能引入显著误差。语料强调 INT8 前必须做全量验证，因为感知误差可能直接转化为碰撞或跌倒。

  4. "端侧推理不需要考虑操作系统"——错。通用 Linux 的调度延迟在数十到数百微秒之间抖动，无法满足最严苛回路的确定性需求。PREEMPT_RT 或双核实时架构是端侧推理进入控制闭环的前提。

왜 존재하는가:痛点과 역사적 위치

VLA 모델이 등장하기 전, 로봇 제어의 주류 패러다임은 "인식-계획-제어" 3단계 파이프라인이었으며, 각 단계는 독립 모듈이 담당하여 추론 지연 시간 예산이 상대적으로 여유로웠다. VLA 모델은 비전, 언어, 행동 매핑을 단일 네트워크로 압축하여 정책 설계를 단순화했지만, 새로운 배포 과제를 도입했다: 수십억 개의 파라미터를 가진 Transformer 모델의 단일 순방향 추론은 범용 하드웨어에서 수백 밀리초가 소요되어 제어 폐루프의 타이밍 요구를 훨씬 초과한다.

클라우드 추론의 유혹은 무한한 컴퓨팅 파워에 있지만, 물리 법칙은 피할 수 없다: 데이터가 로봇에서 클라우드로 갔다가 다시 돌아오는 데는 이상적인 네트워크 조건에서도 수십 밀리초의 전송 시간이 소요되며, 지터(jitter)가 동반된다. 0.5–2ms 하드 실시간 주기를 요구하는 관절 전류 루프와 균형 제어에는 이러한 불확실성이 치명적이다. 따라서 온디바이스 추론은 성능 타협이 아니라 실시간성 제약 하의 필연적 선택이다——실제로 바꾸는 것은 "모델이 무엇을 할 수 있는가"가 아니라 "모델이 어떤 시간 척도 내에서 반응할 수 있는가"이다.
