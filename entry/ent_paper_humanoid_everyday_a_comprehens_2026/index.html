Humanoid｜Everyday 用于开放世界人形操作的综合机器人数据集

Humanoid Everyday: A Comprehensive Robotic Dataset for Open-World Humanoid Manipulation

摘要

Humanoid 主要解决数据闭环：用语言指令、相机图像/多视角观测、遥操作/外骨骼数据采集人类操作和机器人状态，再通过扩散策略/流匹配转成可训练、可复用的可执行动作命令。关键点是把动作生成看成条件生成问题，用扩散或流匹配在多模态动作分布里采样可执行轨迹。

来源与参考

  • Humanoid project page

概述

本文提出 Humanoid Everyday，一个面向开放世界人形机器人操作的综合数据集，旨在解决服务机器人程序生成与评估中缺乏真实世界数据的问题。核心贡献包括机器人无关工具 CodeBotler、评估基准 RoboEval、LLM 生成程序的失败模式分类学，以及减少执行失败的拒绝采样机制。该工作通过符号模拟与时序逻辑检查，为 LLM 驱动的机器人程序提供了可扩展的评估框架。

它改变了什么

现有代码补全基准（如处理简单数据处理函数或低层机器人技能）只适合简单输入输出单元测试，无法评估服务机器人程序：例如任务“Check how many conference rooms have no markers”，仅测试程序是否输出正确答案不够，正确程序必须先访问所有会议室并检查标记。这暴露了机器人程序评估的根本矛盾——正确性不仅取决于最终输出，更取决于动作的时序与空间排序。

作者观察到 LLM 生成程序对自然语言任务描述的微小措辞变化存在显著正确性差异，这动摇了“LLM 可直接生成可靠机器人程序”的假设。该工作真正改变了评估范式：从“输出正确性”转向“时序约束满足性”，使机器人程序评估不再依赖物理仿真或真实部署，而是通过符号模拟在毫秒级完成验证。同时，CodeBotler 的 eDSL 设计将感知、交互、导航等异构技能统一抽象，使 LLM 生成程序与具体机器人平台解耦，这是迈向通用机器人编程的关键一步。

方法拆解

架构总览

系统由三部分组成：CodeBotler（程序生成器）、RoboEval（评估器）、拒绝采样机制。

CodeBotler 的 eDSL 设计

  • 8 种技能抽象：get_current_location、get_all_rooms（状态查询）、is_in_room（VLM 感知）、ask（人机交互）、pick、place、go_to（操作与导航）。
  • 关键设计：get_current_location 和 get_all_rooms 避免在提示中硬编码世界配置，使程序可跨世界状态泛化。
  • ask 使用多项选择结构化接口，支持触摸屏或音频输入，降低 LLM 生成自由文本交互的歧义。
  • 少样本提示：前缀包含技能定义和示例程序，支持 OpenAI API、Google PaLM API、HuggingFace 模型（AutoModel 和 Text-Generation-Inference）。

部署机制

  • 通过 ROS Actionlib 作为客户端：执行 LMP 遇到技能调用（如 go_to("lobby")）时，发布目标到远程话题（如 /go_to_server）供 ROS action server 接收。
  • 这使得 CodeBotler 与具体机器人平台无关，可机载或外部运行。

RoboEval 评估框架

  • 任务定义：T_i = ⟨{p_i^j | j=1:M}, {⟨w_i^k, c_i^k⟩ | k=1:K}⟩，M 个提示改写，K 个世界状态。
  • 世界状态包含：房间列表、对象列表、可操作对象列表、响应人类列表及定义 Ask() 响应的正则表达式。
  • 模拟器：Python 解释器加每个机器人技能的符号模拟，轨迹记录为执行的技能序列及参数；所有 Python 错误或机器人执行错误在模拟中记录。
  • 评估器：检查轨迹是否满足时序检查 c_i^k，以合取范式表达多个时序约束。
  • 时序语言 RTL：从 LTL 派生，更适合机器人任务规范，理由包括：1) 针对具体场景（如 Alice 说 yes 和 no 的不同场景）指定时序逻辑更容易且不易出错；2) 机器人任务的时序公式必然依赖机器人技能。RTL 相比 LTL 的优点是改进的可读性。

基准构成

  • 16 个任务，每个任务 5 个不同的提示改写，用于评估 LLM 对轻微提示变化的鲁棒性。
  • 任务设计检查 LMP 能否：1) 将语言指令接地到正确的机器人原语函数调用；2) 准确排序机器人动作；3) 处理基于不同世界配置的复杂控制流；4) 解决算术问题；5) 理解开放世界知识。

关键创新

  1. 符号模拟替代物理仿真：RoboEval 用 Python 解释器加技能符号模拟，将评估时间从小时级降至毫秒级，使大规模 LLM 程序评估成为可能。这是对现有“仿真-部署”评估范式的根本性简化。

  2. 时序逻辑 RTL 的领域适配：RTL 从 LTL 派生但针对机器人任务重新设计，解决了 LTL 在指定“Alice 说 yes 和 no 的不同场景”时的易错性。其可读性改进使非形式化方法专家也能编写任务规范，降低了基准构建门槛。

  3. eDSL 的机器人无关抽象：CodeBotler 通过 ROS Actionlib 解耦程序生成与平台执行，使同一 LLM 生成程序可部署到不同机器人。get_current_location 和 get_all_rooms 的动态查询设计，避免了先前工作需要在提示中硬编码世界配置的局限，提升了跨世界泛化能力。

边界与局限

作者承认现有代码补全基准不适用于服务机器人程序评估，因为不能仅靠输入输出序列测试。创建仿真可能耗时，作者因此创建轻量级 RoboEval 使用符号模拟器评估时序正确性。论文未明确列出其他局限或未做之事，包括：真实机器人部署验证、VLM 感知误差对程序正确性的影响、以及符号模拟与物理世界之间的语义鸿沟。论文未明确。

工程启示

  1. 复现优先核对：先访问 https://amrl.cs.utexas.edu/codebotler/ 获取完整任务描述列表，确认 16 个任务的具体世界状态配置。机器人技能实现代码在 https://github.com/ut-amrl/codebotler_amrl_impl ，需检查 ROS 版本兼容性（Actionlib 在 ROS 1 与 ROS 2 中接口不同）。

  2. 最容易踩坑处：is_in_room 依赖零样本 VLM，其输出不确定性可能被符号模拟器忽略——模拟器假设 VLM 返回真值，但真实部署中 VLM 误判会导致程序轨迹偏离。评估时需明确 VLM 误差是否纳入时序检查。

  3. 下游团队选型建议：若团队已有 ROS 系统，CodeBotler 的 Actionlib 接口可直接集成；若使用 ROS 2，需自行适配 action 接口。拒绝采样机制可立即用于减少执行错误，但需注意其可能降低 LLM 生成程序的多样性——建议在任务要求高可靠性时启用，在探索性任务中关闭。

  4. 评估基准迁移：RoboEval 的 RTL 语言设计值得借鉴，但迁移到新任务时需注意时序约束的合取范式表达——复杂任务可能产生指数级约束组合，建议从简单任务开始验证约束可满足性。
