摘要

ScheduleStream 是首个通用型规划与调度框架，由研究团队提出，用于解决双臂及人形机器人的多臂并行任务与运动规划调度问题。其核心贡献在于通过混合持续动作建模时间动态，并利用 GPU 加速采样器提升规划效率，在仿真和真实场景中均优于现有方法。

概述

ScheduleStream 是一个完全基于 Python 构建的通用规划与调度语言，由作者团队提出，旨在超越传统 TAMP 框架（如 PDDLStream）仅支持顺序计划的局限，直接支持动作在时间上异步重叠的调度（schedules）。其核心贡献在于将声明式规划语言与过程式 Python 编程无缝对接，并引入连续采样操作（流）来实例化无限常量域中的动作参数，同时提出 Eager Stream Scheduling 算法求解最小 makespan 调度。

它改变了什么

它真正改变的是 TAMP 问题的“解空间形态”。以往 PDDLStream 等框架的输出是动作序列，隐含了“一个动作完成、下一个动作开始”的串行约束，这在多机械臂协同场景中严重浪费了并行硬件能力。ScheduleStream 将解定义为带时间戳的调度 τ，允许动作重叠执行，这直接改变了规划问题的组合结构——从“排列动作”变为“在时间轴上安排动作的起止”，并引入 makespan 作为优化目标。此外，它打破了声明式语言（PDDL）与过程式语言（Python）之间的鸿沟，让用户可以用 Python 函数直接定义谓词（如碰撞检测）和采样器（如轨迹规划），这解决了 PDDL 无法表达无限连续参数空间（如 SE(3) 配置）的痛点。

方法拆解

语言核心：函数式状态与重载操作符

  • 状态被定义为对函数（functions）的赋值，例如 At(arm1)<=q1 表示机械臂 1 当前配置为 q1。采用封闭世界假设变体：未声明的函数求值为 None，未声明的谓词为 False。
  • 通过重载 Python 的 <=（赋值）和 ==（测试）操作符，将声明式建模语法嵌入 Python，使得状态更新和条件检查在代码层面直接可读。

动作模型：瞬时与持续

  • 瞬时动作（如 pick）：类似 STRIPS，有前置条件（如 Kin(...)、Attached("?obj")==None）和效果（如 Holding("?arm")<="?obj"）。
  • 持续动作（如 move）：扩展为有开始条件/效果、进行中条件、结束条件/效果和持续时间。例如 move 的开始效果是 At("?arm")<="?t"（中间轨迹点），结束效果是 At("?arm")<="?q2"，持续时间由过程式函数 Duration("?t") 计算。

流（Streams）作为连续采样器

  • 流是 PDDLStream 的扩展，用于生成无限多的连续参数值。例如 grasps 流生成抓取位姿，ik_qs 生成逆解配置，motions 规划轨迹。
  • 每个流有条件生成器，通过 next(grasps.gen(arm1)) 调用，返回新常量或 None。流输出被加入“流计划” ψ，并更新初始状态，诱导下一轮求解。

Eager Stream Scheduling 算法

  1. 用当前常量集求解有限调度问题（子程序 schedule）。
  2. 若失败，实例化流 s ∈ 𝒮 为 s(x)，调用生成器产生新常量 y。
  3. 若 y 有效且未被探索，将流输出谓词 p(x,y) 加入 ψ，更新初始状态 I，重新求解。
  4. 重复直至找到调度或流耗尽。

Schedule 子程序：从顺序计划到调度

  • 将每个持续动作 a 编译为两个瞬时动作：a.start 和 a.end。引入谓词 Ongoing（动作进行中）和函数 Remaining（剩余时间）。
  • 求解顺序规划得到计划 π 后，按时间戳构建调度：遇到 a.start 设置开始时间 T[a(x)] ← t；遇到 a.end 计算 Δt ← a(x).duration − (t − T[a(x)])，更新 t ← t + max(0, Δt)，并记录 ⟨T[a(x)], a(x), t*⟩。

关键创新

  1. 解空间从序列到调度：这是对 TAMP 问题定义的根本性扩展。允许动作重叠意味着规划器必须处理并发约束（如机械臂碰撞避免），而不仅仅是顺序因果链。这直接提升了多机械臂场景的吞吐量上限。
  2. 声明式与过程式的无缝融合：通过 Python 函数定义谓词（如 collision_cond）和持续时间（Duration），使得复杂几何计算（碰撞检测、逆运动学）可以直接嵌入规划逻辑，无需像 PDDL 那样用外部工具预计算所有可能值。这是对 PDDLStream 的“流”概念的实用化升级。
  3. Eager 流实例化策略：与 PDDLStream 的“先采样后规划”不同，Eager 策略在求解失败时才按需生成新常量，避免了无效采样爆炸，且与调度求解器紧密耦合，能更快收敛到可行调度。

边界与局限

  • 未提供实验验证：论文片段完全没有实验部分，无法判断该方法在真实机器人系统上的可行性、鲁棒性或计算效率。
  • 未讨论最优性保证：Eager Stream Scheduling 是贪心式的流实例化策略，论文未说明其与最优调度的差距，也未提及任何剪枝或启发式来保证解的质量。
  • 未处理资源冲突的全局优化：调度子程序通过顺序规划编译而来，可能无法捕捉动作间复杂的资源竞争（如共享工作空间），论文未明确说明如何处理此类全局约束。
  • 论文未明确：作者未讨论扩展到高维连续空间（如 7-DOF 机械臂）时的采样效率、未提及对动态环境（移动障碍物）的适应性、未讨论与学习方法的结合。

工程启示

  • 复现前先核对核心接口：重点检查 <= 和 == 操作符的重载是否与 Python 对象模型兼容，特别是当函数值本身是 PyTorch 张量时，== 的语义需要自定义（张量比较返回张量，需转换为布尔）。
  • 流生成器的实现是最大坑点：next(s.gen(x)) 必须保证在有限时间内返回有效常量或 None，且生成器内部不能有状态泄漏（如缓存未清空导致重复输出）。建议为每个流实例维护独立的生成器对象。
  • 调度子程序的编译逻辑需仔细验证：将持续动作编译为 start/end 两个瞬时动作时，Remaining 函数的更新逻辑容易出错，特别是当多个动作并行时，t* 的推进必须严格按时间戳排序处理。
  • 对下游团队的指导：如果目标是多机械臂协同装配，建议先用 Problem 1 和 3 的场景做单元测试，验证调度器能否正确产生重叠动作；若发现规划时间过长，优先检查流实例化是否过于频繁（Eager 策略可能在某些问题上退化为穷举采样）。
  • 注意封闭世界假设的副作用：未声明的函数求值为 None，这意味着任何遗漏的状态初始化都会导致规划失败，且错误难以追踪。建议在建模时显式初始化所有可能涉及的函数。
