概述

OMPL（Open Motion Planning Library）是一个实现了 RRT、RRT、PRM、BIT 等基于采样的运动规划算法的开源 C++ 库，是 ROS 生态中 MoveIt 框架的默认规划器后端。它本身不包含碰撞检测或可视化代码，而是通过插件化接口与外部系统集成，广泛用于机械臂及人形机器人的全身运动规划。

核心内容

是什么：准确定义

OMPL 是一个纯算法库，核心资产是一组状态空间（state space）抽象与在其上运行的采样规划器实现。它不关心机器人长什么样、障碍物如何表示、路径如何可视化——这些全部留给集成方。官方文档明确写道："OMPL itself does not contain any code related to, e.g., collision checking or visualization. This is a deliberate design choice, so that OMPL is not tied to a particular collision checker or visualization front end."

这个定位使它区别于 MoveIt（完整规划框架）和 Pinocchio（动力学计算库）。OMPL 解决的是几何路径搜索问题：给定构型空间 C-space 中的起点与目标，找到一条无碰撞的连续路径。它不负责动力学可行性——那是下层控制器（如 WBC 或 MPC）的职责。

为什么存在：痛点与历史定位

在 OMPL 出现之前，运动规划算法研究与机器人应用之间存在一条鸿沟。研究者实现一个 RRT 变体，往往要花大量时间处理碰撞检测、模型加载、可视化等与算法本身无关的工程问题；而应用工程师想用上最新算法，又缺乏统一接口。

OMPL 的诞生正是为了填平这条鸿沟：把算法层与系统层彻底解耦。它真正改变的不是某个具体算法，而是算法研究与工程部署之间的协作方式——研究者只需实现规划器接口，应用方只需提供状态空间与碰撞检测回调，双方通过 OMPL 的抽象层对接，互不侵入。

在人形机器人领域，这个痛点尤为尖锐。人形机器人全身上下数十个执行器以毫秒级周期闭环，显式表示其 C-space 障碍在计算上不可行（40+ 自由度的构型空间维度极高），采样式规划的概率完备性使其成为少数可行的方案之一。OMPL 因此成为 MoveIt 的默认规划器后端，并支撑了 NASA Robonaut2 在国际空间站的步态规划等标志性应用。

原理拆解

① 采样式规划的核心思想

采样式规划的基本思想是在构型空间（configuration space, C-space）中随机采样并局部连接，逐步构建可达路径图或树，从而回避了对高维空间障碍的显式建模。这对 40+ 自由度的人形机器人至关重要，因为显式表示其 C-space 障碍在计算上不可行。

② 概率完备性

采样规划器在采样数趋于无穷时以概率 1 找到可行解（若解存在）的性质，称为概率完备性（probabilistic completeness）。这是 OMPL 中 RRT、PRM、BIT* 等算法的理论基石——它们不保证有限时间内找到解，但保证"只要采样足够多，找到解的概率趋近于 1"。

③ 算法族谱

OMPL 包含三类核心算法：

  • RRT（Rapidly-exploring Random Tree）：从起点出发，随机采样并逐步扩展一棵树，偏向于探索未访问区域。
  • RRT*：在 RRT 基础上引入重连（rewiring）机制，保证渐近最优性——随着采样数增加，解路径收敛到最优。
  • PRM（Probabilistic Roadmap）：在 C-space 中随机采样大量点，连接邻近点构成路标图，适合多查询场景。
  • BIT*：结合图搜索与采样，利用启发式信息加速收敛。

④ 与碰撞检测的接口

OMPL 通过 StateValidityChecker 回调接口询问"某个状态是否合法"，由集成方实现具体的碰撞检测逻辑。官方默认支持 VAMP（SIMD 加速的碰撞检测与正运动学库），可将规划时间缩短数个数量级（several orders of magnitude）；也支持 Pinocchio 作为运动学计算后端。

关键区别：MoveIt 是"框架"，OMPL 是"库"。MoveIt 把碰撞环境表示、正逆运动学插件、碰撞检测与规划器接口整合为一套管线，OMPL 作为其默认规划器后端被调用。Pinocchio 提供 WBC/MPC 与仿真器共用的动力学内核，与 OMPL 解决的是不同维度的问题——前者算力/力矩，后者找路径。

谁在用·应用案例

① NASA Robonaut2（国际空间站）

OMPL 被用于规划 Robonaut2 的足部步态（footsteps）。这是 OMPL 在太空环境中的标志性应用——在微重力下，机器人需要规划复杂的足部移动序列以在空间站内导航。

② Amazon Picking Challenge（2016）

代尔夫特理工大学团队使用基于 MoveIt 的定制运动规划管线赢得比赛，其中 OMPL 承担核心规划任务。这验证了 OMPL 在仓储抓取场景中的工程可靠性。

③ 多模态运动规划

OMPL 被用于多模态规划器，实现复杂机器人行为——例如从拼图盒中取出杠铃物体。这类任务需要切换不同的运动模式（如"推动"与"抓取"），OMPL 的低层规划能力是其中的关键环节。

④ 约束运动规划

OMPL 支持运动学约束机器人的规划。官方演示的并联机构超过 150 个自由度，但可行运动仍可在数秒内计算得出——这得益于约束流形上的采样策略。

⑤ 人形机器人软件栈

在人形机器人中，OMPL 位于规划层（1–20 Hz，延迟预算数十 ms），与 MoveIt 配合生成无碰撞的几何路径，再由下层控制器（WBC 或 MPC）负责动力学可行的实时执行。工程上常用"规划于粗模型、执行时在线避障"的两级结构，以应对规划-执行异步问题。

局限与边界

① 不解决动力学可行性

OMPL 生成的路径是几何无碰撞的，但不保证动力学可行——关节速度、加速度、力矩约束均不在其考虑范围内。工程上必须由下层控制器（WBC/MPC）对路径做时间参数化与动力学修正。

② 概率完备 ≠ 确定性完备

OMPL 的算法不保证有限时间内找到解，也不保证解的最优性（RRT 甚至不保证渐近最优）。在狭窄通道（narrow passage）场景中，采样效率可能极低，需要偏置采样或学习先验来加速。

③ 规划-执行异步问题

规划完成时环境可能已偏离规划假设，导致轨迹过时。人形机器人场景中，全身碰撞对数量大（含自碰撞）、平衡约束需与控制层协调，这些问题 OMPL 本身不处理，需要集成方在架构层面解决。

④ 不包含感知与状态估计

OMPL 假设已知 C-space 中的障碍分布，但障碍从何而来（感知、建图、预测）完全不在其职责范围内。它真正改变的不是"机器人如何感知世界"，而是"给定世界模型后如何找到路径"。

常见误区

  1. "OMPL 就是 MoveIt"——错。MoveIt 是完整规划框架，OMPL 只是其默认规划器后端。团队可以只复用 MoveIt 的碰撞管线而自研规划器，或反之。OMPL 本身不包含任何碰撞检测或可视化代码。

  2. "OMPL 能直接用于人形机器人全身控制"——错。OMPL 输出的是几何路径，不是控制指令。它位于规划层（1–20 Hz），而全身控制（WBC）位于控制层（100–1000 Hz），两者之间必须经过轨迹时间参数化与动力学修正。

  3. "RRT* 一定比 RRT 好"——不一定。RRT* 保证渐近最优性，但计算开销更大。在时限严格的场景中，RRT 可能更快找到可行解。工程上需要根据延迟预算（数十 ms 级）权衡。

  4. "OMPL 只用于机械臂"——错。官方文档明确列出其应用范围包括（移动）机械臂、类车系统、无人机和水下航行器，以及人形机器人的步态规划。

  5. "采样规划器能找到最优解"——只有渐近最优。RRT 和 BIT 在采样数趋于无穷时收敛到最优解，但有限时间内只能保证"足够好"的可行解。
