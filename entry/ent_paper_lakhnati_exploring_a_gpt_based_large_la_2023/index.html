探索基于GPT的大语言模型在虚拟现实人机团队协作仿真中的可变自主性

Exploring a GPT-based Large Language Model for Variable Autonomy in a VR-based Human-Robot Teaming Simulation

领域
AI 模型与算法软件中间件应用与市场设计工程
层级
智能层中游验证与市场层
审校
待审校

摘要

本文提出一个基于Unity VR的仿真框架，用户可通过自然语言与多个由独立GPT-4实例驱动的机器人进行交互，并利用OpenAI的函数调用API将非结构化语音转化为结构化机器人动作。通过12名参与者的用户研究，探讨了对话策略，并为LLM驱动的人机协作提供了经验教训。

来源与参考

  • Exploring a GPT-based Large Language Model for Variable Autonomy in a VR-based Human-Robot Teaming Simulation

概述

本文探索将现成的 GPT-4 大语言模型集成到基于 Unity/VR 的人-机器人团队模拟环境中，通过 OpenAI function calling 将非结构化自然语言映射为结构化机器人动作，以实现可变自主性。研究基于 12 名参与者的探索性被试内实验，结合 SASSI 问卷与主题分析，揭示了用户与 LLM 驱动机器人交互中的关键行为模式与系统局限。

它改变了什么

这项工作的真正价值不在于“用 GPT 控制机器人”这一表面命题，而在于它把 LLM 的非确定性与机器人控制所需的确定性之间的张力，从一个理论担忧变成了一个可观察、可分析的实证对象。传统 HRI 研究要么依赖 Wizard-of-Oz 模拟完美 AI，要么使用预定脚本的对话系统，两者都回避了 LLM 在实际部署中“会犯错、会犹豫、会过度解释”的真实行为。作者选择现成的 GPT-4 而非微调模型，本身就是一种立场：先进 AI 技术已达到非 AI 专家可应用的水平，因此探索其原生行为模式比追求定制优化更有现实意义。

更重要的是，这项研究改变了我们对“可变自主性”的理解方式。以往可变自主性通常被设计为一种显式的控制机制（如用户通过界面切换自主等级），而本文展示了一种隐式的、由对话协商产生的自主性分配：LLM 可以在“夺取控制”执行函数与“放弃控制”请求澄清之间自主决定。这种自主性不是由用户显式选择的，而是在交互中涌现的，这既是其创新之处，也是其问题之源——用户往往不清楚机器人何时会自主行动、何时需要明确指令。

方法拆解

系统架构

  • 中央控制器 + 每机器人独立 GPT 实例：控制器基于对话历史解释用户输入并分发给相关代理（0…n 个），避免所有代理处理每个输入，兼顾可扩展性与计算效率。
  • 函数调用作为人-机接口：采用 OpenAI function calling，将非结构化自然语言映射为结构化机器人动作。函数本质是描述过程的 JSON 对象，包含函数本身、合格参数、调用时机等。GPT 模块可决定不回答而返回函数调用，或在不明确时向用户请求澄清。

提示工程

  • Briefing：角色与情境描述（如“你是黄色机器人代理 Jupiter…”）。
  • Restraints：指示模型保持角色（如“永远不要打破角色。永远不要提及你是 AI 模型”）。
  • Few-shot 示例：如控制器被指示当与单个代理继续对话时“you”可能指该代理，当与多个代理对话时“you”可能指所有代理。

实现细节

  • 平台：Unity 2022.3.4f1 创建的 VR 环境，优化用于 Meta Quest 2；通过 Srcnalt 的 OpenAI-Unity 包连接 OpenAI 端点。
  • 语音链路：输入用 OpenAI Whisper v2 转录，输出用 Amazon Polly 合成声音。
  • 模型：所有代理使用 gpt-4-0613（截至 2023 年 11 月最新的优化函数调用的 GPT 模型），仅使用聊天补全 API。
  • 函数输出验证：系统验证函数输出并用文本反馈更新 GPT 模块，模拟真实场景中机器人的感官输入（如摄像头和传感器）。例如，若代理尝试拾取物体，系统评估代理与物体间距离并更新模型。

实验设计

  • 探索性被试内研究，12 名参与者（P3–P14，前两名因系统重大变更被排除），平均年龄 36.45 岁（SD = 14.57），9 女 3 男。
  • 共 7 个递进任务，共享相同起始位置，涉及多机器人协调、时序约束（如任务 5 中门定时器故意设置得足够低）、物体属性（如花瓶需在床翻转前拾起）。
  • 数据采集：5 小时 28 分钟实验数据 + 3 小时 46 分钟访谈数据；访谈用 Whisper 转录后手动修正，采用主题分析（三名研究者迭代编码）。

关键创新

  1. 函数调用作为可变自主性的实现机制：这是本文最核心的方法论创新。函数调用不仅是一种接口技术，更是一种自主性分配机制——LLM 在“确定用户意图时夺取控制执行函数”与“不确定时放弃控制请求澄清”之间自主决策。函数描述同时为模型提供能力边界的脚手架，且高度可扩展可修改。相比文本本体方法，函数特性更有效地约束 LLM 行为。

  2. 去中心化的多代理 GPT 架构：中央控制器 + 每机器人独立 GPT 实例的设计，避免了所有代理处理每个输入的计算浪费，同时允许每个机器人保持独立的对话历史和角色一致性。这种架构天然支持异构机器人（Jupiter 黄色强壮、Pluto 红色可飞、Neptune 蓝色轮式）的差异化行为。

  3. VR 环境作为 LLM 驱动 HRI 的测试平台：选择 VR 而非物理机器人，在简化复杂性和增加灵活性的同时保持沉浸感。这一决策使研究者能够系统性地操纵任务复杂度（从单代理单动作到多代理时序协调），而无需承担物理机器人的成本和风险。

实验与结果

SASSI 问卷结果（1–7 分制，7 为最差/最慢）

关键行为发现

  • 用户不将机器人视为平等对话伙伴：所有参与者都将机器人视为指令接收者，但风格分化为命令式（如 P14）与对话式（如 P7）。对话式参与者更可能向机器人寻求建议，但此类问题总体上是例外。
  • LLM 过度健谈：机器人倾向于提供冗长解释并在不确定时请求澄清，导致用户感觉“像与幼儿交谈”（P4、P5）。P9 对机器人要求先接近物体再拾取感到惊讶：“I expected it to act on the instruction directly.”
  • 功能描述的过度挑剔：P11 说“Pluto, please go to the blue trash can”，Pluto 回复“Sorry, I can only go to locations that are defined in my functions.” SASSI 问题 29“I sometimes wondered if I was using the right word”平均得分 5.92（SD = 1.73）。
  • 自主性期望差异：P3 说“In certain situations, I didn’t realize I had to explicitly instruct the system to approach an object before picking it up.” 但也有机器人自主分解任务的例子：P8 要求 Jupiter“take three plates and throw them in the trash bin”时，机器人连续三次执行了正确的功能三元组（移动、拾取、丢弃）。
  • 响应延迟是核心痛点：SASSI Speed 维度 M = 5.25（SD = 1.57），P9 说“the robots’ feedback always came late. There was a lot of narration, and by the time they responded, I had already continued speaking.”

边界与局限

  • LLM 非确定性：即使在低温度下输出也不一致，作者明确承认 GPT 无法作为真实机器人的控制元素，需要额外模块支持以确保一致性。
  • 云服务延迟：GPT API 引入延迟，大学互联网连接的不稳定性加剧了问题；虽然没有断开或完全中断，但转录和模型响应的延迟有时明显更长。
  • 语言限制：实验使用德语，可能是某些意外行为的原因，尤其是功能方面，尽管功能描述中的对象被故意赋予德语名称以防止 LLM 消歧。
  • 未做之事：未进行长期部署测试、不同 LLM 版本的对比实验、非英语语言支持测试；系统在最初两次会话后经历了重大变更（P1 和 P2 被排除）。
  • 错误传播：框架继承 LLM 的潜在偏见和错误向前传播问题（错误输出成为未来输入的一部分）。
  • LLM 幻觉：LLM 有时会产生幻觉，说服参与者相信不真实的事情，并重复或过度分享与任务无关的信息。

工程启示

  • 先核对功能描述的粒度与命名一致性：实验中最常见的失败模式是 LLM 对功能描述中的词语过度挑剔，拒绝执行名称略有偏差的对象（如“blue trash can” vs. “trash bin”）。复现时应仔细设计功能描述中的对象命名，并在提示中明确同义词映射，或增加别名机制。
  • 延迟是最大的工程挑战：SASSI Speed 得分 5.25 表明响应延迟严重影响了用户体验。如果复现，建议考虑本地化 LLM 推理、缓存常见指令的响应、或引入流式输出以降低感知延迟。任务 5 中门定时器故意设置得足够低，使顺序命令因延迟而显得不可行——这提示时序敏感任务需要额外的调度机制。
  • 用户校准至关重要：参与者对机器人自主性的期望差异极大，且这种差异在交互初期就已定型且难以改变。建议在实验开始前增加一个校准阶段，明确告知用户机器人的能力边界和自主性策略，以减少“我没想到要明确指示它先接近物体”这类认知落差。
  • 多代理架构的通信瓶颈：当前框架允许多机器人非结构化交互，但机器人之间缺乏直接通信机制。在协作任务（如任务 7 中 Jupiter 和 Neptune 一起翻转床）中，文本表示和统一对话日志不足，响应应聚类以简化用户响应并避免重复。代理控制器可承担更复杂的代理间通信控制。
  • 干预机制缺失：由于转录和 GPT 模块的处理时间，常规沟通渠道不适合干预。作者建议引入立即停止机器人的按钮，无论 LLM 当前状态如何——这是任何实际部署中必须优先考虑的安全机制。
