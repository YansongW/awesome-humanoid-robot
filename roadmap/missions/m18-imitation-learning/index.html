M18 · 模仿学习训练与部署：50 条演示喂出一个会抓杯子的策略

全局位置：M17 遥操作数据集建成之后、M19 端到端任务集成之前。输入是 ≥50 条按统一协议采集的演示 episode（多视角图像 + 关节状态 + 动作 + 时间戳，Stage 3 判据），输出是一个真机固定协议下抓取成功率 ≥70% 的抓取策略（权重 + 模型卡 + 部署延迟实测），M19 把它作为"抓取技能"接进端到端任务链。

前置条件：M17 · 遥操作与数据采集 完成（episode 格式冻结、训练/验证集划分完毕、数据质量抽查通过）；感知标定达标（Stage 3 判据：杯子 3D 定位误差 ≤1 cm）；有一块能训练视觉策略的 GPU（显存需求按所选官方仓库说明核对）。

理论背景：行为克隆、ACT、Diffusion Policy 三张卡片是本任务的主线；系统论述见 第 18 章 模仿学习与策略学习，数据格式与生态见 第 21 章 数据基础设施 与 附录 B 数据集。

步骤 1：baseline 先行——行为克隆跑通训练管线

【做什么】先用最简单的 行为克隆（BC）跑通完整管线：数据加载 → 图像 + 状态编码 → 逐帧回归动作 → 训练 → 验证集 loss → 开环回放评估（把模型预测的动作序列与演示真值画在同一张图上，逐关节对比）。配置从简：轻量视觉骨干 + 回归头，先把管线跑通，不是把指标刷高。

【为什么】BC 有两个不可替代的价值。一是管线验证：数据加载、时间对齐、归一化、评估脚本里任何一个 bug，用 BC 暴露最便宜——直接上 ACT 出了问题，你分不清是方法不行还是管线错了。二是对照组：BC 的数字是后面一切方法的基线，ACT/扩散策略比 BC 好多少，要拿同一份数据、同一套评估说清楚。BC 的理论短板是复合误差（compounding error）：逐帧回归时每一帧的小误差把机器人带到训练分布之外的状态，误差像滚雪球一样累积——这正是后两步要压制的东西，见 第 18 章。

【你的情况怎么分析】BC 验证集 loss 降但开环回放明显跑偏：先查时间对齐（图像帧与动作帧错位 1–2 帧是采集数据最常见的暗伤），再查动作归一化是否写反。BC 本身真机成功率通常不高，不要恋战——管线通了、数字记了，就进步骤 2。

步骤 2：ACT——动作分块压制复合误差

【做什么】换 ACT（动作分块 Transformer）：模型一次预测约 100 步的动作块（chunk），执行时按时间集成（temporal ensemble）对重叠块加权平滑。训练配置按官方仓库默认起步（学习率、epoch 数、chunk 长度、backbone 都先不动）；M17 数据若按 ALOHA 数据格式组织，可直接复用其数据管线。训练时盯验证集曲线：train 降、val 回升就是过拟合，提前停。

【为什么】动作分块是对抗复合误差的第一条主流路线：一次看一段未来而不是一帧，单帧抖动被块内平均吸收，分布外漂移显著减少。ACT 卡片口径：在精细双臂任务上报告 80%–90% 成功率（来源：ACT 卡片；任务与数据规模和你的场景不同，只作量级参考）。时间集成用"多次预测投票"换执行平滑，代价是推理频率下降。

【你的情况怎么分析】数据量 50–100 条：chunk 长度先按官方默认，不要一上来调大——块越长对数据量要求越高。缺腕部/第一人称视角时 ACT 对精细对位明显变差，回看 M17 的视角覆盖。过拟合三板斧：提前停、图像数据增强（平移/颜色抖动）、回步骤 6 定向补采。

步骤 3：Diffusion Policy——当同一局面有多种合法解法

【做什么】跑 Diffusion Policy：用去噪扩散过程建模动作序列的分布而非单点回归，从噪声迭代采样出一段动作。同样按官方仓库默认配置起步，与 ACT 用同一份数据、同一套划分做对比实验，记录验证集 loss、开环回放误差与真机结果三列。

【为什么】回归类方法对多峰动作天然吃亏：演示里"从左边绕"和"从右边绕"各占一半，回归会学出"从中间撞过去"的平均动作；扩散建模直接表达多峰分布，采到哪个峰都是合法解（见卡片）。代价是训练与推理成本都更高：多步去噪意味着更高的机上推理延迟，部署时必须实测（步骤 5）。实证锚点：ToddlerBot 在 Jetson Orin NX 16GB 上跑 300M 参数扩散策略，机上推理约 100 ms（来源：ToddlerBot 论文）。

两法对比速查（细节见各自卡片）：

维度 ACT Diffusion Policy
动作建模 分块回归 + 时间集成平滑 去噪扩散建模动作分布
多峰动作 弱（回归趋向取平均） 强（从分布中采样）
机上推理 单次前向，延迟低 多步去噪，延迟高（需实测）
首选场景 解法单一、快速起步 同一局面有多种合法解法

【你的情况怎么分析】任务解法单一（固定位置抓固定杯子）：ACT 通常够用，扩散收益小、成本高，可跳过本步，但建议至少跑一次当对照。任务有多种抓法/多条路径：认真做对比实验。两法真机结果接近时选推理更快的——机上频率就是稳定性。

步骤 4：评估协议——离线筛模型，闭环定生死

【做什么】建两级评估并固化成脚本：

  1. 离线：验证集 loss 只是粗筛；必须做开环回放——每个候选模型挑 5–10 条验证集 episode，预测动作与真值叠加画图、渲染视频，逐条人眼看；
  2. 闭环：真机固定协议——固定物体、固定位置网格（如 3×3、间距 5 cm，工程建议值，需按你的任务校核）、每个网格点重复，共 20 次试验记录成败；Stage 3 判据：成功率 ≥70%；
  3. 失败分类学：每次失败归入四类之一并计数——感知错（检测/分割错）、定位错（位姿偏差）、抓取滑脱（碰到但没夹住）、轨迹碰撞（碰倒物体或撞桌）。

闭环试验每次一行记录，脚本自动汇总（字段可按需增删）：

trial_id,grid,success,failure_class,infer_ms,notes
007,(2,1),fail,slip,96,闭合瞬间杯子滑移

【为什么】"loss 降了"和"机器人能抓"之间隔着分布偏移、时间对齐、执行延迟三座大山，只有闭环真机协议是终审；固定协议的意义是可复现、可横向比较——没有它，每次改动的效果都是玄学。失败分类学决定下一步补什么：感知错补视角/光照数据，定位错回去查标定，滑脱改夹爪或补接近段数据，碰撞补障碍场景。评测方法论见 第 25 章 机器人评测体系。

【你的情况怎么分析】20 次是"能放进报告"的下限：网格再密时间爆炸，再少统计噪声太大（20 次里多成功 1 次就是 5 个百分点）。评估当天记录光照、环境温度与电池电量——这三个变量各自都能解释几个百分点的波动。

步骤 5：端侧部署——策略上 Jetson，限幅保安全

【做什么】把策略部署到机载计算平台（典型为 Jetson AGX Orin，分层选型理由见计算平台选型手册），按端侧 VLA 推理卡片的手段压延迟：量化（FP16/INT8）、推理引擎优化、降输入分辨率。然后完成四件事：

  1. 频率对接：实测端到端推理延迟并定策略频率（操作任务 5–10 Hz 通常够，来源：计算平台选型手册）；策略输出交给底层高频环跟踪（自研 QDD 力控闭环 250 Hz–1 kHz 量级，同手册口径）；
  2. 动作限幅：策略输出经工作区软限位（比机械硬限位小 5–10°，M10 规则）与速度限幅后才下发；
  3. 降级策略：推理超时（如 >2 倍控制周期，工程建议值）→ 保持当前姿态；连续超时 → 卸力进阻尼（M14 分级）；
  4. 回归基线：本次部署的延迟实测与闭环成功率写入模型卡；此后任何限幅、频率、量化配置的改动，都必须重跑步骤 4 的闭环协议才算生效。

【为什么】机上推理不能假设网络可用：Wi-Fi 抖动时云端推理等于失控——延迟、连接性、隐私是端侧化的三个硬约束（端侧 VLA 推理卡片）。策略是"会犯错的黑盒"，限幅与降级是把它关进笼子的最后防线，与 M20 的保护机制清单是同一份安全逻辑。

【你的情况怎么分析】ACT 级小模型在 Orin 上通常能直接跑够频率；扩散策略先量化再实测，ToddlerBot 的 300M 扩散策略在 Orin NX 16GB 上约 100 ms（toddlerbot.md 档案）可作量级锚点。延迟不达标按顺序砍：量化 → 降分辨率 → 减去噪步数/动作块长，仍不够再评估 Jetson Thor 级平台。推理进程的 CPU 亲和性与优先级单独配置，别和控制进程抢核。

步骤 6：迭代闭环——失败在哪，数据就补到哪

【做什么】建立固定迭代节奏：每轮只动一个变量（补一类数据 / 调一个超参 / 换一个 backbone），走完"训练 → 离线评估 → 20 次闭环"全流程，登记入表：

模型版本 数据版本 改动 验证集 loss 闭环成功率 失败分类计数
v1.0 d1.0（50 条） BC baseline … … …
v1.1 d1.1（+8 条滑脱场景） 定向补采 … … …

定向补采用 DAgger 思路：把策略跑失败的场景（如网格右上角的滑脱）原样摆出，遥操作补采 5–10 条该场景演示加进训练集。可选：用 LIBERO（主题任务套件 + 程序化场景变化的短程桌面基准）做仿真回归，每次改动先过筛再上真机。

每轮迭代的产出同步更新模型卡：数据版本、训练配置（代码 commit + 关键超参）、离线/闭环指标、部署延迟实测、已知失效场景——M19 集成与 M20 变更管理都以模型卡为准。

【为什么】模仿学习的性能瓶颈几乎永远是数据分布而不是模型容量：失败分类学告诉你分布的洞在哪，定向补采是单位时间收益最大的改动。一次只改一个变量 + 版本对应表，是三个月后还能回答"成功率为什么从 75% 掉到 60%"的唯一方法。LIBERO 的程序化场景变化能暴露过拟合，仿真回归把大部分"改了反而更差"挡在真机之外（见 第 25 章）。

【你的情况怎么分析】每轮补采控制在总量的 10–20%：太多冲淡原始分布，太少不起作用。成功率卡在某个数值两轮不动：回看失败分类计数——感知错占比过半，问题在数据或标定而不在策略，回去修数据比继续调参便宜得多。

验收标准

  • [ ] BC baseline 跑通，管线（加载/对齐/归一化/回放）验证记录成文，数字留作对照组。
  • [ ] ACT 与 Diffusion Policy 至少各训一版，同数据同划分对比表存档。
  • [ ] 真机固定协议（固定物体 + 位置网格 + 20 次）成功率 ≥70%，每次成败与失败类别的原始记录齐全。
  • [ ] 失败分类学四类计数完整，且有至少一轮"定向补采 → 复测"的闭环记录。
  • [ ] 模型卡成文：数据版本、训练配置、评估指标、部署延迟实测值。
  • [ ] 训练与评估脚本连同配置入库（同一数据版本可复跑），闭环原始记录随版本归档。
  • [ ] 端侧部署达标：推理延迟实测满足策略频率，动作限幅与超时降级经实机触发验证。

常见坑与排查

症状 可能原因 排查动作
训练 loss 降，真机完全不行 分布偏移 / 图像与动作时间对齐错位 开环回放逐帧核对时间戳；检查采集端时钟同步
动作块边界处抖动/顿挫 时间集成未启用或权重不当 / 推理频率太低 确认 temporal ensemble 生效；实测端到端延迟；增大块重叠
小数据过拟合（val loss 早升） 数据量太少 / epoch 过多 提前停；图像增强；回步骤 6 定向补采
真机对位总是差几厘米 图像压缩/降采样丢关键细节 / 外参标定漂移 检查数据管线图像变换；重标手眼
推理延迟超标、控制发飘 未量化 / 输入分辨率过高 / 推理与控制抢 CPU 量化 + 推理引擎优化；降分辨率；绑核与进程优先级
换相机/换光照后成功率崩 数据分布对视角/光照过拟合 采集引入视角与光照扰动；用 LIBERO 仿真回归先暴露
