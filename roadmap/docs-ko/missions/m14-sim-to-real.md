# M14 · sim-to-real 배포 및 보행 검증: 시뮬레이션 챔피언에서 실제 로봇으로의 첫걸음

**전체 위치**: M13에서 2~3개의 후보 RL 체크포인트를 훈련 및 선별한 후입니다. 입력은 시뮬레이션에서 강건하게 통과한 보행 전략 + 실제 측정 파라미터로 보정된 모델이며, 출력은 **실제 평지 보행을 통해 Stage 2의 6개 관문을 통과**하는 것입니다. Stage 3(M15부터)에서는 이 보행이 가능한 로봇에 상체를 장착합니다. 보행이 불안정하면 이후 모든 것은 허상에 불과합니다.

**전제 조건**: [M13 · 강화 학습 훈련](m13-rl-training.md) 검증 통과 (최대 무작위화 + 외란 하에서 100 에피소드 낙상률 ≤10%); 전체 조립, 영점 교정, 비상 정지 체인 완료 ([Stage 2 개요](../stage-2-biped.md) Step 4/6 해당); 호이스트 준비, 2인 디버깅 팀 역할 분담 명확.

이론적 배경: [sim-to-real 전이](/entry/ent_method_sim_to_real/), [도메인 무작위화](/entry/ent_method_domain_randomization/), [시스템 식별](/entry/ent_method_system_identification/) 카드, [제11장 조립, 통합 및 테스트](/wiki/chapters/chapter-11/) 및 [제25장 로봇 평가 체계](/wiki/chapters/chapter-25/).

## 단계 1: 배포 파이프라인 구축——전략을 훈련 환경에서 로봇으로 이전

【수행할 작업】네 가지 작업을 순서대로 실행:

1. **전략 내보내기**: 훈련 프레임워크에 따라 jit(PyTorch `torch.jit`) 또는 ONNX로 내보내고, 입력/출력 차원을 고정하며 가중치를 동결합니다. 내보낸 후 즉시 시뮬레이션에서 내보낸 파일로 강건성 평가를 재실행하여 점수 손실이 없는지 확인합니다.
2. **온보드 추론**: 전략은 로봇 메인 컨트롤러에서 실행됩니다. 두 가지 기준 경로: Berkeley Humanoid Lite는 Intel N95에서 C 언어 저수준 배포 사용 (`berkeley_humanoid_lite_lowlevel` 하위 디렉토리는 훈련 스택과 독립적이며, 별도로 부하 테스트만 수행, `data/roadmap/research/berkeley-humanoid-lite.md`); ToddlerBot은 Jetson Orin NX 16GB에서 순수 Python 배포 사용 (`data/roadmap/research/toddlerbot.md`).
3. **주파수 계층화**: 전략은 50Hz 수준으로 추론하여 관절 목표 위치를 출력하고, 저수준 PD는 고주파로 추종합니다. 기준 파일: ToddlerBot 30개 모터 전체 상태 피드백 50Hz (toddlerbot.md), Berkeley 액추에이터 및 IMU의 CAN 통신 250Hz (berkeley-humanoid-lite.md).
4. **프로세스 분할 및 워치독**: 추론, 제어, 통신을 별도 프로세스로 분할합니다. 통신/제어 프로세스는 서로 하트비트를 보내며, 어느 프로세스든 시간 초과로 응답하지 않으면 관절 힘 해제를 트리거합니다.

【이유】훈련 스택과 배포 스택은 다릅니다. 훈련 환경에는 GPU와 실제 값 관측이 있지만, 로봇에는 온보드 연산 능력과 잡음이 있는 센서만 있습니다. 주파수 계층화의 본질은 "느린 결정, 빠른 실행"입니다. 전략은 느려도 되지만, PD는 외란과 액추에이터의 비이상성을 억제하기 위해 고주파여야 합니다 (메커니즘은 [임피던스 제어](/entry/ent_method_impedance_control/) 카드 참조). 워치독은 소프트웨어가 멈출 때 로봇이 제자리에서 힘을 가하는 것을 방지합니다.

【당신의 상황 분석】복제 플랫폼은 공식 배포 코드를 직접 사용하며, 이 단계에서는 내보내기와 주파수 확인만 수행합니다. 자체 개발 스택의 하드 기준: 추론 지연 시간 실제 측정 < 제어 주기의 50% (50Hz 전략의 경우 <10ms), 초과 시 네트워크 크기를 줄이거나 컴파일 런타임을 변경하고, 억지로 버티지 마십시오.

## 단계 2: 관측 정렬——시뮬레이션 obs와 실제 센서를 항목별로 매핑

【수행할 작업】관측 매핑 테이블을 작성하고, 항목별로 정렬, 실제 측정, 서명합니다:

| 시뮬레이션 관측 | 실제 소스 | 정렬 핵심 사항 |
|---|---|---|
| 베이스 자세 (roll/pitch/yaw) | [IMU](/entry/ent_component_imu_2024/) | 설치 방향 vs 모델 base 좌표계의 축 매핑, 코드 주석에 기록 |
| 베이스 각속도 | IMU 자이로 | 단위 rad/s, 필터 대역폭을 시뮬레이션과 일치 |
| 관절 각도 | 엔코더 | 영점을 M06 교정 기록과 일치, 양의 방향을 URDF 축 방향과 동일 |
| 관절 속도 | 엔코더 차분 | 저역 통과 필터 추가, 차단 주파수를 시뮬레이션 처리와 일치 |
| 이전 프레임 동작 | 전략 출력 캐시 | 메모리에서 직접 읽고, 액추에이터에서 재읽지 않음 |

교정 3단계: ① **IMU 바이어스**——로봇을 30초간 정지 상태로 두고 자세 판독값 기록, 드리프트가 임계값(예: 1°, 엔지니어링 권장값, 사용자 IMU에 따라 확인 필요)을 초과하면 바이어스 교정 재실행; ② **엔코더 영점**——M06 지그를 사용하여 재배치하고, 판독값을 교정 기록과 비교; ③ **좌표계 재확인**——로봇을 수동으로 기울여 IMU 판독값 방향과 시뮬레이션 base 좌표계 방향 비교.

【이유】관측 오정렬은 sim-to-real 실패의 첫 번째 원인입니다. IMU가 180° 반대로 설치되면 전략은 "거꾸로 된 세계"를 보게 되어 시작하자마자 넘어집니다. M13에서 세운 규칙을 다시 상기합니다: **실제 로봇에서 얻을 수 없는 관측은 전략에 포함하지 않음**——베이스 선속도 실제 값과 같은 양은 상태 추정 방식이 있거나 obs에서 삭제하고 재훈련해야 하며, 다른 방법은 없습니다.

【당신의 상황 분석】매핑 테이블의 각 행에 대해 "수동 외란 → 판독값 출력 → 시뮬레이션 동일 시나리오와 비교"를 수행합니다. IMU가 하나만 장착된 경우 obs에 발 자세 추정을 포함하지 마십시오. 센서 지원이 없는 관측은 모두 함정입니다.

## 단계 3: 액추에이터 시스템 식별 정밀 보정——무작위화 중심을 실제 로봇에 맞춤

【수행할 작업】

1. **지연 시간 측정**: 계단 위치 명령을 보내고, 명령→엔코더 응답 시간 차이를 기록하여 총 지연 시간(통신 + 드라이브 + 기계)을 얻습니다.
2. **1차 시상수 측정**: 응답 곡선에 1차 모델 `τ_m·q̇ + q = q_cmd`을 피팅하여 τ_m을 추출합니다.
3. **Kt 및 마찰**: M07 테스트 벤치의 전류-토크 교정 및 마찰 실제 측정 데이터를 재사용합니다.
4. **역입력**: 실제 측정된 지연 시간, 토크 계수, 질량 편차를 시뮬레이션에 기록하고, M13 [도메인 무작위화](/entry/ent_method_domain_randomization/) 범위의 **중심**을 실제 측정값으로 이동시키며, 필요한 경우 범위를 좁혀 체크포인트를 재훈련합니다.

【이유】도메인 무작위화의 철학은 "실제 값 주변에서 무작위화"입니다. 범위 중심이 실제 로봇에서 벗어나면 전략은 존재하지 않는 로봇에 대해 강건해지며, 이것이 "환경 적응 실패"의 근본 원인입니다. ToddlerBot의 디지털 트윈은 모범 사례입니다. 3D 프린팅 지그로 1분 만에 영점 교정 완료 + 동일 모델 모터는 1회 [시스템 식별](/entry/ent_method_system_identification/)만 수행하면 전체에 이전 가능하며, 이것이 제로샷 sim-to-real의 핵심입니다 (toddlerbot.md).

【당신의 상황 분석】서보 모터 플랫폼 (ToddlerBot 계열): sysID는 "동일 모델 1대 + 전체 영점"만 수행하면 됩니다. 자체 개발 QDD (Berkeley 계열)는 배치 간 편차가 크므로 지연 시간과 마찰을 모터별로 실제 측정합니다. 역입력 후 재훈련된 체크포인트는 M13 후보와 함께 단계 4로 가져가 실제 로봇에서 최종 비교합니다.

## 단계 4: 단계별 실제 로봇 해제——6단계 계단식, 이상 시 즉시 복귀

【수행할 작업】계단식으로 엄격히 진행하며, 각 단계의 통과 기준을 충족해야만 업그레이드합니다:

| 계단 | 내용 | 통과 기준 | 복귀 조건 |
|---|---|---|---|
| 1 | 호이스트 완전 매달림, 공중 자전거 타기 | 5분간 비정상 전류/온도 없음, 보행 주기 안정 | 이상 발생 시 즉시 정지 및 관측 확인 |
| 2 | 반 하중 (호이스트 로프 30–50% 부담) | 발바닥 접촉 전환 정상, 무게 중심 이동 없음 | 자세 각도 임계값 초과 |
| 3 | 완전 하중 정적 서기 | ≥5분 정지 서기 (즉 Stage 2 서기 관문) | 넘어질 기미 보이면 반 하중으로 복귀 |
| 4 | 제자리 걷기 | 1분간 제자리 걷기, 위치 이탈 없음 | 이탈이 보폭 절반 초과 |
| 5 | 직선 보행 | 연속 ≥3분간 명백한 편향 없음 | 요 편향 명확 시 제자리 걷기로 복귀 |
| 6 | 회전 및 속도 변화 | 좌우 회전 각 5회 성공 | 실패 시 직선 보행으로 복귀 |

규율: 2인 체제 (한 명은 원격 측정 감시, 한 명은 [비상 정지 시스템](/entry/ent_component_emergency_stop_system_2024/) 담당, 비상 정지 손은 떠나지 않음); 각 계단 첫 번째 테스트는 반드시 녹화; 한 번에 하나의 변수만 변경.

【이유】reality gap의 노출은 계층적입니다. 매달린 상태에서는 관측 및 지연 문제가 드러나고, 하중을 가한 후에는 마찰 및 접촉 모델링 문제가 드러나며, 보행을 해야 보행 및 외란 내성 문제가 드러납니다. 한 번에 완전 해제하면 모든 문제가 섞여 디버깅하기 어렵습니다. 통과 기준을 미리 기록하는 것은 "한 걸음 더 시도해보자"는 운에 맡기는 것을 방지하기 위함입니다. 복귀는 실패가 아니라 절차입니다.

【당신의 상황 분석】특정 계단에서 막힌 경우: 먼저 시뮬레이션으로 돌아가 동일한 명령을 재현합니다. 시뮬레이션에서 재현 가능 = 모델 문제 (단계 3 또는 M13으로 복귀), 시뮬레이션에서 재현 불가 = 관측/액추에이터 문제 (단계 2로 복귀). 16kg급 (Berkeley)은 넘어지면 사람을 다칠 수 있으므로 호이스트와 2인 체제는 선택 사항이 아닙니다. 3.4kg급 (ToddlerBot)도 동일한 규칙을 따릅니다. 절차는 작은 로봇에서 길러집니다.

## 5단계: 보호 전략 및 고장 등급 분류 – 넘어짐을 데이터로 전환하기

【수행할 작업】

1. **소프트 고장(복구 가능)**: 자세각 임계값 초과(예: roll/pitch > 30°, 엔지니어링 권장값, 플랫폼에 따라 검증 필요) → 댐핑 착륙/쪼그리기 유발, 관절을 댐핑 모드로 전환하여 지면 접촉 완충.
2. **하드 고장(복구 불가)**: 통신 두절, 과전류, 비상 정지 트리거 → 즉시 힘 해제 및 전원 차단; 비상 정지는 하드와이어링으로 모든 소프트웨어 체인과 독립적.
3. **넘어짐 로그**: 넘어질 때마다 시간, 자세 시퀀스, 배터리 전압, 모터 온도, 비디오 파일 번호 기록 – 넘어짐은 데이터이지 수치가 아님.
4. **구조 보호**: 취약 부품(종아리, 발목, 외부 케이싱)은 빠르게 교체 가능한 프린트 부품으로 제작. 참고 규모: ToddlerBot은 약 7회의 넘어짐을 견딜 수 있으며, 단일 수리에 21분 프린팅 + 14분 조립 소요 (toddlerbot.md).

【이유】 걷기를 배우면 반드시 넘어집니다. 차이는 넘어진 후 진단 데이터를 얻느냐, 아니면 파편을 얻느냐에 있습니다. 소프트/하드 고장 분류를 통해 로봇이 "넘어지는 법"을 배웁니다 – 댐핑 착륙은 충격을 전체 과정에 분산시켜, 단단히 땅에 부딪히는 것보다 구조 부품을 절약합니다; 로그 피드백 루프는 4단계의 모든 롤백이 기록으로 확인 가능하게 하여, 기억에 의존한 추측을 방지합니다.

【상황 분석 방법】 첫 주 테스트에서는 소프트 고장 임계값을 보수적으로 설정하여, 댐핑 착륙이 여러 번 트리거되도록 합니다. 프린트 예비 부품은 "가장 쉽게 파손되는 3개 부품 × 2"를 상시 비치; 배터리 과방전, 팽창, 넘어짐 발생 시 즉시 폐기, 규정은 [휴머노이드 로봇 리튬 이온 배터리 시스템](/entry/ent_tech_li_battery_humanoid/) 카드 참조.

## 6단계: 2단계 검증 실행 – 6개 관문을 순서대로 통과하고 데이터 기록

【수행할 작업】 [2단계 개요](../stage-2-biped.md) 검증 기준에 따라 순서대로 실행 (목록은 아래 참조). 배터리 지속 시간은 아카이브 기준으로 기대치 관리: ToddlerBot RL 보행 실제 측정 19분 후 과열로 주파수 저하 (toddlerbot.md), Berkeley 6S 4000 mAh LiPo 약 30분 (berkeley-humanoid-lite.md), BRUCE 약 20분 (bruce-westwood.md) – 동등한 규모에 도달하면 정상, "실온 만충 새 배터리"라는 환상으로 자신을 괴롭히지 마십시오.

【이유】 6개 관문은 3단계의 입장권입니다: 서기 관문은 M15에 팔을 장착한 후에도 안정적인 베이스를 보장하고, 외란 저항 관문은 추후 손 조작 시 전체 기계가 안정적으로 유지되도록 보장합니다. 전체 과정 기록(비디오 + 원격 측정 곡선)은 3단계에서 "보행 성능 저하"를 진단할 때의 기준 데이터입니다.

【상황 분석 방법】 특정 관문에서 막힘: [2단계 개요](../stage-2-biped.md)의 일반적인 문제 표를 참조하여 확인하고, **검증 현장에서 임시로 전략을 변경하지 마십시오** – 검증은 측정이지 디버깅이 아닙니다. 변경 후에는 계단 3부터 다시 재훈련하고 처음부터 다시 진행하십시오.

## 검증 기준

- [ ] 정책이 jit/ONNX로 내보내져 시뮬레이션 내에서 재테스트 시 손실 없음; 온보드 추론 지연 시간 < 제어 주기 50%.
- [ ] 관측 매핑 테이블이 문서화되고 항목별로 실제 측정 검증 완료; IMU 30초 정적 드리프트 및 엔코더 영점 재확인 통과.
- [ ] 액추에이터 지연/시정수/Kt 실제 측정 후 재입력, 도메인 무작위화 중심이 실제 측정값에 정렬됨.
- [ ] 6단계 계단 전체 과정 비디오 녹화, 각 단계 판정 기준 통과 기록 있음, 롤백 시 로그 있음.
- [ ] **서기 관문**: 지지대 없이 완전 하중 정적 서기 ≥5분, 모터 온도가 공식 제한치 미만 (명시되지 않은 모델은 공급업체에 직접 확인 필요).
- [ ] **보행 관문**: 평평한 단단한 지면에서 연속 보행 ≥10분, 넘어짐 없음, 누적 요(yaw) < 90°.
- [ ] **외란 저항 관문**: 한 손으로 가볍게 밀기(약 5–10 N, 0.5초 이내) 후 균형 회복, 넘어지지 않음, 보호적 종료 상태 진입 없음.
- [ ] **보호 관문**: 지지대 보호 하에 인위적으로 넘어짐 시나리오 유발, 비상 정지 및 댐핑 착륙 작동, 구조 부품 파손 없음.
- [ ] **안전 관문**: 비상 정지 버튼 누름부터 동력 차단까지 실제 측정 <1초; 배터리 충전 및 보관全程 리튬 배터리 안전 규정 준수.
- [ ] 넘어짐 로그 및 배터리 지속 시간 데이터(전압/온도/시간) 아카이브, 배터리 지속 시간이 아카이브 동등 규모에 도달.

## 일반적인 문제 및 진단

| 증상 | 가능한 원인 | 진단 조치 |
|---|---|---|
| 시작하자마자 넘어짐 | 관측 좌표계 오류(IMU 장착 방향 vs base 좌표계) | 2단계로 돌아가 좌표계 재확인 3단계 수행, 항목별로 출력 비교 |
| 관절 고주파 떨림, 윙윙거리는 소음 | 액추에이터 지연 미모델링 / 이득 과다 | 3단계로 돌아가 실제 지연 측정 후 재입력; PD 이득 낮춰 재테스트 |
| 시뮬레이션 챔피언이 실제 기계에서 "적응 실패" | 도메인 무작위화 중심이 실제 측정 매개변수에서 벗어남 | sysID 데이터 재입력 후 범위 좁혀 재훈련 (3단계) |
| 서기 시 한쪽으로 천천히 기울어짐 | IMU 제로 오프셋 드리프트 / 자세 필터 발산 | 30초 정적 상태에서 자세 판독값 확인; 제로 오프셋 재보정 |
| 지지대에서 너무 일찍 내려와 하중을 견디자마자 넘어짐 | 계단 건너뛰기, 판정 기준이 형식적임 | 4단계 해당 계단으로 돌아가, 판정 기준을 하나씩 통과하고 기록 남기기 |
| 몇 분 걷다가 토크가 약해지고 보행 악화 | 배터리 전압 강하 / 액추에이터 과열로 주파수 저하 | 전압 및 온도 원격 측정 확인; ToddlerBot 19분 과열 주파수 저하 아카이브 참조 |
