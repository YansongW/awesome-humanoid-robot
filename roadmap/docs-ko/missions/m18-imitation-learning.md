# M18 · 모방 학습 훈련 및 배포: 50개의 데모로 컵을 잡는 전략 만들기

**전체 위치**: M17 원격 조작 데이터셋 구축 이후, M19 엔드투엔드 작업 통합 이전. 입력은 ≥50개의 통일된 프로토콜로 수집된 데모 에피소드(다중 시점 이미지 + 관절 상태 + 동작 + 타임스탬프, Stage 3 기준)이며, 출력은 **실기 고정 프로토콜 하에서 그립 성공률 ≥70%의 그립 전략**(가중치 + 모델 카드 + 배포 지연 실측)입니다. M19는 이를 "그립 스킬"로 엔드투엔드 작업 체인에 통합합니다.

**전제 조건**: [M17 · 원격 조작 및 데이터 수집](m17-teleop-data.md) 완료(에피소드 형식 고정, 훈련/검증 세트 분할 완료, 데이터 품질 샘플링 통과); 인식 캘리브레이션 기준 충족(Stage 3 기준: 컵 3D 위치 오차 ≤1 cm); 시각 전략을 훈련할 수 있는 GPU 1개(VRAM 요구 사항은 선택한 공식 저장소 설명에 따라 확인).

이론적 배경: [행동 복제](/entry/ent_method_behavior_cloning/), [ACT](/entry/ent_method_action_chunking_transformer/), [Diffusion Policy](/entry/ent_method_diffusion_policy/) 세 장의 카드가 이 작업의 주요 내용입니다. 체계적인 논의는 [제18장 모방 학습 및 전략 학습](/wiki/chapters/chapter-18/)에서, 데이터 형식과 생태계는 [제21장 데이터 인프라](/wiki/chapters/chapter-21/) 및 [부록 B 데이터셋](/wiki/appendices/appendix-b/)에서 확인하세요.

## 1단계: baseline 우선——행동 복제로 훈련 파이프라인 실행

【무엇을 할까】가장 간단한 [행동 복제](/entry/ent_method_behavior_cloning/)(BC)로 전체 파이프라인을 먼저 실행합니다: 데이터 로드 → 이미지 + 상태 인코딩 → 프레임별 동작 회귀 → 훈련 → 검증 세트 loss → **개방 루프 재생 평가**(모델이 예측한 동작 시퀀스를 데모 실제 값과 동일한 그래프에 그려 관절별로 비교). 구성은 간단하게: 경량 시각 백본 + 회귀 헤드, 먼저 파이프라인을 실행하는 것이 목적이며, 지표를 높이는 것이 아닙니다.

【왜】BC는 대체 불가능한 두 가지 가치가 있습니다. 첫째는 **파이프라인 검증**입니다: 데이터 로드, 시간 정렬, 정규화, 평가 스크립트의 모든 버그는 BC를 사용할 때 가장 저렴하게 드러납니다——ACT를 바로 사용하면 문제가 발생했을 때 방법의 문제인지 파이프라인의 문제인지 구분하기 어렵습니다. 둘째는 **대조군**입니다: BC의 수치는 이후 모든 방법의 기준선이며, ACT/확산 전략이 BC보다 얼마나 나은지는 동일한 데이터, 동일한 평가로 설명해야 합니다. BC의 이론적 단점은 복합 오류(compounding error)입니다: 프레임별 회귀 시 각 프레임의 작은 오류가 로봇을 훈련 분포 밖의 상태로 이끌어 오류가 눈덩이처럼 누적됩니다——이것이 바로 이후 두 단계에서 억제하려는 것이며, [제18장](/wiki/chapters/chapter-18/)을 참조하세요.

【상황 분석】BC 검증 세트 loss는 낮지만 개방 루프 재생이 명백히 빗나가는 경우: 먼저 시간 정렬을 확인하고(이미지 프레임과 동작 프레임이 1–2프레임 어긋나는 것은 데이터 수집에서 가장 흔한 숨은 문제), 그 다음 동작 정규화가 잘못되었는지 확인합니다. BC 자체의 실기 성공률은 일반적으로 높지 않으므로, 집착하지 말고 파이프라인이 실행되고 수치가 기록되면 2단계로 넘어갑니다.

## 2단계: ACT——동작 청킹으로 복합 오류 억제

【무엇을 할까】[ACT(동작 청킹 Transformer)](/entry/ent_method_action_chunking_transformer/)로 전환합니다: 모델이 한 번에 약 100단계의 동작 청크(chunk)를 예측하고, 실행 시 시간적 앙상블(temporal ensemble)로 중첩 청크에 가중치를 부여하여 평활화합니다. 훈련 구성은 **공식 저장소 기본값으로 시작**합니다(학습률, 에포크 수, 청크 길이, 백본은 모두 그대로 유지); M17 데이터가 [ALOHA](/entry/ent_technology_aloha_teleoperation_system_2023/) 데이터 형식으로 구성된 경우 해당 데이터 파이프라인을 직접 재사용할 수 있습니다. 훈련 시 검증 세트 곡선을 주시합니다: train이 감소하고 val이 증가하면 과적합이므로 조기 중단합니다.

【왜】동작 청킹은 복합 오류에 대항하는 첫 번째 주요 경로입니다: 한 번에 한 프레임이 아닌 미래의 일부를 보므로 단일 프레임의 흔들림이 청크 내 평균에 흡수되어 분포 외 드리프트가 크게 줄어듭니다. ACT 카드 구경: 정밀 양팔 작업에서 80%–90% 성공률 보고(출처: ACT 카드; 작업 및 데이터 규모가 사용자 시나리오와 다르므로 참고 수준으로만 사용). 시간적 앙상블은 "여러 번 예측 투표"로 실행 평활화를 얻는 대신 추론 빈도가 감소합니다.

【상황 분석】데이터 양 50–100개: 청크 길이는 먼저 공식 기본값을 따르고, 처음부터 늘리지 마십시오——청크가 길수록 더 많은 데이터가 필요합니다. 손목/1인칭 시점이 없으면 ACT의 정밀 정렬이 현저히 나빠지므로 M17의 시점 커버리지를 다시 확인합니다. 과적합 해결 3가지: 조기 중단, 이미지 데이터 증강(이동/색상 지터링), 6단계로 돌아가 추가 데이터 수집.

## 3단계: Diffusion Policy——동일한 상황에 여러 합법적 해결책이 있을 때

【무엇을 할까】[Diffusion Policy](/entry/ent_method_diffusion_policy/)를 실행합니다: 잡음 제거 확산 과정을 사용하여 동작 시퀀스의 **분포**를 모델링하고(단일 점 회귀 대신), 잡음에서 반복적으로 샘플링하여 동작 세그먼트를 생성합니다. 마찬가지로 공식 저장소 기본 구성으로 시작하고, ACT와 **동일한 데이터, 동일한 분할**로 비교 실험을 수행하여 검증 세트 loss, 개방 루프 재생 오류 및 실기 결과 세 가지 열을 기록합니다.

【왜】회귀 기반 방법은 다중 모드 동작에 본질적으로 취약합니다: 데모에서 "왼쪽으로 돌기"와 "오른쪽으로 돌기"가 각각 절반씩 있을 때, 회귀는 "가운데로 충돌"하는 평균 동작을 학습합니다; 확산 모델링은 다중 모드 분포를 직접 표현하므로 어떤 모드를 샘플링하든 합법적인 해결책입니다(카드 참조). 대가는 훈련 및 추론 비용이 모두 더 높다는 것입니다: 다단계 잡음 제거는 더 높은 기내 추론 지연 시간을 의미하므로 배포 시 반드시 실측해야 합니다(5단계). 실증적 앵커: ToddlerBot은 Jetson Orin NX 16GB에서 300M 매개변수 확산 전략을 실행할 때 기내 추론 시간이 약 100ms입니다(출처: `data/roadmap/research/toddlerbot.md`).

두 방법 비교 빠른 참조(자세한 내용은 각 카드 참조):

| 차원 | ACT | Diffusion Policy |
|---|---|---|
| 동작 모델링 | 청킹 회귀 + 시간적 앙상블 평활화 | 잡음 제거 확산으로 동작 분포 모델링 |
| 다중 모드 동작 | 약함(회귀는 평균을 취하는 경향) | 강함(분포에서 샘플링) |
| 기내 추론 | 단일 순방향, 지연 시간 낮음 | 다단계 잡음 제거, 지연 시간 높음(실측 필요) |
| 선호 시나리오 | 해결책이 단일하고 빠른 시작이 필요할 때 | 동일한 상황에 여러 합법적 해결책이 있을 때 |

【상황 분석】작업 해결책이 단일한 경우(고정 위치에서 고정 컵 잡기): ACT로 충분하며, 확산의 이점은 적고 비용은 높으므로 이 단계를 건너뛸 수 있지만, 적어도 한 번은 대조군으로 실행하는 것이 좋습니다. 작업에 여러 잡는 방법/여러 경로가 있는 경우: 신중하게 비교 실험을 수행합니다. 두 방법의 실기 결과가 비슷할 때는 추론이 더 빠른 방법을 선택하십시오——기내 주파수가 곧 안정성입니다.

## 4단계: 평가 프로토콜——오프라인에서 모델 선별, 폐루프에서 최종 결정

【무엇을 할까】2단계 평가를 구축하고 스크립트로 고정합니다:

1. **오프라인**: 검증 세트 loss는 단지 거친 선별일 뿐입니다; 반드시 개방 루프 재생을 수행해야 합니다——각 후보 모델에 대해 5–10개의 검증 세트 에피소드를 선택하고, 예측 동작과 실제 값을 겹쳐 그래프를 그리고 비디오를 렌더링하여 하나씩 사람이 확인합니다;
2. **폐루프**: 실기 고정 프로토콜——고정 물체, 고정 위치 그리드(예: 3×3, 간격 5cm, 엔지니어링 권장 값, 사용자 작업에 따라 확인 필요), 각 그리드 포인트를 반복하여 총 20회 실험으로 성공/실패를 기록합니다; Stage 3 기준: 성공률 ≥70%;
3. **실패 분류학**: 각 실패를 네 가지 범주 중 하나로 분류하고 카운트합니다——인식 오류(감지/분할 오류), 위치 오류(자세 편차), 그립 미끄러짐(닿았지만 잡지 못함), 궤적 충돌(물체를 넘어뜨리거나 테이블에 충돌).

폐루프 실험은 각 행을 기록하고 스크립트가 자동으로 집계합니다(필드는 필요에 따라 추가/삭제 가능):

```
trial_id,grid,success,failure_class,infer_ms,notes
007,(2,1),fail,slip,96,닫히는 순간 컵 미끄러짐
```

【왜】"loss가 낮아졌다"와 "로봇이 잡을 수 있다" 사이에는 분포 이동, 시간 정렬, 실행 지연이라는 세 가지 큰 장벽이 있으며, 폐루프 실기 프로토콜만이 최종 심사입니다; 고정 프로토콜의 의미는 재현 가능하고 수평 비교가 가능하다는 것입니다——이것 없이는 모든 변경의 효과가 불확실합니다. 실패 분류학은 다음에 무엇을 보완할지 결정합니다: 인식 오류는 시점/조명 데이터 보충, 위치 오류는 캘리브레이션 재확인, 미끄러짐은 그리퍼 변경 또는 접근 단계 데이터 보충, 충돌은 장애물 시나리오 보충. 평가 방법론은 [제25장 로봇 평가 체계](/wiki/chapters/chapter-25/)를 참조하세요.

【상황 분석】20회는 "보고서에 넣을 수 있는" 최소한입니다: 그리드가 더 조밀하면 시간이 폭발하고, 더 적으면 통계적 잡음이 너무 큽니다(20회에서 성공이 1회 더 많으면 5% 포인트 차이). 평가 당일 조명, 환경 온도 및 배터리 잔량을 기록하십시오——이 세 변수 각각은 몇 % 포인트의 변동을 설명할 수 있습니다.

## 5단계: 엣지 배포 – 전략은 Jetson에, 제한을 걸어 안전 확보

【무엇을 할 것인가】전략을 탑재형 컴퓨팅 플랫폼(일반적으로 [Jetson AGX Orin](/entry/ent_component_nvidia_jetson_agx_orin_2024/), 계층별 선정 이유는 [컴퓨팅 플랫폼 선정 매뉴얼](../playbooks/compute-selection.md) 참조)에 배포하고, [엣지 VLA 추론](/entry/ent_tech_on_device_vla_inference/) 카드의 방법으로 지연 시간을 줄입니다: 양자화(FP16/INT8), 추론 엔진 최적화, 입력 해상도 저하. 그런 다음 네 가지 작업을 완료합니다:

1. **주파수 연동**: 엔드투엔드 추론 지연 시간을 측정하고 전략 주파수를 결정합니다(조작 작업은 5–10 Hz면 일반적으로 충분, 출처: 컴퓨팅 플랫폼 선정 매뉴얼); 전략 출력은 하위 고주파수 추종 루프에 전달됩니다(자체 개발 QDD 힘 제어 폐루프 250 Hz–1 kHz 수준, 동일 매뉴얼 기준);
2. **동작 제한**: 전략 출력은 작업 공간 소프트 리미트(기계적 하드 리미트보다 5–10° 작음, M10 규칙)와 속도 제한을 거친 후에야 하달됩니다;
3. **다운그레이드 전략**: 추론 시간 초과(예: >2배 제어 주기, 엔지니어링 권장값) → 현재 자세 유지; 연속 시간 초과 → 힘 해제 후 댐핑 진입([M14](m14-sim-to-real.md) 단계별);
4. **베이스라인 회귀**: 이번 배포의 지연 시간 측정값과 폐루프 성공률을 모델 카드에 기록합니다; 이후 제한, 주파수, 양자화 설정의 모든 변경은 4단계의 폐루프 프로토콜을 다시 실행해야만 효력이 발생합니다.

【왜 하는가】탑재 추론은 네트워크 가용성을 가정할 수 없습니다: Wi-Fi 지터 발생 시 클라우드 추론은 사실상 제어 불능입니다 – 지연 시간, 연결성, 프라이버시는 엣지화의 세 가지 하드 제약 조건입니다(엣지 VLA 추론 카드). 전략은 "실수하는 블랙박스"이며, 제한과 다운그레이드는 이를 우리 안에 가두는 최후의 방어선으로, M20의 보호 메커니즘 목록과 동일한 안전 로직입니다.

【당신의 상황 분석】ACT급 소형 모델은 Orin에서 일반적으로 충분한 주파수를 직접 실행할 수 있습니다; 확산 전략은 먼저 양자화한 후 측정하며, ToddlerBot의 300M 확산 전략은 Orin NX 16GB에서 약 100 ms(toddlerbot.md 아카이브)로 규모 기준점으로 사용할 수 있습니다. 지연 시간이 기준에 미치지 못하면 순서대로 줄입니다: 양자화 → 해상도 저하 → 노이즈 제거 단계/동작 블록 길이 감소, 그래도 부족하면 [Jetson Thor](/entry/ent_component_nvidia_jetson_thor/)급 플랫폼을 평가합니다. 추론 프로세스의 CPU 친화성과 우선순위는 별도로 구성하고, 제어 프로세스와 코어를 경쟁하지 않도록 합니다.

## 6단계: 반복 폐루프 – 실패한 곳에 데이터를 보충하라

【무엇을 할 것인가】고정된 반복 주기를 설정합니다: 각 라운드에서는 **하나의 변수**만 변경하고(한 종류의 데이터 보충 / 하나의 하이퍼파라미터 조정 / 하나의 백본 교체), "훈련 → 오프라인 평가 → 20회 폐루프" 전체 프로세스를 완료하여 표에 등록합니다:

| 모델 버전 | 데이터 버전 | 변경 사항 | 검증 세트 loss | 폐루프 성공률 | 실패 분류 개수 |
|---|---|---|---|---|---|
| v1.0 | d1.0(50개) | BC baseline | … | … | … |
| v1.1 | d1.1(+8개 미끄러짐 시나리오) | 방향성 추가 수집 | … | … | … |

방향성 추가 수집은 DAgger 아이디어를 사용합니다: 전략이 실패한 시나리오(예: 그리드 오른쪽 위 모서리의 미끄러짐)를 원래대로 배치하고, 원격 조작으로 해당 시나리오의 데모 5–10개를 추가 수집하여 훈련 세트에 추가합니다. 선택 사항: [LIBERO](/entry/ent_benchmark_libero/)(주제 작업 제품군 + 프로그래밍 방식 장면 변화의 단거리 데스크탑 벤치마크)를 사용하여 시뮬레이션 회귀를 수행하고, 각 변경 사항은 먼저 선별을 거친 후 실제 로봇에 적용합니다.

각 라운드 반복의 결과물은 **모델 카드**를 동시에 업데이트합니다: 데이터 버전, 훈련 설정(코드 커밋 + 주요 하이퍼파라미터), 오프라인/폐루프 지표, 배포 지연 시간 측정값, 알려진 실패 시나리오 – M19 통합과 M20 변경 관리는 모두 모델 카드를 기준으로 합니다.

【왜 하는가】모방 학습의 성능 병목은 거의 항상 데이터 분포이지 모델 용량이 아닙니다: 실패 분류학은 분포의 구멍이 어디인지 알려주며, 방향성 추가 수집은 단위 시간당 수익이 가장 큰 변경입니다. 한 번에 하나의 변수만 변경 + 버전 대응표는 석 달 후에도 "성공률이 왜 75%에서 60%로 떨어졌는지"에 답할 수 있는 유일한 방법입니다. LIBERO의 프로그래밍 방식 장면 변화는 과적합을 드러낼 수 있으며, 시뮬레이션 회귀는 "변경했더니 오히려 더 나빠진" 대부분의 경우를 실제 로봇 밖에서 차단합니다([제25장](/wiki/chapters/chapter-25/) 참조).

【당신의 상황 분석】각 라운드 추가 수집은 전체의 10–20%로 제어합니다: 너무 많으면 원래 분포가 희석되고, 너무 적으면 효과가 없습니다. 성공률이 특정 값에서 두 라운드 동안 움직이지 않으면: 실패 분류 개수를 다시 확인합니다 – 인식 오류가 절반 이상을 차지하면 문제는 데이터 또는 캘리브레이션에 있고 전략에 있지 않으므로, 계속 파라미터를 조정하는 것보다 데이터를 수정하는 것이 훨씬 저렴합니다.

## 검수 기준

- [ ] BC baseline이 실행되고, 파이프라인(로드/정렬/정규화/재생) 검증이 문서화되어 숫자가 대조군으로 남습니다.
- [ ] ACT와 Diffusion Policy를 각각 최소 한 버전씩 훈련하고, 동일 데이터 및 동일 분할로 비교표를 아카이브합니다.
- [ ] 실제 로봇 고정 프로토콜(고정 물체 + 위치 그리드 + 20회) 성공률 ≥70%, 각 성공/실패 및 실패 범주의 원본 기록이 완전합니다.
- [ ] 실패 분류학 네 가지 범주의 개수가 완전하고, 최소 한 라운드의 "방향성 추가 수집 → 재테스트" 폐루프 기록이 있습니다.
- [ ] 모델 카드가 문서화됨: 데이터 버전, 훈련 설정, 평가 지표, 배포 지연 시간 측정값.
- [ ] 훈련 및 평가 스크립트가 설정과 함께 저장소에 커밋됨(동일 데이터 버전으로 재실행 가능), 폐루프 원본 기록이 버전과 함께 아카이브됩니다.
- [ ] 엣지 배포 기준 충족: 추론 지연 시간 측정값이 전략 주파수를 만족하고, 동작 제한 및 시간 초과 다운그레이드가 실제 기계 트리거로 검증되었습니다.

## 일반적인 문제 및 문제 해결

| 증상 | 가능한 원인 | 문제 해결 조치 |
|---|---|---|
| 훈련 loss는 낮아지는데 실제 로봇은 전혀 안 됨 | 분포 이동 / 이미지와 동작 시간 정렬 오류 | 오픈 루프 재생으로 프레임별 타임스탬프 확인; 수집 측 클록 동기화 확인 |
| 동작 블록 경계에서 떨림/울퉁불퉁함 | 시간 통합 미활성화 또는 가중치 부적절 / 추론 주파수 너무 낮음 | temporal ensemble 활성화 확인; 엔드투엔드 지연 시간 측정; 블록 중첩 증가 |
| 소량 데이터 과적합(val loss 조기 상승) | 데이터 양 너무 적음 / epoch 너무 많음 | 조기 중단; 이미지 증강; 6단계 방향성 추가 수집 |
| 실제 로봇 위치가 항상 몇 cm 차이남 | 이미지 압축/다운샘플링으로 중요한 세부 정보 손실 / 외부 파라미터 캘리브레이션 드리프트 | 데이터 파이프라인 이미지 변환 확인; 핸드-아이 재캘리브레이션 |
| 추론 지연 시간 초과, 제어 떠다님 | 양자화 안 함 / 입력 해상도 너무 높음 / 추론과 제어가 CPU 경쟁 | 양자화 + 추론 엔진 최적화; 해상도 저하; 코어 바인딩 및 프로세스 우선순위 |
| 카메라/조명 변경 후 성공률 폭락 | 데이터 분포가 시점/조명에 과적합 | 수집 시 시점 및 조명 변동 도입; LIBERO 시뮬레이션 회귀로 먼저 노출 |
