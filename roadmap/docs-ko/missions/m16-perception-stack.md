# M16 · 인식 스택 구축: 로봇이 컵이 어디 있는지 볼 수 있게 하기

**전체 위치**: 팔과 엔드 이펙터 준비(M15) 이후, 원격 조작 데이터 수집(M17) 이전. 입력은 장착된 센서 하드웨어이며, 출력은 **캘리브레이션된 비전/위치 인식 스택**입니다. 즉, 장면을 입력하면 대상물의 3D 자세와 로봇 자체 위치를 출력합니다. 이 출력은 M17 데이터 수집, M18 모방 학습, M19 작업 계획의 공통 소비자입니다.

**전제 조건**: M10의 URDF와 M15의 팔 이후, 전신 TF 트리를 사용할 수 있습니다. 센서는 이미 구매했거나 구매 목록에 있습니다(선정 기준은 [센서 선정 핸드북](../playbooks/sensor-selection.md) 참조). 탑재 컴퓨팅 플랫폼이 준비되었습니다([컴퓨팅 플랫폼 선정 핸드북](../playbooks/compute-selection.md) 참조).

이론적 배경: [제5장 센싱 및 인식 하드웨어](/wiki/chapters/chapter-05/)는 센서 원리를 설명하고, [제22장 소프트웨어 미들웨어](/wiki/chapters/chapter-22/)는 통신 프레임워크를 설명합니다. 이 작업은 이들을 "픽셀 → 3D 자세" 파이프라인으로 연결하는 것입니다.

## 단계 1: 센서 구성方案 결정

【무엇을 할까】작업에 따라 세 가지 등급의 구성을 결정하고, 구매 및 설치 목록에 작성합니다:

1.  **주 비전(필수)**: 머리/가슴에 하나의 [RGB-D 카메라](/entry/ent_component_rgbd_camera/). 주류 선택은 [Intel RealSense](/entry/ent_component_intel_realsense_depth_camera_2024/) D435i(약 USD 199, 측정 범위 0.1–10 m, 내장 IMU – 공식 데이터시트 기준) 또는 D455(약 USD 299, 깊이 정밀도 <2% @ 4 m, 글로벌 셔터 – 카드 기준)입니다. 온보드 깊이 및 공간 AI가 필요하면 [ZED 스테레오 카메라](/entry/ent_component_zed_stereo_camera_2024/)를 고려하십시오(깊이 계산은 호스트 GPU 생태계에 의존하며, 가격은 공급업체에 직접 확인해야 합니다).
2.  **손목 근접 카메라(강력 권장)**: 각 손목에 하나의 소형 RGB 카메라. 손목 시점은 조작 데이터의 핵심 소스입니다. 즉, 마지막 10 cm를 잡을 때 머리 카메라는 종종 로봇 팔에 의해 가려집니다.
3.  **360° LiDAR(내비게이션에만 필요)**: 실내 방 간 내비게이션을 위해 [Livox Mid-360](/entry/ent_component_livox_mid_360_lidar_2024/) 추가(약 CNY 3,999, 265 g, 40 m @ 10% 반사율, 내장 IMU – 공식 데이터시트/카드 기준), SLAM 위치 인식 실행.

동시에 **USB 대역폭 예산**을 계산합니다: 단일 D435i의 깊이 + RGB를 모두 켜면 트래픽이 수백 MB/s 수준입니다(엔지니어링 권장 값, 해상도/프레임 속도에 따라 실제 측정). 여러 카메라를 동일한 USB 컨트롤러에 연결하면 서로 대역폭을 경쟁하여 프레임 드롭이 발생합니다. "카메라 하나당 USB 3 컨트롤러 하나를 독점"하도록 할당하거나, 해상도/프레임 속도를 낮추십시오.

【왜 필요한가】깊이 획득에는 세 가지 경로가 있습니다: 구조광/액티브 스테레오(실내 근거리 정밀도가 좋고 강한 빛에 약함), ToF, 패시브 스테레오(햇빛에 강하지만 텍스처에 의존). 장단점은 [RGB-D 카드](/entry/ent_component_rgbd_camera/)를 참조하십시오. 앵커: [ToddlerBot](/entry/ent_robot_system_toddlerbot/)은 이중 어안 카메라 + 가슴 IMU를 사용합니다([ToddlerBot 프로젝트 홈페이지](https://toddlerbot.github.io/)). D435i는 Qinglong, G1 등의 플랫폼에서 헤드 비전으로 사용됩니다(센서 선정 핸드북).

【당신의 상황 분석】"고정 자세 + 테이블 위 물체 잡기"만 수행: D435i 하나 + 손목 카메라면 충분하며, LiDAR는 순전히 낭비입니다. 테이블 가장자리까지 이동하여 잡아야 함: Mid-360 추가. 예산 한계: 먼저 D435i 하나만, 손목 카메라는 나중에 추가하되, 기계적으로 장착 위치와 케이블 배선 경로는 미리预留하십시오.

## 단계 2: 드라이버, 시간 동기화 및 TF 트리 병합

【무엇을 할까】

1.  [ROS 2](/entry/ent_software_ros_2_middleware_2024/) 드라이버 설치(RealSense는 공식 ROS 2 wrapper 사용, Livox는 공식 드라이버 사용), topic별로 확인: `ros2 topic hz`로 프레임 속도가 기준에 도달하는지 확인, `ros2 topic echo`로 타임스탬프가 단조 증가하는지 확인.
2.  **시간 동기화**: 동일한 메인 컨트롤러의 센서는 시스템 클록을 사용하여 타임스탬프를 생성합니다. 메인 컨트롤러와 Jetson 이중 시스템 배포 시 chrony/NTP를 사용하여 시간을 맞춥니다(밀리초 수준, 엔지니어링 권장 값). VIO/다중 센서 융합을 수행하는 경우 PTP 또는 하드웨어 트리거를 사용합니다.
3.  **TF 트리 병합**: 각 센서의 프레임을 M15의 전신 TF 트리에 연결합니다(URDF에 fixed joint 추가 또는 launch 파일에서 static transform 발행). `tf2_tools view_frames`를 사용하여 전체 트리가 연결되어 있고 고립된 프레임이 없는지 확인합니다.

【왜 필요한가】다중 센서 융합의 모든 알고리즘은 "외부 파라미터 알려짐, 클록 동기화"를 가정합니다. 타임스탬프가 30 ms 차이나면 움직임 중 융합 결과는 고스팅 현상이 발생합니다. VIO 발산, 포인트 클라우드 컬러링 오류 등이 이로 인해 발생합니다([센서 선정 핸드북](../playbooks/sensor-selection.md) 3절). 이중 시스템 시간 동기화가 제대로 되지 않으면 이미지와 관절 상태가 일치하지 않아 M17에서 수집한 데이터가 바로 폐기됩니다.

【당신의 상황 분석】단일 시스템 배포 + 단일 카메라: 이 단계는 반나절이면 완료됩니다. 이중 시스템(메인 컨트롤러 + Jetson): 먼저 시간 동기화를 완료한 후 다음 단계로 진행하십시오. 50 ms의 클록 오프셋을 안고 진행하지 마십시오. 이후의 모든 단계가 오염됩니다.

## 단계 3: 캘리브레이션 체인 – 내부 파라미터, 핸드-아이, 다중 센서 결합

【무엇을 할까】순서대로 세 가지 수준의 캘리브레이션을 수행하고, 모두 원클릭 스크립트로 작성하여 보관합니다:

1.  **카메라 내부 파라미터**: 체스보드/도트 패턴을 여러 자세로 20장 이상 촬영하고, 캘리브레이션 도구가 fx/fy/cx/cy와 왜곡 계수를 출력합니다. **재투영 오차가 0.5 px 수준 미만**(엔지니어링 권장 값, 캘리브레이션 도구 보고서 기준)이면 완료합니다.
2.  **핸드-아이 캘리브레이션**: 아이-투-핸드(헤드 카메라 대 베이스) 또는 아이-인-핸드(손목 카메라 대 엔드 이펙터)는 본질적으로 AX=XB를 푸는 것입니다. 캘리브레이션 보드를 카메라에 대해 10–15개의 다른 자세(회전이 충분해야 함)로 움직여 카메라에서 로봇 시스템으로의 변환을 구합니다.
3.  **카메라-LiDAR-IMU 결합 캘리브레이션**(LiDAR를 장착한 경우에만 수행): 절차는 [결합 캘리브레이션](/entry/ent_method_calibration_joint_camera_imu/) 카드를 참조하십시오: 캘리브레이션 타겟 다중 자세 촬영 → 카메라 코너 검출 + LiDAR 평면 추출 → 초기값 + ICP/비선형 최적화 → 재투영 오차 검증.

철칙: **분해, 충돌, 운송 후에는 반드시 다시 캘리브레이션해야 합니다.** 이 단계의 검수 기준: RGB 포인트 클라우드 컬러링에 명백한 오프셋이 없고, 재투영 오차 < 2 px(Stage 3 판단 기준).

【왜 필요한가】조작은 본질적으로 좌표 변환 체인입니다: 픽셀 → 카메라 좌표계 → 베이스 좌표계 → 엔드 이펙터. 어느 한 링크의 외부 파라미터가 잘못되면 허공을 잡게 됩니다(Stage 3 원문). 캘리브레이션을 스크립트로 만들지 않으면, 분해/재조립할 때마다 파라미터를 어떻게 조정했는지 기억하는 데 하루를 소비하게 됩니다.

【당신의 상황 분석】테이블 위 물체 잡기만 수행: 1+2만 완료하면 충분하며, LiDAR 결합 캘리브레이션은 내비게이션 기능을 해제할 때까지 남겨둡니다. 캘리브레이션 결과는 날짜와 버전 번호와 함께 보관하십시오. M17 데이터셋 카드에는 캘리브레이션 버전을 기록해야 합니다. 데이터와 캘리브레이션이 일치하지 않으면 수집한 데이터가 무용지물이 됩니다.

## 단계 4: 인식 알고리즘 파이프라인 – 포인트 클라우드에서 물체 자세까지

【무엇을 할까】4단계 파이프라인 구축:

1.  **포인트 클라우드 전처리**: 복셀 다운샘플링 → 패스스루 필터링(테이블 작업 공간만 남김) → 평면 분할(테이블 제거). 파라미터는 테이블 높이와 카메라 설치 각도에 따라 실제 측정하여 조정합니다.
2.  **객체 감지 두 가지 경로**:
    *   기하학적 방법: 컵 ≈ 원기둥, RANSAC 원기둥 피팅, 훈련 비용 제로, 즉시 사용 가능.
    *   학습 기반 방법: 감지/분할 모델이 마스크를 출력하며, 물체 종류를 바꿔도 기하학적 가정을 다시 작성할 필요가 없습니다.
3.  **6D 자세**: 기하학적 방법은 피팅 파라미터에서 직접 자세를 제공합니다. 학습 기반 방법은 6D 자세 추정 모델을 연결할 수 있습니다(첫 번째 버전은 "마스크 중심점 + 주축 방향" 근사치 사용 가능).
4.  **출력 정의**(인터페이스로 고정): `{객체 클래스, 3D 자세, 신뢰도}`, 발행 빈도 **10–30 Hz**(엔지니어링 권장 값, 연산 능력에 따라 실제 측정).

【왜 필요한가】첫 번째 버전은 항상 기하학적 방법을 먼저 사용하십시오. 훈련 데이터가 전혀 없을 때도 엔드-투-엔드 baseline을 제공하며, 학습 기반 방법을 위한 자동 레이블링도 제공할 수 있습니다. 출력 인터페이스를 고정하면 M17/M18/M19는 이 정의만 인식하므로, 나중에 알고리즘을 변경해도 하위 단계에 영향을 주지 않습니다.

【당신의 상황 분석】장면에 한 가지 종류의 컵만 있음: 기하학적 방법으로 충분하며, 에너지는 캘리브레이션과 위치 인식에 집중하십시오. 여러 종류의 물체로 일반화해야 함: 학습 기반 방법으로 시작하되, 먼저 기하학적 방법 결과를 대략적인 레이블로 사용하고, 처음부터 수백 장의 이미지를 수동으로 레이블링하지 마십시오.

## 5단계: 위치 파악 – 로봇이 어디에 있는가

【무엇을 할 것인가】세 가지 모드를 작업에 따라 선택:

| 모드 | 방식 | 적용 상황 |
|---|---|---|
| 다리 오도메트리 | 관절 엔코더 운동학 + 몸통 [IMU](/entry/ent_component_imu_2024/) 융합 | 정지 작업, 짧은 거리 이동 |
| VIO | 카메라 + IMU 시각 관성 오도메트리 (D435i 내장 IMU로 외장 1개 절약 가능) | 실내 고정 공간, 텍스처 충분 |
| LiDAR SLAM | Mid-360 + 내장 IMU로 LIO 수행 | 방 간 이동, 장거리 |

**드리프트 정량화**: 로봇이 폐쇄 경로를 따라 출발점(또는 표식)으로 돌아오게 한 후, 최종 자세와 출발점의 편차를 측정하고 경로 길이로 나누어 상대 드리프트율을 계산 – 이 수치는 검수에 포함되어야 함.

【왜 필요한가】고정된 방에서 테이블 위 물체 잡기에는 RGB-D 오도메트리 수준의 정밀도로 충분함 (Stage 3 기준); 방 간 이동 시 순수 자체 감각만으로는 드리프트가 발생하여 허공을 잡게 됨. 오픈소스 참고 자료는 [ORB-SLAM3](/entry/ent_paper_orb_slam3_an_accurate_open_sou_2026/) 및 [VINS-Fusion](/entry/ent_paper_vins_fusion_an_optimization_ba_2026/) 논문 카드 참조.

【상황 분석 방법】1단계(정지 상태에서 잡기)에서는 다리 오도메트리 + 시각 서보 폐루프만 유지하고, 위치 오차는 "보이는 서보"로 흡수; 이동 기능 해제 후 VIO/LIO를 추가하며, 한 번에 세 가지 모드를 모두 적용하지 말 것.

## 6단계: 연산 자원 할당 및 엔지니어링

【무엇을 할 것인가】

1. **인식은 L2 계층에서 실행**: 모든 비전/SLAM 노드는 지능형 계층(예: [Jetson AGX Orin](/entry/ent_component_nvidia_jetson_agx_orin_2024/), 최대 275 TOPS @ 64 GB 버전, 15–60 W, 개발 키트 약 USD 1,999 – 카드 기준)에 배포하며, 제어 루프 프로세스와 분리, 가능하면 기계적으로도 분리.
2. **장애 시뮬레이션**: 모든 인식 프로세스를 수동으로 종료(kill)해도 제어 루프는 중단되지 않고 로봇은 안전 상태로 전환되어야 함 (Stage 3 검수 기준).
3. **주파수/지연 시간 예산표** (엔지니어링 권장값, 실제 측정으로 검증):

| 노드 | 목표 주파수 | 단일 프레임 지연 예산 |
|---|---|---|
| 카메라 드라이버 | 30 Hz | — |
| 포인트 클라우드 전처리 | 15–30 Hz | < 30 ms |
| 검출 + 자세 | 10–30 Hz | < 100 ms |
| 위치 파악 | 10–100 Hz (모드에 따라 다름) | < 50 ms |

4. **자원 모니터링**: CPU/GPU/메모리/온도 상시 모니터링. ToddlerBot 실제 기기 추론 시 19분 만에 과열로 클럭 저하 발생 (조사 기록) – 열은 인식의 숨겨진 예산.

【왜 필요한가】제어 루프는 결정적(deterministic)이어야 하고, 인식은 처리량(throughput)이 중요하며, 혼합 실행 시 서로 성능 저하를 유발함 ([컴퓨팅 플랫폼 선택 가이드](../playbooks/compute-selection.md)의 계층적 논리). 프로세스 분리 아키텍처를 통해 인식이 중단되어도 제어가 안전하게 정지 가능 (Stage 3 14단계).

【상황 분석 방법】메인보드가 하나만 있는 경우: 최소한 프로세스 분리 + 인식 프로세스 우선순위 낮춤 + 워치독(watchdog) 구현; 듀얼 머신(메인 컨트롤러 + Jetson)이 가능하다면 사용 – ToddlerBot은 Orin NX 16GB로 300M 파라미터 확산 정책을 약 100 ms 지연, 10 Hz로 온보드 스테레오 깊이 추정 (조사 기록)하여 이 정도 규모로 인식 + 소형 정책이 충분함을 입증.

## 검수 기준

- [ ] 센서 구성 문서화: 각 센서의 장착 위치, 인터페이스, 대역폭 예산 명시; USB 컨트롤러 할당 충돌 없음.
- [ ] 모든 토픽의 프레임 속도/타임스탬프 확인 완료; 듀얼 머신 배포 시 클록 동기화 기록 존재.
- [ ] 카메라 내부 파라미터 재투영 오차 < 0.5 px 수준으로 기록; 손-눈 캘리브레이션 완료; 캘리브레이션 원클릭 스크립트 저장, 분해 후 재캘리브레이션 절차 시뮬레이션 완료.
- [ ] RGB 포인트 클라우드 색상화에 눈에 띄는 오차 없음 (재투영 < 2 px, Stage 3 기준).
- [ ] 컵 3D 위치 오차 ≤ 1 cm @ 테이블 거리 (Stage 3 기준), 10회 반복 측정 분포 기록.
- [ ] 위치 복귀 편차 수치화 (경로 길이 대비 편차), 검수 문서에 포함.
- [ ] 인식 프로세스 종료(kill) 후 제어 루프 중단 없음, 로봇 안전 상태 진입 (실제 측정 영상存档).

## 일반적인 문제 및 해결 방법

| 증상 | 가능 원인 | 해결 조치 |
|---|---|---|
| 다중 카메라 시 깊이 스트림 프레임 드롭 | USB 대역폭 부족, 여러 카메라가 동일 컨트롤러 경쟁 | `lsusb -t`로 컨트롤러 토폴로지 확인; 해상도/프레임 속도 낮춤; 독립 컨트롤러에 분배 |
| 포인트 클라우드 색상화 오차, 중첩 | 카메라-LiDAR 외부 파라미터 만료 (충돌 후) / 시간 오프셋 미보정 | 공동 캘리브레이션 재수행하여 재투영 오차 확인; 타임스탬프 출처 통일 여부 확인 |
| 손-눈 캘리브레이션이 계속 맞지 않음 | 수집 자세 회전 부족 / 타임스탬프 불일치 | 자세 다양성 증가 (특히 회전); 시간 동기화 먼저 확인 후 재캘리브레이션 |
| 투명/반사 물체 깊이에 큰 구멍 발생 | 구조광/능동 IR 방식의 고유 결함 | 관찰 각도 변경; 무광택 분말 도포; 수동 스테레오 또는 학습 기반 깊이로 전환 |
| 햇빛 아래에서 깊이 측정 실패 | 능동 IR이 햇빛에 압도됨 | 실내 사용 또는 차광; 야외 작업 시 LiDAR/수동 방식으로 전환 |
| RViz에서 TF 끊김 보고 | 프레임 이름 불일치 / static transform 미전송 | `tf2_tools view_frames`로 고립 프레임 확인; M15 명명 규칙 대조 |
| 인식 실행 몇 분 후 프레임 속도 급감 | 과열로 클럭 저하 (ToddlerBot 19분 선례) | 온도 곡선 모니터링; 전력 모드 낮춤; 방열 통로 개선 |
