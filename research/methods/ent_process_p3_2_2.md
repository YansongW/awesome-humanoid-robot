## 概述

通信网络架构（Communication network architecture）是人形机器人系统架构与机电总体设计阶段（P3）中的关键工序节点，负责在关节控制、视觉感知、AI 计算等异构通信需求之间建立统一的带宽与时延预算体系。它真正改变的不是线缆的数量，而是"每个数据包在何时必须到达何处"的确定性工程纪律——所有实时性承诺必须在设计阶段被量化论证，而非等到联调时才发现总线拥塞。

## 核心内容

### 是什么：准确定义

通信网络架构是指人形机器人内部各计算单元、执行器、传感器之间数据传输的拓扑结构、协议选择与资源分配方案。在 WBS V3 的 P3.2 电气架构设计工作包中，通信网络架构（P3.2.2）与电源架构、计算架构并列，是决定系统实时性与可扩展性的核心设计任务。

该工序节点的输出物包括通信拓扑图、协议分配表、带宽/延迟预算三份关键文档。通信拓扑图定义节点间物理连接关系；协议分配表明确每条链路采用何种总线协议（CAN-FD / EtherCAT / Ethernet / TSN）；带宽/延迟预算则量化每个数据流的周期、帧长与最坏情况时延，确保所有实时性需求在纸面上即可被验证。

在流程上，P3.2.2 遵循统一的五步法：输入梳理与目标量化（P3.2.2.1）、方案/方法设计（P3.2.2.2）、实施/原型/样件制作（P3.2.2.3）、验证与问题闭环（P3.2.2.4）、文档输出与下游交付（P3.2.2.5）。每个子任务都有明确的四级关键动作，确保设计决策可追溯、可验收。

### 为什么存在：痛点与历史定位

在早期机器人开发中，通信架构往往在硬件选型之后"自然形成"——电机驱动器用 CAN，摄像头用 USB，激光雷达用以太网，各节点各自为政。这种自发式架构在关节数量少、传感器单一的原型机上尚可工作，但当系统扩展到全身 40+ 个关节、多目视觉、力传感器阵列时，问题集中爆发：

第一，**总线冲突不可预测**。多个传感器同时上报数据时，低优先级帧可能被无限期阻塞，导致控制周期抖动。第二，**线缆数量失控**。每个传感器独立走线，整机线束重量可达数公斤，直接影响动态性能与装配效率。第三，**故障隔离困难**。单点短路可能拖垮整条总线，排查耗时以天计。

通信网络架构作为独立设计工序出现，正是为了在系统层面解决上述问题。它将"通信"从附属功能提升为与机械结构同等重要的设计对象，要求在方案冻结前完成带宽预算、时延分析与协议选型论证。它真正改变的不是某条总线的速率，而是"从传感器到执行器的端到端时延是否可被数学证明"这一工程能力。

### 原理拆解

**① 实时性 vs 带宽：两类需求的本质冲突**

人形机器人的通信需求可划分为两个极端类别。关节控制回路要求高实时性：力矩指令与位置反馈的周期通常为 1 kHz，端到端时延必须控制在亚毫秒级，且抖动（jitter）越小越好。视觉/AI 处理则要求高带宽：多目相机的原始数据流可达数百 Mbps，但对时延的敏感度远低于控制回路。

这两类需求在物理层上难以用单一协议同时满足。CAN-FD 实时性好但带宽有限（典型有效数据率约 5 Mbps 量级），Ethernet 带宽充裕但标准以太网的 CSMA/CD 机制无法保证确定性时延。EtherCAT 通过"飞读飞写"（processing on the fly）机制在标准以太网帧上实现了确定性通信，但其拓扑灵活性受限。TSN（时间敏感网络）则通过 IEEE 802.1Qbv 等标准在标准以太网上提供确定性时延保障，但实现复杂度与成本较高。

**② 双总线架构：工程上的务实解**

针对上述冲突，人形机器人领域的主流做法是"必要时双总线"：一条高实时总线（如 EtherCAT 或 CAN-FD）承载关节控制与状态反馈，一条高带宽总线（如 Ethernet 或 TSN）承载视觉与 AI 数据。两条总线在计算单元侧汇合，通过共享内存或 DMA 实现数据交换。

这种架构的带宽/延迟预算可形式化表达。设控制总线有 n 个从站，每个从站每周期传输 b 字节数据，控制周期为 T_c，则控制总线的最小带宽需求为：

$$
B_{\text{ctrl}} = \frac{n \cdot b \cdot 8}{T_c} \quad \text{(bit/s)}
$$

对于 EtherCAT，实际可用带宽还需扣除帧头、寻址与工作计数器（WC）开销。工程上通常预留 30%–50% 的带宽余量（工程判断），以应对协议开销与未来扩展。视觉总线的带宽预算则直接由相机分辨率、帧率与压缩比决定，典型值需自行确认。

**③ 关键约束的量化权衡**

通信网络架构设计受四大约束共同作用：线缆数量、EMC（电磁兼容性）、成本、可扩展性。线缆数量直接影响装配工时与弯折寿命，EMC 决定屏蔽与布线方式，成本约束协议选型（TSN 交换机价格显著高于普通交换机），可扩展性则要求拓扑结构支持后续增加传感器节点而不需重新设计。

通信网络架构的核心设计参数包括：

### 谁在用·应用案例

通信网络架构设计方法广泛应用于全尺寸双足人形机器人产品开发流程中。在 P3 系统架构与机电总体设计阶段，机械总体设计（P3.1）、电气架构设计（P3.2）、控制架构设计（P3.3）并行推进，其中 P3.2.2 通信网络架构的输出直接决定下游的线束设计、PCB 布局与控制软件接口。

典型应用场景包括：全身运动控制系统的关节总线设计（采用 EtherCAT 或 CAN-FD 组网）、头部视觉系统的数据通路设计（采用 Ethernet 或 TSN）、以及整机线束的拓扑规划（在满足 EMC 要求的前提下最小化线缆数量）。该工序的完成标准是输出通信拓扑图、协议分配表、带宽/延迟预算三份文档，并通过内部评审与版本控制后发布给下游依赖方。

### 局限与边界

通信网络架构设计存在明确的边界条件。第一，它解决的是"数据如何传输"的问题，而非"数据如何产生"——传感器选型与算法部署不在本工序范围内。第二，带宽/延迟预算是基于设计阶段的估算，实际性能需在 P3.2.2.4 验证阶段通过测试确认，若偏差超过预算需回溯修改方案。第三，双总线架构增加了系统复杂度与成本，对于关节数量少、无视觉需求的简化平台，单总线方案可能更优（工程判断）。

### 常见误区

1. **"带宽越高越好"**——错。高带宽协议（如 TSN）带来的是成本与复杂度上升，而关节控制回路真正需要的是确定性时延，而非高吞吐。选型的核心是匹配需求，而非追求参数极致。

2. **"EtherCAT 可以替代所有总线"**——错。EtherCAT 的确定性通信依赖主站与从站的严格同步，对于视觉这类大流量、非周期数据，它并非最优选择。"必要时双总线"正是对这一误区的工程纠正。

3. **"带宽预算只是纸面计算"**——错。带宽/延迟预算是后续验证与问题闭环的基准。P3.2.2.4 要求制定测试/评审计划与通过准则，执行测试并记录原始数据，输出问题清单与改进措施——没有预算，验证就失去标尺。

## Overview

Communication network architecture is a critical process node in the system architecture and electromechanical overall design phase (P3) of humanoid robot system architecture. It is responsible for establishing a unified bandwidth and latency budget system across heterogeneous communication requirements such as joint control, visual perception, and AI computing. What it truly changes is not the number of cables, but the deterministic engineering discipline of "when each data packet must arrive where"—all real-time commitments must be quantitatively demonstrated during the design phase, rather than discovering bus congestion only during integration testing.

## Content

### What It Is: Precise Definition

Communication network architecture refers to the topology, protocol selection, and resource allocation scheme for data transmission among computing units, actuators, and sensors within a humanoid robot. In work package P3.2 Electrical Architecture Design of WBS V3, communication network architecture (P3.2.2) stands alongside power architecture and computing architecture as a core design task that determines system real-time performance and scalability.

The deliverables of this process node include three key documents: communication topology diagram, protocol allocation table, and bandwidth/latency budget. The communication topology diagram defines physical connection relationships between nodes; the protocol allocation table specifies which bus protocol (CAN-FD / EtherCAT / Ethernet / TSN) is used for each link; the bandwidth/latency budget quantifies the period, frame length, and worst-case latency of each data stream, ensuring all real-time requirements can be verified on paper.

In terms of process, P3.2.2 follows a unified five-step method: input review and target quantification (P3.2.2.1), solution/method design (P3.2.2.2), implementation/prototype/sample fabrication (P3.2.2.3), verification and issue closure (P3.2.2.4), and documentation output and downstream delivery (P3.2.2.5). Each subtask has clearly defined four-level key actions, ensuring design decisions are traceable and acceptable.

### Why It Exists: Pain Points and Historical Positioning

In early robot development, communication architecture often "naturally formed" after hardware selection—motor drivers used CAN, cameras used USB, LiDAR used Ethernet, with each node operating independently. This ad-hoc architecture worked adequately on prototypes with few joints and single sensors, but when the system scaled to 40+ joints across the whole body, multi-camera vision, and force sensor arrays, problems erupted:

First, **bus conflicts were unpredictable**. When multiple sensors reported data simultaneously, low-priority frames could be blocked indefinitely, causing control cycle jitter. Second, **cable count spiraled out of control**. Each sensor had its own wiring, and the total harness weight could reach several kilograms, directly impacting dynamic performance and assembly efficiency. Third, **fault isolation was difficult**. A single short circuit could bring down an entire bus, with troubleshooting taking days.

Communication network architecture emerged as an independent design process precisely to solve these problems at the system level. It elevates "communication" from a subsidiary function to a design object as important as mechanical structure, requiring bandwidth budgeting, latency analysis, and protocol selection justification before design freeze. What it truly changes is not the speed of a particular bus, but the engineering capability of "whether end-to-end latency from sensor to actuator can be mathematically proven."

### Principle Breakdown

**① Real-time vs. Bandwidth: The Fundamental Conflict Between Two Demand Types**

Communication requirements for humanoid robots can be divided into two extreme categories. Joint control loops demand high real-time performance: torque commands and position feedback typically run at 1 kHz, end-to-end latency must be controlled at sub-millisecond levels, and jitter should be minimized. Vision/AI processing demands high bandwidth: raw data streams from multi-camera systems can reach hundreds of Mbps, but latency sensitivity is far lower than for control loops.

These two demand types are difficult to satisfy simultaneously with a single protocol at the physical layer. CAN-FD offers good real-time performance but limited bandwidth (typically on the order of 5 Mbps effective data rate); Ethernet provides ample bandwidth, but the CSMA/CD mechanism of standard Ethernet cannot guarantee deterministic latency. EtherCAT achieves deterministic communication on standard Ethernet frames through its "processing on the fly" mechanism, but its topology flexibility is limited. TSN (Time-Sensitive Networking) provides deterministic latency guarantees on standard Ethernet through standards such as IEEE 802.1Qbv, but at higher implementation complexity and cost.

**② Dual-Bus Architecture: A Pragmatic Engineering Solution**

To address the above conflict, the mainstream approach in humanoid robotics is "dual-bus when necessary": one high-real-time bus (such as EtherCAT or CAN-FD) carries joint control and status feedback, while one high-bandwidth bus (such as Ethernet or TSN) carries vision and AI data. The two buses converge at the computing unit side, exchanging data through shared memory or DMA.

The bandwidth/latency budget for this architecture can be formally expressed. Let the control bus have n slave stations, each transmitting b bytes of data per cycle, with a control period of T_c. The minimum bandwidth requirement for the control bus is:

$$
B_{\text{ctrl}} = \frac{n \cdot b \cdot 8}{T_c} \quad \text{(bit/s)}
$$

For EtherCAT, the actual usable bandwidth must also account for frame headers, addressing, and working counter (WC) overhead. In engineering practice, 30%–50% bandwidth margin is typically reserved (engineering judgment) to accommodate protocol overhead and future expansion. The vision bus bandwidth budget is directly determined by camera resolution, frame rate, and compression ratio; typical values need to be confirmed on a case-by-case basis.

**③ Quantitative Trade-offs of Key Constraints**

Communication network architecture design is governed by four constraints acting together: cable count, EMC (electromagnetic compatibility), cost, and scalability. Cable count directly affects assembly labor hours and bending fatigue life; EMC determines shielding and routing methods; cost constrains protocol selection (TSN switches are significantly more expensive than ordinary switches); scalability requires that the topology supports adding sensor nodes later without redesign.

### Who Uses It: Application Cases

Communication network architecture design methods are widely applied in the product development process of full-size bipedal humanoid robots. In the P3 system architecture and electromechanical overall design phase, mechanical overall design (P3.1), electrical architecture design (P3.2), and control architecture design (P3.3) proceed in parallel, with the output of P3.2.2 communication network architecture directly determining downstream harness design, PCB layout, and control software interfaces.

Typical application scenarios include: joint bus design for whole-body motion control systems (using EtherCAT or CAN-FD networking), data path design for head vision systems (using Ethernet or TSN), and overall harness topology planning (minimizing cable count while satisfying EMC requirements). The completion criterion for this process is the output of three documents—communication topology diagram, protocol allocation table, and bandwidth/latency budget—which are released to downstream dependents after internal review and version control.

### Limitations and Boundaries

Communication network architecture design has clear boundary conditions. First, it addresses the question of "how data is transmitted," not "how data is generated"—sensor selection and algorithm deployment fall outside this process. Second, the bandwidth/latency budget is an estimate based on the design phase; actual performance must be confirmed through testing in the P3.2.2.4 verification phase, and if deviations exceed the budget, the solution must be revisited. Third, the dual-bus architecture increases system complexity and cost; for simplified platforms with few joints and no vision requirements, a single-bus solution may be superior (engineering judgment).

### Common Misconceptions

1. **"Higher bandwidth is always better"**—Wrong. High-bandwidth protocols (such as TSN) bring increased cost and complexity, while joint control loops truly need deterministic latency, not high throughput. The core of protocol selection is matching requirements, not pursuing extreme specifications.

2. **"EtherCAT can replace all buses"**—Wrong. EtherCAT's deterministic communication relies on strict synchronization between master and slave stations; for high-volume, non-periodic data such as vision, it is not the optimal choice. "Dual-bus when necessary" is precisely the engineering correction for this misconception.

3. **"Bandwidth budgeting is just paper calculation"**—Wrong. The bandwidth/latency budget serves as the benchmark for subsequent verification and issue closure. P3.2.2.4 requires formulating test/review plans and acceptance criteria, executing tests and recording raw data, and outputting issue lists and improvement measures—without a budget, verification loses its yardstick.

## 핵심 내용

### 무엇인가: 정확한 정의

통신 네트워크 아키텍처는 휴머노이드 로봇 내부의 각 컴퓨팅 유닛, 액추에이터, 센서 간 데이터 전송의 토폴로지 구조, 프로토콜 선택 및 리소스 할당 방안을 의미합니다. WBS V3의 P3.2 전기 아키텍처 설계 작업 패키지에서 통신 네트워크 아키텍처(P3.2.2)는 전원 아키텍처, 컴퓨팅 아키텍처와 함께 시스템의 실시간성과 확장성을 결정하는 핵심 설계 작업입니다.

이 공정 노드의 산출물에는 통신 토폴로지 다이어그램, 프로토콜 할당 테이블, 대역폭/지연 예산의 세 가지 핵심 문서가 포함됩니다. 통신 토폴로지 다이어그램은 노드 간 물리적 연결 관계를 정의하고, 프로토콜 할당 테이블은 각 링크가 사용할 버스 프로토콜(CAN-FD / EtherCAT / Ethernet / TSN)을 명확히 하며, 대역폭/지연 예산은 각 데이터 흐름의 주기, 프레임 길이 및 최악의 경우 지연을 정량화하여 모든 실시간성 요구가 문서상에서 검증될 수 있도록 합니다.

프로세스 측면에서 P3.2.2는 통일된 5단계 방법을 따릅니다: 입력 정리 및 목표 정량화(P3.2.2.1), 방안/방법 설계(P3.2.2.2), 구현/프로토타입/시제품 제작(P3.2.2.3), 검증 및 문제 폐루프(P3.2.2.4), 문서 출력 및 하류 인계(P3.2.2.5). 각 하위 작업은 명확한 4단계 핵심 액션이 있어 설계 결정의 추적 가능성과 검수 가능성을 보장합니다.

### 왜 존재하는가:痛点 및 역사적 위치

초기 로봇 개발에서 통신 아키텍처는 종종 하드웨어 선정 이후 "자연스럽게 형성"되었습니다—모터 드라이버는 CAN, 카메라는 USB, 라이다는 이더넷을 사용하며 각 노드가 제각각 운영되었습니다. 이러한 자생적 아키텍처는 관절 수가 적고 센서가 단일한 프로토타입에서는 작동할 수 있었지만, 시스템이 전신 40+ 관절, 다중 시각, 힘 센서 어레이로 확장되면서 문제가 집중적으로 발생했습니다:

첫째, **버스 충돌이 예측 불가능**합니다. 여러 센서가 동시에 데이터를 보고할 때 낮은 우선순위 프레임이 무기한 차단되어 제어 주기 지터가 발생할 수 있습니다. 둘째, **케이블 수량이 통제 불능**입니다. 각 센서가 독립적으로 배선되면 전체 와이어 하니스 무게가 수 킬로그램에 달할 수 있어 동적 성능과 조립 효율에 직접 영향을 미칩니다. 셋째, **장애 격리가 어렵습니다**. 단일 지점 단락이 전체 버스를 마비시킬 수 있으며, 문제 해결에 며칠이 소요될 수 있습니다.

통신 네트워크 아키텍처가 독립적인 설계 공정으로 등장한 것은 바로 시스템 수준에서 위 문제를 해결하기 위해서입니다. 이는 "통신"을 부속 기능에서 기계 구조와 동등하게 중요한 설계 대상으로 승격시키며, 방안 확정 전에 대역폭 예산, 지연 분석 및 프로토콜 선정 타당성 검토를 완료하도록 요구합니다. 이는 실제로 특정 버스의 속도를 바꾸는 것이 아니라 "센서에서 액추에이터까지의 종단 간 지연이 수학적으로 증명 가능한지"라는 엔지니어링 역량을 확립하는 것입니다.

### 원리 분석

**① 실시간성 vs 대역폭: 두 가지 요구의 본질적 충돌**

휴머노이드 로봇의 통신 요구는 두 가지 극단적 범주로 나눌 수 있습니다. 관절 제어 루프는 높은 실시간성을 요구합니다: 토크 명령과 위치 피드백의 주기는 일반적으로 1 kHz이며, 종단 간 지연은 서브 밀리초 수준으로 제어되어야 하고 지터는 작을수록 좋습니다. 시각/AI 처리는 높은 대역폭을 요구합니다: 다중 카메라의 원시 데이터 스트림은 수백 Mbps에 달할 수 있지만, 지연 민감도는 제어 루프보다 훨씬 낮습니다.

이 두 가지 요구는 물리 계층에서 단일 프로토콜로 동시에 충족하기 어렵습니다. CAN-FD는 실시간성이 좋지만 대역폭이 제한적이며(일반적인 유효 데이터율 약 5 Mbps 수준), Ethernet은 대역폭이 충분하지만 표준 이더넷의 CSMA/CD 메커니즘은 결정론적 지연을 보장할 수 없습니다. EtherCAT은 "플라잉 리드/라이트"(processing on the fly) 메커니즘을 통해 표준 이더넷 프레임에서 결정론적 통신을 구현하지만 토폴로지 유연성이 제한됩니다. TSN(시간 민감 네트워킹)은 IEEE 802.1Qbv 등의 표준을 통해 표준 이더넷에서 결정론적 지연 보장을 제공하지만 구현 복잡성과 비용이 높습니다.

**② 이중 버스 아키텍처: 엔지니어링의 실용적 해법**

위 충돌에 대응하여 휴머노이드 로봇 분야의 주류 접근 방식은 "필요 시 이중 버스"입니다: 하나의 고실시간 버스(예: EtherCAT 또는 CAN-FD)가 관절 제어와 상태 피드백을 담당하고, 하나의 고대역폭 버스(예: Ethernet 또는 TSN)가 시각 및 AI 데이터를 담당합니다. 두 버스는 컴퓨팅 유닛 측에서 만나 공유 메모리 또는 DMA를 통해 데이터를 교환합니다.

이 아키텍처의 대역폭/지연 예산은 형식적으로 표현할 수 있습니다. 제어 버스에 n개의 슬레이브가 있고 각 슬레이브가 주기당 b바이트 데이터를 전송하며 제어 주기가 T_c라고 할 때, 제어 버스의 최소 대역폭 요구는 다음과 같습니다:

$$
B_{\text{ctrl}} = \frac{n \cdot b \cdot 8}{T_c} \quad \text{(bit/s)}
$$

EtherCAT의 경우 실제 사용 가능한 대역폭은 프레임 헤더, 주소 지정 및 워크 카운터(WC) 오버헤드를 차감해야 합니다. 엔지니어링에서는 일반적으로 프로토콜 오버헤드와 향후 확장에 대비하여 30%–50%의 대역폭 여유(엔지니어링 판단)를 예약합니다. 시각 버스의 대역폭 예산은 카메라 해상도, 프레임 속도 및 압축 비율에 의해 직접 결정되며, 일반적인 값은 자체 확인이 필요합니다.

**③ 핵심 제약의 정량적 균형**

통신 네트워크 아키텍처 설계는 네 가지 제약의 공동 작용을 받습니다: 케이블 수량, EMC(전자기 적합성), 비용, 확장성. 케이블 수량은 조립 공수와 굴곡 수명에 직접 영향을 미치고, EMC는 차폐 및 배선 방식을 결정하며, 비용은 프로토콜 선택을 제약하고(TSN 스위치 가격은 일반 스위치보다 현저히 높음), 확장성은 토폴로지 구조가 향후 센서 노드 추가를 재설계 없이 지원할 것을 요구합니다.

### 핵심 파라미터 및 사양

통신 네트워크 아키텍처의 핵심 설계 파라미터는 다음과 같습니다:

| 파라미터 | 일반 값/범위 | 설명 |
|---|---|---|
| 제어 주기 T_c | 1 kHz (1 ms) | 관절 제어 루프의 표준 주기 |
| 제어 버스 종단 간 지연 | < 1 ms | 센서 샘플링부터 액추에이터 응답까지의 총 지연 |
| 제어 버스 대역폭 여유 | 30%–50% | 프로토콜 오버헤드 및 확장 대비 예약(엔지니어링 판단) |
| 시각 버스 대역폭 | 자체 확인 필요 | 카메라 해상도, 프레임 속도 및 압축 비율에 따라 결정 |
| 후보 방안 수 | ≥ 2 | P3.2.2.2는 2개 이상의 후보 방안 형성 요구 |
| 평가 매트릭스 차원 | 자체 확인 필요 | 일반적으로 지연, 대역폭, 비용, EMC, 확장성 포함 |

### 누가 사용하는가·적용 사례

통신 네트워크 아키텍처 설계 방법은 풀사이즈 이족 휴머노이드 로봇 제품 개발 프로세스에 널리 적용됩니다. P3 시스템 아키텍처 및 전기기계 총체 설계 단계에서 기계 총체 설계(P3.1), 전기 아키텍처 설계(P3.2), 제어 아키텍처 설계(P3.3)가 병렬로 진행되며, 그중 P3.2.2 통신 네트워크 아키텍처의 출력은 하류의 와이어 하니스 설계, PCB 레이아웃 및 제어 소프트웨어 인터페이스를 직접 결정합니다.

일반적인 적용 시나리오는 다음과 같습니다: 전신 운동 제어 시스템의 관절 버스 설계(EtherCAT 또는 CAN-FD 네트워킹 사용), 헤드 시각 시스템의 데이터 경로 설계(Ethernet 또는 TSN 사용), 그리고 EMC 요구를 충족하면서 케이블 수량을 최소화하는 전체 와이어 하니스 토폴로지 계획. 이 공정의 완료 기준은 통신 토폴로지 다이어그램, 프로토콜 할당 테이블, 대역폭/지연 예산의 세 가지 문서를 출력하고 내부 검토 및 버전 관리를 거쳐 하류 의존 부서에 배포하는 것입니다.

### 한계 및 경계

통신 네트워크 아키텍처 설계에는 명확한 경계 조건이 있습니다. 첫째, 이는 "데이터가 어떻게 전송되는가"의 문제를 해결하며 "데이터가 어떻게 생성되는가"는 다루지 않습니다—센서 선정과 알고리즘 배포는 이 공정 범위에 포함되지 않습니다. 둘째, 대역폭/지연 예산은 설계 단계의 추정치이며, 실제 성능은 P3.2.2.4 검증 단계에서 테스트를 통해 확인해야 하고, 예산과의 편차가 발생하면 방안 수정으로 회귀해야 합니다. 셋째, 이중 버스 아키텍처는 시스템 복잡성과 비용을 증가시키므로, 관절 수가 적고 시각 요구가 없는 단순 플랫폼에서는 단일 버스 방안이 더 우수할 수 있습니다(엔지니어링 판단).

### 일반적인 오해

1. **"대역폭이 높을수록 좋다"**—틀림. 고대역폭 프로토콜(예: TSN)은 비용과 복잡성 증가를 가져오며, 관절 제어 루프가 실제로 필요로 하는 것은 결정론적 지연이지 높은 처리량이 아닙니다. 선정의 핵심은 요구에 맞추는 것이지 파라미터 극대화가 아닙니다.

2. **"EtherCAT이 모든 버스를 대체할 수 있다"**—틀림. EtherCAT의 결정론적 통신은 마스터와 슬레이브의 엄격한 동기화에 의존하며, 대용량 비주기 데이터인 시각 트래픽에는 최적의 선택이 아닙니다. "필요 시 이중 버스"는 바로 이 오해에 대한 엔지니어링적 교정입니다.

3. **"대역폭 예산은 문서상 계산일 뿐"**—틀림. 대역폭/지연 예산은 이후 검증과 문제 폐루프의 기준입니다. P3.2.2.4는 테스트/검토 계획과 통과 기준 수립, 테스트 실행 및 원시 데이터 기록, 문제 목록과 개선 조치 출력을 요구합니다—예산이 없으면 검증의 기준이 사라집니다.
