## 概述

仿真平台选型与导入（P7.1.1）是人形机器人仿真环境搭建的第一个工序节点，其任务是在 Isaac Sim、Gazebo、MuJoCo、RaiSim、Bullet 等候选工具中完成量化评估与方案冻结，并将机器人 URDF/SDF 模型成功导入选定平台、通过基础站立仿真验证。它真正改变的不是"挑一个仿真器装上去"这一工具选择动作，而是将仿真平台从"算法调试的附属品"提升为"产品级验证的基础设施"，使仿真能力成为与硬件能力并列的核心开发资产。

## 核心内容

### 是什么：仿真平台选型与导入的准确定义

仿真平台选型与导入属于 **方法** 类型，所属领域包括软件中间件与评测基准，价值链层级覆盖智能层与验证市场层。该工序节点以 P6 阶段输出的 URDF/SDF 模型为基础输入，通过对比 Isaac Sim、Gazebo、MuJoCo、RaiSim、Bullet 五类主流仿真工具，在考虑 License、硬件要求、sim-to-real gap、团队熟悉度等关键约束后确定最终方案，并完成模型导入与基础站立仿真验证。

从工程流程角度看，P7.1.1 在 WBS V3 中展开为五个三级子任务：P7.1.1.1 输入梳理与目标量化、P7.1.1.2 候选方案建立与评估、P7.1.1.3 实施/原型/样件制作、P7.1.1.4 验证与问题闭环、P7.1.1.5 文档输出与下游交付。每个子任务内部遵循统一的三级关键动作结构，确保选型过程可追溯、可量化、可评审。

### 为什么存在：痛点与历史定位

在人形机器人开发的早期实践中，仿真平台的选择往往依赖团队个人偏好或"哪个免费用哪个"的惯性思维，导致后期频繁更换平台、模型重复导入、算法迁移成本高昂。更深层的痛点是：人形机器人是典型的高自由度、高接触、高动态系统，其仿真对物理引擎的接触稳定性、计算并行性、传感器保真度提出了远超工业机械臂的要求——一个在静态抓取场景表现良好的仿真器，可能在双足站立或动态行走场景中产生严重的穿透与漂移。

从历史定位看，仿真平台选型是 P7 仿真阶段的第一道工序，其决策质量直接决定后续 P7.1.2 传感器模型配置、P7.1.3 接触参数标定以及 P7.2 仿真验证实施的可行性与效率。选型错误意味着后续所有仿真工作建立在错误的地基上，返工成本随阶段推进呈指数放大。因此，该工序节点在流程中被赋予"冻结方案"的强制评审节点地位，要求形成不少于 2 个候选方案、建立评估矩阵并量化打分、组织评审并冻结方案。

### 原理拆解

**① 物理引擎的接触模型：选型的核心物理判据**

人形机器人仿真的本质困难在于足底与地面的接触力学。不同仿真器采用不同的接触求解方法：Bullet 使用基于冲量的 LCP（线性互补问题）求解器，Gazebo 基于 ODE 引擎同样采用 LCP 方法；MuJoCo 采用软接触模型与凸优化求解；RaiSim 使用其特有的接触稳定算法；Isaac Sim 基于 PhysX 引擎，支持 GPU 并行刚体动力学。接触模型的差异直接表现为仿真中足底是否会发生微小穿透、站立时是否会产生抖动、行走时摩擦力是否足够真实——这些正是"基础站立仿真通过"这一完成标准所要检验的核心指标。

**② GPU 并行：从"仿真速度"到"强化学习可行性"的跨越**

传统 CPU 仿真器（如 Gazebo、Bullet）单次仿真速度受限于物理引擎的串行计算，而 Isaac Sim 等 GPU 并行仿真器可同时运行数百个并行环境。这一差异对强化学习训练具有决定性意义：人形机器人控制策略的强化学习训练需要海量交互样本，GPU 并行将训练时间从"周"级缩短到"天"级。因此，选型报告中"优先 GPU 并行"的设计思考逻辑，本质上是在为后续 P7.2 的强化学习训练预留计算可行性。

**③ sim-to-real gap：仿真保真度的终极检验**

sim-to-real gap 是指仿真环境与真实物理世界之间的差异，其来源包括：接触参数不准确、传感器噪声模型简化、执行器延迟未建模、摩擦各向异性缺失等。选型阶段对 sim-to-real gap 的考量，不是追求"绝对真实"（这在计算上不可行），而是追求"对目标任务足够真实"——例如，对于站立控制任务，足底接触刚度与摩擦系数的准确性比视觉渲染的真实性更重要。这一判断标准将贯穿后续 P7.1.3 接触参数标定与 P7.2.3 sim-to-real 迁移评估。

### 横向对比

**Isaac Sim vs. MuJoCo**：Isaac Sim 的 GPU 并行能力使其在强化学习训练场景中具有压倒性优势，但硬件要求高（需 NVIDIA GPU）；MuJoCo 的软接触模型在足式机器人控制验证中精度较高，且计算开销小，适合快速迭代控制算法。工程判断：两者可互补使用——用 MuJoCo 做控制算法的快速原型验证，用 Isaac Sim 做大规模强化学习训练。

**Gazebo vs. RaiSim**：Gazebo 的最大优势在于 ROS 生态的深度集成，适合需要与真实机器人软件栈无缝对接的场景；RaiSim 的接触稳定算法在足式机器人动态行走仿真中表现优异，但社区规模较小、文档相对有限。工程判断：若团队已有 ROS 技术栈积累，Gazebo 是低风险选择；若追求接触仿真精度，RaiSim 值得评估。

**Bullet 的定位**：Bullet 在碰撞检测与刚体动力学方面性能均衡，且开源协议宽松，适合作为备选方案或特定子任务（如抓取规划中的碰撞检测）的补充工具。其劣势在于传感器仿真与高级特性相对薄弱，不适合作为主仿真平台。

### 谁在用·应用案例

**案例一：强化学习驱动的行走控制**——某团队在 Isaac Sim 中构建双足机器人模型，利用 GPU 并行同时运行 512 个仿真环境进行 PPO 算法训练，仅用 3 天即完成从随机初始化到稳定行走的策略收敛（按语料数据推算，若使用 CPU 仿真器，同等训练量需数周）。该案例验证了"优先 GPU 并行"选型逻辑的实际收益。

**案例二：ROS 生态的仿真验证**——某团队基于 Gazebo 搭建仿真环境，复用真实机器人上的 ROS 节点（包括 SLAM、路径规划、运动控制），在仿真中完成整机软件栈的集成测试，发现并修复了 3 处节点通信时序问题，避免了在实物样机上的调试成本。该案例体现了 Gazebo 在软件栈验证中的独特价值。

**案例三：接触参数标定的前置验证**——某团队在 MuJoCo 中完成足底接触刚度与摩擦系数的初步标定，再将标定参数迁移至 Isaac Sim 进行大规模训练，有效减少了 sim-to-real gap。该案例展示了"不同场景可互补使用"的设计思考逻辑。

### 局限与边界

**计算资源边界**：GPU 并行仿真虽然大幅提升训练效率，但对硬件投入要求较高——Isaac Sim 的流畅运行需要中高端 NVIDIA GPU，这对预算有限的团队构成实际门槛。工程判断：若团队无 GPU 资源，可优先选择 MuJoCo 或 RaiSim 作为替代方案。

**仿真保真度边界**：无论选择何种仿真器，sim-to-real gap 都无法完全消除。仿真平台验证通过不等于实物验证通过，P7 阶段的仿真结果必须经过 P10 实机测试的最终检验。该工序节点的完成标准"基础站立仿真通过"仅代表仿真环境搭建成功，不代表控制算法已具备实物部署条件。

**模型导入边界**：URDF/SDF 模型导入并非简单的文件拷贝，涉及关节类型映射、碰撞体简化、惯性参数校验等工程细节。不同仿真器对模型格式的支持程度存在差异，导入失败或仿真异常时需回溯检查模型文件本身的质量。

### 常见误区

1. **"仿真器越高级越好"**——错。选型的核心是匹配任务需求与团队能力。一个没有 GPU 资源的团队选择 Isaac Sim，不如选择 MuJoCo 更务实；一个以 ROS 集成为主的团队，Gazebo 可能是比 Isaac Sim 更合适的选择。选型报告的价值在于"量化评估后的理性决策"，而非"追求参数表上的最优"。

2. **"选型是一次性决策"**——错。仿真平台选型应保持"主平台 + 备选平台"的弹性结构。随着项目推进，主平台可能因新需求（如新增传感器类型、需要更精细的接触模型）而暴露不足，此时备选平台的评估数据可加速切换决策。

3. **"基础站立仿真通过 = 仿真环境搭建完成"**——错。基础站立仿真通过仅验证了模型导入正确性与物理引擎基本稳定性，后续还需完成传感器模型配置（P7.1.2）、接触参数标定（P7.1.3）等工序，才能构建完整的仿真验证能力。

## Overview

Simulation platform selection and import (P7.1.1) is the first process node in building the humanoid robot simulation environment. Its task is to complete quantitative evaluation and solution freezing among candidate tools such as Isaac Sim, Gazebo, MuJoCo, RaiSim, and Bullet, successfully import the robot URDF/SDF model into the selected platform, and verify it through basic standing simulation. What it truly changes is not the tool-selection action of "picking a simulator and installing it," but rather elevating the simulation platform from an "accessory for algorithm debugging" to "infrastructure for product-level verification," making simulation capability a core development asset on par with hardware capability.

## Content

### What It Is: Precise Definition of Simulation Platform Selection and Import

Simulation platform selection and import belongs to the **method** type, spanning the domains of software middleware and evaluation benchmarks, with value chain coverage across the intelligence layer and the verification market layer. This process node takes the URDF/SDF model output from the P6 phase as its foundational input, compares five mainstream simulation tools—Isaac Sim, Gazebo, MuJoCo, RaiSim, and Bullet—and determines the final solution after considering key constraints such as License, hardware requirements, sim-to-real gap, and team familiarity, then completes model import and basic standing simulation verification.

From an engineering process perspective, P7.1.1 is decomposed into five third-level subtasks in WBS V3: P7.1.1.1 Input review and target quantification, P7.1.1.2 Candidate solution establishment and evaluation, P7.1.1.3 Implementation/prototype/sample fabrication, P7.1.1.4 Verification and issue closure, and P7.1.1.5 Documentation output and downstream delivery. Each subtask follows a unified three-level key action structure internally, ensuring that the selection process is traceable, quantifiable, and reviewable.

### Why It Exists: Pain Points and Historical Positioning

In early humanoid robot development practices, simulation platform selection often relied on team personal preferences or the inertia of "use whichever is free," leading to frequent platform changes, repeated model imports, and high algorithm migration costs in later stages. The deeper pain point is that humanoid robots are typical high-degree-of-freedom, high-contact, high-dynamic systems whose simulation demands on physics engines—contact stability, computational parallelism, and sensor fidelity—far exceed those of industrial robotic arms. A simulator that performs well in static grasping scenarios may exhibit severe penetration and drift in bipedal standing or dynamic walking scenarios.

From a historical positioning perspective, simulation platform selection is the first process in the P7 simulation phase, and its decision quality directly determines the feasibility and efficiency of subsequent P7.1.2 sensor model configuration, P7.1.3 contact parameter calibration, and P7.2 simulation verification implementation. A wrong selection means all subsequent simulation work is built on an incorrect foundation, with rework costs amplifying exponentially as the phase progresses. Therefore, this process node is assigned the mandatory review status of "solution freezing" in the workflow, requiring the formation of no fewer than 2 candidate solutions, the establishment of an evaluation matrix with quantitative scoring, and the organization of reviews to freeze the solution.

### Principle Breakdown

**① Physics Engine Contact Models: The Core Physical Criterion for Selection**

The fundamental difficulty in humanoid robot simulation lies in the contact mechanics between the foot sole and the ground. Different simulators employ different contact solution methods: Bullet uses an impulse-based LCP (Linear Complementarity Problem) solver; Gazebo, based on the ODE engine, also uses the LCP method; MuJoCo adopts a soft contact model with convex optimization; RaiSim uses its proprietary contact-stabilizing algorithm; Isaac Sim, based on the PhysX engine, supports GPU-parallel rigid body dynamics. Differences in contact models directly manifest as whether the foot sole experiences minor penetration, whether jitter occurs during standing, and whether friction is realistic enough during walking—these are precisely the core indicators that the completion criterion of "basic standing simulation passed" is designed to test.

**② GPU Parallelism: The Leap from "Simulation Speed" to "Reinforcement Learning Feasibility"**

Traditional CPU simulators (e.g., Gazebo, Bullet) have single-simulation speeds limited by the serial computation of the physics engine, whereas GPU-parallel simulators like Isaac Sim can run hundreds of parallel environments simultaneously. This difference is decisive for reinforcement learning training: training humanoid control policies via reinforcement learning requires massive interaction samples, and GPU parallelism reduces training time from "weeks" to "days." Therefore, the design rationale of "prioritizing GPU parallelism" in the selection report is essentially reserving computational feasibility for subsequent P7.2 reinforcement learning training.

**③ Sim-to-Real Gap: The Ultimate Test of Simulation Fidelity**

The sim-to-real gap refers to the difference between the simulation environment and the real physical world, with sources including inaccurate contact parameters, simplified sensor noise models, unmodeled actuator latency, and missing friction anisotropy. The consideration of sim-to-real gap during the selection phase is not about pursuing "absolute realism" (which is computationally infeasible), but rather "sufficient realism for the target task"—for example, for a standing control task, the accuracy of foot sole contact stiffness and friction coefficients matters more than the realism of visual rendering. This judgment standard will carry through subsequent P7.1.3 contact parameter calibration and P7.2.3 sim-to-real transfer evaluation.

### Horizontal Comparison

**Isaac Sim vs. MuJoCo**: Isaac Sim's GPU parallelism gives it an overwhelming advantage in reinforcement learning training scenarios, but it has high hardware requirements (NVIDIA GPU required); MuJoCo's soft contact model offers high accuracy in legged robot control verification and has low computational overhead, making it suitable for rapid iteration of control algorithms. Engineering judgment: the two can be used complementarily—use MuJoCo for rapid prototyping of control algorithms and Isaac Sim for large-scale reinforcement learning training.

**Gazebo vs. RaiSim**: Gazebo's greatest strength lies in its deep integration with the ROS ecosystem, making it suitable for scenarios requiring seamless interfacing with real robot software stacks; RaiSim's contact-stabilizing algorithm excels in dynamic walking simulation of legged robots, but its community is smaller and documentation is relatively limited. Engineering judgment: if the team already has accumulated ROS technology stack expertise, Gazebo is a low-risk choice; if contact simulation accuracy is the priority, RaiSim is worth evaluating.

**Bullet's Positioning**: Bullet offers balanced performance in collision detection and rigid body dynamics, with a permissive open-source license, making it suitable as a backup option or a supplementary tool for specific subtasks (e.g., collision detection in grasp planning). Its disadvantage lies in relatively weak sensor simulation and advanced features, making it unsuitable as a primary simulation platform.

### Who Uses It: Application Cases

**Case 1: Reinforcement Learning-Driven Walking Control**—A team built a bipedal robot model in Isaac Sim, used GPU parallelism to run 512 simulation environments simultaneously for PPO algorithm training, and achieved policy convergence from random initialization to stable walking in just 3 days (based on corpus data estimates, the same training volume would take weeks with a CPU simulator). This case validates the practical benefits of the "prioritize GPU parallelism" selection logic.

**Case 2: Simulation Verification in the ROS Ecosystem**—A team built a simulation environment based on Gazebo, reused ROS nodes from the real robot (including SLAM, path planning, and motion control), completed integration testing of the full software stack in simulation, and discovered and fixed 3 node communication timing issues, avoiding debugging costs on the physical prototype. This case demonstrates Gazebo's unique value in software stack verification.

**Case 3: Pre-Verification for Contact Parameter Calibration**—A team completed preliminary calibration of foot sole contact stiffness and friction coefficients in MuJoCo, then transferred the calibrated parameters to Isaac Sim for large-scale training, effectively reducing the sim-to-real gap. This case illustrates the design rationale that "different scenarios can be used complementarily."

### Limitations and Boundaries

**Computational Resource Boundary**: While GPU-parallel simulation significantly improves training efficiency, it imposes high hardware investment requirements—smooth operation of Isaac Sim requires a mid-to-high-end NVIDIA GPU, which poses a practical barrier for teams with limited budgets. Engineering judgment: if the team lacks GPU resources, MuJoCo or RaiSim can be prioritized as alternatives.

**Simulation Fidelity Boundary**: Regardless of the simulator chosen, the sim-to-real gap cannot be completely eliminated. Passing simulation platform verification does not equate to passing physical verification; P7-phase simulation results must undergo final validation through P10 real-machine testing. The completion criterion of "basic standing simulation passed" for this process node only indicates successful simulation environment setup, not that the control algorithm is ready for physical deployment.

**Model Import Boundary**: URDF/SDF model import is not a simple file copy; it involves engineering details such as joint type mapping, collision body simplification, and inertia parameter validation. Different simulators have varying levels of support for model formats, and import failures or simulation anomalies require tracing back to check the quality of the model file itself.

### Common Misconceptions

1. **"The more advanced the simulator, the better"**—Wrong. The core of selection is matching task requirements with team capabilities. A team without GPU resources choosing Isaac Sim is less pragmatic than choosing MuJoCo; a team focused on ROS integration may find Gazebo more suitable than Isaac Sim. The value of a selection report lies in "rational decision-making after quantitative evaluation," not in "pursuing the best on a specification sheet."

2. **"Selection is a one-time decision"**—Wrong. Simulation platform selection should maintain a flexible structure of "primary platform + backup platform." As the project progresses, the primary platform may expose shortcomings due to new requirements (e.g., new sensor types, need for finer contact models), at which point evaluation data for the backup platform can accelerate the switching decision.

3. **"Passing basic standing simulation = simulation environment setup complete"**—Wrong. Passing basic standing simulation only verifies model import correctness and basic physics engine stability. Subsequent processes such as sensor model configuration (P7.1.2) and contact parameter calibration (P7.1.3) are still required to build complete simulation verification capability.

- `ent_process_p7_1_3` — Adjacent process in the same family: contact and friction parameter calibration (parallel process within the same work package).

## 개요

시뮬레이션 플랫폼 선정 및 가져오기(P7.1.1)는 휴머노이드 로봇 시뮬레이션 환경 구축의 첫 번째 공정 노드로, Isaac Sim, Gazebo, MuJoCo, RaiSim, Bullet 등의 후보 도구 중에서 정량적 평가와 방안 확정을 완료하고, 로봇 URDF/SDF 모델을 선택된 플랫폼에 성공적으로 가져와 기본 기립 시뮬레이션 검증을 수행하는 작업입니다. 이 공정이 실제로 바꾸는 것은 "시뮬레이터 하나 골라 설치하기"라는 도구 선택 행위가 아니라, 시뮬레이션 플랫폼을 "알고리즘 디버깅의 부속물"에서 "제품급 검증의 인프라"로 승격시켜, 시뮬레이션 역량을 하드웨어 역량과 나란히 서는 핵심 개발 자산으로 만드는 것입니다.

## 핵심 내용

### 무엇인가: 시뮬레이션 플랫폼 선정 및 가져오기의 정확한 정의

시뮬레이션 플랫폼 선정 및 가져오기는 **방법** 유형에 속하며, 소속 분야는 소프트웨어 미들웨어와 평가 벤치마크를 포함하고, 가치사슬 계층은 지능 계층과 검증 시장 계층을 포괄합니다. 이 공정 노드는 P6 단계에서 출력된 URDF/SDF 모델을 기본 입력으로 삼아, Isaac Sim, Gazebo, MuJoCo, RaiSim, Bullet 다섯 가지 주요 시뮬레이션 도구를 비교하고, License, 하드웨어 요구사항, sim-to-real gap, 팀 친숙도 등의 핵심 제약 조건을 고려한 후 최종 방안을 확정하며, 모델 가져오기와 기본 기립 시뮬레이션 검증을 완료합니다.

엔지니어링 프로세스 관점에서 P7.1.1은 WBS V3에서 다섯 개의 3차 하위 작업으로 전개됩니다: P7.1.1.1 입력 정리 및 목표 정량화, P7.1.1.2 후보 방안 수립 및 평가, P7.1.1.3 구현/프로토타입/시제품 제작, P7.1.1.4 검증 및 문제 폐루프, P7.1.1.5 문서 출력 및 하류 전달. 각 하위 작업 내부는 통일된 3차 핵심 액션 구조를 따르며, 선정 과정이 추적 가능하고 정량화 가능하며 검토 가능하도록 보장합니다.

### 왜 존재하는가:痛点과 역사적 위치

휴머노이드 로봇 개발의 초기 실무에서 시뮬레이션 플랫폼 선택은 종종 팀 개인의 선호나 "무료면 그냥 쓰자"는 관성적 사고에 의존하여, 후기에 플랫폼을 자주 교체하고, 모델을 반복적으로 가져오며, 알고리즘 마이그레이션 비용이 높아지는 결과를 초래했습니다. 더 깊은痛点은 휴머노이드 로봇이 전형적인 고자유도, 고접촉, 고동적 시스템이라는 점으로, 그 시뮬레이션은 물리 엔진의 접촉 안정성, 계산 병렬성, 센서 충실도에 대해 산업용 로봇 팔을 훨씬 초과하는 요구를 제기한다는 것입니다. 정적 그리핑 시나리오에서 잘 작동하는 시뮬레이터가 이족 기립이나 동적 보행 시나리오에서는 심각한 관통과 드리프트를 발생시킬 수 있습니다.

역사적 위치에서 볼 때, 시뮬레이션 플랫폼 선정은 P7 시뮬레이션 단계의 첫 번째 공정이며, 그 결정 품질은 후속 P7.1.2 센서 모델 구성, P7.1.3 접촉 파라미터 보정, 그리고 P7.2 시뮬레이션 검증 구현의 실현 가능성과 효율성을 직접 결정합니다. 선정 오류는 이후 모든 시뮬레이션 작업이 잘못된 기반 위에 세워지는 것을 의미하며, 재작업 비용은 단계가 진행됨에 따라 지수적으로 확대됩니다. 따라서 이 공정 노드는 프로세스에서 "방안 확정"을 위한 강제 검토 노드 지위를 부여받아, 2개 이상의 후보 방안을 구성하고, 평가 매트릭스를 수립하여 정량적으로 점수를 매기고, 검토를 조직하여 방안을 확정하도록 요구합니다.

### 원리 분해

**① 물리 엔진의 접촉 모델: 선정의 핵심 물리 판단 기준**

휴머노이드 로봇 시뮬레이션의 본질적 어려움은 발바닥과 지면 사이의 접촉 역학에 있습니다. 서로 다른 시뮬레이터는 서로 다른 접촉 해법을 사용합니다: Bullet은 충격량 기반 LCP(선형 상보 문제) 해석기를 사용하고, Gazebo는 ODE 엔진을 기반으로 역시 LCP 방법을 사용합니다; MuJoCo는 소프트 접촉 모델과 볼록 최적화 해법을 사용합니다; RaiSim은 고유의 접촉 안정화 알고리즘을 사용합니다; Isaac Sim은 PhysX 엔진을 기반으로 GPU 병렬 강체 동역학을 지원합니다. 접촉 모델의 차이는 시뮬레이션에서 발바닥이 미세한 관통을 일으키는지, 기립 시 떨림이 발생하는지, 보행 시 마찰력이 충분히 현실적인지로 직접 나타나며, 이는 바로 "기본 기립 시뮬레이션 통과"라는 완료 기준이 검증하려는 핵심 지표입니다.

**② GPU 병렬: "시뮬레이션 속도"에서 "강화학습 실현 가능성"으로의 도약**

기존 CPU 시뮬레이터(예: Gazebo, Bullet)의 단일 시뮬레이션 속도는 물리 엔진의 직렬 계산에 제한되는 반면, Isaac Sim과 같은 GPU 병렬 시뮬레이터는 수백 개의 병렬 환경을 동시에 실행할 수 있습니다. 이 차이는 강화학습 훈련에 결정적 의미를 갖습니다: 휴머노이드 로봇 제어 정책의 강화학습 훈련은 대량의 상호작용 샘플을 필요로 하며, GPU 병렬은 훈련 시간을 "주" 단위에서 "일" 단위로 단축합니다. 따라서 선정 보고서에서 "GPU 병렬 우선"이라는 설계 사고 논리는 본질적으로 후속 P7.2의 강화학습 훈련을 위한 계산 실현 가능성을 미리 확보하는 것입니다.

**③ sim-to-real gap: 시뮬레이션 충실도의 궁극적 검증**

sim-to-real gap은 시뮬레이션 환경과 실제 물리 세계 사이의 차이를 의미하며, 그 원인에는 접촉 파라미터 부정확성, 센서 노이즈 모델 단순화, 액추에이터 지연 미모델링, 마찰 이방성 부재 등이 포함됩니다. 선정 단계에서 sim-to-real gap에 대한 고려는 "절대적 현실성"(이는 계산상 불가능)을 추구하는 것이 아니라 "목표 작업에 대해 충분히 현실적인" 것을 추구하는 것입니다. 예를 들어, 기립 제어 작업의 경우 발바닥 접촉 강성과 마찰 계수의 정확성이 시각적 렌더링의 현실성보다 더 중요합니다. 이 판단 기준은 후속 P7.1.3 접촉 파라미터 보정과 P7.2.3 sim-to-real 전이 평가에 걸쳐 관통합니다.

### 횡적 비교

**Isaac Sim vs. MuJoCo**: Isaac Sim의 GPU 병렬 능력은 강화학습 훈련 시나리오에서 압도적 우위를 제공하지만, 하드웨어 요구사항이 높습니다(NVIDIA GPU 필요); MuJoCo의 소프트 접촉 모델은 족식 로봇 제어 검증에서 정확도가 높고 계산 오버헤드가 작아 제어 알고리즘의 빠른 반복에 적합합니다. 엔지니어링 판단: 둘은 상호 보완적으로 사용할 수 있습니다 — MuJoCo로 제어 알고리즘의 빠른 프로토타입 검증을, Isaac Sim으로 대규모 강화학습 훈련을 수행합니다.

**Gazebo vs. RaiSim**: Gazebo의 최대 장점은 ROS 생태계와의 깊은 통합으로, 실제 로봇 소프트웨어 스택과의 원활한 연동이 필요한 시나리오에 적합합니다; RaiSim의 접촉 안정화 알고리즘은 족식 로봇의 동적 보행 시뮬레이션에서 우수한 성능을 보이지만, 커뮤니티 규모가 작고 문서가 상대적으로 제한적입니다. 엔지니어링 판단: 팀이 이미 ROS 기술 스택을 축적했다면 Gazebo는 저위험 선택입니다; 접촉 시뮬레이션 정확도를 추구한다면 RaiSim을 평가할 가치가 있습니다.

**Bullet의 위치**: Bullet은 충돌 감지와 강체 동역학에서 균형 잡힌 성능을 보이고 오픈소스 라이선스가 관대하여, 예비 방안이나 특정 하위 작업(예: 그리핑 계획의 충돌 감지)의 보조 도구로 적합합니다. 단점은 센서 시뮬레이션과 고급 기능이 상대적으로 취약하여 주 시뮬레이션 플랫폼으로는 부적합하다는 점입니다.

### 누가 사용하는가·응용 사례

**사례 1: 강화학습 기반 보행 제어** — 한 팀이 Isaac Sim에서 이족 로봇 모델을 구축하고, GPU 병렬로 512개의 시뮬레이션 환경을 동시에 실행하여 PPO 알고리즘을 훈련했으며, 단 3일 만에 무작위 초기화에서 안정적 보행까지의 정책 수렴을 완료했습니다(말뭉치 데이터 기준 추산, CPU 시뮬레이터를 사용했다면 동일한 훈련량에 수 주가 필요). 이 사례는 "GPU 병렬 우선" 선정 논리의 실제 이점을 검증합니다.

**사례 2: ROS 생태계의 시뮬레이션 검증** — 한 팀이 Gazebo 기반 시뮬레이션 환경을 구축하고, 실제 로봇의 ROS 노드(SLAM, 경로 계획, 운동 제어 포함)를 재사용하여 시뮬레이션에서 전체 소프트웨어 스택의 통합 테스트를 완료하고, 3건의 노드 통신 타이밍 문제를 발견 및 수정하여 실물 프로토타입에서의 디버깅 비용을 피했습니다. 이 사례는 Gazebo가 소프트웨어 스택 검증에서 지니는 독특한 가치를 보여줍니다.

**사례 3: 접촉 파라미터 보정의 사전 검증** — 한 팀이 MuJoCo에서 발바닥 접촉 강성과 마찰 계수의 초기 보정을 완료한 후, 보정된 파라미터를 Isaac Sim으로 전이하여 대규모 훈련을 수행함으로써 sim-to-real gap을 효과적으로 줄였습니다. 이 사례는 "시나리오에 따라 상호 보완적으로 사용 가능"한 설계 사고 논리를 보여줍니다.

### 한계와 경계

**계산 자원 경계**: GPU 병렬 시뮬레이션은 훈련 효율을 크게 향상시키지만, 하드웨어 투자 요구사항이 높습니다 — Isaac Sim의 원활한 실행에는 중상급 NVIDIA GPU가 필요하며, 이는 예산이 제한된 팀에게 실질적 장벽이 됩니다. 엔지니어링 판단: 팀에 GPU 자원이 없다면 MuJoCo나 RaiSim을 대체 방안으로 우선 선택할 수 있습니다.

**시뮬레이션 충실도 경계**: 어떤 시뮬레이터를 선택하든 sim-to-real gap은 완전히 제거될 수 없습니다. 시뮬레이션 플랫폼 검증 통과가 실물 검증 통과를 의미하지 않으며, P7 단계의 시뮬레이션 결과는 반드시 P10 실기 테스트의 최종 검증을 거쳐야 합니다. 이 공정 노드의 완료 기준인 "기본 기립 시뮬레이션 통과"는 시뮬레이션 환경 구축 성공만을 의미하며, 제어 알고리즘이 실물 배포 조건을 갖추었다는 의미는 아닙니다.

**모델 가져오기 경계**: URDF/SDF 모델 가져오기는 단순한 파일 복사가 아니라, 관절 유형 매핑, 충돌체 단순화, 관성 파라미터 검증 등의 엔지니어링 세부 사항을 포함합니다. 서로 다른 시뮬레이터의 모델 형식 지원 수준에는 차이가 있으며, 가져오기 실패나 시뮬레이션 이상 시 모델 파일 자체의 품질을 역추적하여 점검해야 합니다.

### 흔한 오해

1. **"시뮬레이터가 고급일수록 좋다"** — 틀림. 선정의 핵심은 작업 요구사항과 팀 역량의 매칭입니다. GPU 자원이 없는 팀이 Isaac Sim을 선택하는 것보다 MuJoCo를 선택하는 것이 더 실용적입니다; ROS 통합 중심의 팀에게는 Gazebo가 Isaac Sim보다 더 적합한 선택일 수 있습니다. 선정 보고서의 가치는 "정량적 평가 후의 합리적 결정"에 있으며, "파라미터 표상의 최적"을 추구하는 것이 아닙니다.

2. **"선정은 일회성 결정이다"** — 틀림. 시뮬레이션 플랫폼 선정은 "주 플랫폼 + 예비 플랫폼"의 탄력적 구조를 유지해야 합니다. 프로젝트가 진행됨에 따라 주 플랫폼이 새로운 요구사항(예: 새로운 센서 유형 추가, 더 정밀한 접촉 모델 필요)으로 인해 한계를 드러낼 수 있으며, 이때 예비 플랫폼의 평가 데이터가 전환 결정을 가속화할 수 있습니다.

3. **"기본 기립 시뮬레이션 통과 = 시뮬레이션 환경 구축 완료"** — 틀림. 기본 기립 시뮬레이션 통과는 모델 가져오기 정확성과 물리 엔진의 기본 안정성만 검증하며, 후속으로 센서 모델 구성(P7.1.2), 접촉 파라미터 보정(P7.1.3) 등의 공정을 완료해야 완전한 시뮬레이션 검증 역량을 구축할 수 있습니다.

### 관련 지식

- `ent_process_p7` — 시뮬레이션 플랫폼 구축 및 검증 단계(P7)의 전체 프로세스와 작업 패키지 구분, 본 공정 노드는 그 첫 번째 하위 작업입니다.
- `ent_process_p7_1_2` — 동일 계열 인접 공정: 센서 및 액추에이터 모델 구성(동일 작업 패키지 내 병렬 공정).
- `ent_process_p7_1_3` — 동일 계열 인접 공정: 접촉 및 마찰 파라미터 보정(동일 작업 패키지 내 병렬 공정).
