## 概述

硬件在环测试（Hardware-in-the-Loop, HIL）是一种将真实硬件控制器与被控对象的实时仿真模型相连、在闭环中验证控制软件正确性与性能的测试方法。它真正改变的不是"测试地点"，而是"测试的时机与风险结构"——让控制软件在物理样机存在之前就能在真实处理器上、以真实时序运行，从而把灾难性故障从现场转移到实验室。HIL 位于组装集成测试领域（domain 04）的中游环节，是连接纯仿真（SIL/MIL）与整机实测之间的关键验证层。

## 核心内容

### 是什么：准确定义

HIL 的核心结构是**真实硬件 + 虚拟被控对象**。被测对象（Device Under Test, DUT）通常是真实的控制器硬件——人形机器人中的主控计算单元（如执行 MPC 或 WBC 的工控机或嵌入式板卡）——它通过真实的总线接口（如 EtherCAT、CAN）连接到一个实时仿真机。仿真机以固定步长实时解算被控对象的动力学模型（如整机多刚体动力学、电机驱动模型、接触模型），并将传感器信号（关节角度、力矩、IMU 数据）反馈给控制器，形成闭环。

$$
\text{HIL 闭环:}\quad \underbrace{\text{真实控制器}}_{\text{真实硬件}} \;\xrightarrow{\text{控制指令}}\; \underbrace{\text{实时仿真机}}_{\text{虚拟被控对象}} \;\xrightarrow{\text{传感器反馈}}\; \text{真实控制器}
$$

关键区别在于：**控制器不知道（也不关心）自己连接的是真机还是仿真机**——它看到的只是总线上的传感器数据流。这正是 HIL 的哲学：让被测对象"以为"自己在控制一台真实的机器人。

### 为什么存在：痛点与历史定位

在人形机器人开发中，纯仿真（SIL）无法验证控制软件在真实硬件上的时序行为——编译器优化、中断延迟、总线通信抖动、浮点精度差异，这些在 x86 仿真环境里完全被掩盖。而直接上真机测试则面临三重困境：

1. **安全风险**：人形机器人是高能量、欠驱动系统，控制软件的一个 bug 可能导致整机摔倒、损坏甚至伤人。
2. **成本高昂**：每一次真机测试都消耗硬件寿命，且需要安全防护设施与操作人员。
3. **不可重复性**：真机测试受环境、磨损、电池状态影响，难以精确复现同一场景。

HIL 的历史定位正是填补这一鸿沟：它把"控制软件在真实处理器上运行"这一事实保留下来，同时把"被控对象"替换为可重复、可注入故障、可加速时间的实时仿真模型。在项目工作流中，HIL 被明确列为 CI/CD 与仿真测试链的关键环节——与 GitLab CI、Docker、SIL/HIL 自动化测试、代码覆盖率共同构成持续集成体系，其设计思考逻辑是"持续集成保证软件质量，减少回归问题"（来源：项目 Wiki 第 2 章 §2.2.2、工作流 P14.2.3）。

### 原理拆解

**① 实时性：HIL 的第一性约束**

HIL 与普通仿真的本质区别在于**实时性**。仿真机必须在每个控制周期（典型为 1 kHz，即 1 ms）内完成：读取控制指令 → 解算动力学 → 生成传感器反馈。若仿真步长超过控制周期，控制器会"看到"过时的传感器数据，导致时序失真。

$$
T_{\text{sim}} = T_{\text{control}} \quad \Rightarrow \quad \Delta t_{\text{HIL}} \le \frac{1}{f_{\text{control}}}
$$

其中 $T_{\text{sim}}$ 为仿真步长，$T_{\text{control}}$ 为控制周期，$f_{\text{control}}$ 为控制频率。工程上要求仿真机的最坏情况执行时间（WCET）必须小于控制周期，通常需预留 20%–30% 的裕量（工程判断）。

**② 被控对象模型：保真度与实时性的权衡**

HIL 中被控对象模型的复杂度受实时性约束。全阶柔性多体动力学（如考虑连杆弹性、关节柔性）在 1 ms 内难以实时解算，因此工程上常用**降阶模型**：

- 刚体动力学 + 简化接触模型（如弹簧-阻尼模型）
- 电机驱动模型（电流环等效为一阶惯性环节）
- 执行器饱和与延迟模型

模型保真度与实时性构成一对矛盾：模型越精细，仿真越真实，但可能超出实时预算。工程判断是：**HIL 的目标不是验证动力学模型的精度，而是验证控制软件的逻辑正确性**——模型只需在趋势上正确，关键是要覆盖控制器可能遇到的边界工况（如关节限位、力矩饱和、传感器噪声）。

**③ 故障注入：HIL 的独特价值**

HIL 仿真机可以精确注入真实系统中难以复现的故障：传感器断线、通信丢包、执行器卡死、电源跌落。这些故障在真机上测试既危险又难以控制时机，而在 HIL 中可以通过脚本精确到毫秒级触发。这使得**故障注入测试**成为 HIL 区别于其他验证手段的核心能力。

| 参数 | 典型值/范围 | 说明 |
|------|------------|------|

### 横向对比

| 验证层级 | 被测对象 | 被控对象 | 实时性 | 保真度 | 成本 |
|---------|---------|---------|--------|--------|------|
| MIL（Model-in-the-Loop） | 控制算法模型 | 被控对象模型 | 非实时 | 中 | 低 |
| SIL（Software-in-the-Loop） | 控制软件代码 | 被控对象模型 | 非实时 | 中 | 低 |
| **HIL（Hardware-in-the-Loop）** | **真实控制器硬件** | **实时仿真模型** | **实时** | **中高** | **中** |
| 整机实测 | 真实控制器 | 真实机器人 | 实时 | 最高 | 最高 |

HIL 的独特定位在于：它是唯一同时具备**真实硬件时序行为**与**虚拟被控对象可重复性**的验证层级。相比 SIL，HIL 能捕获编译器优化、中断延迟、总线抖动等真实时序问题；相比整机实测，HIL 能安全、可重复地测试危险工况。

### 谁在用·应用案例

在人形机器人开发中，HIL 主要应用于以下场景：

1. **控制软件回归测试**：在 CI/CD 流水线中，每次代码提交后自动运行 HIL 测试，验证 MPC/WBC 控制器在真实硬件上的行为是否与预期一致。工作流 P14.2.3 明确将"HIL 自动化测试"列为 CI/CD 与仿真测试链的关键工具（来源：工作流 P14.2.3）。

2. **故障注入与安全验证**：在 HIL 环境中注入传感器故障、通信中断等异常，验证控制器的容错与安全停机逻辑。这是整机实测中难以安全执行的测试。

3. **算法部署前的最后验证**：在将新算法（如新的运动规划器、学习策略）部署到真机前，先在 HIL 环境中验证其与现有控制栈的兼容性。这与 sim-to-real 方法形成互补——sim-to-real 解决策略在仿真中训练后如何迁移到真机的问题，而 HIL 解决控制器在真实硬件上运行时是否正确的问题（来源：项目 Wiki 第 18 章 §18.6）。

4. **多机协同与通信测试**：在 HIL 环境中模拟多台机器人之间的通信延迟与丢包，验证分布式控制算法的鲁棒性。

### 局限与边界

HIL 并非万能，其核心局限在于**模型保真度的天花板**：

1. **接触模型不精确**：人形机器人行走、操作高度依赖足底/手部接触力。实时仿真中的接触模型（弹簧-阻尼或简化摩擦锥）与真实接触力学存在差距，可能导致 HIL 中验证通过的控制器在真机上表现异常。

2. **执行器动态建模困难**：谐波减速器的柔性、摩擦非线性、温度漂移等难以在实时模型中精确刻画。HIL 中验证的力矩跟踪性能可能与真机有偏差。

3. **实时性与保真度的矛盾**：模型越精细，实时解算越困难。工程上必须在两者间取舍，这意味着 HIL 永远无法完全替代整机实测。

4. **硬件在环的"环"是虚拟的**：HIL 验证的是控制器与"模型"的交互，而非与真实物理世界的交互。感知环节（视觉、力觉）通常难以在 HIL 中真实复现，需要额外的传感器仿真或注入。

### 常见误区

1. **"HIL 可以替代整机实测"**——错。HIL 验证的是控制软件在真实硬件上的逻辑正确性，但无法验证动力学模型的精度、接触力学的真实性、以及真实环境中的感知性能。整机实测仍是最终验收的必经环节。

2. **"HIL 就是实时仿真"**——不完全是。实时仿真是 HIL 的必要条件，但 HIL 的核心是"真实硬件 + 虚拟被控对象"的闭环。仅有实时仿真机而没有真实控制器，只是实时仿真而非 HIL。

3. **"HIL 模型越精细越好"**——错。模型精细度受实时性约束，过度精细的模型可能导致仿真超时，反而破坏实时性。工程上应优先保证模型覆盖关键工况，而非追求绝对精度。

4. **"HIL 只用于测试阶段"**——不。HIL 在开发早期即可用于算法原型验证，在开发中期用于回归测试，在发布前用于验收测试，贯穿整个开发生命周期。

## Overview

Hardware-in-the-Loop (HIL) testing is a method that connects a real hardware controller to a real-time simulation model of the plant, verifying the correctness and performance of control software in a closed loop. What it truly changes is not the "test location," but the "timing and risk structure of testing"—it allows control software to run on real processors with real timing before a physical prototype exists, thereby shifting catastrophic failures from the field to the laboratory. HIL sits in the middle of the assembly integration testing domain (domain 04), serving as a critical verification layer connecting pure simulation (SIL/MIL) with full-machine physical testing.

## Content

### What It Is: A Precise Definition

The core structure of HIL is **real hardware + virtual plant**. The Device Under Test (DUT) is typically the real controller hardware—such as the main control computing unit in a humanoid robot (e.g., an industrial PC or embedded board running MPC or WBC)—which connects via real bus interfaces (e.g., EtherCAT, CAN) to a real-time simulator. The simulator solves the plant's dynamic model (e.g., full-body multi-rigid-body dynamics, motor drive models, contact models) in real time with a fixed step size, and feeds sensor signals (joint angles, torques, IMU data) back to the controller, forming a closed loop.

$$
\text{HIL closed loop:}\quad \underbrace{\text{Real Controller}}_{\text{Real Hardware}} \;\xrightarrow{\text{Control Commands}}\; \underbrace{\text{Real-Time Simulator}}_{\text{Virtual Plant}} \;\xrightarrow{\text{Sensor Feedback}}\; \text{Real Controller}
$$

The key distinction is that **the controller does not know (and does not care) whether it is connected to a real machine or a simulator**—it only sees the sensor data stream on the bus. This is the philosophy of HIL: making the DUT "believe" it is controlling a real robot.

### Why It Exists: Pain Points and Historical Positioning

In humanoid robot development, pure simulation (SIL) cannot verify the timing behavior of control software on real hardware—compiler optimizations, interrupt latencies, bus communication jitter, and floating-point precision differences are all masked in an x86 simulation environment. Direct physical testing, on the other hand, faces three-fold challenges:

1. **Safety risks**: Humanoid robots are high-energy, underactuated systems; a single bug in control software can cause the robot to fall, be damaged, or even injure people.
2. **High costs**: Every physical test consumes hardware lifespan and requires safety protection facilities and operators.
3. **Non-reproducibility**: Physical testing is affected by environment, wear, and battery state, making it difficult to precisely reproduce the same scenario.

The historical positioning of HIL is precisely to fill this gap: it preserves the fact that "control software runs on real processors," while replacing the "plant" with a reproducible real-time simulation model that supports fault injection and time acceleration. In the project workflow, HIL is explicitly listed as a key component of the CI/CD and simulation testing chain—together with GitLab CI, Docker, SIL/HIL automated testing, and code coverage, it forms the continuous integration system. The design rationale is that "continuous integration ensures software quality and reduces regression issues" (source: Project Wiki Chapter 2 §2.2.2, Workflow P14.2.3).

### Principle Breakdown

**① Real-Time Performance: The First-Principle Constraint of HIL**

The essential difference between HIL and ordinary simulation is **real-time performance**. The simulator must complete the following within each control cycle (typically 1 kHz, i.e., 1 ms): read control commands → solve dynamics → generate sensor feedback. If the simulation step exceeds the control cycle, the controller will "see" outdated sensor data, leading to timing distortion.

$$
T_{\text{sim}} = T_{\text{control}} \quad \Rightarrow \quad \Delta t_{\text{HIL}} \le \frac{1}{f_{\text{control}}}
$$

where $T_{\text{sim}}$ is the simulation step size, $T_{\text{control}}$ is the control period, and $f_{\text{control}}$ is the control frequency. In engineering practice, the worst-case execution time (WCET) of the simulator must be less than the control period, typically requiring a 20%–30% margin (engineering judgment).

**② Plant Model: Trade-off Between Fidelity and Real-Time Performance**

The complexity of the plant model in HIL is constrained by real-time requirements. Full-order flexible multi-body dynamics (e.g., considering link elasticity and joint flexibility) are difficult to solve in real time within 1 ms, so engineering practice commonly uses **reduced-order models**:

- Rigid-body dynamics + simplified contact models (e.g., spring-damper models)
- Motor drive models (current loop equivalent to a first-order inertial element)
- Actuator saturation and delay models

Model fidelity and real-time performance form a pair of contradictions: the finer the model, the more realistic the simulation, but the more likely it exceeds the real-time budget. The engineering judgment is: **the goal of HIL is not to verify the accuracy of the dynamic model, but to verify the logical correctness of the control software**—the model only needs to be correct in trend, and the key is to cover the boundary conditions the controller may encounter (e.g., joint limits, torque saturation, sensor noise).

**③ Fault Injection: The Unique Value of HIL**

The HIL simulator can precisely inject faults that are difficult to reproduce in real systems: sensor disconnection, communication packet loss, actuator jamming, and power supply drops. Testing these faults on a physical machine is both dangerous and difficult to control in timing, whereas in HIL they can be triggered with millisecond precision via scripts. This makes **fault injection testing** a core capability that distinguishes HIL from other verification methods.

### Key Parameters and Specifications

| Parameter | Typical Value/Range | Description |
|-----------|--------------------|-------------|
| Control period | 1 kHz (1 ms) | Typical frequency for humanoid robot joint control (engineering judgment) |
| Simulation step | ≤ 1 ms | Must be less than or equal to the control period |
| Real-time jitter | < 10 µs | Deviation between the simulator's worst-case execution time and the control period (engineering judgment) |
| Communication bus | EtherCAT, CAN | Consistent with the real controller interface (source: Project Wiki Chapter 2 §2.2.2 mentions EtherCAT) |
| Model degrees of freedom | 20–40 DOF | Typical scale for full-body rigid-body dynamics (engineering judgment) |
| Fault injection precision | Millisecond level | Can precisely trigger sensor/communication faults (engineering judgment) |

### Horizontal Comparison

| Verification Level | Device Under Test | Plant | Real-Time | Fidelity | Cost |
|--------------------|-------------------|-------|-----------|----------|------|
| MIL (Model-in-the-Loop) | Control algorithm model | Plant model | Non-real-time | Medium | Low |
| SIL (Software-in-the-Loop) | Control software code | Plant model | Non-real-time | Medium | Low |
| **HIL (Hardware-in-the-Loop)** | **Real controller hardware** | **Real-time simulation model** | **Real-time** | **Medium-high** | **Medium** |
| Full-machine physical testing | Real controller | Real robot | Real-time | Highest | Highest |

The unique positioning of HIL is that it is the only verification level that simultaneously possesses **real hardware timing behavior** and **reproducibility of the virtual plant**. Compared to SIL, HIL can capture real timing issues such as compiler optimizations, interrupt latencies, and bus jitter; compared to full-machine physical testing, HIL can safely and reproducibly test dangerous scenarios.

### Who Uses It: Application Cases

In humanoid robot development, HIL is mainly applied in the following scenarios:

1. **Control software regression testing**: In the CI/CD pipeline, HIL tests are automatically run after each code commit to verify whether the behavior of MPC/WBC controllers on real hardware matches expectations. Workflow P14.2.3 explicitly lists "HIL automated testing" as a key tool in the CI/CD and simulation testing chain (source: Workflow P14.2.3).

2. **Fault injection and safety verification**: Injecting sensor faults, communication interruptions, and other anomalies in the HIL environment to verify the controller's fault tolerance and safe shutdown logic. This is a test that is difficult to execute safely in full-machine physical testing.

3. **Final verification before algorithm deployment**: Before deploying new algorithms (e.g., new motion planners, learned policies) to the physical robot, verify their compatibility with the existing control stack in the HIL environment. This complements the sim-to-real approach—sim-to-real addresses how policies trained in simulation transfer to the physical robot, while HIL addresses whether the controller runs correctly on real hardware (source: Project Wiki Chapter 18 §18.6).

4. **Multi-robot coordination and communication testing**: Simulating communication delays and packet loss between multiple robots in the HIL environment to verify the robustness of distributed control algorithms.

### Limitations and Boundaries

HIL is not a panacea; its core limitation lies in the **ceiling of model fidelity**:

1. **Inaccurate contact models**: Humanoid robot walking and manipulation rely heavily on foot/hand contact forces. Contact models in real-time simulation (spring-damper or simplified friction cones) differ from real contact mechanics, which may cause controllers that pass HIL verification to behave abnormally on the physical robot.

2. **Difficulty in modeling actuator dynamics**: The flexibility of harmonic drives, friction nonlinearities, and temperature drift are difficult to characterize precisely in real-time models. Torque tracking performance verified in HIL may deviate from the physical robot.

3. **The contradiction between real-time performance and fidelity**: The finer the model, the harder it is to solve in real time. Engineering practice must trade off between the two, meaning HIL can never fully replace full-machine physical testing.

4. **The "loop" in hardware-in-the-loop is virtual**: HIL verifies the interaction between the controller and a "model," not with the real physical world. Perception components (vision, force sensing) are typically difficult to reproduce realistically in HIL, requiring additional sensor simulation or injection.

### Common Misconceptions

1. **"HIL can replace full-machine physical testing"**—Wrong. HIL verifies the logical correctness of control software on real hardware, but cannot verify the accuracy of dynamic models, the realism of contact mechanics, or perception performance in real environments. Full-machine physical testing remains a mandatory step for final acceptance.

2. **"HIL is just real-time simulation"**—Not entirely. Real-time simulation is a necessary condition for HIL, but the core of HIL is the closed loop of "real hardware + virtual plant." Having only a real-time simulator without a real controller is real-time simulation, not HIL.

3. **"The finer the HIL model, the better"**—Wrong. Model fidelity is constrained by real-time requirements; overly detailed models may cause simulation timeouts, undermining real-time performance. Engineering practice should prioritize covering critical operating conditions rather than pursuing absolute accuracy.

4. **"HIL is only used in the testing phase"**—No. HIL can be used for algorithm prototype verification in early development, regression testing in mid-development, and acceptance testing before release, spanning the entire development lifecycle.

## 개요

하드웨어 인 더 루프(Hardware-in-the-Loop, HIL) 테스트는 실제 하드웨어 컨트롤러와 피제어 객체의 실시간 시뮬레이션 모델을 연결하여, 폐루프에서 제어 소프트웨어의 정확성과 성능을 검증하는 테스트 방법입니다. 이것이 진정으로 바꾸는 것은 '테스트 장소'가 아니라 '테스트의 시기와 위험 구조'입니다. 즉, 제어 소프트웨어가 물리적 프로토타입이 존재하기 전에 실제 프로세서에서 실제 타이밍으로 실행될 수 있게 하여, 치명적 고장을 현장에서 실험실로 옮기는 것입니다. HIL은 조립 통합 테스트 영역(도메인 04)의 중간 단계에 위치하며, 순수 시뮬레이션(SIL/MIL)과 전체 기계 실측을 연결하는 핵심 검증 계층입니다.

## 핵심 내용

### 무엇인가: 정확한 정의

HIL의 핵심 구조는 **실제 하드웨어 + 가상 피제어 객체**입니다. 피시험 객체(Device Under Test, DUT)는 일반적으로 실제 컨트롤러 하드웨어입니다. 휴머노이드 로봇의 경우 메인 제어 컴퓨팅 유닛(예: MPC 또는 WBC를 실행하는 산업용 PC 또는 임베디드 보드)이며, 이는 실제 버스 인터페이스(예: EtherCAT, CAN)를 통해 실시간 시뮬레이터에 연결됩니다. 시뮬레이터는 고정 스텝으로 피제어 객체의 동역학 모델(예: 전체 기체 다강체 동역학, 모터 구동 모델, 접촉 모델)을 실시간으로 해석하고, 센서 신호(관절 각도, 토크, IMU 데이터)를 컨트롤러에 피드백하여 폐루프를 형성합니다.

$$
\text{HIL 폐루프:}\quad \underbrace{\text{실제 컨트롤러}}_{\text{실제 하드웨어}} \;\xrightarrow{\text{제어 명령}}\; \underbrace{\text{실시간 시뮬레이터}}_{\text{가상 피제어 객체}} \;\xrightarrow{\text{센서 피드백}}\; \text{실제 컨트롤러}
$$

핵심 차이점은 **컨트롤러는 자신이 실제 기계에 연결되었는지 시뮬레이터에 연결되었는지 알지 못한다(그리고 신경 쓰지 않는다)**는 것입니다. 컨트롤러가 보는 것은 버스의 센서 데이터 스트림뿐입니다. 이것이 바로 HIL의 철학입니다. 피시험 객체가 '자신이 실제 로봇을 제어하고 있다고' 생각하게 만드는 것입니다.

### 왜 존재하는가: 문제점과 역사적 위치

휴머노이드 로봇 개발에서 순수 시뮬레이션(SIL)은 제어 소프트웨어가 실제 하드웨어에서 보이는 타이밍 동작을 검증할 수 없습니다. 컴파일러 최적화, 인터럽트 지연, 버스 통신 지터, 부동소수점 정밀도 차이는 x86 시뮬레이션 환경에서 완전히 가려집니다. 반면 실제 기계 테스트는 세 가지 어려움에 직면합니다:

1. **안전 위험**: 휴머노이드 로봇은 고에너지, 부족 구동 시스템으로, 제어 소프트웨어의 버그 하나가 전체 기계의 넘어짐, 손상, 심지어 인명 피해를 초래할 수 있습니다.
2. **높은 비용**: 실제 기계 테스트는 매번 하드웨어 수명을 소모하며, 안전 보호 시설과 운영 인력이 필요합니다.
3. **비반복성**: 실제 기계 테스트는 환경, 마모, 배터리 상태의 영향을 받아 동일한 시나리오를 정확히 재현하기 어렵습니다.

HIL의 역사적 위치는 바로 이 간극을 메우는 것입니다. '제어 소프트웨어가 실제 프로세서에서 실행된다'는 사실을 유지하면서, '피제어 객체'를 반복 가능하고, 고장 주입이 가능하며, 시간 가속이 가능한 실시간 시뮬레이션 모델로 대체합니다. 프로젝트 워크플로우에서 HIL은 CI/CD 및 시뮬레이션 테스트 체인의 핵심 단계로 명시됩니다. GitLab CI, Docker, SIL/HIL 자동화 테스트, 코드 커버리지와 함께 지속적 통합 시스템을 구성하며, 그 설계 사고 논리는 '지속적 통합이 소프트웨어 품질을 보장하고 회귀 문제를 줄인다'는 것입니다(출처: 프로젝트 Wiki 2장 §2.2.2, 워크플로우 P14.2.3).

### 원리 분석

**① 실시간성: HIL의 제1 원리적 제약**

HIL과 일반 시뮬레이션의 본질적 차이는 **실시간성**입니다. 시뮬레이터는 각 제어 주기(일반적으로 1 kHz, 즉 1 ms) 내에 다음을 완료해야 합니다: 제어 명령 읽기 → 동역학 해석 → 센서 피드백 생성. 시뮬레이션 스텝이 제어 주기를 초과하면 컨트롤러는 '오래된' 센서 데이터를 보게 되어 타이밍 왜곡이 발생합니다.

$$
T_{\text{sim}} = T_{\text{control}} \quad \Rightarrow \quad \Delta t_{\text{HIL}} \le \frac{1}{f_{\text{control}}}
$$

여기서 $T_{\text{sim}}$은 시뮬레이션 스텝, $T_{\text{control}}$은 제어 주기, $f_{\text{control}}$은 제어 주파수입니다. 공학적으로 시뮬레이터의 최악 실행 시간(WCET)은 제어 주기보다 작아야 하며, 일반적으로 20%–30%의 여유를预留해야 합니다(공학적 판단).

**② 피제어 객체 모델: 충실도와 실시간성의 균형**

HIL에서 피제어 객체 모델의 복잡도는 실시간성 제약을 받습니다. 전차수 유연 다강체 동역학(예: 링크 탄성, 관절 유연성 고려)은 1 ms 내에 실시간 해석이 어렵기 때문에, 공학적으로는 **축소 모델**을 주로 사용합니다:

- 강체 동역학 + 단순화된 접촉 모델(예: 스프링-댐퍼 모델)
- 모터 구동 모델(전류 루프를 1차 관성 요소로 등가화)
- 액추에이터 포화 및 지연 모델

모델 충실도와 실시간성은 한 쌍의 모순을 이룹니다. 모델이 정밀할수록 시뮬레이션은 더 현실적이지만, 실시간 예산을 초과할 수 있습니다. 공학적 판단은 다음과 같습니다: **HIL의 목표는 동역학 모델의 정밀도를 검증하는 것이 아니라 제어 소프트웨어의 논리적 정확성을 검증하는 것입니다.** 모델은 추세적으로만 정확하면 되며, 핵심은 컨트롤러가 직면할 수 있는 경계 조건(관절 리미트, 토크 포화, 센서 노이즈)을 커버하는 것입니다.

**③ 고장 주입: HIL의 독특한 가치**

HIL 시뮬레이터는 실제 시스템에서 재현하기 어려운 고장을 정밀하게 주입할 수 있습니다: 센서 단선, 통신 패킷 손실, 액추에이터 고착, 전원 강하. 이러한 고장은 실제 기계에서 테스트하기에는 위험하고 타이밍 제어도 어렵지만, HIL에서는 스크립트로 밀리초 단위까지 정밀하게 트리거할 수 있습니다. 이로 인해 **고장 주입 테스트**는 HIL을 다른 검증 수단과 구별하는 핵심 역량이 됩니다.

### 핵심 파라미터 및 사양

| 파라미터 | 일반값/범위 | 설명 |
|------|------------|------|
| 제어 주기 | 1 kHz (1 ms) | 휴머노이드 로봇 관절 제어 일반 주파수 (공학적 판단) |
| 시뮬레이션 스텝 | ≤ 1 ms | 제어 주기보다 작거나 같아야 함 |
| 실시간 지터 | < 10 µs | 시뮬레이터 최악 실행 시간과 제어 주기의 편차 (공학적 판단) |
| 통신 버스 | EtherCAT, CAN | 실제 컨트롤러 인터페이스와 일치 (출처: 프로젝트 Wiki 2장 §2.2.2에서 EtherCAT 언급) |

| 고장 주입 정밀도 | 밀리초 단위 | 센서/통신 고장 정밀 트리거 가능 (공학적 판단) |

### 수평 비교

| 검증 계층 | 피시험 객체 | 피제어 객체 | 실시간성 | 충실도 | 비용 |
|---------|---------|---------|--------|--------|------|
| MIL (Model-in-the-Loop) | 제어 알고리즘 모델 | 피제어 객체 모델 | 비실시간 | 중 | 낮음 |
| SIL (Software-in-the-Loop) | 제어 소프트웨어 코드 | 피제어 객체 모델 | 비실시간 | 중 | 낮음 |
| **HIL (Hardware-in-the-Loop)** | **실제 컨트롤러 하드웨어** | **실시간 시뮬레이션 모델** | **실시간** | **중상** | **중** |
| 전체 기계 실측 | 실제 컨트롤러 | 실제 로봇 | 실시간 | 최고 | 최고 |

HIL의 독특한 위치는 **실제 하드웨어 타이밍 동작**과 **가상 피제어 객체의 반복 가능성**을 동시에 갖춘 유일한 검증 계층이라는 점입니다. SIL과 비교하여 HIL은 컴파일러 최적화, 인터럽트 지연, 버스 지터와 같은 실제 타이밍 문제를 포착할 수 있고, 전체 기계 실측과 비교하여 HIL은 위험한 조건을 안전하고 반복적으로 테스트할 수 있습니다.

### 사용처·적용 사례

휴머노이드 로봇 개발에서 HIL은 주로 다음 시나리오에 적용됩니다:

1. **제어 소프트웨어 회귀 테스트**: CI/CD 파이프라인에서 코드 커밋 후 자동으로 HIL 테스트를 실행하여 MPC/WBC 컨트롤러가 실제 하드웨어에서 기대와 일치하는 동작을 보이는지 검증합니다. 워크플로우 P14.2.3은 'HIL 자동화 테스트'를 CI/CD 및 시뮬레이션 테스트 체인의 핵심 도구로 명시합니다(출처: 워크플로우 P14.2.3).

2. **고장 주입 및 안전 검증**: HIL 환경에서 센서 고장, 통신 중단 등의 이상을 주입하여 컨트롤러의 내결함성 및 안전 정지 로직을 검증합니다. 이는 전체 기계 실측에서 안전하게 실행하기 어려운 테스트입니다.

3. **알고리즘 배포 전 최종 검증**: 새 알고리즘(예: 새로운 운동 플래너, 학습 정책)을 실제 기계에 배포하기 전에 HIL 환경에서 기존 제어 스택과의 호환성을 검증합니다. 이는 sim-to-real 방법과 상호 보완적입니다. sim-to-real은 시뮬레이션에서 훈련된 정책을 실제 기계로 전이하는 문제를 해결하고, HIL은 컨트롤러가 실제 하드웨어에서 실행될 때 올바른지 여부를 해결합니다(출처: 프로젝트 Wiki 18장 §18.6).

4. **다중 로봇 협력 및 통신 테스트**: HIL 환경에서 여러 로봇 간 통신 지연과 패킷 손실을 시뮬레이션하여 분산 제어 알고리즘의 견고성을 검증합니다.

### 한계와 경계

HIL은 만능이 아니며, 핵심 한계는 **모델 충실도의 천장**입니다:

1. **접촉 모델 부정확성**: 휴머노이드 로봇의 보행, 조작은 발바닥/손 접촉력에 크게 의존합니다. 실시간 시뮬레이션의 접촉 모델(스프링-댐퍼 또는 단순화된 마찰 원뿔)은 실제 접촉 역학과 차이가 있어, HIL에서 검증된 컨트롤러가 실제 기계에서 이상 동작을 보일 수 있습니다.

2. **액추에이터 동역학 모델링 어려움**: 하모닉 드라이브의 유연성, 마찰 비선형성, 온도 드리프트는 실시간 모델에서 정밀하게刻画하기 어렵습니다. HIL에서 검증된 토크 추종 성능은 실제 기계와 편차가 있을 수 있습니다.

3. **실시간성과 충실도의 모순**: 모델이 정밀할수록 실시간 해석이 어려워집니다. 공학적으로 둘 사이에서 절충해야 하므로, HIL은 전체 기계 실측을 완전히 대체할 수 없습니다.

4. **하드웨어 인 더 루프의 '루프'는 가상입니다**: HIL은 컨트롤러와 '모델'의 상호작용을 검증하며, 실제 물리 세계와의 상호작용은 아닙니다. 인식 단계(시각, 힘 감각)는 일반적으로 HIL에서 실제로 재현하기 어렵고, 추가적인 센서 시뮬레이션 또는 주입이 필요합니다.

### 일반적인 오해

1. **"HIL은 전체 기계 실측을 대체할 수 있다"** — 틀렸습니다. HIL은 제어 소프트웨어가 실제 하드웨어에서 실행될 때의 논리적 정확성을 검증하지만, 동역학 모델의 정밀도, 접촉 역학의 실제성, 실제 환경에서의 인식 성능은 검증할 수 없습니다. 전체 기계 실측은 여전히 최종 검수의 필수 단계입니다.

2. **"HIL은 실시간 시뮬레이션이다"** — 완전히 맞지는 않습니다. 실시간 시뮬레이션은 HIL의 필요 조건이지만, HIL의 핵심은 '실제 하드웨어 + 가상 피제어 객체'의 폐루프입니다. 실시간 시뮬레이터만 있고 실제 컨트롤러가 없다면 실시간 시뮬레이션이지 HIL이 아닙니다.

3. **"HIL 모델은 정밀할수록 좋다"** — 틀렸습니다. 모델 정밀도는 실시간성 제약을 받으며, 과도하게 정밀한 모델은 시뮬레이션 시간 초과를 유발하여 오히려 실시간성을 파괴할 수 있습니다. 공학적으로는 모델이 핵심 조건을 커버하는 것을 우선시해야 하며, 절대 정밀도를 추구해서는 안 됩니다.

4. **"HIL은 테스트 단계에서만 사용된다"** — 아닙니다. HIL은 개발 초기에 알고리즘 프로토타입 검증, 개발 중기에 회귀 테스트, 출시 전에 검수 테스트에 사용되며, 전체 개발 수명 주기에 걸쳐 활용됩니다.

### 관련 지식

- `ent_method_sim_to_real` — HIL과 sim-to-real은 상호 보완적입니다. 전자는 컨트롤러가 실제 하드웨어에서의 동작을 검증하고, 후자는 정책이 시뮬레이션에서 실제 기계로 전이될 때 성능 유지 문제를 해결합니다.
- `ent_method_system_identification` — 시스템 식별은 HIL에 더 정밀한 피제어 객체 모델 파라미터를 제공하여 HIL과 실제 기계 간의 모델 격차를 줄입니다.
- `ent_technology_urdf_robot_description_format_2024` — URDF는 HIL 시뮬레이션에 필요한 로봇 운동학 및 동역학 설명(링크, 관절, 관성)을 제공합니다.
- `ent_process_p14_2_3` — 이 워크플로우는 HIL 자동화 테스트를 CI/CD 및 시뮬레이션 테스트 체인의 핵심 도구로 명시하며, 소프트웨어 품질 보증에서의 위치를 명확히 합니다.
- `ent_process_p14_3_2` — HIL과 관련된 후속 테스트 프로세스로, 전체 기계 통합 테스트와의 연결을 포함할 수 있습니다.
- `ent_paper_hil_hybrid_imitation_diverse_parkour_ski_2025` — 이 논문은 혼합 모방 학습과 다양한 파쿠르/스키 기술 검증에서 HIL의 적용을 보여주며, 복잡한 운동 기술 테스트에서 HIL의 가치를 나타냅니다.
- `ent_process_p14` — 소프트웨어 미들웨어 및 시스템 통합의 전체 작업 패키지로, HIL은 테스트 체인의 구성 요소입니다.
- `ent_benchmark_humanoidbench` — 이 벤치마크는 HIL 테스트에서 컨트롤러의 성능 지표를 평가하는 데 사용될 수 있으며, HIL 테스트 결과에 정량적 참조를 제공합니다.
