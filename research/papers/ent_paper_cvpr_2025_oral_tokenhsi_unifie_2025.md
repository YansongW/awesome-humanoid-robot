## 概述

TokenHSI 是一个面向双臂人形机器人的物理仿真平台，基于 AI2-THOR 扩展并集成 Unity 物理引擎，通过任务 Token 化统一合成物理人-场景交互。该平台支持连续交互过程、模拟执行不确定性，并评估 VLM 在复杂双臂任务中的规划能力，代码已开源。

## 它改变了什么

现有仿真平台（如 ThreeDWorld、iGibson、RoboThor）大多依赖简化机器人形态（轮式、单臂），缺乏对双臂人形机器人的原生支持，这直接限制了策略向 Unitree H1、Agibot X1 这类真实人形平台的迁移。更关键的是，多数平台采用瞬时、闪变式的状态转换，绕过了低层技能执行的随机性和潜在失败——这种“理想化”假设在真实世界中几乎不存在，导致基于 VLM 的规划器在 sim-to-real 部署时性能骤降。

TokenHSI 真正改变的是“评估范式”：它不再把仿真当作一个确定性环境，而是引入偶然性机制（随机执行错误），让智能体必须感知技能进展、应对失败并重新规划。这使得 VLM 的规划能力不再只是“在完美环境中生成动作序列”，而是要在有噪声的执行过程中保持鲁棒性——这是从“规划正确”到“执行可靠”的关键转变。

## 方法拆解

### 平台架构
- 基于 AI2-THOR 扩展，集成 Unity 物理引擎，Python 后端与 Unity 引擎通过 JSON over TCP 双向通信。
- IK 系统实现为跨平台 HTTP 服务：Python 后端发送目标对象 ID 和动作类型，Unity 计算交互点并转换到机器人基座坐标系，提交给本地 IK 服务器求解关节角度，再通过三次样条插值实现平滑运动。

### 机器人资产与任务分类
- Unitree H1（灵巧手，擅长力量与稳定性）和 Agibot X1（夹爪，高灵巧性与精度）。
- 任务分为三类：双臂必需（必须双臂参与）、双臂可选（单臂可完成但双臂更高效）、单臂任务（源自 AI2-THOR）。

### 动作空间
- 对象无关动作：MOVE、ROTATE、OBSERVE、CROUCH、STAND。
- 对象相关动作：PICKUP、OPEN、FILL、TOGGLE。

### 关键设计决策
- 姿态计算采用 OmniManip 进行 IK 求解；X1 采用解耦方法，使用简化姿态矩阵（3×3）独立求解每只手臂。
- 视觉系统：第一人称相机（最高 360 度全景视角）+ 第三人称四相机套件（后视、前视、左视、右视），水平视场角 160 度。
- 任务回放机制：支持“撤销”和“重做”，无需完全重启仿真器即可探索替代轨迹，减少计算资源消耗。
- 偶然性机制：随机模拟动作执行错误，迫使智能体发展重新规划能力。

## 关键创新

1. **任务 Token 化**：将物理交互任务分解为可组合的 Token 序列（动作类别、目标对象 ID、选定手臂），统一了单臂/双臂/对象无关动作的表达，使 VLM 可以基于 Token 进行规划，而非直接输出关节角度——这大幅降低了动作空间的维度，提升了规划效率。
2. **偶然性机制**：这是现有平台（如 ManipulaThor、ProcThor）普遍缺失的。通过随机注入执行错误，TokenHSI 让 VLM 在训练阶段就暴露于失败场景，从而发展出重新规划能力——这是从“理想化仿真”到“可信仿真”的关键一步。
3. **双臂人形原生支持**：不同于 RoboThor 的单臂或轮式平台，TokenHSI 从底层 IK 到动作空间都针对双臂人形设计，且支持 H1（灵巧手）和 X1（夹爪）两种异构末端，覆盖了从重物搬运到精细操作的全谱系任务。

## 实验与结果

| 对比维度 | 现有平台（ThreeDWorld、iGibson、RoboThor 等） | TokenHSI |
|---------|---------------------------------------------|----------|
| 智能体形态 | 轮式/单臂 | 双臂人形（H1、X1） |
| 转换方式 | 瞬时/闪变 | 连续 |
| 动作控制 | 离散或连续 | 离散+连续 |
| 偶然性 | 无 | 有 |

实验结果显示，现有开源和专有 VLM 模型在双臂具身任务中的规划能力有限，鲁棒性差（具体数字论文未明确）。这印证了平台设计动机：缺乏偶然性机制和双臂原生支持的环境，无法有效评估 VLM 在真实执行噪声下的表现。

## 边界与局限

论文未明确列出作者承认的其他局限。但从方法描述可推断：平台依赖传统 IK 求解（OmniManip），而非学习式控制，这限制了策略在高动态任务（如快速抓取）中的表现；场景对象基于 AI2-THOR 重新渲染，虽保证高度兼容性，但视觉多样性可能不如真实世界；偶然性机制是随机注入的，未必能模拟真实执行错误的分布。此外，训练配置、数据量、推理频率、硬件细节均未提供。

## 工程启示

复现或使用 TokenHSI 时，先核对以下几点：
1. **通信链路**：Python 后端与 Unity 的 JSON over TCP 通信是核心瓶颈，务必先验证延迟和吞吐量，否则高频率动作控制会卡顿。
2. **IK 服务依赖**：IK 通过 HTTP 跨平台服务访问，需确认 OmniManip 的部署环境与 Unity 版本兼容性，X1 的解耦 IK 方法与 H1 的完整 IK 求解路径不同，切换机器人时需重新配置。
3. **偶然性参数**：随机执行错误的注入频率和幅度直接影响 VLM 的鲁棒性评估结果，建议先在小场景中校准，避免偶然性过强导致任务完全不可完成。
4. **任务回放机制**：撤销/重做功能依赖任务历史管理系统，需注意内存占用，长时程任务中频繁回放可能累积大量状态快照。
5. **场景兼容性**：所有对象基于 AI2-THOR 重新渲染，若需引入新对象，需确保其高度与人形机器人兼容，否则 IK 求解可能失败。

## 개요
현재 HSI 합성 방법은 주로 단일 상호작용 작업을 위해 독립 컨트롤러를 개발하며, 다중 기술 통합이 필요한 복잡한 작업(예: 물체를 들고 앉기)을 처리하기 어렵습니다. TokenHSI는 통합 Transformer 정책을 통해 이 문제를 해결하며, 휴머노이드 로봇의 고유 감각을 공유 토큰으로 사용하고, 다양한 작업 토큰과 마스크 메커니즘을 통해 결합하여 교차 기술 지식 공유와 다중 작업 훈련을 구현합니다. 이 정책은 가변 길이 입력을 지원하여 새로운 시나리오에 유연하게 적응할 수 있으며, 추가 작업 토크나이저를 훈련하여 상호작용 목표의 기하학적 형태를 수정하거나 다중 기술을 조정하여 복잡한 작업을 처리할 수 있습니다.
