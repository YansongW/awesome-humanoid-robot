## 概述

本文探索将GPT-4作为人-机器人团队中可变自主性的核心控制器，通过OpenAI function calling将自然语言映射为结构化机器人动作，并在VR环境中进行12名参与者的用户研究。核心贡献在于揭示了LLM作为唯一控制器在真实交互中的可用性边界——包括过度沟通、自主性不匹配和响应延迟——并提出了校准过程与干预渠道的设计启示。

## 它改变了什么

这项工作的真正改变在于把LLM从“对话组件”提升为“自主性仲裁者”。以往可变自主性系统依赖显式的控制共享协议或Wizard-of-Oz模拟完美AI，而本文让GPT直接决定何时“夺取控制”执行函数、何时“放弃控制”向用户澄清——这实质上是把自主性协商从工程规则转移到了语言模型的隐式判断中。对行家而言，这意味着自主性不再是被编程的，而是被“提示”出来的，其行为边界由模型对函数描述和对话历史的解读共同决定。

更值得注意的转变是，作者没有选择微调或定制模型，而是坚持使用现成的GPT-4，并明确将“非AI专家也能应用”作为设计目标。这改变了该领域的默认假设——过去认为机器人控制需要专门训练或领域适配，而本文暗示通用LLM加上精心设计的函数描述可能足以支撑多智能体协调。这种“少工程、多提示”的路线，对资源有限的研究团队具有直接的吸引力，但也将不确定性从代码转移到了模型行为中。

## 方法拆解

### 系统架构
- **中央控制器 + 每机器人独立GPT实例**：控制器根据对话历史和上下文解释用户输入，分发给0…n个相关代理。这种去中心化设计旨在可扩展且计算高效——每个机器人只处理与其相关的指令，避免单一模型成为瓶颈。

### Function Calling机制
- 函数是描述过程的JSON对象，包含函数本身、合格参数、调用时机等信息。
- GPT模块可决定返回函数调用而非聊天回复；不确定时向用户请求澄清。
- 这实现了可变自主性的核心逻辑：LLM认为用户意图明确时“夺取控制”执行函数，不确定时“放弃控制”请求更多信息。

### 初始提示结构
- **Briefing**：角色和情境描述
- **Restraints**：保持角色不偏离GPT标准行为
- **Few-shot examples**：提供正确行为示例

### 语音与数据流
用户语音 → OpenAI Whisper v2转录 → 代理控制器 → GPT模块决定目标代理 → 代理GPT模块根据函数描述和机器人状态解释命令并执行函数 → 回复 → Amazon Polly语音合成输出

### 关键设计决策
- **函数输出验证**：系统验证函数输出并用文本反馈更新GPT模块，模拟真实机器人感官输入——这是弥补LLM缺乏感知能力的关键桥接。
- **VR环境而非物理机器人**：简化复杂性、增加灵活性，同时保持沉浸感以促进真实交互动态。
- **gpt-4-0613模型**：截至2023年11月OpenAI最新优化用于函数调用的GPT模型，仅使用chat completions API。

## 关键创新

1. **将function calling作为自主性协商的机制**：这不是简单的“LLM生成命令”，而是让模型在“执行”与“澄清”之间自主决策，将可变自主性从显式状态机转化为语言模型的隐式判断。其新颖性在于，自主性级别不是预设的，而是随对话上下文动态涌现的。

2. **多智能体场景下的去中心化LLM控制**：每个机器人拥有独立GPT实例，由中央控制器分发指令。这种架构避免了单一模型处理所有机器人状态的上下文爆炸问题，同时保持了模块化——每个机器人可以独立更新函数描述而不影响其他代理。

3. **对LLM非确定性的实证暴露**：作者明确指出即使设置低温度参数，输出仍不一致，不适合作为真实机器人的唯一控制元素。这一发现本身即是贡献——它量化了“LLM作为控制器”的可靠性边界，为后续研究提供了基准认知。

## 实验与结果

实验采用12名参与者（P3-P14，排除P1、P2因系统重大变更），在VR环境中完成7个复杂度递增的任务，平均实验时长27分28秒。

**SASSI问卷结果（1-7分制，7为最强烈/最慢）**：

| 维度 | 均值（M） | 标准差（SD） |
|------|-----------|-------------|
| 系统响应准确性 | 4.43 | 0.95 |
| 喜爱度 | 5.36 | 1.01 |
| 认知需求 | 4.88 | 1.02 |
| 烦恼度 | 3.80 | 1.44 |
| 可居住性 | 4.44 | 1.22 |
| 速度 | 5.25 | 1.57 |

关键行为发现：
- **所有参与者均成功完成任务**，无失败案例——这证明GPT-4在函数调用约束下具备基本任务执行能力。
- **SASSI问题29**（“我有时怀疑自己是否用对了词”）得分M=5.92，SD=1.73，显著高于其他维度——用户普遍存在“措辞焦虑”，担心自己的表达不被系统理解。
- **P12案例**：Neptune最初拒绝取黄色钥匙（认为玻璃pane不可穿越），直到P12明确告知“玻璃墙已打开”后才执行——暴露了LLM对函数描述中隐含物理约束的僵化理解。
- **P8案例**：请求Jupiter“取三个盘子并扔进垃圾桶”，机器人自主执行了三次正确的函数三元组（移动、拾取、投掷）——展示了LLM解析复合指令并分解为动作序列的能力。
- **P11案例**：Pluto拒绝去“蓝色垃圾桶”，称其不在函数列表中，但建议去“垃圾箱”——说明LLM对同义词的泛化存在边界，且会主动提供替代方案。

## 边界与局限

- **LLM不可调试性**：作者承认程序难以调试，研究期间LLM意外行为仅造成轻微不便，但未系统评估其潜在风险。
- **语言因素**：使用德语可能引发部分意外行为，尽管函数描述中的对象名称故意使用德语以避免歧义——但跨语言泛化问题未被单独测试。
- **网络依赖**：大学网络连接不稳定导致转录和模型响应延迟明显变长，但无断连或完全中断——云服务架构的固有脆弱性未被量化。
- **未做之事**：未进行定量成功率/误差指标测量（如任务完成时间、错误率），仅报告所有参与者成功；未测试除GPT外的其他LLM；未进行对照实验；未实现机器人间直接通信；未提供传感器或摄像头信息给LLM。
- **论文未明确**：低温度参数的具体值、推理频率、硬件配置等工程细节未披露。

## 工程启示

1. **先核对函数描述的粒度与术语一致性**：P11案例表明，对象名称的微小偏差（“蓝色垃圾桶”vs“垃圾箱”）会导致拒绝执行。复现时应确保函数描述覆盖所有可能的用户表达变体，或设计同义词映射层。

2. **预期LLM的“僵化时刻”并设计降级路径**：P12案例中Neptune对“玻璃墙已打开”的物理状态更新反应迟钝，说明LLM不会主动推断环境变化。工程上应在函数输出验证环节加入环境状态显式更新，而非依赖模型推理。

3. **响应延迟是最大可用性风险**：速度维度得分M=5.25（7为最慢）表明用户对延迟敏感。云API+转录+合成的流水线在真实部署中会叠加网络抖动，建议考虑本地模型或异步处理架构。

4. **“措辞焦虑”是真实且普遍的现象**：SASSI问题29的高分（M=5.92）提示，用户在与LLM交互时会自我审查表达方式。设计上应提供即时反馈（如转录可视化）来缓解不确定性，而非让用户猜测系统是否理解。

5. **最易踩坑处：LLM的非确定性**：即使低温度参数，输出仍不一致。不要将LLM作为唯一控制元素，应保留人工干预渠道（如紧急停止按钮），并考虑将关键决策路径用确定性规则兜底。

## Overview

This paper explores using GPT-4 as the central controller for variable autonomy in human-robot teams, mapping natural language to structured robot actions via OpenAI function calling, and conducting a user study with 12 participants in a VR environment. The core contribution lies in revealing the usability boundaries of LLMs as the sole controller in real interactions—including over-communication, autonomy mismatches, and response latency—and proposing design insights for calibration processes and intervention channels.

## What It Changes

The true shift in this work is elevating the LLM from a "conversational component" to an "autonomy arbiter." Previous variable autonomy systems relied on explicit control-sharing protocols or Wizard-of-Oz simulations of perfect AI, whereas this paper lets GPT directly decide when to "take control" to execute functions and when to "relinquish control" to clarify with the user—effectively moving autonomy negotiation from engineering rules to the implicit judgments of a language model. For experts, this means autonomy is no longer programmed but "prompted," with its behavioral boundaries jointly determined by the model's interpretation of function descriptions and conversation history.

A more notable shift is that the authors did not choose fine-tuning or custom models but insisted on using off-the-shelf GPT-4, explicitly setting "applicable by non-AI experts" as a design goal. This changes the field's default assumption—previously, robot control was thought to require specialized training or domain adaptation, whereas this paper suggests that a general-purpose LLM plus carefully designed function descriptions may suffice for multi-agent coordination. This "less engineering, more prompting" approach holds direct appeal for research teams with limited resources, but it also transfers uncertainty from code to model behavior.

## Method Breakdown

### System Architecture
- **Central controller + independent GPT instance per robot**: The controller interprets user input based on conversation history and context, distributing it to 0…n relevant agents. This decentralized design aims for scalability and computational efficiency—each robot processes only instructions relevant to it, avoiding a single model becoming a bottleneck.

### Function Calling Mechanism
- Functions are JSON objects describing processes, including the function itself, qualified parameters, invocation timing, and more.
- The GPT module can decide to return a function call rather than a chat reply; when uncertain, it requests clarification from the user.
- This implements the core logic of variable autonomy: the LLM "takes control" to execute functions when user intent is clear, and "relinquishes control" to request more information when uncertain.

### Initial Prompt Structure
- **Briefing**: Role and scenario description
- **Restraints**: Keeping the role from deviating from GPT's standard behavior
- **Few-shot examples**: Providing examples of correct behavior

### Speech and Data Flow
User speech → OpenAI Whisper v2 transcription → Agent controller → GPT module decides target agent → Agent GPT module interprets the command based on function descriptions and robot state, executes the function → Reply → Amazon Polly speech synthesis output

### Key Design Decisions
- **Function output validation**: The system validates function outputs and updates the GPT module with textual feedback, simulating real robot sensory input—this is a critical bridge compensating for the LLM's lack of perception.
- **VR environment rather than physical robots**: Simplifies complexity and increases flexibility while maintaining immersion to foster realistic interaction dynamics.
- **gpt-4-0613 model**: As of November 2023, OpenAI's latest GPT model optimized for function calling, using only the chat completions API.

## Key Innovations

1. **Using function calling as a mechanism for autonomy negotiation**: This is not simply "LLM generates commands," but rather letting the model autonomously decide between "executing" and "clarifying," transforming variable autonomy from an explicit state machine into the implicit judgments of a language model. Its novelty lies in autonomy levels not being preset but dynamically emerging from conversational context.

2. **Decentralized LLM control in multi-agent scenarios**: Each robot has an independent GPT instance, with instructions distributed by a central controller. This architecture avoids the context explosion problem of a single model handling all robot states while maintaining modularity—each robot can independently update its function descriptions without affecting other agents.

3. **Empirical exposure of LLM non-determinism**: The authors explicitly note that even with low temperature settings, outputs remain inconsistent and unsuitable as the sole control element for real robots. This finding itself is a contribution—it quantifies the reliability boundaries of "LLM as controller," providing baseline knowledge for subsequent research.

## Experiments and Results

The experiment involved 12 participants (P3-P14, excluding P1 and P2 due to major system changes), completing 7 tasks of increasing complexity in a VR environment, with an average experiment duration of 27 minutes and 28 seconds.

**SASSI Questionnaire Results (1-7 scale, 7 = most intense/slowest)**:

| Dimension | Mean (M) | Standard Deviation (SD) |
|-----------|----------|-------------------------|
| System response accuracy | 4.43 | 0.95 |
| Likeability | 5.36 | 1.01 |
| Cognitive demand | 4.88 | 1.02 |
| Annoyance | 3.80 | 1.44 |
| Habitability | 4.44 | 1.22 |
| Speed | 5.25 | 1.57 |

Key behavioral findings:
- **All participants successfully completed the tasks**, with no failures—this demonstrates that GPT-4 possesses basic task execution capability under function-calling constraints.
- **SASSI question 29** ("I sometimes wondered if I used the right words") scored M=5.92, SD=1.73, significantly higher than other dimensions—users generally experienced "wording anxiety," worrying that their expressions would not be understood by the system.
- **P12 case**: Neptune initially refused to pick up the yellow key (believing the glass pane was impassable), only executing after P12 explicitly stated "the glass wall is open"—exposing the LLM's rigid understanding of implicit physical constraints in function descriptions.
- **P8 case**: Requesting Jupiter to "take three plates and throw them into the trash can," the robot autonomously executed three correct function triples (move, pick up, throw)—demonstrating the LLM's ability to parse compound instructions and decompose them into action sequences.
- **P11 case**: Pluto refused to go to the "blue trash can," stating it was not in the function list, but suggested going to the "garbage bin"—indicating boundaries in the LLM's synonym generalization, along with its proactive provision of alternatives.

## Boundaries and Limitations

- **LLM non-debuggability**: The authors acknowledge that programs are difficult to debug; unexpected LLM behaviors during the study caused only minor inconvenience, but potential risks were not systematically assessed.
- **Language factors**: Using German may have triggered some unexpected behaviors, although object names in function descriptions were deliberately in German to avoid ambiguity—yet cross-language generalization issues were not separately tested.
- **Network dependency**: Unstable university network connections caused noticeably longer transcription and model response delays, but no disconnections or complete outages—the inherent fragility of cloud service architectures was not quantified.
- **What was not done**: No quantitative success rate/error metrics were measured (e.g., task completion time, error rates), only reporting that all participants succeeded; no other LLMs besides GPT were tested; no control experiments were conducted; no direct inter-robot communication was implemented; no sensor or camera information was provided to the LLM.
- **Not explicitly stated in the paper**: Engineering details such as the specific low temperature value, inference frequency, and hardware configuration were not disclosed.

## Engineering Insights

1. **First verify the granularity and terminology consistency of function descriptions**: The P11 case shows that minor deviations in object names ("blue trash can" vs. "garbage bin") can lead to refusal to execute. When reproducing, ensure function descriptions cover all possible user expression variants, or design a synonym mapping layer.

2. **Anticipate the LLM's "rigid moments" and design degradation paths**: In the P12 case, Neptune was slow to respond to the physical state update of "glass wall is open," indicating that the LLM does not proactively infer environmental changes. Engineering-wise, environmental state updates should be explicitly incorporated into the function output validation step, rather than relying on model reasoning.

3. **Response latency is the greatest usability risk**: The speed dimension score of M=5.25 (7 = slowest) indicates user sensitivity to delays. The cloud API + transcription + synthesis pipeline will compound network jitter in real deployments; consider local models or asynchronous processing architectures.

4. **"Wording anxiety" is real and widespread**: The high score on SASSI question 29 (M=5.92) suggests that users self-censor their expressions when interacting with LLMs. Design should provide immediate feedback (e.g., transcription visualization) to alleviate uncertainty, rather than leaving users to guess whether the system understands.

5. **The most common pitfall: LLM non-determinism**: Even with low temperature settings, outputs remain inconsistent. Do not use the LLM as the sole control element; retain human intervention channels (e.g., emergency stop buttons) and consider backing up critical decision paths with deterministic rules.

## 그것이 바꾸는 것

이 작업의 진정한 변화는 LLM을 '대화 구성 요소'에서 '자율성 중재자'로 승격시킨 것입니다. 기존의 가변 자율성 시스템은 명시적인 제어 공유 프로토콜이나 완벽한 AI를 시뮬레이션하는 Wizard-of-Oz 방식에 의존했지만, 본 논문은 GPT가 언제 '제어권을 장악'하여 함수를 실행하고, 언제 '제어권을 포기'하고 사용자에게 명확화를 요청할지 직접 결정하도록 합니다. 이는 본질적으로 자율성 협상을 엔지니어링 규칙에서 언어 모델의 암묵적 판단으로 이동시킨 것입니다. 전문가에게 이는 자율성이 더 이상 프로그래밍되는 것이 아니라 '프롬프트'되는 것이며, 그 행동 경계는 함수 설명과 대화 기록에 대한 모델의 해석에 의해 공동으로 결정됨을 의미합니다.

더욱 주목할 만한 변화는 저자들이 미세 조정이나 맞춤형 모델을 선택하지 않고 기성 GPT-4를 고수하면서, 'AI 비전문가도 적용 가능'을 명시적으로 설계 목표로 삼았다는 점입니다. 이는 해당 분야의 기본 가정을 바꿉니다. 과거에는 로봇 제어에 전용 훈련이나 도메인 적응이 필요하다고 여겨졌지만, 본 논문은 일반 LLM과 정교하게 설계된 함수 설명만으로도 다중 에이전트 조정을 지원할 수 있음을 시사합니다. 이러한 '적은 엔지니어링, 많은 프롬프트' 접근 방식은 자원이 제한된 연구 팀에게 직접적인 매력을 지니지만, 동시에 불확실성을 코드에서 모델 행동으로 이동시킵니다.

## 방법 분석

### 시스템 아키텍처
- **중앙 컨트롤러 + 로봇별 독립 GPT 인스턴스**: 컨트롤러는 대화 기록과 맥락에 따라 사용자 입력을 해석하여 0…n개의 관련 에이전트에 배포합니다. 이러한 분산형 설계는 확장 가능하고 계산 효율적이도록 의도되었습니다. 각 로봇은 자신과 관련된 지시만 처리하여 단일 모델이 병목 현상이 되는 것을 방지합니다.

### Function Calling 메커니즘
- 함수는 프로세스를 설명하는 JSON 객체로, 함수 자체, 적격 매개변수, 호출 시점 등의 정보를 포함합니다.
- GPT 모듈은 채팅 응답 대신 함수 호출을 반환하기로 결정할 수 있으며, 불확실할 때는 사용자에게 명확화를 요청합니다.
- 이는 가변 자율성의 핵심 로직을 구현합니다. LLM이 사용자 의도가 명확하다고 판단하면 '제어권을 장악'하여 함수를 실행하고, 불확실하면 '제어권을 포기'하고 추가 정보를 요청합니다.

### 초기 프롬프트 구조
- **Briefing**: 역할 및 상황 설명
- **Restraints**: GPT 표준 행동에서 역할이 벗어나지 않도록 유지
- **Few-shot examples**: 올바른 행동 예시 제공

### 음성 및 데이터 흐름
사용자 음성 → OpenAI Whisper v2 전사 → 에이전트 컨트롤러 → GPT 모듈이 대상 에이전트 결정 → 에이전트 GPT 모듈이 함수 설명과 로봇 상태에 따라 명령을 해석하고 함수 실행 → 응답 → Amazon Polly 음성 합성 출력

### 주요 설계 결정
- **함수 출력 검증**: 시스템은 함수 출력을 검증하고 텍스트 피드백으로 GPT 모듈을 업데이트하여 실제 로봇의 감각 입력을 시뮬레이션합니다. 이는 LLM의 지각 능력 부족을 보완하는 핵심 브리지입니다.
- **물리적 로봇 대신 VR 환경**: 복잡성을 줄이고 유연성을 높이면서도 몰입감을 유지하여 실제 상호작용 역학을 촉진합니다.
- **gpt-4-0613 모델**: 2023년 11월 기준 OpenAI가 함수 호출에 최적화한 최신 GPT 모델로, chat completions API만 사용합니다.

## 핵심 혁신

1. **자율성 협상 메커니즘으로서의 function calling**: 이는 단순한 'LLM 명령 생성'이 아니라, 모델이 '실행'과 '명확화' 사이에서 자율적으로 결정하도록 하여 가변 자율성을 명시적 상태 머신에서 언어 모델의 암묵적 판단으로 전환합니다. 그 참신함은 자율성 수준이 사전 설정되는 것이 아니라 대화 맥락에 따라 동적으로 창발한다는 점입니다.

2. **다중 에이전트 시나리오에서의 분산형 LLM 제어**: 각 로봇은 독립적인 GPT 인스턴스를 가지며, 중앙 컨트롤러가 지시를 배포합니다. 이 아키텍처는 단일 모델이 모든 로봇 상태를 처리할 때 발생하는 컨텍스트 폭발 문제를 피하면서도 모듈성을 유지합니다. 각 로봇은 다른 에이전트에 영향을 주지 않고 함수 설명을 독립적으로 업데이트할 수 있습니다.

3. **LLM 비결정성에 대한 경험적 노출**: 저자들은 낮은 온도 매개변수를 설정해도 출력이 여전히 일관되지 않아 실제 로봇의 유일한 제어 요소로는 부적합하다고 명시합니다. 이 발견 자체가 기여입니다. 'LLM을 컨트롤러로 사용'할 때의 신뢰성 경계를 정량화하여 후속 연구에 기준 인식을 제공합니다.

- **SASSI 질문 29**("때때로 내가 올바른 단어를 사용했는지 의심한다")의 점수 M=5.92, SD=1.73으로 다른 차원보다 유의미하게 높았습니다. 사용자들은 전반적으로 '표현 불안'을 느끼며 자신의 표현이 시스템에 이해되지 않을까 걱정했습니다.

- **P11 사례**: Pluto가 "파란색 쓰레기통"에 가기를 거부하며 함수 목록에 없다고 말했지만, "쓰레기통"으로 가는 것을 제안했습니다. 이는 LLM의 동의어 일반화에 경계가 있으며 대체 방안을 능동적으로 제시함을 설명합니다.

## 경계 및 한계

- **LLM 디버깅 불가능성**: 저자들은 프로그램 디버깅이 어렵다고 인정하며, 연구 기간 중 LLM의 예기치 않은 행동은 경미한 불편만 초래했지만 잠재적 위험은 체계적으로 평가되지 않았습니다.
- **언어 요소**: 독일어 사용이 일부 예기치 않은 행동을 유발할 수 있지만, 함수 설명의 객체 이름은 의도적으로 독일어를 사용하여 모호성을 피했습니다. 그러나 교차 언어 일반화 문제는 별도로 테스트되지 않았습니다.
- **네트워크 의존성**: 대학 네트워크 연결 불안정으로 전사 및 모델 응답 지연이 눈에 띄게 길어졌지만, 연결 끊김이나 완전한 중단은 없었습니다. 클라우드 서비스 아키텍처의 고유한 취약성은 정량화되지 않았습니다.
- **수행하지 않은 것**: 정량적 성공률/오류 지표(작업 완료 시간, 오류율 등)를 측정하지 않았으며, 모든 참가자의 성공만 보고했습니다. GPT 외 다른 LLM을 테스트하지 않았고, 대조 실험을 수행하지 않았으며, 로봇 간 직접 통신을 구현하지 않았고, LLM에 센서나 카메라 정보를 제공하지 않았습니다.
- **논문에 명시되지 않은 것**: 낮은 온도 매개변수의 구체적인 값, 추론 빈도, 하드웨어 구성 등의 엔지니어링 세부 사항은 공개되지 않았습니다.

## 엔지니어링 시사점

1. **함수 설명의 세분성과 용어 일관성을 먼저 검증하라**: P11 사례는 객체 이름의 미세한 차이("파란색 쓰레기통" vs "쓰레기통")가 실행 거부로 이어질 수 있음을 보여줍니다. 재현 시 함수 설명이 가능한 모든 사용자 표현 변형을 포함하도록 하거나 동의어 매핑 계층을 설계해야 합니다.

2. **LLM의 '경직된 순간'을 예상하고 대체 경로를 설계하라**: P12 사례에서 Neptune이 "유리벽이 열렸다"는 물리적 상태 업데이트에 둔감했던 것은 LLM이 환경 변화를 능동적으로 추론하지 않음을 시사합니다. 엔지니어링적으로는 모델 추론에 의존하지 말고 함수 출력 검증 단계에서 환경 상태를 명시적으로 업데이트해야 합니다.

3. **응답 지연이 가장 큰 사용성 위험이다**: 속도 차원 점수 M=5.25(7이 가장 느림)는 사용자가 지연에 민감함을 나타냅니다. 클라우드 API + 전사 + 합성의 파이프라인은 실제 배포에서 네트워크 지터가 중첩되므로, 로컬 모델이나 비동기 처리 아키텍처를 고려해야 합니다.

4. **'표현 불안'은 실제적이고 보편적인 현상이다**: SASSI 질문 29의 높은 점수(M=5.92)는 사용자가 LLM과 상호작용할 때 자신의 표현 방식을 자기 검열함을 시사합니다. 설계상으로는 사용자가 시스템이 이해하는지 추측하게 두지 말고, 전사 시각화와 같은 즉각적인 피드백을 제공하여 불확실성을 완화해야 합니다.

5. **가장 쉽게 빠지는 함정: LLM의 비결정성**: 낮은 온도 매개변수에서도 출력은 여전히 일관되지 않습니다. LLM을 유일한 제어 요소로 사용하지 말고, 긴급 정지 버튼과 같은 인간 개입 채널을 유지하며, 핵심 결정 경로는 결정적 규칙으로 백업하는 것을 고려해야 합니다.
