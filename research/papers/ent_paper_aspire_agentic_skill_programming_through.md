## 概述

ASPIRE 是一个面向机器人持续学习的自改进系统，由闭环执行引擎、持续扩展的技能库和程序化进化搜索三部分组成，旨在让机器人通过迭代探索自主编写、调试并积累可复用的控制程序。系统依赖冻结的前沿 LLM（Claude Opus 4.6）和预定义原语 API，在多个操作基准上大幅超越 VLA 与编码智能体基线，并展现出跨具身迁移的初步能力。

## 它改变了什么

现有机器人学习范式（如 VLA 模型和单轨迹自改进）本质上仍是"任务内优化"：模型在给定轨迹或演示上拟合策略，缺乏对失败的系统性归因与跨任务知识复用。ASPIRE 真正改变的是将"调试"而非"拟合"置于学习循环的中心——它把机器人控制程序的改进视为一个可迭代的软件工程过程，而非端到端的策略学习问题。这一转变意味着系统不再追求从数据中隐式泛化，而是显式地定位失败、验证修复、沉淀技能，从而把单次任务经验转化为可检索、可迁移的库。

另一个关键改变在于探索的组织方式。传统自改进局限于单条轨迹的反复试错，而 ASPIRE 通过进化搜索在程序空间生成多样化候选并并行细化，将探索从"轨迹级"提升到"程序级"。这使得系统能够覆盖更广的行为空间，并在未见过的长时程任务上获得零样本迁移能力——这是单轨迹方法难以企及的。本质上，ASPIRE 把机器人学习重新定义为"程序合成 + 迭代调试"的持续过程，而非"数据拟合"的一次性建模。

## 方法拆解

ASPIRE 由三个核心组件构成，形成一个闭环的持续学习架构：

### 闭环机器人执行引擎
- 对每次感知、规划、抓取和控制调用，记录观测、输入、输出及可能的视觉证据，生成多模态轨迹。
- 关键设计：允许智能体**选择性检查关键原始日志**，而非全量回放，从而逐步定位失败点。
- 修复通过**重新执行验证**，确保修改确实解决了问题而非引入新错误。

### 持续扩展的技能库
- 将验证过的修复提炼为模块化、可迁移的机器人知识，作为上下文指导供未来任务检索。
- 设计决策：**优先存储经过验证的可复用修复**，而非所有经验，以保证知识质量。
- 该库作为检索增强的上下文，为后续任务的程序生成提供先验。

### 程序化进化搜索
- 生成多样化的任务序列和控制程序，通过迭代调试和并行细化超越单轨迹自改进。
- 过程涉及多次 LLM 调用和 rollout：生成候选程序 → 执行 → 定位失败 → 修复 → 再验证，形成进化循环。
- 依赖冻结的前沿 LLM（Claude Opus 4.6）维持调试循环，使用预定义感知、规划、控制原语 API 集合保证调试安全性。

**关键设计决策及理由**：
- **冻结 LLM**：避免训练不稳定，将学习负担转移到程序搜索与技能积累上。
- **预定义原语 API**：限制动作空间，使调试过程可控、可验证，避免自由形式代码带来的不可预测行为。
- **技能库验证优先**：防止错误知识污染库，确保检索到的上下文可靠。

## 关键创新

1. **程序级进化搜索替代轨迹级自改进**：现有方法（如 VLA 微调或单轨迹 RL）在固定轨迹上优化，而 ASPIRE 在程序空间进行多样化生成与并行细化。这一创新将探索维度从"状态-动作对"提升到"可执行程序"，使系统能覆盖更广的行为策略空间，并支持显式的失败归因与修复验证。

2. **验证驱动的技能库设计**：不同于常见的经验回放或演示缓存，ASPIRE 只存储经过重新执行验证的修复，将其提炼为模块化知识。这一设计保证了库中条目的可靠性，使检索到的上下文能真正指导新任务，而非引入噪声——这是持续学习系统中知识质量的关键保障。

3. **跨具身迁移的显式支持**：通过将技能抽象为与具体机器人 API 解耦的程序模块，ASPIRE 展示了仿真中发现的技能可迁移到不同具身（不同机器人、不同 API），显著降低真实机器人编程的 token 成本。这一能力源于技能库的模块化设计，而非端到端模型的隐式泛化。

## 边界与局限

- **尚未成为完全自主的真实世界学习者**：真实部署仍需鲁棒的成功检测、安全重置、安全监控和校准，意味着系统在仿真中的表现可能无法直接迁移到真实环境的开放条件。
- **依赖冻结的前沿 LLM**：未验证更小或更弱的 LLM 能否维持调试循环。若 LLM 能力不足，进化搜索的修复质量可能崩溃，系统鲁棒性存疑。
- **受限于预定义原语 API**：固定的感知、规划、控制原语集合限制了可表达的行为范围。对于需要新颖动作的任务，系统可能无法生成有效程序。
- **长期记忆管理不完整**：技能库优先存储验证过的修复，但未完全解决库增长带来的过时、冗余、误导问题。随着库规模扩大，检索质量可能下降。
- **计算密集型搜索循环**：调试和进化搜索每任务消耗大量 LLM 调用和 rollout，扩展需要更廉价的推理或更样本高效的搜索。这意味着当前方法在计算资源受限场景下可能不实用。

## Overview

ASPIRE is a self-improving system for robot continual learning, composed of a closed-loop execution engine, a continuously expanding skill library, and programmatic evolutionary search. It aims to enable robots to autonomously write, debug, and accumulate reusable control programs through iterative exploration. The system relies on a frozen frontier LLM (Claude Opus 4.6) and predefined primitive APIs, significantly outperforming VLA and coding-agent baselines across multiple manipulation benchmarks, while demonstrating preliminary cross-embodiment transfer capabilities.

## What It Changes

Existing robot learning paradigms (such as VLA models and single-trajectory self-improvement) remain essentially "within-task optimization": models fit policies on given trajectories or demonstrations, lacking systematic failure attribution and cross-task knowledge reuse. What ASPIRE truly changes is placing "debugging" rather than "fitting" at the center of the learning loop—it treats the improvement of robot control programs as an iterative software engineering process, rather than an end-to-end policy learning problem. This shift means the system no longer pursues implicit generalization from data, but instead explicitly localizes failures, verifies fixes, and consolidates skills, thereby transforming single-task experience into a retrievable, transferable library.

Another key change lies in the organization of exploration. Traditional self-improvement is limited to repeated trial-and-error on a single trajectory, whereas ASPIRE uses evolutionary search to generate diverse candidates in program space and refine them in parallel, elevating exploration from the "trajectory level" to the "program level." This enables the system to cover a broader behavioral space and achieve zero-shot transfer on unseen long-horizon tasks—something single-trajectory methods struggle to attain. In essence, ASPIRE redefines robot learning as a continuous process of "program synthesis + iterative debugging," rather than a one-shot modeling exercise of "data fitting."

## Method Breakdown

ASPIRE consists of three core components forming a closed-loop continual learning architecture:

### Closed-Loop Robot Execution Engine
- For each perception, planning, grasping, and control call, it records observations, inputs, outputs, and possible visual evidence, generating multimodal trajectories.
- Key design: allows the agent to **selectively inspect critical primitive logs** rather than full replays, thereby progressively localizing failure points.
- Fixes are verified through **re-execution validation**, ensuring that modifications actually resolve the issue rather than introducing new errors.

### Continuously Expanding Skill Library
- Distills validated fixes into modular, transferable robot knowledge, serving as contextual guidance for retrieval in future tasks.
- Design decision: **prioritizes storing validated, reusable fixes** rather than all experiences, ensuring knowledge quality.
- The library acts as retrieval-augmented context, providing priors for program generation in subsequent tasks.

### Programmatic Evolutionary Search
- Generates diverse task sequences and control programs, surpassing single-trajectory self-improvement through iterative debugging and parallel refinement.
- The process involves multiple LLM calls and rollouts: generate candidate programs → execute → localize failures → fix → re-validate, forming an evolutionary loop.
- Relies on a frozen frontier LLM (Claude Opus 4.6) to sustain the debugging loop, using a predefined set of perception, planning, and control primitive APIs to ensure debugging safety.

**Key design decisions and rationale**:
- **Frozen LLM**: avoids training instability, shifting the learning burden to program search and skill accumulation.
- **Predefined primitive APIs**: constrain the action space, making the debugging process controllable and verifiable, avoiding unpredictable behavior from free-form code.
- **Validation-first skill library**: prevents erroneous knowledge from contaminating the library, ensuring retrieved context is reliable.

## Key Innovations

1. **Program-level evolutionary search replacing trajectory-level self-improvement**: Existing methods (such as VLA fine-tuning or single-trajectory RL) optimize on fixed trajectories, whereas ASPIRE performs diverse generation and parallel refinement in program space. This innovation elevates the exploration dimension from "state-action pairs" to "executable programs," enabling the system to cover a broader space of behavioral policies and supporting explicit failure attribution and fix validation.

2. **Validation-driven skill library design**: Unlike common experience replay or demonstration caches, ASPIRE stores only fixes validated through re-execution, distilling them into modular knowledge. This design ensures the reliability of library entries, allowing retrieved context to genuinely guide new tasks rather than introducing noise—a critical guarantee of knowledge quality in continual learning systems.

3. **Explicit support for cross-embodiment transfer**: By abstracting skills into program modules decoupled from specific robot APIs, ASPIRE demonstrates that skills discovered in simulation can transfer to different embodiments (different robots, different APIs), significantly reducing token costs for real-robot programming. This capability stems from the modular design of the skill library, rather than implicit generalization in end-to-end models.

## Boundaries and Limitations

- **Not yet a fully autonomous real-world learner**: Real-world deployment still requires robust success detection, safe resetting, safety monitoring, and calibration, implying that the system's performance in simulation may not directly transfer to open conditions in real environments.
- **Reliance on a frozen frontier LLM**: It is unverified whether smaller or weaker LLMs can sustain the debugging loop. If LLM capability is insufficient, the fix quality of evolutionary search may collapse, raising concerns about system robustness.
- **Constrained by predefined primitive APIs**: The fixed set of perception, planning, and control primitives limits the range of expressible behaviors. For tasks requiring novel actions, the system may fail to generate effective programs.
- **Incomplete long-term memory management**: The skill library prioritizes storing validated fixes but does not fully address issues of obsolescence, redundancy, and misleading entries as the library grows. Retrieval quality may degrade as the library scales.
- **Computationally intensive search loop**: Debugging and evolutionary search consume substantial LLM calls and rollouts per task; scaling requires cheaper inference or more sample-efficient search. This implies the current approach may be impractical in compute-constrained scenarios.

## Engineering Implications

- **Verify LLM dependency first**: The system relies entirely on Claude Opus 4.6's debugging capability. Before reproduction, confirm the model's availability and cost, and test whether smaller models can maintain fix quality on your tasks—this is the biggest risk point.
- **Primitive API design determines the ceiling**: The predefined primitive set directly limits expressible behaviors. When reproducing, first map out the perception/planning/control primitives required by your tasks to ensure sufficient behavioral coverage; otherwise, evolutionary search cannot generate effective programs.
- **The validation mechanism of the skill library is core**: Do not skip the "re-execution validation" step. If unvalidated fixes are stored directly, library quality will rapidly degrade, causing retrieved context to mislead subsequent tasks. Implement a strict validation pipeline.
- **Assess computational costs early**: Evolutionary search consumes substantial LLM calls and rollouts per task. Under resource constraints, first validate search efficiency on small-scale tasks before deciding whether to scale to long-horizon tasks.
- **Reproduction notes for cross-embodiment transfer**: Preliminary evidence suggests skills can transfer across embodiments, but only if skills are abstracted as modules decoupled from APIs. When reproducing, ensure skill library entries do not contain embodiment-specific parameters; otherwise, transfer will fail.
- **Most likely pitfall**: Success detection and safe-reset mechanisms. The paper explicitly acknowledges these components are needed for real-world deployment but provides no implementation details. They may be irrelevant in simulation, but must be addressed before migrating to real robots.

기존 로봇 학습 패러다임(예: VLA 모델 및 단일 궤적 자기 개선)은 본질적으로 여전히 "작업 내 최적화"이다. 모델은 주어진 궤적이나 데모에 대해 정책을 피팅하며, 실패에 대한 체계적 귀인과 교차 작업 지식 재사용이 부족하다. ASPIRE가 진정으로 바꾸는 것은 "피팅"이 아닌 "디버깅"을 학습 루프의 중심에 두는 것이다. 즉, 로봇 제어 프로그램의 개선을 엔드투엔드 정책 학습 문제가 아닌 반복 가능한 소프트웨어 엔지니어링 프로세스로 간주한다. 이러한 전환은 시스템이 더 이상 데이터에서 암시적으로 일반화하는 것을 추구하지 않고, 실패를 명시적으로 위치시키고, 수정을 검증하고, 스킬을 침전시켜 단일 작업 경험을 검색 가능하고 전이 가능한 라이브러리로 전환함을 의미한다.

또 다른 핵심 변화는 탐색의 조직 방식에 있다. 기존 자기 개선은 단일 궤적의 반복적 시행착오에 국한되지만, ASPIRE는 진화 검색을 통해 프로그램 공간에서 다양한 후보를 생성하고 병렬로 정제하여 탐색을 "궤적 수준"에서 "프로그램 수준"으로 끌어올린다. 이를 통해 시스템은 더 넓은 행동 공간을 커버하고, 보지 못한 장기 작업에서 제로샷 전이 능력을 얻을 수 있다. 이는 단일 궤적 방법으로는 달성하기 어렵다. 본질적으로 ASPIRE는 로봇 학습을 "데이터 피팅"의 일회성 모델링이 아닌 "프로그램 합성 + 반복 디버깅"의 지속적 프로세스로 재정의한다.

## 방법 분해

ASPIRE는 세 가지 핵심 구성 요소로 구성되며, 폐루프 지속 학습 아키텍처를 형성한다:

### 폐루프 로봇 실행 엔진
- 각 인식, 계획, 그리핑 및 제어 호출에 대해 관측, 입력, 출력 및 가능한 시각적 증거를 기록하여 다중 모달 궤적을 생성한다.
- 핵심 설계: 에이전트가 전체 재생이 아닌 **핵심 원시 로그를 선택적으로 검사**할 수 있게 하여 실패 지점을 점진적으로 위치시킨다.
- 수정은 **재실행 검증**을 통해 이루어지며, 수정이 실제로 문제를 해결했는지, 새로운 오류를 도입하지 않았는지 확인한다.

### 지속적으로 확장되는 스킬 라이브러리
- 검증된 수정을 모듈화되고 전이 가능한 로봇 지식으로 정제하여 향후 작업 검색을 위한 컨텍스트 지침으로 제공한다.
- 설계 결정: 지식 품질을 보장하기 위해 모든 경험이 아닌 **검증된 재사용 가능한 수정을 우선 저장**한다.
- 이 라이브러리는 검색 증강 컨텍스트로 작동하여 후속 작업의 프로그램 생성을 위한 사전 지식을 제공한다.

### 절차적 진화 검색
- 다양한 작업 시퀀스와 제어 프로그램을 생성하고, 반복적 디버깅과 병렬 정제를 통해 단일 궤적 자기 개선을 능가한다.
- 프로세스는 여러 LLM 호출과 롤아웃을 포함한다: 후보 프로그램 생성 → 실행 → 실패 위치 파악 → 수정 → 재검증, 진화 루프를 형성한다.
- 동결된 최첨단 LLM(Claude Opus 4.6)에 의존하여 디버깅 루프를 유지하고, 사전 정의된 인식, 계획, 제어 프리미티브 API 세트를 사용하여 디버깅 안전성을 보장한다.

**핵심 설계 결정 및 근거**:
- **동결 LLM**: 훈련 불안정성을 피하고 학습 부담을 프로그램 검색과 스킬 축적으로 전환한다.
- **사전 정의된 프리미티브 API**: 행동 공간을 제한하여 디버깅 프로세스를 제어 가능하고 검증 가능하게 만들고, 자유 형식 코드로 인한 예측 불가능한 행동을 피한다.
- **스킬 라이브러리 검증 우선**: 잘못된 지식이 라이브러리를 오염시키는 것을 방지하고 검색된 컨텍스트의 신뢰성을 보장한다.

(구체적인 알고리즘 의사 코드, 하이퍼파라미터, 검색 전략 세부 사항: 논문에 명시되지 않음)

## 핵심 혁신

1. **프로그램 수준 진화 검색이 궤적 수준 자기 개선을 대체**: 기존 방법(예: VLA 미세 조정 또는 단일 궤적 RL)은 고정된 궤적에서 최적화하지만, ASPIRE는 프로그램 공간에서 다양한 생성과 병렬 정제를 수행한다. 이 혁신은 탐색 차원을 "상태-행동 쌍"에서 "실행 가능한 프로그램"으로 끌어올려 시스템이 더 넓은 행동 정책 공간을 커버하고 명시적 실패 귀인과 수정 검증을 지원한다.

2. **검증 기반 스킬 라이브러리 설계**: 일반적인 경험 재생이나 데모 캐시와 달리, ASPIRE는 재실행 검증을 통과한 수정만 저장하고 이를 모듈화된 지식으로 정제한다. 이 설계는 라이브러리 항목의 신뢰성을 보장하여 검색된 컨텍스트가 노이즈를 도입하는 대신 실제로 새 작업을 안내할 수 있게 한다. 이는 지속 학습 시스템에서 지식 품질의 핵심 보장이다.

3. **교차 구현 전이의 명시적 지원**: 스킬을 특정 로봇 API와 분리된 프로그램 모듈로 추상화함으로써, ASPIRE는 시뮬레이션에서 발견된 스킬이 다른 구현(다른 로봇, 다른 API)으로 전이될 수 있음을 보여주며, 실제 로봇 프로그래밍의 토큰 비용을 크게 줄인다. 이 능력은 엔드투엔드 모델의 암시적 일반화가 아닌 스킬 라이브러리의 모듈화 설계에서 비롯된다.

## 실험 및 결과

실험은 다양한 로봇 조작 벤치마크 작업을 포괄하며, 비교 베이스라인 및 핵심 지표는 다음과 같다:

| 지표 | ASPIRE | VLA 베이스라인 | 코딩 에이전트 베이스라인 |
|------|--------|----------|----------------|
| 유지 성공률 (%) | 명시되지 않음 | 명시되지 않음 | 명시되지 않음 |
| 출력 토큰 (M) | 명시되지 않음 | 명시되지 않음 | 명시되지 않음 |
| 총 토큰 (M) | 명시되지 않음 | 명시되지 않음 | 명시되지 않음 |

(구체적인 수치는 사실 요점에 제공되지 않았으며, 차트 레이블은 존재하지만 텍스트 데이터는 없음)

**정성적 결론**:
- ASPIRE는 여러 벤치마크에서 기존 VLA 및 코딩 에이전트 베이스라인을 **크게 능가**한다.
- **보지 못한 장기 작업**에서 **강력한 제로샷 전이** 능력을 보여준다.
- **교차 구현 전이**: 초기 증거는 시뮬레이션에서 발견된 스킬이 다른 로봇 구현(API가 다름)으로 전이될 수 있음을 보여주며, 실제 로봇 프로그래밍의 토큰 비용을 크게 줄인다.

**결과 해석**: 구체적인 수치는 부족하지만, "크게 능가"와 "강력한 제로샷 전이"의 정성적 표현은 프로그램 수준 탐색 + 스킬 라이브러리의 조합이 엔드투엔드 VLA 및 순수 코딩 에이전트보다 일반화에서 우수함을 시사한다. 교차 구현 전이의 초기 증거는 특히 주목할 만하다. 이는 스킬 라이브러리의 모듈화된 지식이 특정 로봇 플랫폼을 넘어서는 일반성을 가짐을 암시한다.

(실험 플랫폼, 작업 목록, 훈련 구성, 추론 빈도, 하드웨어 세부 사항: 논문에 명시되지 않음)

## 경계 및 한계

- **완전한 자율적 실제 세계 학습자가 아님**: 실제 배포는 여전히 견고한 성공 감지, 안전 리셋, 안전 모니터링 및 보정이 필요하며, 이는 시뮬레이션에서의 성능이 실제 환경의 개방 조건으로 직접 전이되지 않을 수 있음을 의미한다.
- **동결된 최첨단 LLM에 의존**: 더 작거나 약한 LLM이 디버깅 루프를 유지할 수 있는지 검증되지 않았다. LLM 능력이 부족하면 진화 검색의 수정 품질이 붕괴될 수 있으며, 시스템 견고성에 의문이 제기된다.
- **사전 정의된 프리미티브 API에 제한**: 고정된 인식, 계획, 제어 프리미티브 세트는 표현 가능한 행동 범위를 제한한다. 새로운 행동이 필요한 작업의 경우 시스템이 유효한 프로그램을 생성하지 못할 수 있다.
- **장기 메모리 관리 불완전**: 스킬 라이브러리는 검증된 수정을 우선 저장하지만, 라이브러리 성장으로 인한 구식, 중복, 오도 문제를 완전히 해결하지는 못한다. 라이브러리 규모가 커짐에 따라 검색 품질이 저하될 수 있다.
- **계산 집약적 검색 루프**: 디버깅 및 진화 검색은 작업당 많은 LLM 호출과 롤아웃을 소비하며, 확장에는 더 저렴한 추론 또는 더 샘플 효율적인 검색이 필요하다. 이는 현재 방법이 계산 자원이 제한된 시나리오에서 실용적이지 않을 수 있음을 의미한다.

## 공학적 시사점

- **LLM 의존성 먼저 확인**: 시스템은 전적으로 Claude Opus 4.6의 디버깅 능력에 의존한다. 재현 전에 해당 모델의 가용성과 비용을 확인하고, 더 작은 모델이 작업에서 수정 품질을 유지할 수 있는지 테스트하라. 이것이 가장 큰 위험 요소이다.
- **프리미티브 API 설계가 상한을 결정**: 사전 정의된 프리미티브 세트는 표현 가능한 행동을 직접 제한한다. 재현 시 작업에 필요한 인식/계획/제어 프리미티브를 먼저 정리하여 충분한 행동 공간을 커버하는지 확인하라. 그렇지 않으면 진화 검색이 유효한 프로그램을 생성할 수 없다.
- **스킬 라이브러리의 검증 메커니즘이 핵심**: "재실행 검증" 단계를 건너뛰지 마라. 검증되지 않은 수정을 직접 저장하면 라이브러리 품질이 빠르게 저하되어 검색된 컨텍스트가 후속 작업을 오도할 수 있다. 엄격한 검증 파이프라인을 구현하는 것이 좋다.
- **계산 비용 사전 평가**: 진화 검색은 작업당 많은 LLM 호출과 롤아웃을 소비한다. 자원이 제한된 경우 먼저 소규모 작업에서 검색 효율성을 검증한 후 장기 작업으로 확장할지 결정하라.
- **교차 구현 전이 재현 시 주의**: 초기 증거는 스킬이 교차 구현으로 전이될 수 있음을 보여주지만, 전제는 스킬이 API와 분리된 모듈로 추상화되는 것이다. 재현 시 스킬 라이브러리 항목에 구현 특정 매개변수가 포함되지 않도록 해야 한다. 그렇지 않으면 전이가 실패한다.
- **가장 쉽게 함정에 빠지는 부분**: 성공 감지 및 안전 리셋 메커니즘. 논문은 실제 배포에 이러한 구성 요소가 필요함을 명시적으로 인정하지만 구현 세부 사항은 제공하지 않는다. 시뮬레이션에서는 무시할 수 있지만 실제 로봇으로 전이하기 전에 반드시 보완해야 한다.
