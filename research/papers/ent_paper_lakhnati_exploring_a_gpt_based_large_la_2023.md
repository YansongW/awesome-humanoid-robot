## 概述

本文探索将现成的 GPT-4 大语言模型集成到基于 Unity/VR 的人-机器人团队模拟环境中，通过 OpenAI function calling 将非结构化自然语言映射为结构化机器人动作，以实现可变自主性。研究基于 12 名参与者的探索性被试内实验，结合 SASSI 问卷与主题分析，揭示了用户与 LLM 驱动机器人交互中的关键行为模式与系统局限。

## 它改变了什么

这项工作的真正价值不在于“用 GPT 控制机器人”这一表面命题，而在于它把 LLM 的非确定性与机器人控制所需的确定性之间的张力，从一个理论担忧变成了一个可观察、可分析的实证对象。传统 HRI 研究要么依赖 Wizard-of-Oz 模拟完美 AI，要么使用预定脚本的对话系统，两者都回避了 LLM 在实际部署中“会犯错、会犹豫、会过度解释”的真实行为。作者选择现成的 GPT-4 而非微调模型，本身就是一种立场：先进 AI 技术已达到非 AI 专家可应用的水平，因此探索其原生行为模式比追求定制优化更有现实意义。

更重要的是，这项研究改变了我们对“可变自主性”的理解方式。以往可变自主性通常被设计为一种显式的控制机制（如用户通过界面切换自主等级），而本文展示了一种隐式的、由对话协商产生的自主性分配：LLM 可以在“夺取控制”执行函数与“放弃控制”请求澄清之间自主决定。这种自主性不是由用户显式选择的，而是在交互中涌现的，这既是其创新之处，也是其问题之源——用户往往不清楚机器人何时会自主行动、何时需要明确指令。

## 方法拆解

### 系统架构
- **中央控制器 + 每机器人独立 GPT 实例**：控制器基于对话历史解释用户输入并分发给相关代理（0…n 个），避免所有代理处理每个输入，兼顾可扩展性与计算效率。
- **函数调用作为人-机接口**：采用 OpenAI function calling，将非结构化自然语言映射为结构化机器人动作。函数本质是描述过程的 JSON 对象，包含函数本身、合格参数、调用时机等。GPT 模块可决定不回答而返回函数调用，或在不明确时向用户请求澄清。

### 提示工程
- **Briefing**：角色与情境描述（如“你是黄色机器人代理 Jupiter…”）。
- **Restraints**：指示模型保持角色（如“永远不要打破角色。永远不要提及你是 AI 模型”）。
- **Few-shot 示例**：如控制器被指示当与单个代理继续对话时“you”可能指该代理，当与多个代理对话时“you”可能指所有代理。

### 实现细节
- **平台**：Unity 2022.3.4f1 创建的 VR 环境，优化用于 Meta Quest 2；通过 Srcnalt 的 OpenAI-Unity 包连接 OpenAI 端点。
- **语音链路**：输入用 OpenAI Whisper v2 转录，输出用 Amazon Polly 合成声音。
- **模型**：所有代理使用 gpt-4-0613（截至 2023 年 11 月最新的优化函数调用的 GPT 模型），仅使用聊天补全 API。
- **函数输出验证**：系统验证函数输出并用文本反馈更新 GPT 模块，模拟真实场景中机器人的感官输入（如摄像头和传感器）。例如，若代理尝试拾取物体，系统评估代理与物体间距离并更新模型。

### 实验设计
- 探索性被试内研究，12 名参与者（P3–P14，前两名因系统重大变更被排除），平均年龄 36.45 岁（SD = 14.57），9 女 3 男。
- 共 7 个递进任务，共享相同起始位置，涉及多机器人协调、时序约束（如任务 5 中门定时器故意设置得足够低）、物体属性（如花瓶需在床翻转前拾起）。
- 数据采集：5 小时 28 分钟实验数据 + 3 小时 46 分钟访谈数据；访谈用 Whisper 转录后手动修正，采用主题分析（三名研究者迭代编码）。

## 关键创新

1. **函数调用作为可变自主性的实现机制**：这是本文最核心的方法论创新。函数调用不仅是一种接口技术，更是一种自主性分配机制——LLM 在“确定用户意图时夺取控制执行函数”与“不确定时放弃控制请求澄清”之间自主决策。函数描述同时为模型提供能力边界的脚手架，且高度可扩展可修改。相比文本本体方法，函数特性更有效地约束 LLM 行为。

2. **去中心化的多代理 GPT 架构**：中央控制器 + 每机器人独立 GPT 实例的设计，避免了所有代理处理每个输入的计算浪费，同时允许每个机器人保持独立的对话历史和角色一致性。这种架构天然支持异构机器人（Jupiter 黄色强壮、Pluto 红色可飞、Neptune 蓝色轮式）的差异化行为。

3. **VR 环境作为 LLM 驱动 HRI 的测试平台**：选择 VR 而非物理机器人，在简化复杂性和增加灵活性的同时保持沉浸感。这一决策使研究者能够系统性地操纵任务复杂度（从单代理单动作到多代理时序协调），而无需承担物理机器人的成本和风险。

### 关键行为发现
- **用户不将机器人视为平等对话伙伴**：所有参与者都将机器人视为指令接收者，但风格分化为命令式（如 P14）与对话式（如 P7）。对话式参与者更可能向机器人寻求建议，但此类问题总体上是例外。
- **LLM 过度健谈**：机器人倾向于提供冗长解释并在不确定时请求澄清，导致用户感觉“像与幼儿交谈”（P4、P5）。P9 对机器人要求先接近物体再拾取感到惊讶：“I expected it to act on the instruction directly.”
- **功能描述的过度挑剔**：P11 说“Pluto, please go to the blue trash can”，Pluto 回复“Sorry, I can only go to locations that are defined in my functions.” SASSI 问题 29“I sometimes wondered if I was using the right word”平均得分 5.92（SD = 1.73）。
- **自主性期望差异**：P3 说“In certain situations, I didn’t realize I had to explicitly instruct the system to approach an object before picking it up.” 但也有机器人自主分解任务的例子：P8 要求 Jupiter“take three plates and throw them in the trash bin”时，机器人连续三次执行了正确的功能三元组（移动、拾取、丢弃）。
- **响应延迟是核心痛点**：SASSI Speed 维度 M = 5.25（SD = 1.57），P9 说“the robots’ feedback always came late. There was a lot of narration, and by the time they responded, I had already continued speaking.”

## 边界与局限

- **LLM 非确定性**：即使在低温度下输出也不一致，作者明确承认 GPT 无法作为真实机器人的控制元素，需要额外模块支持以确保一致性。
- **云服务延迟**：GPT API 引入延迟，大学互联网连接的不稳定性加剧了问题；虽然没有断开或完全中断，但转录和模型响应的延迟有时明显更长。
- **语言限制**：实验使用德语，可能是某些意外行为的原因，尤其是功能方面，尽管功能描述中的对象被故意赋予德语名称以防止 LLM 消歧。
- **未做之事**：未进行长期部署测试、不同 LLM 版本的对比实验、非英语语言支持测试；系统在最初两次会话后经历了重大变更（P1 和 P2 被排除）。
- **错误传播**：框架继承 LLM 的潜在偏见和错误向前传播问题（错误输出成为未来输入的一部分）。
- **LLM 幻觉**：LLM 有时会产生幻觉，说服参与者相信不真实的事情，并重复或过度分享与任务无关的信息。

## 工程启示

- **先核对功能描述的粒度与命名一致性**：实验中最常见的失败模式是 LLM 对功能描述中的词语过度挑剔，拒绝执行名称略有偏差的对象（如“blue trash can” vs. “trash bin”）。复现时应仔细设计功能描述中的对象命名，并在提示中明确同义词映射，或增加别名机制。
- **延迟是最大的工程挑战**：SASSI Speed 得分 5.25 表明响应延迟严重影响了用户体验。如果复现，建议考虑本地化 LLM 推理、缓存常见指令的响应、或引入流式输出以降低感知延迟。任务 5 中门定时器故意设置得足够低，使顺序命令因延迟而显得不可行——这提示时序敏感任务需要额外的调度机制。
- **用户校准至关重要**：参与者对机器人自主性的期望差异极大，且这种差异在交互初期就已定型且难以改变。建议在实验开始前增加一个校准阶段，明确告知用户机器人的能力边界和自主性策略，以减少“我没想到要明确指示它先接近物体”这类认知落差。
- **多代理架构的通信瓶颈**：当前框架允许多机器人非结构化交互，但机器人之间缺乏直接通信机制。在协作任务（如任务 7 中 Jupiter 和 Neptune 一起翻转床）中，文本表示和统一对话日志不足，响应应聚类以简化用户响应并避免重复。代理控制器可承担更复杂的代理间通信控制。
- **干预机制缺失**：由于转录和 GPT 模块的处理时间，常规沟通渠道不适合干预。作者建议引入立即停止机器人的按钮，无论 LLM 当前状态如何——这是任何实际部署中必须优先考虑的安全机制。

## Overview

This paper explores integrating an off-the-shelf GPT-4 large language model into a Unity/VR-based human-robot team simulation environment, mapping unstructured natural language to structured robot actions via OpenAI function calling to achieve variable autonomy. Based on an exploratory within-subjects study with 12 participants, combining the SASSI questionnaire and thematic analysis, it reveals key behavioral patterns and system limitations in user interaction with LLM-driven robots.

## What It Changes

The real value of this work lies not in the superficial proposition of "using GPT to control robots," but in transforming the tension between LLM nondeterminism and the determinism required for robot control from a theoretical concern into an observable, analyzable empirical object. Traditional HRI research either relies on Wizard-of-Oz simulations of perfect AI or uses scripted dialogue systems, both of which sidestep the real-world behavior of LLMs in deployment—"making mistakes, hesitating, over-explaining." The authors' choice of off-the-shelf GPT-4 over fine-tuned models is itself a stance: advanced AI technology has reached a level where non-AI experts can apply it, so exploring its native behavioral patterns is more practically relevant than pursuing customized optimization.

More importantly, this study changes how we understand "variable autonomy." Previously, variable autonomy was typically designed as an explicit control mechanism (e.g., users switching autonomy levels via an interface), whereas this paper demonstrates an implicit, dialogue-negotiated allocation of autonomy: the LLM can autonomously decide between "taking control" to execute functions and "relinquishing control" to request clarification. This autonomy is not explicitly selected by the user but emerges in interaction—which is both its innovation and its source of problems: users often do not know when the robot will act autonomously versus when it requires explicit instructions.

## Method Breakdown

### System Architecture
- **Central controller + per-robot independent GPT instances**: The controller interprets user input based on dialogue history and distributes it to relevant agents (0…n), avoiding all agents processing every input, balancing scalability and computational efficiency.
- **Function calling as the human-robot interface**: Uses OpenAI function calling to map unstructured natural language to structured robot actions. Functions are essentially JSON objects describing procedures, including the function itself, valid parameters, invocation timing, etc. The GPT module can decide not to answer but instead return a function call, or request clarification from the user when uncertain.

### Prompt Engineering
- **Briefing**: Role and scenario descriptions (e.g., "You are the yellow robot agent Jupiter…").
- **Restraints**: Instructions to maintain role (e.g., "Never break character. Never mention that you are an AI model").
- **Few-shot examples**: E.g., the controller is instructed that when continuing a dialogue with a single agent, "you" may refer to that agent, and when conversing with multiple agents, "you" may refer to all agents.

### Implementation Details
- **Platform**: VR environment created with Unity 2022.3.4f1, optimized for Meta Quest 2; connected to the OpenAI endpoint via Srcnalt's OpenAI-Unity package.
- **Voice pipeline**: Input transcribed with OpenAI Whisper v2, output synthesized with Amazon Polly.
- **Model**: All agents use gpt-4-0613 (the latest function-calling-optimized GPT model as of November 2023), using only the chat completions API.
- **Function output validation**: The system validates function outputs and updates the GPT module with textual feedback, simulating real-world robot sensory input (e.g., cameras and sensors). For example, if an agent attempts to pick up an object, the system evaluates the distance between the agent and the object and updates the model.

### Experimental Design
- Exploratory within-subjects study with 12 participants (P3–P14; the first two were excluded due to major system changes), mean age 36.45 years (SD = 14.57), 9 female, 3 male.
- A total of 7 progressive tasks sharing the same starting position, involving multi-robot coordination, timing constraints (e.g., in Task 5, the door timer was deliberately set low enough), and object properties (e.g., the vase must be picked up before the bed is flipped).
- Data collection: 5 hours 28 minutes of experimental data + 3 hours 46 minutes of interview data; interviews were transcribed with Whisper and manually corrected, then analyzed using thematic analysis (three researchers iteratively coded).

## Key Innovations

1. **Function calling as a mechanism for variable autonomy**: This is the paper's most central methodological innovation. Function calling is not merely an interface technique but an autonomy allocation mechanism—the LLM autonomously decides between "taking control to execute functions when user intent is clear" and "relinquishing control to request clarification when uncertain." Function descriptions simultaneously scaffold the model's capability boundaries and are highly scalable and modifiable. Compared to text ontology approaches, function properties more effectively constrain LLM behavior.

2. **Decentralized multi-agent GPT architecture**: The central controller + per-robot independent GPT instance design avoids the computational waste of all agents processing every input while allowing each robot to maintain independent dialogue history and role consistency. This architecture naturally supports differentiated behavior across heterogeneous robots (Jupiter, yellow and strong; Pluto, red and flying; Neptune, blue and wheeled).

3. **VR environment as a testbed for LLM-driven HRI**: Choosing VR over physical robots simplifies complexity and increases flexibility while maintaining immersion. This decision enables researchers to systematically manipulate task complexity (from single-agent single-action to multi-agent temporal coordination) without the cost and risk of physical robots.

### Key Behavioral Findings
- **Users do not treat robots as equal conversational partners**: All participants viewed robots as instruction receivers, but styles diverged into imperative (e.g., P14) and conversational (e.g., P7). Conversational participants were more likely to seek advice from robots, but such questions were generally the exception.
- **LLM over-talkativeness**: Robots tended to provide lengthy explanations and request clarification when uncertain, leading users to feel "like talking to a toddler" (P4, P5). P9 was surprised that the robot required approaching an object before picking it up: "I expected it to act on the instruction directly."
- **Over-pickiness with function descriptions**: P11 said "Pluto, please go to the blue trash can," and Pluto replied "Sorry, I can only go to locations that are defined in my functions." SASSI question 29, "I sometimes wondered if I was using the right word," averaged 5.92 (SD = 1.73).
- **Autonomy expectation differences**: P3 said, "In certain situations, I didn't realize I had to explicitly instruct the system to approach an object before picking it up." However, there were also examples of robots autonomously decomposing tasks: when P8 asked Jupiter to "take three plates and throw them in the trash bin," the robot correctly executed the function triple (move, pick up, drop) three consecutive times.
- **Response latency is a core pain point**: SASSI Speed dimension M = 5.25 (SD = 1.57); P9 said, "the robots' feedback always came late. There was a lot of narration, and by the time they responded, I had already continued speaking."

## Boundaries and Limitations

- **LLM nondeterminism**: Outputs are inconsistent even at low temperatures; the authors explicitly acknowledge that GPT cannot serve as a control element for real robots and requires additional modules to ensure consistency.
- **Cloud service latency**: GPT API introduces latency, exacerbated by unstable university internet connections; although there were no disconnections or complete outages, transcription and model response delays were sometimes noticeably longer.
- **Language limitations**: The experiment was conducted in German, which may explain some unexpected behaviors, especially regarding functions, although objects in function descriptions were deliberately given German names to prevent LLM disambiguation.
- **What was not done**: No long-term deployment testing, no comparative experiments across different LLM versions, no non-English language support testing; the system underwent major changes after the first two sessions (P1 and P2 were excluded).
- **Error propagation**: The framework inherits LLM potential biases and error-forward-propagation issues (erroneous outputs become part of future inputs).
- **LLM hallucination**: The LLM sometimes hallucinated, convincing participants of untrue things, and repeated or over-shared task-irrelevant information.

## Engineering Implications

- **First verify the granularity and naming consistency of function descriptions**: The most common failure mode in the experiment was the LLM being overly picky about words in function descriptions, refusing to execute objects with slightly different names (e.g., "blue trash can" vs. "trash bin"). When reproducing, carefully design object naming in function descriptions and explicitly map synonyms in prompts, or add an alias mechanism.
- **Latency is the biggest engineering challenge**: The SASSI Speed score of 5.25 indicates that response latency severely impacted user experience. If reproducing, consider local LLM inference, caching responses to common instructions, or introducing streaming output to reduce perceived latency. In Task 5, the door timer was deliberately set low enough that sequential commands appeared infeasible due to latency—this suggests timing-sensitive tasks require additional scheduling mechanisms.
- **User calibration is critical**: Participant expectations of robot autonomy varied greatly, and this variation was established early in interaction and difficult to change. It is recommended to add a calibration phase before the experiment, explicitly informing users of the robot's capability boundaries and autonomy strategy, to reduce cognitive gaps such as "I didn't realize I had to explicitly instruct it to approach the object first."
- **Communication bottleneck in multi-agent architecture**: The current framework allows unstructured interaction across multiple robots, but robots lack direct communication mechanisms. In collaborative tasks (e.g., Jupiter and Neptune flipping the bed together in Task 7), textual representations and unified dialogue logs are insufficient; responses should be clustered to simplify user responses and avoid repetition. The agent controller could take on more complex inter-agent communication control.
- **Missing intervention mechanisms**: Due to processing times in transcription and the GPT module, conventional communication channels are unsuitable for intervention. The authors recommend adding a button to immediately stop robots regardless of the LLM's current state—this is a safety mechanism that must be prioritized in any real deployment.

## 개요

본 논문은 기성 GPT-4 대규모 언어 모델을 Unity/VR 기반 인간-로봇 팀 시뮬레이션 환경에 통합하는 방법을 탐구하며, OpenAI 함수 호출(function calling)을 통해 비구조화된 자연어를 구조화된 로봇 동작으로 매핑하여 가변 자율성(variable autonomy)을 구현한다. 연구는 12명의 참가자를 대상으로 한 탐색적 피험자 내 실험으로, SASSI 설문지와 주제 분석을 결합하여 사용자와 LLM 기반 로봇 간 상호작용에서 나타난 핵심 행동 패턴과 시스템 한계를 밝혀낸다.

## 그것이 바꾼 것

이 작업의 진정한 가치는 "GPT로 로봇을 제어한다"는 표면적命题에 있지 않다. 오히려 LLM의 비결정성과 로봇 제어에 필요한 결정성 사이의 긴장을 이론적 우려에서 관찰 가능하고 분석 가능한 실증적 대상으로 전환한 데 있다. 기존 HRI 연구는 완벽한 AI를 시뮬레이션하는 Wizard-of-Oz 방식이나 사전 정의된 스크립트 기반 대화 시스템에 의존해 왔으며, 둘 다 LLM이 실제 배포에서 "실수하고, 망설이고, 과도하게 설명하는" 실제 행동을 회피했다. 저자가 미세 조정 모델 대신 기성 GPT-4를 선택한 것 자체가 하나의 입장이다: 첨단 AI 기술이 비전문가도 적용할 수 있는 수준에 도달했으므로, 맞춤형 최적화를 추구하기보다 원래의 행동 패턴을 탐구하는 것이 더 현실적 의미를 갖는다.

더 중요하게, 이 연구는 "가변 자율성"에 대한 이해 방식을 변화시킨다. 기존의 가변 자율성은 일반적으로 사용자가 인터페이스를 통해 자율성 수준을 전환하는 명시적 제어 메커니즘으로 설계되었다. 그러나 본 논문은 대화적 협상을 통해 발생하는 암시적 자율성 할당을 보여준다: LLM은 "제어를 장악"하여 함수를 실행할지, "제어를 포기"하고 명확화를 요청할지 스스로 결정할 수 있다. 이러한 자율성은 사용자가 명시적으로 선택하는 것이 아니라 상호작용 과정에서 창발적으로 나타난다. 이것이 혁신이자 문제의 원천이다—사용자는 로봇이 언제 자율적으로 행동하고 언제 명시적 지시가 필요한지 종종 알지 못한다.

## 방법 분석

### 시스템 아키텍처
- **중앙 컨트롤러 + 로봇별 독립 GPT 인스턴스**: 컨트롤러는 대화 기록을 기반으로 사용자 입력을 해석하고 관련 에이전트(0…n개)에게 배포하여 모든 에이전트가 모든 입력을 처리하는 것을 방지하며, 확장성과 계산 효율성을兼顾한다.
- **함수 호출을 인간-기계 인터페이스로 사용**: OpenAI 함수 호출을 채택하여 비구조화된 자연어를 구조화된 로봇 동작으로 매핑한다. 함수는 본질적으로 프로세스를 설명하는 JSON 객체로, 함수 자체, 적격 매개변수, 호출 시점 등을 포함한다. GPT 모듈은 응답하지 않고 함수 호출을 반환하거나, 불명확한 경우 사용자에게 명확화를 요청할 수 있다.

### 프롬프트 엔지니어링
- **브리핑(Briefing)**: 역할 및 상황 설명(예: "당신은 노란 로봇 에이전트 Jupiter입니다…").
- **제약(Restraints)**: 모델이 역할을 유지하도록 지시(예: "절대 역할을 깨지 마세요. 절대 당신이 AI 모델임을 언급하지 마세요").
- **Few-shot 예시**: 예를 들어 컨트롤러는 단일 에이전트와의 대화가 계속될 때 "you"가 해당 에이전트를 가리킬 수 있고, 여러 에이전트와의 대화에서는 "you"가 모든 에이전트를 가리킬 수 있도록 지시받는다.

### 구현 세부사항
- **플랫폼**: Unity 2022.3.4f1으로 제작된 VR 환경, Meta Quest 2에 최적화; Srcnalt의 OpenAI-Unity 패키지를 통해 OpenAI 엔드포인트에 연결.
- **음성 파이프라인**: 입력은 OpenAI Whisper v2로 전사, 출력은 Amazon Polly로 음성 합성.
- **모델**: 모든 에이전트는 gpt-4-0613(2023년 11월 기준 함수 호출에 최적화된 최신 GPT 모델)을 사용하며, 채팅 완성 API만 사용.
- **함수 출력 검증**: 시스템은 함수 출력을 검증하고 텍스트 피드백으로 GPT 모듈을 업데이트하여 실제 로봇의 감각 입력(예: 카메라 및 센서)을 시뮬레이션한다. 예를 들어 에이전트가 물체를 집으려 하면 시스템은 에이전트와 물체 사이의 거리를 평가하고 모델을 업데이트한다.

### 실험 설계
- 탐색적 피험자 내 연구, 12명의 참가자(P3–P14, 처음 두 명은 시스템의 중대한 변경으로 제외), 평균 연령 36.45세(SD = 14.57), 여성 9명 남성 3명.
- 총 7개의 점진적 과제로 구성되며 동일한 시작 위치를 공유하고, 다중 로봇 협력, 시간 제약(예: 과제 5에서 문 타이머가 의도적으로 충분히 낮게 설정됨), 객체 속성(예: 침대가 뒤집히기 전에 꽃병을 집어야 함)을 포함한다.
- 데이터 수집: 5시간 28분의 실험 데이터 + 3시간 46분의 인터뷰 데이터; 인터뷰는 Whisper로 전사 후 수동 수정, 주제 분석(세 명의 연구자가 반복 코딩)을 사용.

## 핵심 혁신

1. **함수 호출을 가변 자율성의 구현 메커니즘으로 사용**: 이는 본 논문의 가장 핵심적인 방법론적 혁신이다. 함수 호출은 단순한 인터페이스 기술이 아니라 자율성 할당 메커니즘이다—LLM은 "사용자 의도가 확실할 때 제어를 장악하여 함수를 실행"할지 "불확실할 때 제어를 포기하고 명확화를 요청"할지 스스로 결정한다. 함수 설명은 동시에 모델에 능력 경계를 제공하는 스캐폴드 역할을 하며, 확장성과 수정 가능성이 높다. 텍스트 온톨로지 방식보다 함수 특성이 LLM 행동을 더 효과적으로 제약한다.

2. **분산형 다중 에이전트 GPT 아키텍처**: 중앙 컨트롤러 + 로봇별 독립 GPT 인스턴스 설계는 모든 에이전트가 모든 입력을 처리하는 계산 낭비를 방지하면서도 각 로봇이 독립적인 대화 기록과 역할 일관성을 유지할 수 있게 한다. 이 아키텍처는 이기종 로봇(Jupiter 노란색 강한 로봇, Pluto 빨간색 비행 가능, Neptune 파란색 바퀴형)의 차별화된 행동을 자연스럽게 지원한다.

3. **VR 환경을 LLM 기반 HRI의 테스트 플랫폼으로 사용**: 물리적 로봇 대신 VR을 선택함으로써 복잡성을 단순화하고 유연성을 높이면서도 몰입감을 유지한다. 이 결정은 연구자가 물리적 로봇의 비용과 위험을 부담하지 않고도 작업 복잡성(단일 에이전트 단일 동작에서 다중 에이전트 시간적 협력까지)을 체계적으로 조작할 수 있게 한다.

### 핵심 행동 발견
- **사용자는 로봇을 동등한 대화 파트너로 여기지 않음**: 모든 참가자는 로봇을 지시 수신자로 간주했지만, 스타일은 명령형(예: P14)과 대화형(예: P7)으로 분화되었다. 대화형 참가자는 로봇에게 조언을 구할 가능성이 더 높았지만, 이러한 질문은 전반적으로 예외적이었다.
- **LLM의 과도한 말 많음**: 로봇은 장황한 설명을 제공하고 불확실할 때 명확화를 요청하는 경향이 있어, 사용자가 "어린아이와 대화하는 것 같은" 느낌을 받았다(P4, P5). P9는 로봇이 물체를 집기 전에 먼저 접근해야 한다고 요구한 것에 놀라움을 표현했다: "지시에 직접 행동할 줄 알았어요."
- **기능 설명에 대한 과도한 까다로움**: P11이 "Pluto, please go to the blue trash can"이라고 말하자 Pluto는 "죄송합니다. 제 기능에 정의된 위치로만 이동할 수 있습니다."라고 응답했다. SASSI 질문 29 "올바른 단어를 사용하고 있는지 가끔 의문이 들었다"의 평균 점수는 5.92(SD = 1.73)였다.
- **자율성 기대 차이**: P3는 "특정 상황에서 물체를 집기 전에 먼저 접근하도록 명시적으로 지시해야 한다는 것을 인식하지 못했다"고 말했다. 그러나 로봇이 작업을 자율적으로 분해한 사례도 있었다: P8이 Jupiter에게 "접시 세 개를 가져다가 쓰레기통에 버려"라고 요청했을 때, 로봇은 올바른 기능 삼중항(이동, 집기, 버리기)을 연속 세 번 실행했다.
- **응답 지연이 핵심 문제점**: SASSI Speed 차원 M = 5.25(SD = 1.57), P9는 "로봇의 피드백이 항상 늦게 왔어요. 설명이 너무 많아서, 응답할 때쯤에는 이미 계속 말하고 있었죠."라고 말했다.

## 경계 및 한계

- **LLM 비결정성**: 낮은 온도에서도 출력이 일관되지 않으며, 저자는 GPT가 실제 로봇의 제어 요소로 사용될 수 없음을 명시적으로 인정하고, 일관성 보장을 위한 추가 모듈이 필요하다고 밝혔다.
- **클라우드 서비스 지연**: GPT API가 지연을 도입하고, 대학 인터넷 연결의 불안정성이 문제를 악화시켰다; 연결 끊김이나 완전한 중단은 없었지만, 전사 및 모델 응답의 지연이 때때로 현저히 길어졌다.
- **언어 제한**: 실험은 독일어로 진행되었으며, 이는 특히 기능 측면에서 일부 예상치 못한 행동의 원인일 수 있다. 기능 설명의 객체는 LLM의 의미적 모호성 해소를 방지하기 위해 의도적으로 독일어 이름을 부여받았다.
- **수행하지 않은 것**: 장기 배포 테스트, 서로 다른 LLM 버전 간 비교 실험, 비영어권 언어 지원 테스트는 수행되지 않았다; 시스템은 처음 두 세션 이후 중대한 변경을 겪었다(P1 및 P2 제외).
- **오류 전파**: 프레임워크는 LLM의 잠재적 편향과 오류 전방 전파 문제(잘못된 출력이 향후 입력의 일부가 됨)를 상속한다.
- **LLM 환각**: LLM은 때때로 환각을 일으켜 참가자에게 사실이 아닌 것을 확신시키고, 작업과 무관한 정보를 반복하거나 과도하게 공유했다.

## 공학적 시사점

- **기능 설명의 세분성과 명명 일관성을 먼저 검토하라**: 실험에서 가장 흔한 실패 모드는 LLM이 기능 설명의 단어에 과도하게 까다로워 이름이 약간 다른 객체(예: "blue trash can" vs. "trash bin")의 실행을 거부하는 것이었다. 재현 시 기능 설명의 객체 명명을 신중히 설계하고, 프롬프트에 동의어 매핑을 명시하거나 별칭 메커니즘을 추가해야 한다.
- **지연이 가장 큰 공학적 과제다**: SASSI Speed 점수 5.25는 응답 지연이 사용자 경험에 심각한 영향을 미쳤음을 보여준다. 재현 시 로컬 LLM 추론, 일반 명령 응답 캐싱, 또는 스트리밍 출력 도입을 통해 인지 지연을 줄이는 것을 고려하라. 과제 5에서 문 타이머가 의도적으로 충분히 낮게 설정되어 순차 명령이 지연으로 인해 실행 불가능해 보였다—이는 시간 민감 작업에 추가 스케줄링 메커니즘이 필요함을 시사한다.
- **사용자 캘리브레이션이 중요하다**: 참가자의 로봇 자율성에 대한 기대는 극도로 다양했으며, 이러한 차이는 상호작용 초기에 이미 고정되어 변경하기 어려웠다. 실험 시작 전에 로봇의 능력 경계와 자율성 전략을 명확히 알려주는 캘리브레이션 단계를 추가하여 "먼저 접근하라고 명시적으로 지시해야 한다는 것을 몰랐다"와 같은 인지적 격차를 줄이는 것이 좋다.
- **다중 에이전트 아키텍처의 통신 병목**: 현재 프레임워크는 다중 로봇 비구조화 상호작용을 허용하지만, 로봇 간 직접 통신 메커니즘이 부족하다. 협력 작업(예: 과제 7에서 Jupiter와 Neptune이 함께 침대를 뒤집는 경우)에서 텍스트 표현과 통합 대화 로그는 부족하며, 응답을 클러스터링하여 사용자 응답을 단순화하고 중복을 피해야 한다. 에이전트 컨트롤러가 더 복잡한 에이전트 간 통신 제어를 담당할 수 있다.
- **개입 메커니즘 부재**: 전사 및 GPT 모듈의 처리 시간으로 인해 일반적인 통신 채널은 개입에 적합하지 않다. 저자는 LLM의 현재 상태와 무관하게 로봇을 즉시 중지시키는 버튼을 도입할 것을 제안한다—이는 실제 배포에서 반드시 우선시되어야 하는 안전 메커니즘이다.
