## 概述

UniLab 提出了一种异构 CPU-仿真/GPU-学习的机器人 RL 训练架构，挑战"高效训练必须 GPU 驻留仿真"的社区默认假设。该系统通过 MuJoCoUni 和 MotrixSim 两个 CPU 物理后端与统一运行时协调，在 PPO、SAC、TD3、APPO 等算法上实现 3–10× 端到端训练效率提升，并支持 Apple macOS、AMD ROCm、Intel XPU 跨平台部署。

## 它改变了什么

这篇论文真正改变的是机器人 RL 训练系统的"硬件分工"心智模型。社区默认（Isaac Gym、Isaac Lab、Genesis 等）将物理仿真、rollout 收集与策略学习全部绑定在单一 GPU 执行路径上，这虽然简化了工程实现，却将高吞吐实验锁死在 GPU 驻留软件栈内。作者指出，机器人 RL 是闭环系统，端到端效率取决于仿真吞吐量、学习者利用率、收集器-学习者同步、数据移动与缓冲开销的联合优化，而非单纯由物理仿真所在处理器决定。GPU 内核擅长规则、密集、静态形状的执行，但动态活动接触集、稀疏交互、碰撞处理、闭链约束等接触丰富操作恰恰是 GPU 仿真的压力点。

因此，UniLab 将问题重新定义为"仿真-学习闭环的系统组织问题"：CPU 负责大规模批量刚体仿真与数据生成，GPU 专注策略与价值学习，统一运行时最小化协调成本。这一转变的实质是承认硬件各有其角色——CPU 的灵活性与高核心数更适合并行环境步进，GPU 的矩阵吞吐更适合密集学习更新——而非让单一加速器包揽一切。论文在受控单 CPU/单 GPU 设置中证明，这种异构分工不仅可行，而且在墙钟效率上可与 GPU 驻留范式匹敌甚至超越。

## 方法拆解

### 架构总览
UniLab 由三部分组成：CPU 侧仿真后端（MuJoCoUni、MotrixSim）、GPU 侧学习者（PPO/APPO/SAC/TD3/FlashSAC）、统一运行时（协调数据移动、缓冲、调度与参数同步）。

### 收集-更新时序
- **同步模式（标准 PPO）**：CPU 收集器生成固定视界 rollout，GPU 学习者执行完整更新，两者交替进行。
- **松散耦合模式（APPO）**：收集器将固定视界 rollout、行为策略对数概率与 bootstrap 信息写入共享环形缓冲区，同时继续在 CPU 步进下一 rollout；学习者在 GPU 排空可用 rollout 并执行 V-trace 校正与 PPO 风格更新。CPU 收集与 GPU 学习在墙钟时间上重叠，参数同步接近 rollout 边界。
- **回放模式（SAC/TD3/FlashSAC）**：收集器将转移批次插入共享回放缓冲区，学习者从设备批次执行多次更新。优化路径提前一个 tick 请求 CPU 回放打包与设备传输，使其与当前学习者更新重叠。

### 回放路径优化（附录 A）
关键设计是将回放边界从回放缓冲区移动到采样批次：
1. 收集器执行 CPU actor 推理、环境步进与回放插入。
2. 学习者请求下一训练批次时，收集器从 CPU 回放快照采样并打包到两个共享包槽之一。
3. CUDA 上包槽注册为固定主机内存源，用于异步 H2D 传输。
4. 学习者侧后台 H2D 提交线程在学习者消费当前热槽时，传输打包批次到冷 GPU 批次槽。

### 运行时抽象
统一运行时让同步与松散耦合执行共享一个系统栈，通过显式接口连接机器人资产、任务配置、仿真后端与学习算法。共享接口解耦仿真器后端与学习者加速器后端，学习者可映射到 Apple macOS、AMD ROCm、Intel XPU。

## 关键创新

1. **硬件角色分工的重新定义**：不要求 GPU 驻留仿真，而是遵循"CPU 生成大规模仿真数据、GPU 执行密集学习更新、运行时最小化协调成本"的原则。这是对 GPU 主导范式的直接挑战，且用受控实验证明其效率可比。

2. **双缓冲回放路径**：将回放边界从缓冲区移到采样批次，通过共享包槽与后台 H2D 提交线程实现收集器打包与学习者更新的墙钟重叠。附录 A 数据显示，该优化将周期时间从 211 ms 降至 136 ms，收集器停顿从 103 ms 降至 <1 ms，训练时间减少 34.34%。

3. **跨平台可移植性**：共享接口使学习者可映射到 Apple macOS、AMD ROCm、Intel XPU，打破 GPU 驻留范式对 NVIDIA CUDA 生态的绑定。表 3 显示 M5 Max 上 PPO G1 Flip Tracking 训练时间 16.8 分钟，与 RTX 4090 + AMD 9950X3D 的 16.4 分钟相当。

## 边界与局限

论文明确不声称 GPU 驻留仿真过时：当仿真器吞吐量不再是主导瓶颈、使用更大加速器丰富配置或专用 GPU 原生栈优于异构执行时，GPU 仿真仍可能更可取。UniLab 在仿真主导且仿真可有效与学习解耦时最有利；严格同步流水线或由渲染、感知、表示学习主导的视觉工作负载可能收益较小。主张限于受控单 CPU/单 GPU 设置中的端到端训练效率，不涉及极端规模下的绝对峰值吞吐量；多 GPU 或更大分布式配置可能改变权衡。当前实现聚焦刚体机器人控制，不覆盖可变形物体、软体或流体。任务覆盖、性能、操作符覆盖与算法成熟度在各后端间不均匀。未进行物理语义对 sim-to-sim 或 sim-to-real 鲁棒性影响的专门实验。追踪不是完整因果消融，因为学习者更新内核在两个追踪中持续时间也不同。G1 Box Tracking 在 APPO 下不可用；Go2 Arm Manip Loco 仅 MuJoCoUni 可用；Sharpa Inhand 的接触位置通道当前为零，等待后端接触帧支持。

## 工程启示

复现 UniLab 时，先核对硬件配置与后端选择：默认 Linux 工作站为 RTX 4090 + AMD Ryzen 9 9950X3D + 64 GB 4800 MT/s 内存，附录 A 追踪机器为 A100 80 GB + 双 Intel Xeon Gold 5320 + 188 GiB 内存。最容易踩坑的是回放路径优化——双缓冲包槽依赖 CUDA 固定主机内存与后台 H2D 提交线程，若未正确注册固定内存源，异步传输会退化为同步拷贝，周期时间可能回到 211 ms 级别而非 136 ms。另一个关键点是任务级超参数覆盖：PPO 默认 num_envs=4096、num_steps_per_env=24，但 G1 运动跟踪任务降至 1024、Allegro 升至 16384，且 G1 Flip 在 MuJoCoUni/MotrixSim 下 max_iterations 分别为 20000/30000——直接套用全局默认会得到不可比的结果。跨后端移植时注意领域随机化差异：MotrixSim 下 G1 Walk Rough 禁用 Kp/Kd 随机化，Sharpa 重力随机化仅限方向，G1 Flip 在 MotrixSim 下锚点/末端执行器 z 误差阈值回退到环境默认值。对于下游团队，建议先在小任务（如 Go2 Joystick Flat，FlashSAC 1.1 分钟）上验证双缓冲路径是否生效，再扩展到 G1 运动跟踪等长训练任务。

## Overview

UniLab proposes a heterogeneous CPU-simulation/GPU-learning robotic RL training architecture, challenging the community's default assumption that "efficient training requires GPU-resident simulation." The system coordinates two CPU physics backends, MuJoCoUni and MotrixSim, with a unified runtime, achieving 3–10× end-to-end training efficiency improvements on algorithms such as PPO, SAC, TD3, and APPO, while supporting cross-platform deployment on Apple macOS, AMD ROCm, and Intel XPU.

## What It Changes

What this paper truly changes is the "hardware division of labor" mental model for robotic RL training systems. The community default (Isaac Gym, Isaac Lab, Genesis, etc.) binds physics simulation, rollout collection, and policy learning all onto a single GPU execution path. While this simplifies engineering, it locks high-throughput experimentation into GPU-resident software stacks. The authors point out that robotic RL is a closed-loop system, and end-to-end efficiency depends on the joint optimization of simulation throughput, learner utilization, collector-learner synchronization, data movement, and buffering overhead—not solely on which processor runs the physics simulation. GPU kernels excel at regular, dense, static-shape execution, but contact-rich operations such as dynamic active contact sets, sparse interactions, collision handling, and closed-chain constraints are precisely the pressure points of GPU simulation.

Therefore, UniLab reframes the problem as a "system organization problem for the simulation-learning closed loop": the CPU handles large-scale batched rigid-body simulation and data generation, the GPU focuses on policy and value learning, and a unified runtime minimizes coordination costs. The essence of this shift is acknowledging that each hardware component has its role—CPU flexibility and high core counts are better suited for parallel environment stepping, while GPU matrix throughput is better for dense learning updates—rather than having a single accelerator do everything. The paper demonstrates in controlled single-CPU/single-GPU settings that this heterogeneous division of labor is not only feasible but can match or even surpass the GPU-resident paradigm in wall-clock efficiency.

## Method Breakdown

### Architecture Overview
UniLab consists of three components: CPU-side simulation backends (MuJoCoUni, MotrixSim), GPU-side learners (PPO/APPO/SAC/TD3/FlashSAC), and a unified runtime (coordinating data movement, buffering, scheduling, and parameter synchronization).

### Collection-Update Timing
- **Synchronous mode (standard PPO)**: CPU collectors generate fixed-horizon rollouts, GPU learners perform full updates, alternating between the two.
- **Loosely coupled mode (APPO)**: Collectors write fixed-horizon rollouts, behavior policy log-probabilities, and bootstrap information into a shared ring buffer while continuing to step the next rollout on the CPU; learners drain available rollouts on the GPU and perform V-trace corrections and PPO-style updates. CPU collection and GPU learning overlap in wall-clock time, with parameter synchronization near rollout boundaries.
- **Replay mode (SAC/TD3/FlashSAC)**: Collectors insert transition batches into a shared replay buffer, and learners perform multiple updates from device batches. The optimization path requests CPU replay packing and device transfer one tick ahead, overlapping them with the current learner update.

### Replay Path Optimization (Appendix A)
The key design is moving the replay boundary from the replay buffer to the sampled batch:
1. Collectors perform CPU actor inference, environment stepping, and replay insertion.
2. When the learner requests the next training batch, the collector samples from the CPU replay snapshot and packs it into one of two shared packet slots.
3. On CUDA, the packet slot is registered as a pinned host memory source for asynchronous H2D transfers.
4. A learner-side background H2D submission thread transfers the packed batch to a cold GPU batch slot while the learner consumes the current hot slot.

### Runtime Abstraction
The unified runtime allows synchronous and loosely coupled execution to share a single system stack, connecting robot assets, task configurations, simulation backends, and learning algorithms through explicit interfaces. The shared interface decouples simulator backends from learner accelerator backends, allowing learners to map to Apple macOS, AMD ROCm, and Intel XPU.

## Key Innovations

1. **Redefinition of hardware role division**: Rather than requiring GPU-resident simulation, it follows the principle of "CPU generates large-scale simulation data, GPU performs dense learning updates, and the runtime minimizes coordination costs." This is a direct challenge to the GPU-dominant paradigm, with controlled experiments demonstrating comparable efficiency.

2. **Double-buffered replay path**: Moving the replay boundary from the buffer to the sampled batch, achieving wall-clock overlap between collector packing and learner updates via shared packet slots and a background H2D submission thread. Appendix A data shows this optimization reduces cycle time from 211 ms to 136 ms, collector stalls from 103 ms to <1 ms, and training time by 34.34%.

3. **Cross-platform portability**: The shared interface enables learners to map to Apple macOS, AMD ROCm, and Intel XPU, breaking the GPU-resident paradigm's binding to the NVIDIA CUDA ecosystem. Table 3 shows PPO G1 Flip Tracking training time of 16.8 minutes on M5 Max, comparable to 16.4 minutes on RTX 4090 + AMD 9950X3D.

## Boundaries and Limitations

The paper explicitly does not claim GPU-resident simulation is obsolete: GPU simulation may still be preferable when simulator throughput is no longer the dominant bottleneck, when using larger accelerators with richer configurations, or when specialized GPU-native stacks outperform heterogeneous execution. UniLab is most advantageous when simulation dominates and can be effectively decoupled from learning; strictly synchronous pipelines or vision-dominated workloads driven by rendering, perception, or representation learning may benefit less. Claims are limited to end-to-end training efficiency in controlled single-CPU/single-GPU settings, not absolute peak throughput at extreme scales; multi-GPU or larger distributed configurations may shift the trade-offs. The current implementation focuses on rigid-body robot control and does not cover deformable objects, soft bodies, or fluids. Task coverage, performance, operator coverage, and algorithm maturity are uneven across backends. No dedicated experiments were conducted on the impact of physical semantics on sim-to-sim or sim-to-real robustness. The traces are not full causal ablations because learner update kernels also differ in duration across the two traces. G1 Box Tracking is unavailable under APPO; Go2 Arm Manip Loco is only available with MuJoCoUni; Sharpa Inhand's contact position channel is currently zero, pending backend contact frame support.

## Engineering Insights

When reproducing UniLab, first verify hardware configuration and backend selection: the default Linux workstation is RTX 4090 + AMD Ryzen 9 9950X3D + 64 GB 4800 MT/s memory, and the Appendix A trace machine is A100 80 GB + dual Intel Xeon Gold 5320 + 188 GiB memory. The most likely pitfall is the replay path optimization—the double-buffered packet slots rely on CUDA pinned host memory and a background H2D submission thread; if the pinned memory source is not correctly registered, asynchronous transfers degrade to synchronous copies, and cycle time may return to the 211 ms level rather than 136 ms. Another key point is task-level hyperparameter overrides: PPO defaults to num_envs=4096, num_steps_per_env=24, but G1 motion tracking tasks drop to 1024, Allegro rises to 16384, and G1 Flip uses max_iterations of 20000/30000 under MuJoCoUni/MotrixSim—directly applying global defaults yields incomparable results. When porting across backends, note domain randomization differences: MotrixSim disables Kp/Kd randomization for G1 Walk Rough, Sharpa gravity randomization is direction-only, and G1 Flip falls back to environment default anchor/end-effector z error thresholds under MotrixSim. For downstream teams, it is recommended to first validate the double-buffered path on a small task (e.g., Go2 Joystick Flat, FlashSAC 1.1 minutes) before scaling to longer training tasks such as G1 motion tracking.

## 개요

UniLab은 이기종 CPU-시뮬레이션/GPU-학습 로봇 RL 훈련 아키텍처를 제안하며, "효율적인 훈련은 GPU 상주 시뮬레이션이 필수"라는 커뮤니티의 암묵적 가정에 도전한다. 이 시스템은 MuJoCoUni와 MotrixSim이라는 두 개의 CPU 물리 백엔드를 통합 런타임과 조정하여 PPO, SAC, TD3, APPO 등의 알고리즘에서 3–10배의 종단 간 훈련 효율성 향상을 달성하고, Apple macOS, AMD ROCm, Intel XPU 크로스 플랫폼 배포를 지원한다.

## 그것이 바꾸는 것

이 논문이 실제로 바꾸는 것은 로봇 RL 훈련 시스템의 "하드웨어 역할 분담"에 대한 사고 모델이다. 커뮤니티의 기본 설정(Isaac Gym, Isaac Lab, Genesis 등)은 물리 시뮬레이션, 롤아웃 수집, 정책 학습을 모두 단일 GPU 실행 경로에 묶어두지만, 이는 엔지니어링 구현을 단순화하는 대신 고처리량 실험을 GPU 상주 소프트웨어 스택에 가둬버린다. 저자들은 로봇 RL이 폐루프 시스템이며, 종단 간 효율성은 물리 시뮬레이션이 실행되는 프로세서에 의해서만 결정되는 것이 아니라 시뮬레이션 처리량, 학습자 활용률, 수집기-학습자 동기화, 데이터 이동 및 버퍼 오버헤드의 결합 최적화에 달려 있다고 지적한다. GPU 커널은 규칙적이고 밀집되며 정적 형태의 실행에 능숙하지만, 동적 활성 접촉 집합, 희소 상호작용, 충돌 처리, 폐쇄 사슬 제약과 같은 접촉이 풍부한 연산은 오히려 GPU 시뮬레이션의 취약 지점이다.

따라서 UniLab은 문제를 "시뮬레이션-학습 폐루프의 시스템 구성 문제"로 재정의한다: CPU는 대규모 배치 강체 시뮬레이션과 데이터 생성을 담당하고, GPU는 정책 및 가치 학습에 집중하며, 통합 런타임이 조정 비용을 최소화한다. 이러한 전환의 본질은 각 하드웨어에 역할이 있음을 인정하는 것이다—CPU의 유연성과 높은 코어 수는 병렬 환경 스테핑에 더 적합하고, GPU의 행렬 처리량은 밀집 학습 업데이트에 더 적합하다—단일 가속기가 모든 것을 처리하게 하는 대신. 논문은 통제된 단일 CPU/단일 GPU 설정에서 이러한 이기종 역할 분담이 실현 가능할 뿐만 아니라 벽시계 효율성에서 GPU 상주 패러다임과 견줄 수 있거나 능가할 수 있음을 증명한다.

## 방법 분해

### 아키텍처 개요
UniLab은 세 부분으로 구성된다: CPU 측 시뮬레이션 백엔드(MuJoCoUni, MotrixSim), GPU 측 학습자(PPO/APPO/SAC/TD3/FlashSAC), 통합 런타임(데이터 이동, 버퍼링, 스케줄링, 파라미터 동기화 조정).

### 수집-업데이트 타이밍
- **동기 모드(표준 PPO)**: CPU 수집기가 고정 시야 롤아웃을 생성하고, GPU 학습자가 전체 업데이트를 수행하며, 둘은 교대로 진행된다.
- **느슨한 결합 모드(APPO)**: 수집기는 고정 시야 롤아웃, 행동 정책 로그 확률, 부트스트랩 정보를 공유 링 버퍼에 쓰면서 동시에 CPU에서 다음 롤아웃을 스테핑한다; 학습자는 GPU에서 사용 가능한 롤아웃을 비우고 V-trace 보정과 PPO 스타일 업데이트를 수행한다. CPU 수집과 GPU 학습은 벽시계 시간에서 중첩되며, 파라미터 동기화는 롤아웃 경계에 가깝게 이루어진다.
- **재생 모드(SAC/TD3/FlashSAC)**: 수집기는 전이 배치를 공유 재생 버퍼에 삽입하고, 학습자는 디바이스 배치에서 여러 업데이트를 수행한다. 최적화 경로는 한 틱 앞서 CPU 재생 패킹과 디바이스 전송을 요청하여 현재 학습자 업데이트와 중첩시킨다.

### 재생 경로 최적화(부록 A)
핵심 설계는 재생 경계를 재생 버퍼에서 샘플링 배치로 이동시키는 것이다:
1. 수집기는 CPU 액터 추론, 환경 스테핑, 재생 삽입을 수행한다.
2. 학습자가 다음 훈련 배치를 요청하면, 수집기는 CPU 재생 스냅샷에서 샘플링하여 두 개의 공유 패킷 슬롯 중 하나에 패킹한다.
3. CUDA에서 패킷 슬롯은 고정 호스트 메모리 소스로 등록되어 비동기 H2D 전송에 사용된다.
4. 학습자 측 백그라운드 H2D 제출 스레드는 학습자가 현재 핫 슬롯을 소비하는 동안 패킹된 배치를 콜드 GPU 배치 슬롯으로 전송한다.

### 런타임 추상화
통합 런타임은 동기 및 느슨한 결합 실행이 하나의 시스템 스택을 공유하도록 하며, 명시적 인터페이스를 통해 로봇 자산, 작업 구성, 시뮬레이션 백엔드, 학습 알고리즘을 연결한다. 공유 인터페이스는 시뮬레이터 백엔드와 학습자 가속기 백엔드를 분리하며, 학습자는 Apple macOS, AMD ROCm, Intel XPU에 매핑될 수 있다.

## 핵심 혁신

1. **하드웨어 역할 분담의 재정의**: GPU 상주 시뮬레이션을 요구하지 않고, "CPU가 대규모 시뮬레이션 데이터를 생성하고, GPU가 밀집 학습 업데이트를 수행하며, 런타임이 조정 비용을 최소화한다"는 원칙을 따른다. 이는 GPU 중심 패러다임에 대한 직접적인 도전이며, 통제된 실험으로 효율성이 견줄 수 있음을 증명한다.

2. **이중 버퍼 재생 경로**: 재생 경계를 버퍼에서 샘플링 배치로 이동시키고, 공유 패킷 슬롯과 백그라운드 H2D 제출 스레드를 통해 수집기 패킹과 학습자 업데이트의 벽시계 중첩을 구현한다. 부록 A 데이터에 따르면 이 최적화는 주기 시간을 211 ms에서 136 ms로, 수집기 정지를 103 ms에서 <1 ms로 줄이고 훈련 시간을 34.34% 단축한다.

3. **크로스 플랫폼 이식성**: 공유 인터페이스는 학습자를 Apple macOS, AMD ROCm, Intel XPU에 매핑할 수 있게 하여, GPU 상주 패러다임의 NVIDIA CUDA 생태계 종속을 깨뜨린다. 표 3은 M5 Max에서 PPO G1 Flip Tracking 훈련 시간이 16.8분으로, RTX 4090 + AMD 9950X3D의 16.4분과 견줄 만함을 보여준다.

## 실험과 결과

통제 비교는 기본 Linux 하드웨어(RTX 4090 + AMD Ryzen 9 9950X3D + 64 GB)에서 수행되었으며, 작업은 사족, 바퀴형 사족, 휴머노이드, 손재주 조작을 포함한다.

| Go2 | Xeon 8558 | 100.24 | 84.72 |

**그림 5(a)**: GPU 상주 MjLab과 CPU 스테핑/GPU 학습자 UniLab이 동일한 PPO 작업에서 견줄 만한 효율성을 달성한다(120.5/111.4분 vs. 109.3/109.2분).

**그림 6 학습자 주기 절제**: UniLab-MuJoCoUni는 학습자 업데이트 종료 전에 수집기 작업을 완료한다; GPU 상주 MjWarp 연결은 주기를 연장한다(수집기 측 GPU 시뮬레이션과 학습자 업데이트가 리소스를 경쟁).

**부록 A 타임라인 통계(A100 머신)**: 이중 버퍼 경로는 주기 시간을 211 ms에서 136 ms로, 수집기 정지를 103 ms에서 <1 ms로, 복구 간격을 12.3 ms에서 2.9 ms로 줄인다; 500 반복 추적에서 훈련 시간이 107.50 s에서 70.58 s로 감소(-34.34%); 환경 스텝/초가 9.69k에서 15.05k로 증가. UniLab에서 학습자 측 재생 소비는 평균 0.23 ms, CPU 패킹 6.30 ms, GPU H2D 전송 3.13 ms로, 99.50%의 수집기 활동이 학습자 업데이트와 중첩된다.

느슨한 결합 훈련에서 APPO, SAC, FlashSAC는 3–10배의 종단 간 훈련 효율성 개선을 얻는다.

## 경계와 한계

논문은 GPU 상주 시뮬레이션이 구식이라고 명시적으로 주장하지 않는다: 시뮬레이터 처리량이 더 이상 지배적 병목이 아니거나, 더 큰 가속기로 풍부한 구성을 사용하거나, 전용 GPU 네이티브 스택이 이기종 실행보다 우수한 경우 GPU 시뮬레이션이 여전히 더 바람직할 수 있다. UniLab은 시뮬레이션이 지배적이고 시뮬레이션이 학습과 효과적으로 분리될 수 있을 때 가장 유리하다; 엄격한 동기 파이프라인이나 렌더링, 인식, 표현 학습이 지배하는 시각 워크로드는 이점이 적을 수 있다. 주장은 통제된 단일 CPU/단일 GPU 설정에서의 종단 간 훈련 효율성에 국한되며, 극단적 규모에서의 절대 최고 처리량을 다루지 않는다; 다중 GPU 또는 더 큰 분산 구성은 균형을 바꿀 수 있다. 현재 구현은 강체 로봇 제어에 초점을 맞추며, 변형 가능한 물체, 소프트 바디, 유체를 다루지 않는다. 작업 범위, 성능, 연산자 범위, 알고리즘 성숙도는 백엔드 간에 고르지 않다. 물리 의미론이 sim-to-sim 또는 sim-to-real 견고성에 미치는 영향에 대한 전용 실험은 수행되지 않았다. 추적은 완전한 인과 절제가 아니다. 학습자 업데이트 커널의 지속 시간도 두 추적에서 다르기 때문이다. G1 Box Tracking은 APPO에서 사용 불가; Go2 Arm Manip Loco는 MuJoCoUni에서만 사용 가능; Sharpa Inhand의 접촉 위치 채널은 현재 0이며, 백엔드 접촉 프레임 지원을 기다리고 있다.

## 엔지니어링 시사점

UniLab을 재현할 때 먼저 하드웨어 구성과 백엔드 선택을 확인하라: 기본 Linux 워크스테이션은 RTX 4090 + AMD Ryzen 9 9950X3D + 64 GB 4800 MT/s 메모리이고, 부록 A 추적 머신은 A100 80 GB + 듀얼 Intel Xeon Gold 5320 + 188 GiB 메모리이다. 가장 쉽게 함정에 빠지는 부분은 재생 경로 최적화이다—이중 버퍼 패킷 슬롯은 CUDA 고정 호스트 메모리와 백그라운드 H2D 제출 스레드에 의존하며, 고정 메모리 소스를 올바르게 등록하지 않으면 비동기 전송이 동기 복사로 퇴화하여 주기 시간이 136 ms가 아닌 211 ms 수준으로 돌아갈 수 있다. 또 다른 핵심 포인트는 작업 수준 하이퍼파라미터 오버라이드이다: PPO 기본 num_envs=4096, num_steps_per_env=24이지만, G1 모션 추적 작업은 1024로, Allegro는 16384로 올라가며, G1 Flip은 MuJoCoUni/MotrixSim에서 max_iterations가 각각 20000/30000이다—전역 기본값을 그대로 적용하면 비교 불가능한 결과가 나온다. 크로스 백엔드 이식 시 도메인 무작위화 차이에 주의하라: MotrixSim에서 G1 Walk Rough는 Kp/Kd 무작위화가 비활성화되고, Sharpa 중력 무작위화는 방향에만 국한되며, G1 Flip은 MotrixSim에서 앵커/엔드 이펙터 z 오차 임계값이 환경 기본값으로 되돌아간다. 하류 팀에게는 작은 작업(예: Go2 Joystick Flat, FlashSAC 1.1분)에서 이중 버퍼 경로가 작동하는지 먼저 검증한 후 G1 모션 추적과 같은 긴 훈련 작업으로 확장할 것을 권장한다.
