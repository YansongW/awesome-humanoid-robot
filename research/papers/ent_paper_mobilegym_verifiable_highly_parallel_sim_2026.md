## 概述

MobileGym 是一个浏览器托管的类 Android 模拟平台，将应用数据、OS 状态和设备上下文表示为结构化 JSON，使环境状态可读、可写、可分叉且完全沙盒化，专为移动 GUI 智能体的可验证评估与大规模并行 RL 训练设计。核心贡献在于用轻量级、可编程状态的模拟器替代重型 Android 模拟器或真实设备，在保持截图-动作交互保真度的前提下，将单实例资源消耗降低两个数量级（约 400 MB RAM vs 4.5-6 GB），并实现确定性结果检查与 GRPO 等 RL 方法的并行回滚。

## 它改变了什么

移动 GUI 智能体研究长期受困于一个基本矛盾：模拟器环境（AndroidWorld、AndroidLab）可重复但覆盖窄、扩展贵；真实设备基准（MobileBench-OL）覆盖日常应用但状态不可控、不可复现、不可并行。MobileGym 真正改变的是这个权衡的底层假设——它论证了 GUI 智能体只观察截图、通过离散动作行动，因此完全可编程状态的轻量级模拟器只需交互保真度即可满足需求，无需完整模拟 Android 系统。这一判断将环境构建从"系统模拟"转向"交互模拟"，使状态可读（确定性结果检查）、可写（配置与重置）、可分叉（并行回滚）成为可能，而这是真实设备和重型模拟器都无法提供的。

更关键的是，MobileGym 将"可验证性"从评估协议层面下沉到环境架构层面。通过分层状态模型（只读世界数据 + 可写运行时覆盖层）、声明式导航规范（EFSM 形式化）和确定性判断器，它让每个任务的结果信号是确定性的、细粒度的，而非依赖不可靠的 VLM 判断。这直接改变了 RL 训练的可能性——GRPO 需要从相同初始状态多次回滚，MobileGym 的 JSON 序列化与快照分叉使 96 个并行环境实例在单节点 3 卡上即可运行，而真实环境同等规模需要 10 台裸机云服务器。

## 方法拆解

### 分层状态模型
- **世界数据层**：大型、主要只读，包含帖子、产品等公共实体（12 个日常应用发布超过 190K 合成实体、350K+ 结构化记录）
- **运行时覆盖层**：紧凑的每环境运行时状态（当前用户配置文件、应用设置），智能体操作仅写入此层
- **OS 运行时**：设备级状态（飞行模式、电池、音量等）
- 视图通过将运行时覆盖层叠加在只读世界数据上生成；仅运行时状态暴露用于配置、重置、判断和比较，保持快照小而稳定

### 声明式导航规范（EFSM）
- 每个应用建模为扩展有限状态机 ℳ = (S, Σ, Δ, s₀, D, G, U)，S 为 UI 状态集（路由路径 + 查询参数唯一组合），Δ: S × Σ × G → S × U 为带守卫和更新的转移函数
- 同一文件驱动运行时导航（`go(transitionId, params)`）和静态分析（BFS 路径枚举、任务轨迹枚举、新任务自动生成）
- EFSM 三个扩展：守卫允许相同输入在不同数据状态触发不同转移；数据驱动扩展允许状态空间随配置数据增长；复合 UI 状态将共享路由路径的不同视觉呈现（弹窗、抽屉、标签页）建模为不同状态节点

### 动作空间与输入注入
- 17 个动作抽象：CLICK、DOUBLE_TAP、LONG_PRESS、TYPE、SWIPE、DRAG、BACK、HOME、RECENT、ENTER、WAIT、AWAKE、ANSWER、COMPLETE、ABORT、INFO、NOOP
- 坐标归一化到 [0,1000]×[0,1000]，通过 Playwright 执行；截图以全分辨率提供（1080×2400 物理像素）
- 输入注入链：截图像素 → CSS 视口坐标（按分辨率比缩放）→ `document.elementFromPoint` 定位 DOM → 派发标准 PointerEvent/TouchEvent

### AnswerSheet 协议
- 查询任务以填写表单结束，字段声明类型并显示格式提示（如"温度（摄氏度，整数）"）
- 提交的类型化状态由类型特定匹配器检查（精确文本、数值容差、格式或选择检查）
- 设计动机：消除自然语言假阴性（"34°C"/"34 degrees"映射到相同数值 34）、消除枚举/混合思考假阳性（数字字段只能容纳一个数值）、兼容小模型（AutoGLM-Phone-9B 等常将思考轨迹放在 `<answer>` 字段，GUI 操作填写更符合其训练分布）
- 带 answer_fields 的任务获得额外 15 步预算补偿执行成本

### 状态序列化与多实例复制
- 完整环境状态可序列化为结构化 JSON 并按需恢复，支持精确重置和从任意快照分叉
- 不可逆操作（转账、停用、删除等）可在每次轨迹后完全恢复
- 完整环境状态比较：比较情节初始和终止状态，报告任务预期结果之外的任何变异为意外副作用（USE 指标）

### 参数化任务实例化
- 416 个条目是模板而非固定实例，通过三种变异源实例化：指令变异（语义等价目标措辞采样）、参数采样（槽值从策划集合/数值范围/当前环境状态抽取）、环境配置（应用状态如联系人或订单历史注入）
- 在有限参数范围内产生超过 27,000 个不同任务实例

### GRPO 训练配置
- 初始策略 Qwen3-VL-4B-Instruct，10 步，单节点 3 个 RTX Pro 6000，96 个并行环境实例
- lr=10⁻⁶，组大小 k=8，批大小 bs=12，KL 0.01，DAPO 风格非对称 clip-higher（0.2/0.28）
- 奖励为 PR 形状密集信号 r = p，乘法折扣：r ← p′ · 0.8^𝕀[goal success ∧ ¬clean] · 0.8^𝕀[false complete ∧ p′ > 0] · 0.5^𝕀[post-success abort] · 0.5^𝕀[overdue]

## 关键创新

1. **状态可验证性从协议层面下沉到架构层面**：MobileGym 不是给模拟器加判断器，而是从根上让状态可读（确定性结果检查）、可写（配置和重置）、可分叉（并行回滚）。这使 RL 训练（GRPO 需要相同初始状态多次回滚）和细粒度评估（USE 指标检测意外副作用）成为环境原生能力，而非事后附加。对比 AndroidWorld 的 /reset 端点仅执行 press_home + clear interaction_cache，不捕获应用内内存状态和账户/后端状态。

2. **EFSM 声明式导航规范同时驱动运行时和静态分析**：同一文件既执行 UI 导航又支持 BFS 路径枚举、任务轨迹枚举和新任务自动生成。这使 416 个参数化模板通过三种变异源产生 27,000+ 任务实例，且 Test/Train 严格不相交——这是真实设备基准无法做到的（MobileBench-OL 只有 80/1080 实例）。

3. **资源消耗两个数量级的下降**：每实例约 400 MB RAM、3 秒冷启动、50 MB 磁盘，256 并行实例单服务器 < 10% CPU 和约 100 GB RAM，完整 256 任务评估约 6 分钟。对比 AndroidWorld 约 4.5 GB 内存、78 秒冷启动、20 GB 磁盘；MAI-UI 需要 10 台裸机云服务器（960 vCPU、3,840 GB RAM）达到 512 并行实例。这使大规模在线 RL 从"需要云集群"变为"单节点可行"。

## 边界与局限

- **视觉外观建模**：MobileGym 与真实应用之间的视觉差异包括细微布局细节、动画和某些应用特定图标。依赖精确识别应用特定图标的任务可能在迁移中受影响。
- **后端和动态内容建模**：不捕获仅后端或随机现象（实时推荐动态、欺诈检查、延迟峰值、服务器端策略更改），除非显式建模为可控状态。可控动态内容注入在架构上受支持但留待未来研究。
- **应用功能覆盖**：每个模拟应用实现主要日常使用场景而非完整功能表面，较少见功能不在范围内。
- **L4 训练几乎持平**：训练模型在 L4 上仅 +0.9 pt（8 模型校准）和 +0.7 pt（4 模型校准），最困难任务仍受容量限制，作者未深入分析根本原因。
- **真实设备评估规模**：59 任务信号桶子集 vs 256 任务测试集，被视为存在性证明而非全面模拟到真实研究。
- **AnswerSheet 严格消融未做**：在同一 rollout 上切换 AnswerSheet 的消融留待未来工作。
- **高风险操作报告是执行能力报告**，不是对此类自主操作的认可；当前训练范式下"执行能力"和"操作谨慎"未解耦。
- **训练模型误判率略高于基座**（11.9% vs 8.5%），作者称"值得进一步研究"。

## 工程启示

- **先核对状态恢复语义**：MobileGym 的"浏览器刷新 = 设备重启"语义是核心设计决策——用户数据在刷新后保留，运行时状态在刷新后重置。复现时需确认你的任务是否依赖此语义，特别是跨应用状态保持（如微信草稿在切换支付宝后保留）。
- **最容易踩坑的是坐标变换链**：截图像素 → CSS 视口坐标 → `document.elementFromPoint` → PointerEvent/TouchEvent。对于声明了 `designViewportWidth`（如微信 412px）的应用，CSS 缩放生效时需要额外逆变换。复现时务必验证此链路，否则动作定位会系统性偏移。
- **AnswerSheet 是保守门槛而非高估**：它不泄露答案、不简化为选择题，仅增加格式与提交的额外障碍。真实设备查询任务不包含 AnswerSheet 提交工作流，因此查询/混合成功行的轨迹长度差异反映协议不对称性（sim 包含额外提交阶段），对比时需注意。
- **VLM 判断器误判率约 10%**：Qwen3.6-Plus 和 GPT-5.4 在 118 条轨迹上均为 12 个错误（10.2%），但分布不同。若下游依赖 VLM 判断，建议用代码级判断器（$0 成本）替代或至少交叉验证。
- **训练配置可直接复现**：GRPO 10 步、3×RTX Pro 6000、96 并行实例、lr=10⁻⁶、k=8、bs=12、KL 0.01、非对称 clip 0.2/0.28、训练温度 0.7（验证 0.1）。单节点即可运行，无需云集群。
- **资源估算**：256 并行实例单服务器 < 10% CPU 和约 100 GB RAM，完整 256 任务评估约 6 分钟。对比 MAI-UI 需 10 台裸机（960 vCPU、3,840 GB RAM）达 512 实例。若你的团队受限于硬件，MobileGym 是唯一可行的在线 RL 选项。
- **应用模拟工作量约 60 人天**（28 应用，典型日常应用 3-4 人天，系统应用 < 1 人天），不含任务模板、判断器和真实设备审计。若需扩展应用覆盖，按此估算排期。

## Overview

MobileGym is a browser-hosted Android-like emulation platform that represents app data, OS state, and device context as structured JSON, making the environment state readable, writable, forkable, and fully sandboxed. It is designed for verifiable evaluation of mobile GUI agents and large-scale parallel RL training. The core contribution is replacing heavyweight Android emulators or real devices with a lightweight, programmable-state emulator that, while preserving screenshot-action interaction fidelity, reduces per-instance resource consumption by two orders of magnitude (approximately 400 MB RAM vs. 4.5-6 GB), enables deterministic result checking, and supports parallel rollback for RL methods such as GRPO.

## What It Changes

Mobile GUI agent research has long been constrained by a fundamental trade-off: emulator environments (AndroidWorld, AndroidLab) are reproducible but have narrow coverage and are expensive to scale; real-device benchmarks (MobileBench-OL) cover everyday apps but have uncontrollable, non-reproducible, and non-parallelizable states. What MobileGym truly changes is the underlying assumption of this trade-off—it demonstrates that GUI agents only observe screenshots and act through discrete actions, so a lightweight emulator with fully programmable state only needs interaction fidelity, not full Android system emulation. This insight shifts environment construction from "system emulation" to "interaction emulation," making states readable (deterministic result checking), writable (configuration and reset), and forkable (parallel rollback)—capabilities that neither real devices nor heavyweight emulators can provide.

More critically, MobileGym moves "verifiability" from the evaluation protocol level down to the environment architecture level. Through a layered state model (read-only world data + writable runtime overlay), declarative navigation specifications (EFSM formalization), and deterministic judges, it ensures that the result signal for each task is deterministic and fine-grained, rather than relying on unreliable VLM judgments. This directly transforms the possibilities for RL training—GRPO requires multiple rollbacks from the same initial state, and MobileGym's JSON serialization and snapshot forking enable 96 parallel environment instances to run on a single node with 3 GPUs, whereas the same scale with real environments would require 10 bare-metal cloud servers.

## Method Breakdown

### Layered State Model
- **World Data Layer**: Large, mostly read-only, containing public entities such as posts and products (12 everyday apps publishing over 190K synthetic entities, 350K+ structured records)
- **Runtime Overlay Layer**: Compact per-environment runtime state (current user profile, app settings); agent actions write only to this layer
- **OS Runtime**: Device-level state (airplane mode, battery, volume, etc.)
- Views are generated by overlaying the runtime overlay on the read-only world data; only runtime state is exposed for configuration, reset, judging, and comparison, keeping snapshots small and stable

### Declarative Navigation Specification (EFSM)
- Each app is modeled as an extended finite state machine ℳ = (S, Σ, Δ, s₀, D, G, U), where S is the set of UI states (unique combinations of route paths + query parameters), and Δ: S × Σ × G → S × U is the transition function with guards and updates
- The same file drives runtime navigation (`go(transitionId, params)`) and static analysis (BFS path enumeration, task trajectory enumeration, automatic new task generation)
- Three EFSM extensions: guards allow the same input to trigger different transitions under different data states; data-driven extensions allow the state space to grow with configuration data; composite UI states model different visual presentations sharing the same route path (popups, drawers, tabs) as distinct state nodes

### Action Space and Input Injection
- 17 action abstractions: CLICK, DOUBLE_TAP, LONG_PRESS, TYPE, SWIPE, DRAG, BACK, HOME, RECENT, ENTER, WAIT, AWAKE, ANSWER, COMPLETE, ABORT, INFO, NOOP
- Coordinates are normalized to [0,1000]×[0,1000] and executed via Playwright; screenshots are provided at full resolution (1080×2400 physical pixels)
- Input injection chain: screenshot pixels → CSS viewport coordinates (scaled by resolution ratio) → `document.elementFromPoint` to locate DOM → dispatch standard PointerEvent/TouchEvent

### AnswerSheet Protocol
- Query tasks end with filling out a form; fields declare types and display format hints (e.g., "temperature (Celsius, integer)")
- Submitted typed states are checked by type-specific matchers (exact text, numeric tolerance, format, or selection checks)
- Design motivation: eliminate natural language false negatives ("34°C"/"34 degrees" map to the same numeric value 34), eliminate enumeration/mixed-thinking false positives (numeric fields can only hold one value), and accommodate small models (AutoGLM-Phone-9B and others often place reasoning traces in the `<answer>` field; GUI operation filling better matches their training distribution)
- Tasks with answer_fields receive an additional 15-step budget to compensate for execution cost

### State Serialization and Multi-Instance Forking
- The complete environment state can be serialized to structured JSON and restored on demand, supporting exact reset and forking from arbitrary snapshots
- Irreversible operations (transfers, deactivations, deletions, etc.) can be fully restored after each trajectory
- Full environment state comparison: compare episode initial and terminal states, reporting any variation beyond the task's expected outcome as unintended side effects (USE metric)

### Parameterized Task Instantiation
- The 416 entries are templates, not fixed instances, instantiated through three sources of variation: instruction variation (semantically equivalent target phrasing sampling), parameter sampling (slot values drawn from curated sets/numeric ranges/current environment state), and environment configuration (app state such as contacts or order history injection)
- Produces over 27,000 distinct task instances within a limited parameter range

### GRPO Training Configuration
- Initial policy Qwen3-VL-4B-Instruct, 10 steps, single node with 3 RTX Pro 6000 GPUs, 96 parallel environment instances
- lr=10⁻⁶, group size k=8, batch size bs=12, KL 0.01, DAPO-style asymmetric clip-higher (0.2/0.28)
- Reward is a PR-shaped dense signal r = p, with multiplicative discounts: r ← p′ · 0.8^𝕀[goal success ∧ ¬clean] · 0.8^𝕀[false complete ∧ p′ > 0] · 0.5^𝕀[post-success abort] · 0.5^𝕀[overdue]

## Key Innovations

1. **State verifiability moves from the protocol level to the architecture level**: MobileGym does not add a judge to an emulator; rather, it makes states readable (deterministic result checking), writable (configuration and reset), and forkable (parallel rollback) from the ground up. This makes RL training (GRPO requires multiple rollbacks from the same initial state) and fine-grained evaluation (USE metric detecting unintended side effects) native environment capabilities, not post-hoc additions. In contrast, AndroidWorld's /reset endpoint only executes press_home + clear interaction_cache, failing to capture in-app memory state and account/backend state.

2. **The EFSM declarative navigation specification drives both runtime and static analysis**: The same file both executes UI navigation and supports BFS path enumeration, task trajectory enumeration, and automatic new task generation. This enables 416 parameterized templates to produce 27,000+ task instances through three sources of variation, with strictly disjoint Test/Train splits—something real-device benchmarks cannot achieve (MobileBench-OL has only 80/1080 instances).

3. **Two orders of magnitude reduction in resource consumption**: Approximately 400 MB RAM per instance, 3-second cold start, 50 MB disk; 256 parallel instances on a single server use < 10% CPU and about 100 GB RAM, with a full 256-task evaluation taking about 6 minutes. In contrast, AndroidWorld requires about 4.5 GB memory, 78-second cold start, and 20 GB disk; MAI-UI requires 10 bare-metal cloud servers (960 vCPU, 3,840 GB RAM) to reach 512 parallel instances. This shifts large-scale online RL from "requires a cloud cluster" to "feasible on a single node."

## Boundaries and Limitations

- **Visual appearance modeling**: Visual differences between MobileGym and real apps include subtle layout details, animations, and certain app-specific icons. Tasks that rely on precise recognition of app-specific icons may be affected in transfer.
- **Backend and dynamic content modeling**: Backend-only or stochastic phenomena (real-time recommendation dynamics, fraud checks, latency spikes, server-side policy changes) are not captured unless explicitly modeled as controllable states. Controllable dynamic content injection is architecturally supported but left for future research.
- **App feature coverage**: Each simulated app implements primary everyday usage scenarios rather than the full feature surface; less common features are out of scope.
- **L4 training is nearly flat**: The trained model gains only +0.9 pt on L4 (8-model calibration) and +0.7 pt (4-model calibration); the hardest tasks remain capacity-limited, and the authors did not deeply analyze the root cause.
- **Real-device evaluation scale**: The 59-task signal bucket subset vs. the 256-task test set is treated as an existence proof rather than a comprehensive sim-to-real study.
- **Strict AnswerSheet ablation not performed**: An ablation switching AnswerSheet on the same rollout is left for future work.
- **The high-risk operation report is a capability report**, not an endorsement of such autonomous operations; under the current training paradigm, "execution capability" and "operational caution" are not decoupled.
- **The trained model has a slightly higher misjudgment rate than the base** (11.9% vs. 8.5%), which the authors describe as "worth further investigation."

## Engineering Insights

- **First verify state restoration semantics**: MobileGym's "browser refresh = device reboot" semantics is a core design decision—user data persists across refreshes, while runtime state resets. When reproducing, confirm whether your tasks depend on this semantics, especially cross-app state persistence (e.g., WeChat drafts persisting after switching to Alipay).
- **The most error-prone area is the coordinate transformation chain**: screenshot pixels → CSS viewport coordinates → `document.elementFromPoint` → PointerEvent/TouchEvent. For apps declaring `designViewportWidth` (e.g., WeChat at 412px), additional inverse transformations are needed when CSS scaling is active. When reproducing, be sure to validate this chain, otherwise action positioning will be systematically offset.
- **AnswerSheet is a conservative threshold, not an overestimate**: It does not leak answers or simplify to multiple choice; it only adds additional obstacles for formatting and submission. Real-device query tasks do not include the AnswerSheet submission workflow, so trajectory length differences on query/mixed success rows reflect protocol asymmetry (sim includes an additional submission phase); be mindful when comparing.
- **VLM judge misjudgment rate is approximately 10%**: Qwen3.6-Plus and GPT-5.4 both had 12 errors on 118 trajectories (10.2%), but with different distributions. If downstream relies on VLM judgment, consider replacing it with code-level judges ($0 cost) or at least cross-validating.
- **Training configuration is directly reproducible**: GRPO 10 steps, 3×RTX Pro 6000, 96 parallel instances, lr=10⁻⁶, k=8, bs=12, KL 0.01, asymmetric clip 0.2/0.28, training temperature 0.7 (validation 0.1). Runs on a single node without a cloud cluster.
- **Resource estimation**: 256 parallel instances on a single server use < 10% CPU and about 100 GB RAM, with a full 256-task evaluation taking about 6 minutes. In contrast, MAI-UI requires 10 bare-metal servers (960 vCPU, 3,840 GB RAM) to reach 512 instances. If your team is hardware-constrained, MobileGym is the only viable option for online RL.
- **App simulation workload is approximately 60 person-days** (28 apps, typical everyday apps 3-4 person-days, system apps < 1 person-day), excluding task templates, judges, and real-device audits. If you need to expand app coverage, schedule accordingly based on this estimate.

## 개요

MobileGym은 브라우저에서 호스팅되는 Android 유사 에뮬레이션 플랫폼으로, 앱 데이터, OS 상태 및 장치 컨텍스트를 구조화된 JSON으로 표현하여 환경 상태를 읽기 가능하고, 쓰기 가능하며, 포크 가능하고 완전히 샌드박스 처리된 상태로 만든다. 이는 모바일 GUI 에이전트의 검증 가능한 평가와 대규모 병렬 RL 훈련을 위해 설계되었다. 핵심 기여는 무거운 Android 에뮬레이터나 실제 장치를 경량화되고 프로그래밍 가능한 상태의 에뮬레이터로 대체하여, 스크린샷-액션 상호작용 충실도를 유지하면서 단일 인스턴스 리소스 소비를 두 자릿수로 줄이고(약 400MB RAM 대 4.5-6GB), 결정적 결과 검사와 GRPO와 같은 RL 방법의 병렬 롤백을 가능하게 한 것이다.

## 무엇을 바꾸었는가

모바일 GUI 에이전트 연구는 오랫동안 근본적인 모순에 시달려 왔다: 에뮬레이터 환경(AndroidWorld, AndroidLab)은 재현 가능하지만 적용 범위가 좁고 확장 비용이 높으며, 실제 장치 벤치마크(MobileBench-OL)는 일상 앱을 다루지만 상태를 제어할 수 없고 재현 불가능하며 병렬화할 수 없다. MobileGym이 진정으로 바꾼 것은 이 트레이드오프의 기본 가정이다—GUI 에이전트가 스크린샷만 관찰하고 이산적 액션으로 행동하므로, 완전히 프로그래밍 가능한 상태의 경량 에뮬레이터는 상호작용 충실도만 있으면 충분하며 전체 Android 시스템을 시뮬레이션할 필요가 없다는 것을 입증했다. 이 판단은 환경 구축을 "시스템 시뮬레이션"에서 "상호작용 시뮬레이션"으로 전환하여, 상태를 읽기 가능(결정적 결과 검사), 쓰기 가능(구성 및 리셋), 포크 가능(병렬 롤백)하게 만들었으며, 이는 실제 장치와 무거운 에뮬레이터 모두 제공할 수 없는 기능이다.

더 중요하게, MobileGym은 "검증 가능성"을 평가 프로토콜 수준에서 환경 아키텍처 수준으로 내렸다. 계층적 상태 모델(읽기 전용 세계 데이터 + 쓰기 가능한 런타임 오버레이 레이어), 선언적 내비게이션 사양(EFSM 형식화) 및 결정적 판정기를 통해 각 작업의 결과 신호가 결정적이고 세분화되며, 신뢰할 수 없는 VLM 판단에 의존하지 않는다. 이는 RL 훈련의 가능성을 직접 바꾸었다—GRPO는 동일한 초기 상태에서 여러 번 롤백해야 하는데, MobileGym의 JSON 직렬화와 스냅샷 포크는 단일 노드 3개 GPU에서 96개의 병렬 환경 인스턴스를 실행할 수 있게 하며, 실제 환경에서 동일한 규모는 10대의 베어메탈 클라우드 서버가 필요하다.

## 방법 분해

### 계층적 상태 모델
- **세계 데이터 레이어**: 대규모, 주로 읽기 전용, 게시물, 제품 등 공개 엔티티 포함(12개 일상 앱에서 190K+ 합성 엔티티, 350K+ 구조화 레코드 게시)
- **런타임 오버레이 레이어**: 컴팩트한 환경별 런타임 상태(현재 사용자 프로필, 앱 설정), 에이전트 작업은 이 레이어에만 기록
- **OS 런타임**: 장치 수준 상태(비행기 모드, 배터리, 볼륨 등)
- 뷰는 읽기 전용 세계 데이터 위에 런타임 오버레이를 겹쳐 생성됨; 구성, 리셋, 판단 및 비교를 위해 런타임 상태만 노출되어 스냅샷을 작고 안정적으로 유지

### 선언적 내비게이션 사양(EFSM)
- 각 앱은 확장 유한 상태 머신 ℳ = (S, Σ, Δ, s₀, D, G, U)로 모델링되며, S는 UI 상태 집합(라우트 경로 + 쿼리 매개변수의 고유 조합), Δ: S × Σ × G → S × U는 가드와 업데이트가 있는 전이 함수
- 동일한 파일이 런타임 내비게이션(`go(transitionId, params)`)과 정적 분석(BFS 경로 열거, 작업 궤적 열거, 새 작업 자동 생성)을 구동
- EFSM의 세 가지 확장: 가드는 동일한 입력이 다른 데이터 상태에서 다른 전이를 트리거하도록 허용; 데이터 기반 확장은 상태 공간이 구성 데이터에 따라 성장하도록 허용; 복합 UI 상태는 공유 라우트 경로의 다른 시각적 표현(팝업, 드로어, 탭)을 다른 상태 노드로 모델링

### 액션 공간 및 입력 주입
- 17개 액션 추상화: CLICK, DOUBLE_TAP, LONG_PRESS, TYPE, SWIPE, DRAG, BACK, HOME, RECENT, ENTER, WAIT, AWAKE, ANSWER, COMPLETE, ABORT, INFO, NOOP
- 좌표는 [0,1000]×[0,1000]으로 정규화되고 Playwright를 통해 실행; 스크린샷은 전체 해상도(1080×2400 물리 픽셀)로 제공
- 입력 주입 체인: 스크린샷 픽셀 → CSS 뷰포트 좌표(해상도 비율로 스케일링) → `document.elementFromPoint`로 DOM 위치 파악 → 표준 PointerEvent/TouchEvent 디스패치

### AnswerSheet 프로토콜
- 쿼리 작업은 양식 작성으로 끝나며, 필드는 유형을 선언하고 형식 힌트를 표시(예: "온도(섭씨, 정수)")
- 제출된 타입화된 상태는 유형별 매처로 검사(정확한 텍스트, 수치 허용 오차, 형식 또는 선택 검사)
- 설계 동기: 자연어 위음성 제거("34°C"/"34 degrees"가 동일한 수치 34로 매핑), 열거/혼합 사고 위양성 제거(숫자 필드는 하나의 수치만 담을 수 있음), 소형 모델과의 호환(AutoGLM-Phone-9B 등은 종종 사고 궤적을 `<answer>` 필드에 넣으며, GUI 작업 작성이 훈련 분포에 더 부합)
- answer_fields가 있는 작업은 실행 비용을 보상하기 위해 추가 15단계 예산을 받음

### 상태 직렬화 및 다중 인스턴스 복제
- 전체 환경 상태는 구조화된 JSON으로 직렬화되고 필요 시 복원 가능, 정확한 리셋 및 임의 스냅샷에서 포크 지원
- 되돌릴 수 없는 작업(송금, 비활성화, 삭제 등)은 각 궤적 후 완전히 복원 가능
- 전체 환경 상태 비교: 에피소드 초기 및 종료 상태를 비교하여 작업 예상 결과 외의 모든 변이를 의도하지 않은 부작용으로 보고(USE 지표)

### 매개변수화된 작업 인스턴스화
- 416개 항목은 템플릿이지 고정 인스턴스가 아니며, 세 가지 변이 소스를 통해 인스턴스화: 지시 변이(의미적으로 동등한 목표 표현 샘플링), 매개변수 샘플링(슬롯 값을 큐레이션된 집합/수치 범위/현재 환경 상태에서 추출), 환경 구성(연락처 또는 주문 내역과 같은 앱 상태 주입)
- 제한된 매개변수 범위 내에서 27,000개 이상의 다양한 작업 인스턴스 생성

### GRPO 훈련 구성
- 초기 정책 Qwen3-VL-4B-Instruct, 10단계, 단일 노드 3개 RTX Pro 6000, 96개 병렬 환경 인스턴스
- lr=10⁻⁶, 그룹 크기 k=8, 배치 크기 bs=12, KL 0.01, DAPO 스타일 비대칭 clip-higher(0.2/0.28)
- 보상은 PR 형태의 밀집 신호 r = p, 곱셈 할인: r ← p′ · 0.8^𝕀[goal success ∧ ¬clean] · 0.8^𝕀[false complete ∧ p′ > 0] · 0.5^𝕀[post-success abort] · 0.5^𝕀[overdue]

## 핵심 혁신

1. **상태 검증 가능성이 프로토콜 수준에서 아키텍처 수준으로 이동**: MobileGym은 에뮬레이터에 판정기를 추가하는 것이 아니라, 근본적으로 상태를 읽기 가능(결정적 결과 검사), 쓰기 가능(구성 및 리셋), 포크 가능(병렬 롤백)하게 만든다. 이는 RL 훈련(GRPO는 동일한 초기 상태에서 여러 번 롤백 필요)과 세분화된 평가(USE 지표로 의도하지 않은 부작용 감지)를 사후 부착이 아닌 환경 고유 기능으로 만든다. AndroidWorld의 /reset 엔드포인트가 press_home + clear interaction_cache만 실행하고 앱 내 메모리 상태와 계정/백엔드 상태를 캡처하지 않는 것과 대조적이다.

2. **EFSM 선언적 내비게이션 사양이 런타임과 정적 분석을 동시에 구동**: 동일한 파일이 UI 내비게이션을 실행하면서 BFS 경로 열거, 작업 궤적 열거 및 새 작업 자동 생성을 지원한다. 이는 416개 매개변수화된 템플릿이 세 가지 변이 소스를 통해 27,000+ 작업 인스턴스를 생성하고 Test/Train이 엄격히 분리되게 한다—실제 장치 벤치마크로는 불가능한 일이다(MobileBench-OL은 80/1080 인스턴스만 보유).

3. **리소스 소비 두 자릿수 감소**: 인스턴스당 약 400MB RAM, 3초 콜드 스타트, 50MB 디스크, 256개 병렬 인스턴스 단일 서버에서 < 10% CPU 및 약 100GB RAM, 전체 256개 작업 평가 약 6분. AndroidWorld의 약 4.5GB 메모리, 78초 콜드 스타트, 20GB 디스크와 대조; MAI-UI는 512개 병렬 인스턴스를 위해 10대의 베어메탈 클라우드 서버(960 vCPU, 3,840GB RAM)가 필요. 이는 대규모 온라인 RL을 "클라우드 클러스터 필요"에서 "단일 노드 가능"으로 바꾼다.

## 경계 및 한계

- **시각적 외관 모델링**: MobileGym과 실제 앱 간의 시각적 차이에는 미세한 레이아웃 세부 사항, 애니메이션 및 일부 앱 특정 아이콘이 포함된다. 앱 특정 아이콘의 정확한 인식에 의존하는 작업은 전이에서 영향을 받을 수 있다.
- **백엔드 및 동적 콘텐츠 모델링**: 명시적으로 제어 가능한 상태로 모델링되지 않는 한 백엔드 전용 또는 무작위 현상(실시간 추천 동적, 사기 검사, 지연 스파이크, 서버 측 정책 변경)을 캡처하지 않는다. 제어 가능한 동적 콘텐츠 주입은 아키텍처적으로 지원되지만 향후 연구로 남겨둔다.
- **앱 기능 범위**: 각 시뮬레이션 앱은 전체 기능 표면이 아닌 주요 일상 사용 시나리오를 구현하며, 덜 일반적인 기능은 범위에 포함되지 않는다.
- **L4 훈련 거의 정체**: 훈련된 모델은 L4에서 +0.9 pt(8개 모델 보정) 및 +0.7 pt(4개 모델 보정)에 그쳤으며, 가장 어려운 작업은 여전히 용량 제한을 받고 저자는 근본 원인을 깊이 분석하지 않았다.
- **실제 장치 평가 규모**: 59개 작업 신호 버킷 하위 집합 대 256개 작업 테스트 세트, 존재 증명으로 간주되며 포괄적인 시뮬레이션-실제 연구가 아니다.
- **AnswerSheet 엄격한 제거 실험 미수행**: 동일한 롤아웃에서 AnswerSheet를 전환하는 제거 실험은 향후 작업으로 남겨둔다.
- **고위험 작업 보고는 실행 능력 보고**이며, 이러한 자율 작업에 대한 승인이 아니다; 현재 훈련 패러다임에서 "실행 능력"과 "작업 신중함"은 분리되지 않았다.
- **훈련된 모델의 오판율이 베이스보다 약간 높음**(11.9% 대 8.5%), 저자는 "추가 연구가 필요하다"고 언급.

## 공학적 시사점

- **먼저 상태 복원 의미론을 확인하라**: MobileGym의 "브라우저 새로고침 = 장치 재시작" 의미론은 핵심 설계 결정이다—사용자 데이터는 새로고침 후 유지되고 런타임 상태는 새로고침 후 리셋된다. 재현 시 작업이 이 의미론에 의존하는지, 특히 앱 간 상태 유지(예: WeChat 초안이 Alipay 전환 후 유지)를 확인해야 한다.
- **가장 함정에 빠지기 쉬운 것은 좌표 변환 체인**: 스크린샷 픽셀 → CSS 뷰포트 좌표 → `document.elementFromPoint` → PointerEvent/TouchEvent. `designViewportWidth`(예: WeChat 412px)를 선언한 앱의 경우 CSS 스케일링이 적용될 때 추가 역변환이 필요하다. 재현 시 이 체인을 반드시 검증해야 하며, 그렇지 않으면 액션 위치가 체계적으로 어긋난다.
- **AnswerSheet는 과대평가가 아닌 보수적 문턱**: 답을 유출하지 않고 객관식으로 단순화하지 않으며, 형식과 제출의 추가 장벽만 증가시킨다. 실제 장치 쿼리 작업에는 AnswerSheet 제출 워크플로가 포함되지 않으므로, 쿼리/혼합 성공 행의 궤적 길이 차이는 프로토콜 비대칭성(sim은 추가 제출 단계 포함)을 반영하며 비교 시 주의해야 한다.
- **VLM 판정기 오판율 약 10%**: Qwen3.6-Plus와 GPT-5.4는 118개 궤적에서 모두 12개 오류(10.2%)지만 분포는 다르다. 다운스트림이 VLM 판단에 의존한다면 코드 수준 판정기($0 비용)로 대체하거나 최소한 교차 검증을 권장한다.
- **훈련 구성은 직접 재현 가능**: GRPO 10단계, 3×RTX Pro 6000, 96개 병렬 인스턴스, lr=10⁻⁶, k=8, bs=12, KL 0.01, 비대칭 clip 0.2/0.28, 훈련 온도 0.7(검증 0.1). 단일 노드로 실행 가능, 클라우드 클러스터 불필요.
- **리소스 추정**: 256개 병렬 인스턴스 단일 서버에서 < 10% CPU 및 약 100GB RAM, 전체 256개 작업 평가 약 6분. MAI-UI는 512개 인스턴스를 위해 10대의 베어메탈(960 vCPU, 3,840GB RAM)이 필요. 팀이 하드웨어에 제약이 있다면 MobileGym이 유일하게 실행 가능한 온라인 RL 옵션이다.
- **앱 시뮬레이션 작업량 약 60인일**(28개 앱, 일반 일상 앱 3-4인일, 시스템 앱 < 1인일), 작업 템플릿, 판정기 및 실제 장치 감사 제외. 앱 범위를 확장해야 한다면 이 추정치로 일정을 계획하라.
