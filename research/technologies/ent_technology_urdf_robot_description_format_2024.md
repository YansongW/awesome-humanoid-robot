## 概述

URDF（Unified Robot Description Format）是一种基于 XML 的机器人描述格式，用于标准化地描述机器人的连杆、关节、惯性、几何与运动学参数。它真正改变的不是"画图方式"，而是"机器人模型的交换与复用方式"——让同一份机械描述可以在仿真、控制、导航与可视化等不同软件栈之间无缝流转，成为 ROS 生态中机器人建模的事实标准。

## 核心内容

### 是什么：准确定义

URDF 是一种 XML 格式，核心是用 `<link>` 和 `<joint>` 两类元素描述机器人的树状运动链。`<link>` 定义刚体属性（视觉几何、碰撞几何、惯性张量），`<joint>` 定义相邻连杆之间的运动约束（关节类型、旋转轴、位置、限位）。一个完整的人形机器人 URDF 文件，本质上是将机械设计中的运动学树（kinematic tree）以机器可读的文本形式固化下来。

其典型结构如下：

```xml
<robot name="humanoid">
  <link name="base_link">
    <inertial>
      <mass value="12.0"/>
      <inertia ixx="0.1" ixy="0.0" ixz="0.0"
               iyy="0.1" iyz="0.0" izz="0.08"/>
    </inertial>
    <visual>
      <geometry><mesh filename="base.dae"/></geometry>
    </visual>
  </link>
  <joint name="hip_pitch" type="revolute">
    <parent link="base_link"/>
    <child link="thigh"/>
    <origin xyz="0 0 -0.4" rpy="0 0 0"/>
    <axis xyz="0 1 0"/>
    <limit lower="-1.57" upper="1.57" effort="150" velocity="3.0"/>
  </joint>
</robot>
```

### 为什么存在：痛点与历史定位

在 URDF 出现之前，机器人描述格式高度碎片化：每个仿真器（如 Gazebo、Webots）有自己的模型格式，每个控制库（如 ODE、Bullet）又有自己的导入接口。这意味着同一个机器人要在不同工具间迁移，需要重复建模，且模型之间的一致性无法保证。

URDF 的诞生正是为了解决这一痛点——它由 ROS 社区推动，定位为**机器人模型的通用交换格式**。它真正改变的不是"建模精度"，而是"生态协同"：一旦一个机器人有了 URDF 描述，它就能被 ROS 的 tf 树、MoveIt 的运动规划、Gazebo 的物理仿真、RViz 的可视化直接消费，无需任何转换。这种"一次建模，处处可用"的特性，使 URDF 成为 ROS 生态中机器人描述的事实标准。

### 原理拆解

**① 树状结构：运动学链的文本映射**

URDF 强制要求机器人描述为树状结构（每个连杆最多一个父关节），这与大多数机器人的运动学链一致。每个 `<joint>` 通过 `<parent>` 和 `<child>` 建立连杆间的父子关系，从而隐式定义了坐标变换链。对于人形机器人，典型的树根是骨盆（pelvis），双腿、躯干、双臂作为子树挂接。

**② 惯性参数：动力学仿真的基石**

`<inertial>` 元素中的质量与惯性张量（`<inertia>` 的 6 个独立分量）是动力学仿真与控制的关键输入。惯性张量的准确性直接影响仿真中关节力矩的计算。以髋关节为例，其承受全身重量并通过大腿传递地面反力，惯性参数错误会导致仿真中的关节力矩与实际偏差巨大（工程判断）。

**③ 关节类型：运动约束的编码**

URDF 支持 6 种关节类型：`revolute`（旋转）、`continuous`（无限旋转）、`prismatic`（滑动）、`fixed`（固定）、`floating`（6-DOF 自由）、`planar`（平面运动）。人形机器人中，髋、膝、踝通常用 `revolute` 并设置限位。例如髋关节的 3-DOF 正交轴系（roll/pitch/yaw），在 URDF 中表现为三个 `revolute` 关节的串联：

$$
T_{\text{hip}} = R_z(\theta_{\text{yaw}}) \cdot R_y(\theta_{\text{pitch}}) \cdot R_x(\theta_{\text{roll}})
$$

**④ 几何与碰撞：仿真与可视化的双通道**

`<visual>` 和 `<collision>` 分别定义可视化网格与碰撞几何。两者分离的设计允许使用高精度的 CAD 模型用于显示，同时用简化的几何体（如盒体、球体）用于碰撞检测，以降低仿真计算量。

### 关键参数与规格

| 参数 | 说明 | 典型值（人形机器人） |
|------|------|----------------------|
| `<mass>` | 连杆质量（kg） | 髋部连杆约 3–5 kg（工程判断） |
| `<inertia>` | 惯性张量（kg·m²） | 需由 CAD 或实测标定 |
| `<limit lower/upper>` | 关节限位（rad） | 髋 pitch 约 ±1.57 rad |
| `<limit effort>` | 最大关节力矩（N·m） | 髋关节约 150–300 N·m（工程判断） |
| `<limit velocity>` | 最大关节速度（rad/s） | 约 3.0–6.0 rad/s |
| `<origin xyz/rpy>` | 关节相对父连杆的位姿 | 由机械设计确定 |
| `<axis xyz>` | 关节旋转轴 | 髋 pitch 为 [0,1,0] |

### 横向对比

| 特性 | URDF | MJCF（MuJoCo） | SDF（Gazebo） |
|------|------|----------------|---------------|
| 核心定位 | ROS 生态标准 | MuJoCo 仿真格式 | Gazebo 仿真格式 |
| 结构 | 树状（严格） | 树状（支持自由关节） | 图状（支持闭环） |
| 惯性描述 | 质量+惯性张量 | 质量+惯性张量 | 质量+惯性张量 |
| 闭合运动链 | 不支持 | 通过 equality 约束 | 支持 |
| 导出工具 | SolidWorks/Onshape 插件 | MuJoCo 自带 | Gazebo 自带 |
| 生态 | ROS/MoveIt/RViz | MuJoCo/DeepMind | Gazebo/ROS |

URDF 的主要局限在于**不支持闭环运动链**（如并联机构），且缺乏对传感器、摩擦、驱动器的标准化描述。对于人形机器人这类开链为主的系统，URDF 足够用；但若涉及并联踝关节或灵巧手的闭环结构，需考虑 MJCF 或 SDF。

### 谁在用·应用案例

**① 仿真验证（SiL/HiL）**：URDF 是 SiL（Software-in-the-Loop）仿真的基础输入。在纯软件环境中验证控制算法时，URDF 提供被控对象的动力学模型。HiL（Hardware-in-the-Loop）测试中，URDF 同样用于生成实时仿真机的 plant model。

**② 运动规划与避障**：MoveIt 直接消费 URDF 构建碰撞场景与运动学树，用于规划机械臂或全身运动。人形机器人的抓取、行走规划均依赖 URDF 提供的几何与运动学信息。

**③ 可视化与调试**：RViz 加载 URDF 实现 3D 可视化，帮助工程师在开发阶段直观检查关节运动、传感器位置与线束走向。

**④ 数据生成**：在合成数据管道中，URDF 驱动的仿真环境（如 Isaac Sim）可批量生成带标注的训练数据，用于强化学习与 VLA 模型训练。

### 局限与边界

1. **树状结构限制**：URDF 不允许一个连杆有多个父节点，无法直接描述并联机构或闭环运动链。对于人形机器人的开链结构（双腿+躯干+双臂）足够，但灵巧手的多指闭环需其他格式。
2. **缺乏传感器与摩擦模型**：URDF 不包含传感器（IMU、力传感器）的标准化描述，也不支持摩擦、阻尼等接触参数。这些需通过 Gazebo 的 `<gazebo>` 扩展或 MJCF 补充。
3. **无版本管理**：URDF 文件格式本身不包含版本信息，不同 ROS 版本间的兼容性需自行确认。
4. **惯性参数准确性**：URDF 中的惯性参数若直接来自 CAD 估算，可能与实际存在偏差。对于高动态控制（如奔跑、跳跃），需通过系统辨识修正（工程判断）。

### 常见误区

1. **"URDF 就是 3D 模型"**——错。URDF 的核心是运动学树与惯性参数，3D 网格只是 `<visual>` 的附属属性。没有正确的关节定义与惯性参数，URDF 无法用于动力学仿真。
2. **"URDF 支持所有机器人结构"**——错。URDF 的树状结构无法描述并联机构或闭环链。对于这类结构，需使用 SDF 或 MJCF。
3. **"URDF 中的惯性参数不重要"**——错。惯性张量直接决定动力学仿真的关节力矩。以髋关节为例，其承受全身重量，惯性参数错误会导致仿真力矩与实际偏差巨大。
4. **"URDF 可以自动生成"**——部分对。虽然 SolidWorks 等 CAD 工具可导出 URDF，但导出的文件通常需要手动修正关节限位、惯性参数与碰撞几何，不能直接用于仿真。

## Overview

URDF (Unified Robot Description Format) is an XML-based robot description format used to standardize the description of a robot's links, joints, inertial properties, geometry, and kinematic parameters. What it truly changes is not the "drawing method," but the "exchange and reuse method of robot models"—allowing the same mechanical description to flow seamlessly across different software stacks such as simulation, control, navigation, and visualization, making it the de facto standard for robot modeling in the ROS ecosystem.

## Content

### What It Is: Precise Definition

URDF is an XML format whose core is to describe a robot's tree-like kinematic chain using two types of elements: `<link>` and `<joint>`. `<link>` defines rigid body properties (visual geometry, collision geometry, inertia tensor), while `<joint>` defines the motion constraints between adjacent links (joint type, rotation axis, position, limits). A complete humanoid robot URDF file essentially solidifies the kinematic tree from mechanical design into a machine-readable text form.

Its typical structure is as follows:

```xml
<robot name="humanoid">
  <link name="base_link">
    <inertial>
      <mass value="12.0"/>
      <inertia ixx="0.1" ixy="0.0" ixz="0.0"
               iyy="0.1" iyz="0.0" izz="0.08"/>
    </inertial>
    <visual>
      <geometry><mesh filename="base.dae"/></geometry>
    </visual>
  </link>
  <joint name="hip_pitch" type="revolute">
    <parent link="base_link"/>
    <child link="thigh"/>
    <origin xyz="0 0 -0.4" rpy="0 0 0"/>
    <axis xyz="0 1 0"/>
    <limit lower="-1.57" upper="1.57" effort="150" velocity="3.0"/>
  </joint>
</robot>
```

### Why It Exists: Pain Points and Historical Positioning

Before URDF, robot description formats were highly fragmented: each simulator (e.g., Gazebo, Webots) had its own model format, and each control library (e.g., ODE, Bullet) had its own import interface. This meant that migrating the same robot between different tools required re-modeling, and consistency between models could not be guaranteed.

URDF was born precisely to solve this pain point—it was driven by the ROS community and positioned as the **universal exchange format for robot models**. What it truly changes is not "modeling precision," but "ecosystem synergy": once a robot has a URDF description, it can be directly consumed by ROS's tf tree, MoveIt's motion planning, Gazebo's physics simulation, and RViz's visualization without any conversion. This "model once, use everywhere" characteristic has made URDF the de facto standard for robot description in the ROS ecosystem.

### Principle Breakdown

**① Tree Structure: Textual Mapping of the Kinematic Chain**

URDF mandates that the robot description be a tree structure (each link has at most one parent joint), which aligns with the kinematic chain of most robots. Each `<joint>` establishes a parent-child relationship between links via `<parent>` and `<child>`, thereby implicitly defining the coordinate transformation chain. For a humanoid robot, the typical tree root is the pelvis, with the legs, torso, and arms attached as subtrees.

**② Inertial Parameters: The Cornerstone of Dynamics Simulation**

The mass and inertia tensor (the 6 independent components of `<inertia>`) in the `<inertial>` element are key inputs for dynamics simulation and control. The accuracy of the inertia tensor directly affects the calculation of joint torques in simulation. Taking the hip joint as an example, it bears the full body weight and transmits ground reaction forces through the thigh; incorrect inertial parameters can cause simulated joint torques to deviate significantly from reality (engineering judgment).

**③ Joint Types: Encoding of Motion Constraints**

URDF supports 6 joint types: `revolute` (rotational), `continuous` (infinite rotation), `prismatic` (sliding), `fixed` (fixed), `floating` (6-DOF free), and `planar` (planar motion). In humanoid robots, the hip, knee, and ankle typically use `revolute` with limits set. For example, the hip joint's 3-DOF orthogonal axis system (roll/pitch/yaw) is represented in URDF as a series of three `revolute` joints:

$$
T_{\text{hip}} = R_z(\theta_{\text{yaw}}) \cdot R_y(\theta_{\text{pitch}}) \cdot R_x(\theta_{\text{roll}})
$$

**④ Geometry and Collision: Dual Channels for Simulation and Visualization**

`<visual>` and `<collision>` define the visualization mesh and collision geometry, respectively. This separation allows high-precision CAD models to be used for display while simplified geometries (such as boxes or spheres) are used for collision detection to reduce simulation computational load.

### Key Parameters and Specifications

| Parameter | Description | Typical Value (Humanoid Robot) |
|-----------|-------------|--------------------------------|
| `<mass>` | Link mass (kg) | Hip link approximately 3–5 kg (engineering judgment) |
| `<inertia>` | Inertia tensor (kg·m²) | Requires calibration via CAD or measurement |
| `<limit lower/upper>` | Joint limits (rad) | Hip pitch approximately ±1.57 rad |
| `<limit effort>` | Maximum joint torque (N·m) | Hip joint approximately 150–300 N·m (engineering judgment) |
| `<limit velocity>` | Maximum joint velocity (rad/s) | Approximately 3.0–6.0 rad/s |
| `<origin xyz/rpy>` | Pose of joint relative to parent link | Determined by mechanical design |
| `<axis xyz>` | Joint rotation axis | Hip pitch is [0,1,0] |

### Horizontal Comparison

| Feature | URDF | MJCF (MuJoCo) | SDF (Gazebo) |
|---------|------|---------------|--------------|
| Core positioning | ROS ecosystem standard | MuJoCo simulation format | Gazebo simulation format |
| Structure | Tree (strict) | Tree (supports free joints) | Graph (supports closed loops) |
| Inertial description | Mass + inertia tensor | Mass + inertia tensor | Mass + inertia tensor |
| Closed kinematic chains | Not supported | Supported via equality constraints | Supported |
| Export tools | SolidWorks/Onshape plugins | Built into MuJoCo | Built into Gazebo |
| Ecosystem | ROS/MoveIt/RViz | MuJoCo/DeepMind | Gazebo/ROS |

The main limitation of URDF is that it **does not support closed kinematic chains** (such as parallel mechanisms), and it lacks standardized descriptions for sensors, friction, and actuators. For systems primarily composed of open chains like humanoid robots, URDF is sufficient; however, for closed-loop structures involving parallel ankle joints or dexterous hands, MJCF or SDF should be considered.

### Who Uses It: Application Cases

**① Simulation Verification (SiL/HiL)**: URDF is the foundational input for SiL (Software-in-the-Loop) simulation. When verifying control algorithms in a pure software environment, URDF provides the dynamic model of the controlled object. In HiL (Hardware-in-the-Loop) testing, URDF is also used to generate the plant model for real-time simulation machines.

**② Motion Planning and Obstacle Avoidance**: MoveIt directly consumes URDF to build collision scenes and kinematic trees for planning manipulator or whole-body motions. Humanoid robot grasping and walking planning both rely on the geometric and kinematic information provided by URDF.

**③ Visualization and Debugging**: RViz loads URDF for 3D visualization, helping engineers visually inspect joint motion, sensor positions, and cable routing during the development phase.

**④ Data Generation**: In synthetic data pipelines, URDF-driven simulation environments (such as Isaac Sim) can batch-generate annotated training data for reinforcement learning and VLA model training.

### Limitations and Boundaries

1. **Tree Structure Limitation**: URDF does not allow a link to have multiple parent nodes, making it impossible to directly describe parallel mechanisms or closed kinematic chains. This is sufficient for the open-chain structure of humanoid robots (legs + torso + arms), but the multi-finger closed loops of dexterous hands require other formats.
2. **Lack of Sensor and Friction Models**: URDF does not include standardized descriptions for sensors (IMU, force sensors), nor does it support contact parameters such as friction and damping. These need to be supplemented via Gazebo's `<gazebo>` extension or MJCF.
3. **No Version Management**: The URDF file format itself does not contain version information, and compatibility across different ROS versions must be verified independently.
4. **Inertial Parameter Accuracy**: Inertial parameters in URDF, if directly estimated from CAD, may deviate from reality. For highly dynamic control (such as running, jumping), system identification corrections are needed (engineering judgment).

### Common Misconceptions

1. **"URDF is just a 3D model"**—Wrong. The core of URDF is the kinematic tree and inertial parameters; the 3D mesh is merely an auxiliary attribute of `<visual>`. Without correct joint definitions and inertial parameters, URDF cannot be used for dynamics simulation.
2. **"URDF supports all robot structures"**—Wrong. URDF's tree structure cannot describe parallel mechanisms or closed-loop chains. For such structures, SDF or MJCF must be used.
3. **"Inertial parameters in URDF are not important"**—Wrong. The inertia tensor directly determines joint torques in dynamics simulation. Taking the hip joint as an example, it bears the full body weight, and incorrect inertial parameters can cause simulated torques to deviate significantly from reality.
4. **"URDF can be automatically generated"**—Partially true. Although CAD tools like SolidWorks can export URDF, the exported files typically require manual correction of joint limits, inertial parameters, and collision geometry before they can be used directly in simulation.

## 개요

URDF(Unified Robot Description Format)는 XML 기반의 로봇 설명 형식으로, 로봇의 링크, 관절, 관성, 기하학 및 운동학적 파라미터를 표준화된 방식으로 설명하는 데 사용됩니다. 그것이 진정으로 바꾼 것은 "그리기 방식"이 아니라 "로봇 모델의 교환 및 재사용 방식"입니다. 동일한 기계적 설명이 시뮬레이션, 제어, 내비게이션 및 시각화 등 서로 다른 소프트웨어 스택 간에 원활하게 흐를 수 있게 하여 ROS 생태계에서 로봇 모델링의 사실상 표준이 되었습니다.

## 핵심 내용

### 무엇인가: 정확한 정의

URDF는 XML 형식으로, 핵심은 `<link>`와 `<joint>` 두 가지 요소를 사용하여 로봇의 트리형 운동 체인을 설명하는 것입니다. `<link>`는 강체 속성(시각적 기하학, 충돌 기하학, 관성 텐서)을 정의하고, `<joint>`는 인접 링크 간의 운동 제약(관절 유형, 회전 축, 위치, 한계)을 정의합니다. 완전한 휴머노이드 로봇 URDF 파일은 본질적으로 기계 설계의 운동학적 트리(kinematic tree)를 기계가 읽을 수 있는 텍스트 형태로 고정시킨 것입니다.

일반적인 구조는 다음과 같습니다:

```xml
<robot name="humanoid">
  <link name="base_link">
    <inertial>
      <mass value="12.0"/>
      <inertia ixx="0.1" ixy="0.0" ixz="0.0"
               iyy="0.1" iyz="0.0" izz="0.08"/>
    </inertial>
    <visual>
      <geometry><mesh filename="base.dae"/></geometry>
    </visual>
  </link>
  <joint name="hip_pitch" type="revolute">
    <parent link="base_link"/>
    <child link="thigh"/>
    <origin xyz="0 0 -0.4" rpy="0 0 0"/>
    <axis xyz="0 1 0"/>
    <limit lower="-1.57" upper="1.57" effort="150" velocity="3.0"/>
  </joint>
</robot>
```

### 왜 존재하는가:痛点과 역사적 위치

URDF가 등장하기 전에는 로봇 설명 형식이 매우 파편화되어 있었습니다. 각 시뮬레이터(예: Gazebo, Webots)는 자체 모델 형식을 가지고 있었고, 각 제어 라이브러리(예: ODE, Bullet)는 또 다른 가져오기 인터페이스를 가지고 있었습니다. 이는 동일한 로봇을 다른 도구 간에 이전하려면 반복적인 모델링이 필요하고, 모델 간의 일관성을 보장할 수 없음을 의미했습니다.

URDF의 탄생은 바로 이痛点을 해결하기 위한 것이었습니다. ROS 커뮤니티가 주도했으며, **로봇 모델의 범용 교환 형식**으로 자리 잡았습니다. 그것이 진정으로 바꾼 것은 "모델링 정밀도"가 아니라 "생태계 협업"입니다. 일단 로봇에 URDF 설명이 있으면 ROS의 tf 트리, MoveIt의 운동 계획, Gazebo의 물리 시뮬레이션, RViz의 시각화에서 변환 없이 직접 소비할 수 있습니다. 이러한 "한 번 모델링, 어디서나 사용 가능" 특성 덕분에 URDF는 ROS 생태계에서 로봇 설명의 사실상 표준이 되었습니다.

### 원리 분석

**① 트리 구조: 운동학적 체인의 텍스트 매핑**

URDF는 로봇 설명을 트리 구조(각 링크는 최대 하나의 부모 관절)로 강제하며, 이는 대부분의 로봇 운동학적 체인과 일치합니다. 각 `<joint>`는 `<parent>`와 `<child>`를 통해 링크 간의 부모-자식 관계를 설정하여 좌표 변환 체인을 암시적으로 정의합니다. 휴머노이드 로봇의 경우 일반적인 트리 루트는 골반(pelvis)이며, 다리, 몸통, 팔이 하위 트리로 연결됩니다.

**② 관성 파라미터: 동역학 시뮬레이션의 기초**

`<inertial>` 요소의 질량과 관성 텐서(`<inertia>`의 6개 독립 성분)는 동역학 시뮬레이션과 제어의 핵심 입력입니다. 관성 텐서의 정확성은 시뮬레이션에서 관절 토크 계산에 직접적인 영향을 미칩니다. 고관절을 예로 들면, 전신 무게를 지탱하고 대퇴부를 통해 지면 반력을 전달하므로, 관성 파라미터 오류는 시뮬레이션 관절 토크가 실제와 크게 편차가 나게 합니다(공학적 판단).

**③ 관절 유형: 운동 제약의 인코딩**

URDF는 6가지 관절 유형을 지원합니다: `revolute`(회전), `continuous`(무한 회전), `prismatic`(슬라이딩), `fixed`(고정), `floating`(6-DOF 자유), `planar`(평면 운동). 휴머노이드 로봇에서 고관절, 무릎, 발목은 일반적으로 `revolute`를 사용하고 한계를 설정합니다. 예를 들어 고관절의 3-DOF 직교 축계(roll/pitch/yaw)는 URDF에서 세 개의 `revolute` 관절 직렬 연결로 표현됩니다:

$$
T_{\text{hip}} = R_z(\theta_{\text{yaw}}) \cdot R_y(\theta_{\text{pitch}}) \cdot R_x(\theta_{\text{roll}})
$$

**④ 기하학과 충돌: 시뮬레이션과 시각화의 이중 채널**

`<visual>`과 `<collision>`은 각각 시각적 메시와 충돌 기하학을 정의합니다. 이 둘을 분리한 설계는 고정밀 CAD 모델을 표시용으로 사용하면서, 충돌 감지에는 단순화된 기하체(예: 박스, 구체)를 사용하여 시뮬레이션 계산량을 줄일 수 있게 합니다.

### 핵심 파라미터 및 사양

| 파라미터 | 설명 | 일반적인 값(휴머노이드 로봇) |
|------|------|----------------------|
| `<mass>` | 링크 질량 (kg) | 고관절 링크 약 3–5 kg (공학적 판단) |
| `<inertia>` | 관성 텐서 (kg·m²) | CAD 또는 실측 교정 필요 |
| `<limit lower/upper>` | 관절 한계 (rad) | 고관절 pitch 약 ±1.57 rad |
| `<limit effort>` | 최대 관절 토크 (N·m) | 고관절 약 150–300 N·m (공학적 판단) |
| `<limit velocity>` | 최대 관절 속도 (rad/s) | 약 3.0–6.0 rad/s |
| `<origin xyz/rpy>` | 부모 링크 기준 관절 자세 | 기계 설계에 의해 결정 |
| `<axis xyz>` | 관절 회전 축 | 고관절 pitch는 [0,1,0] |

### 횡적 비교

| 특성 | URDF | MJCF (MuJoCo) | SDF (Gazebo) |
|------|------|----------------|---------------|
| 핵심 위치 | ROS 생태계 표준 | MuJoCo 시뮬레이션 형식 | Gazebo 시뮬레이션 형식 |
| 구조 | 트리(엄격) | 트리(자유 관절 지원) | 그래프(폐루프 지원) |
| 관성 설명 | 질량+관성 텐서 | 질량+관성 텐서 | 질량+관성 텐서 |
| 폐쇄 운동 체인 | 미지원 | equality 제약으로 지원 | 지원 |
| 내보내기 도구 | SolidWorks/Onshape 플러그인 | MuJoCo 내장 | Gazebo 내장 |
| 생태계 | ROS/MoveIt/RViz | MuJoCo/DeepMind | Gazebo/ROS |

URDF의 주요 한계는 **폐쇄 운동 체인 미지원**(예: 병렬 메커니즘)이며, 센서, 마찰, 구동기에 대한 표준화된 설명이 부족합니다. 휴머노이드 로봇과 같은 개방 체인 중심 시스템에는 URDF로 충분하지만, 병렬 발목 관절이나 다지성 손의 폐루프 구조가 포함되면 MJCF 또는 SDF를 고려해야 합니다.

### 누가 사용하는가·응용 사례

**① 시뮬레이션 검증 (SiL/HiL)**: URDF는 SiL(Software-in-the-Loop) 시뮬레이션의 기본 입력입니다. 순수 소프트웨어 환경에서 제어 알고리즘을 검증할 때 URDF는 피제어 객체의 동역학 모델을 제공합니다. HiL(Hardware-in-the-Loop) 테스트에서도 URDF는 실시간 시뮬레이션 머신의 plant model 생성에 사용됩니다.

**② 운동 계획 및 장애물 회피**: MoveIt은 URDF를 직접 소비하여 충돌 장면과 운동학적 트리를 구축하고, 로봇 팔 또는 전신 운동 계획에 사용합니다. 휴머노이드 로봇의 파지, 보행 계획은 모두 URDF가 제공하는 기하학 및 운동학 정보에 의존합니다.

**③ 시각화 및 디버깅**: RViz는 URDF를 로드하여 3D 시각화를 구현하고, 엔지니어가 개발 단계에서 관절 운동, 센서 위치, 배선 경로를 직관적으로 확인할 수 있게 합니다.

**④ 데이터 생성**: 합성 데이터 파이프라인에서 URDF 기반 시뮬레이션 환경(예: Isaac Sim)은 강화 학습 및 VLA 모델 훈련을 위한 주석이 달린 훈련 데이터를 대량 생성할 수 있습니다.

### 한계와 경계

1. **트리 구조 제한**: URDF는 하나의 링크가 여러 부모 노드를 가지는 것을 허용하지 않아 병렬 메커니즘 또는 폐쇄 운동 체인을 직접 설명할 수 없습니다. 휴머노이드 로봇의 개방 체인 구조(두 다리+몸통+두 팔)에는 충분하지만, 다지성 손의 다중 손가락 폐루프는 다른 형식이 필요합니다.
2. **센서 및 마찰 모델 부족**: URDF는 센서(IMU, 힘 센서)의 표준화된 설명을 포함하지 않으며, 마찰, 감쇠 등 접촉 파라미터도 지원하지 않습니다. 이러한 것은 Gazebo의 `<gazebo>` 확장 또는 MJCF로 보완해야 합니다.
3. **버전 관리 없음**: URDF 파일 형식 자체에는 버전 정보가 포함되지 않아, 서로 다른 ROS 버전 간의 호환성은 직접 확인해야 합니다.
4. **관성 파라미터 정확성**: URDF의 관성 파라미터가 CAD 추정에서 직접 온 경우 실제와 편차가 있을 수 있습니다. 고동적 제어(예: 달리기, 점프)의 경우 시스템 식별을 통한 수정이 필요합니다(공학적 판단).

### 일반적인 오해

1. **"URDF는 3D 모델이다"** — 틀림. URDF의 핵심은 운동학적 트리와 관성 파라미터이며, 3D 메시는 `<visual>`의 부수적 속성일 뿐입니다. 올바른 관절 정의와 관성 파라미터가 없으면 URDF는 동역학 시뮬레이션에 사용할 수 없습니다.
2. **"URDF는 모든 로봇 구조를 지원한다"** — 틀림. URDF의 트리 구조는 병렬 메커니즘 또는 폐루프 체인을 설명할 수 없습니다. 이러한 구조에는 SDF 또는 MJCF를 사용해야 합니다.
3. **"URDF의 관성 파라미터는 중요하지 않다"** — 틀림. 관성 텐서는 동역학 시뮬레이션의 관절 토크를 직접 결정합니다. 고관절을 예로 들면, 전신 무게를 지탱하므로 관성 파라미터 오류는 시뮬레이션 토크가 실제와 크게 편차가 나게 합니다.
4. **"URDF는 자동 생성될 수 있다"** — 부분적으로 맞음. SolidWorks와 같은 CAD 도구가 URDF를 내보낼 수 있지만, 내보낸 파일은 일반적으로 관절 한계, 관성 파라미터, 충돌 기하학을 수동으로 수정해야 하며 시뮬레이션에 직접 사용할 수 없습니다.

### 관련 지식

- `ent_software_nvidia_isaac_sim_2024` — GPU 가속 시뮬레이터로, URDF를 직접 가져와 고충실도 환경을 구축하여 합성 데이터 생성 및 강화 학습 훈련에 사용할 수 있습니다.
- `ent_software_gazebo` — 클래식 로봇 시뮬레이터로, URDF는 기본 지원 모델 형식이며 `<gazebo>` 확장을 통해 물리 속성을 보완합니다.
- `ent_technology_mjcf_simulation_format_2024` — MuJoCo의 MJCF 형식으로, URDF와 위치가 유사하지만 폐루프 체인과 더 풍부한 접촉 모델을 지원하며 상호 변환이 가능합니다.
- `ent_method_hardware_in_the_loop` — HiL 테스트에서 URDF는 실시간 시뮬레이션 머신의 plant model 생성에 사용되어 실제 하드웨어에서 컨트롤러의 타이밍과 성능을 검증합니다.
- `ent_benchmark_humanoidbench` — Unitree H1 기반 시뮬레이션 벤치마크로, 작업 환경은 URDF로 로봇 모델을 설명하며 VLA 및 제어 알고리즘의 통제된 비교에 사용됩니다.
- `ent_robot_unitree_h1_humanoid_robot_2024` — Unitree H1 휴머노이드 로봇으로, 그 URDF 모델은 커뮤니티에서 널리 사용되며 HumanoidBench와 같은 벤치마크의 기초입니다.
