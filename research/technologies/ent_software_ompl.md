## 概述

OMPL（Open Motion Planning Library）是一个实现了 RRT、RRT*、PRM、BIT* 等基于采样的运动规划算法的开源 C++ 库，是 ROS 生态中 MoveIt 框架的默认规划器后端。它本身不包含碰撞检测或可视化代码，而是通过插件化接口与外部系统集成，广泛用于机械臂及人形机器人的全身运动规划。

## 核心内容

### 是什么：准确定义

OMPL 是一个**纯算法库**，核心资产是一组状态空间（state space）抽象与在其上运行的采样规划器实现。它不关心机器人长什么样、障碍物如何表示、路径如何可视化——这些全部留给集成方。官方文档明确写道："OMPL itself does not contain any code related to, e.g., collision checking or visualization. This is a deliberate design choice, so that OMPL is not tied to a particular collision checker or visualization front end."

这个定位使它区别于 MoveIt（完整规划框架）和 Pinocchio（动力学计算库）。OMPL 解决的是**几何路径搜索**问题：给定构型空间 C-space 中的起点与目标，找到一条无碰撞的连续路径。它不负责动力学可行性——那是下层控制器（如 WBC 或 MPC）的职责。

### 为什么存在：痛点与历史定位

在 OMPL 出现之前，运动规划算法研究与机器人应用之间存在一条鸿沟。研究者实现一个 RRT 变体，往往要花大量时间处理碰撞检测、模型加载、可视化等与算法本身无关的工程问题；而应用工程师想用上最新算法，又缺乏统一接口。

OMPL 的诞生正是为了填平这条鸿沟：把算法层与系统层彻底解耦。它真正改变的不是某个具体算法，而是**算法研究与工程部署之间的协作方式**——研究者只需实现规划器接口，应用方只需提供状态空间与碰撞检测回调，双方通过 OMPL 的抽象层对接，互不侵入。

在人形机器人领域，这个痛点尤为尖锐。人形机器人全身上下数十个执行器以毫秒级周期闭环，显式表示其 C-space 障碍在计算上不可行（40+ 自由度的构型空间维度极高），采样式规划的概率完备性使其成为少数可行的方案之一。OMPL 因此成为 MoveIt 的默认规划器后端，并支撑了 NASA Robonaut2 在国际空间站的步态规划等标志性应用。

### 原理拆解

**① 采样式规划的核心思想**

采样式规划的基本思想是在构型空间（configuration space, C-space）中随机采样并局部连接，逐步构建可达路径图或树，从而回避了对高维空间障碍的显式建模。这对 40+ 自由度的人形机器人至关重要，因为显式表示其 C-space 障碍在计算上不可行。

**② 概率完备性**

采样规划器在采样数趋于无穷时以概率 1 找到可行解（若解存在）的性质，称为**概率完备性（probabilistic completeness）**。这是 OMPL 中 RRT、PRM、BIT* 等算法的理论基石——它们不保证有限时间内找到解，但保证"只要采样足够多，找到解的概率趋近于 1"。

**③ 算法族谱**

OMPL 包含三类核心算法：

- **RRT（Rapidly-exploring Random Tree）**：从起点出发，随机采样并逐步扩展一棵树，偏向于探索未访问区域。
- **RRT\***：在 RRT 基础上引入重连（rewiring）机制，保证渐近最优性——随着采样数增加，解路径收敛到最优。
- **PRM（Probabilistic Roadmap）**：在 C-space 中随机采样大量点，连接邻近点构成路标图，适合多查询场景。
- **BIT\***：结合图搜索与采样，利用启发式信息加速收敛。

**④ 与碰撞检测的接口**

OMPL 通过 `StateValidityChecker` 回调接口询问"某个状态是否合法"，由集成方实现具体的碰撞检测逻辑。官方默认支持 VAMP（SIMD 加速的碰撞检测与正运动学库），可将规划时间缩短数个数量级（several orders of magnitude）；也支持 Pinocchio 作为运动学计算后端。

### 谁在用·应用案例

**① NASA Robonaut2（国际空间站）**

OMPL 被用于规划 Robonaut2 的足部步态（footsteps）。这是 OMPL 在太空环境中的标志性应用——在微重力下，机器人需要规划复杂的足部移动序列以在空间站内导航。

**② Amazon Picking Challenge（2016）**

代尔夫特理工大学团队使用基于 MoveIt 的定制运动规划管线赢得比赛，其中 OMPL 承担核心规划任务。这验证了 OMPL 在仓储抓取场景中的工程可靠性。

**③ 多模态运动规划**

OMPL 被用于多模态规划器，实现复杂机器人行为——例如从拼图盒中取出杠铃物体。这类任务需要切换不同的运动模式（如"推动"与"抓取"），OMPL 的低层规划能力是其中的关键环节。

**④ 约束运动规划**

OMPL 支持运动学约束机器人的规划。官方演示的并联机构超过 150 个自由度，但可行运动仍可在数秒内计算得出——这得益于约束流形上的采样策略。

**⑤ 人形机器人软件栈**

在人形机器人中，OMPL 位于规划层（1–20 Hz，延迟预算数十 ms），与 MoveIt 配合生成无碰撞的几何路径，再由下层控制器（WBC 或 MPC）负责动力学可行的实时执行。工程上常用"规划于粗模型、执行时在线避障"的两级结构，以应对规划-执行异步问题。

### 局限与边界

**① 不解决动力学可行性**

OMPL 生成的路径是几何无碰撞的，但不保证动力学可行——关节速度、加速度、力矩约束均不在其考虑范围内。工程上必须由下层控制器（WBC/MPC）对路径做时间参数化与动力学修正。

**② 概率完备 ≠ 确定性完备**

OMPL 的算法不保证有限时间内找到解，也不保证解的最优性（RRT 甚至不保证渐近最优）。在狭窄通道（narrow passage）场景中，采样效率可能极低，需要偏置采样或学习先验来加速。

**③ 规划-执行异步问题**

规划完成时环境可能已偏离规划假设，导致轨迹过时。人形机器人场景中，全身碰撞对数量大（含自碰撞）、平衡约束需与控制层协调，这些问题 OMPL 本身不处理，需要集成方在架构层面解决。

**④ 不包含感知与状态估计**

OMPL 假设已知 C-space 中的障碍分布，但障碍从何而来（感知、建图、预测）完全不在其职责范围内。它真正改变的不是"机器人如何感知世界"，而是"给定世界模型后如何找到路径"。

### 常见误区

1. **"OMPL 就是 MoveIt"**——错。MoveIt 是完整规划框架，OMPL 只是其默认规划器后端。团队可以只复用 MoveIt 的碰撞管线而自研规划器，或反之。OMPL 本身不包含任何碰撞检测或可视化代码。

2. **"OMPL 能直接用于人形机器人全身控制"**——错。OMPL 输出的是几何路径，不是控制指令。它位于规划层（1–20 Hz），而全身控制（WBC）位于控制层（100–1000 Hz），两者之间必须经过轨迹时间参数化与动力学修正。

3. **"RRT* 一定比 RRT 好"**——不一定。RRT* 保证渐近最优性，但计算开销更大。在时限严格的场景中，RRT 可能更快找到可行解。工程上需要根据延迟预算（数十 ms 级）权衡。

4. **"OMPL 只用于机械臂"**——错。官方文档明确列出其应用范围包括（移动）机械臂、类车系统、无人机和水下航行器，以及人形机器人的步态规划。

5. **"采样规划器能找到最优解"**——只有渐近最优。RRT* 和 BIT* 在采样数趋于无穷时收敛到最优解，但有限时间内只能保证"足够好"的可行解。

## Overview

OMPL (Open Motion Planning Library) is an open-source C++ library that implements sampling-based motion planning algorithms such as RRT, RRT*, PRM, and BIT*. It serves as the default planner backend for the MoveIt framework in the ROS ecosystem. It does not include collision checking or visualization code itself but integrates with external systems through plugin interfaces, and is widely used for whole-body motion planning of robotic arms and humanoid robots.

## Content

### What it is: precise definition

OMPL is a **pure algorithm library** whose core assets are a set of state space abstractions and sampling-based planner implementations that operate on them. It does not care what the robot looks like, how obstacles are represented, or how paths are visualized—these are all left to the integrator. The official documentation explicitly states: "OMPL itself does not contain any code related to, e.g., collision checking or visualization. This is a deliberate design choice, so that OMPL is not tied to a particular collision checker or visualization front end."

This positioning distinguishes it from MoveIt (a complete planning framework) and Pinocchio (a dynamics computation library). OMPL addresses the **geometric path search** problem: given a start and goal in the configuration space (C-space), find a collision-free continuous path. It is not responsible for dynamic feasibility—that is the responsibility of lower-level controllers (such as WBC or MPC).

### Why it exists: pain points and historical positioning

Before OMPL emerged, there was a gap between motion planning algorithm research and robotic applications. Researchers implementing an RRT variant often had to spend significant time on engineering issues unrelated to the algorithm itself, such as collision checking, model loading, and visualization. Meanwhile, application engineers wanting to use the latest algorithms lacked a unified interface.

OMPL was born precisely to bridge this gap: by completely decoupling the algorithm layer from the system layer. What it truly changed was not any specific algorithm, but rather **the collaboration model between algorithm research and engineering deployment**—researchers only need to implement the planner interface, and application developers only need to provide the state space and collision checking callbacks. The two sides connect through OMPL's abstraction layer without intruding on each other.

In the humanoid robotics domain, this pain point is particularly acute. A humanoid robot's dozens of actuators close the loop at millisecond-level cycles, and explicitly representing its C-space obstacles is computationally infeasible (the configuration space of 40+ degrees of freedom has extremely high dimensionality). The probabilistic completeness of sampling-based planning makes it one of the few viable approaches. OMPL therefore became the default planner backend for MoveIt and has supported landmark applications such as NASA Robonaut2's gait planning on the International Space Station.

### Principle breakdown

**① Core idea of sampling-based planning**

The fundamental idea of sampling-based planning is to randomly sample and locally connect points in the configuration space (C-space), progressively building a reachable path graph or tree, thereby avoiding explicit modeling of obstacles in high-dimensional spaces. This is crucial for humanoid robots with 40+ degrees of freedom, because explicitly representing their C-space obstacles is computationally infeasible.

**② Probabilistic completeness**

The property that a sampling-based planner finds a feasible solution with probability 1 as the number of samples tends to infinity (if a solution exists) is called **probabilistic completeness**. This is the theoretical cornerstone of algorithms such as RRT, PRM, and BIT* in OMPL—they do not guarantee finding a solution within finite time, but they guarantee that "as long as enough samples are taken, the probability of finding a solution approaches 1."

**③ Algorithm family tree**

OMPL contains three core categories of algorithms:

- **RRT (Rapidly-exploring Random Tree)**: Starting from the start point, randomly samples and progressively expands a tree, biased toward exploring unvisited regions.
- **RRT\***: Introduces a rewiring mechanism on top of RRT, guaranteeing asymptotic optimality—as the number of samples increases, the solution path converges to the optimum.
- **PRM (Probabilistic Roadmap)**: Randomly samples a large number of points in C-space and connects nearby points to form a roadmap graph, suitable for multi-query scenarios.
- **BIT\***: Combines graph search with sampling, using heuristic information to accelerate convergence.

**④ Interface with collision checking**

OMPL queries "whether a state is valid" through the `StateValidityChecker` callback interface, with the integrator implementing the specific collision checking logic. The official default supports VAMP (a SIMD-accelerated collision checking and forward kinematics library), which can reduce planning time by several orders of magnitude; it also supports Pinocchio as a kinematics computation backend.

### Who uses it: application cases

**① NASA Robonaut2 (International Space Station)**

OMPL was used to plan Robonaut2's footsteps. This is a landmark application of OMPL in a space environment—in microgravity, the robot needs to plan complex foot placement sequences to navigate within the space station.

**② Amazon Picking Challenge (2016)**

The Delft University of Technology team won the competition using a customized motion planning pipeline based on MoveIt, with OMPL handling the core planning tasks. This validated OMPL's engineering reliability in warehouse picking scenarios.

**③ Multimodal motion planning**

OMPL has been used in multimodal planners to achieve complex robot behaviors—for example, extracting a barbell-shaped object from a puzzle box. Such tasks require switching between different motion modes (such as "pushing" and "grasping"), and OMPL's low-level planning capability is a key component.

**④ Constrained motion planning**

OMPL supports planning for robots with kinematic constraints. The officially demonstrated parallel mechanism has over 150 degrees of freedom, yet feasible motions can still be computed within seconds—thanks to sampling strategies on constraint manifolds.

**⑤ Humanoid robot software stack**

In humanoid robots, OMPL resides in the planning layer (1–20 Hz, with a latency budget of tens of ms), working with MoveIt to generate collision-free geometric paths, which are then executed in real time by lower-level controllers (WBC or MPC) that ensure dynamic feasibility. In engineering practice, a two-level structure of "planning on a coarse model, online obstacle avoidance during execution" is commonly used to address the planning-execution asynchrony problem.

### Limitations and boundaries

**① Does not address dynamic feasibility**

Paths generated by OMPL are geometrically collision-free but not guaranteed to be dynamically feasible—joint velocity, acceleration, and torque constraints are outside its scope. In engineering practice, lower-level controllers (WBC/MPC) must perform time parameterization and dynamic correction on the paths.

**② Probabilistic completeness ≠ deterministic completeness**

OMPL's algorithms do not guarantee finding a solution within finite time, nor do they guarantee solution optimality (RRT does not even guarantee asymptotic optimality). In narrow passage scenarios, sampling efficiency can be extremely low, requiring biased sampling or learned priors to accelerate.

**③ Planning-execution asynchrony problem**

By the time planning completes, the environment may have deviated from the planning assumptions, causing the trajectory to become outdated. In humanoid scenarios, the large number of whole-body collision pairs (including self-collisions) and balance constraints that must be coordinated with the control layer are issues that OMPL itself does not handle—the integrator must address them at the architecture level.

**④ Does not include perception or state estimation**

OMPL assumes known obstacle distributions in C-space, but where obstacles come from (perception, mapping, prediction) is entirely outside its scope. What it truly changes is not "how the robot perceives the world," but "how to find a path given a world model."

### Common misconceptions

1. **"OMPL is MoveIt"**—Incorrect. MoveIt is a complete planning framework; OMPL is only its default planner backend. Teams can reuse only MoveIt's collision pipeline while developing their own planner, or vice versa. OMPL itself contains no collision checking or visualization code.

2. **"OMPL can be directly used for humanoid whole-body control"**—Incorrect. OMPL outputs geometric paths, not control commands. It resides in the planning layer (1–20 Hz), while whole-body control (WBC) resides in the control layer (100–1000 Hz). Trajectory time parameterization and dynamic correction are required between the two.

3. **"RRT* is always better than RRT"**—Not necessarily. RRT* guarantees asymptotic optimality but has higher computational overhead. In scenarios with strict time limits, RRT may find a feasible solution faster. Engineering trade-offs must be made based on latency budgets (on the order of tens of ms).

4. **"OMPL is only for robotic arms"**—Incorrect. The official documentation explicitly lists its application scope, including (mobile) manipulators, car-like systems, drones, and underwater vehicles, as well as gait planning for humanoid robots.

5. **"Sampling-based planners can find optimal solutions"**—Only asymptotically optimal. RRT* and BIT* converge to optimal solutions as the number of samples tends to infinity, but within finite time they can only guarantee "good enough" feasible solutions.

### Related knowledge

- `ent_software_moveit_motion_planning_2024` — MoveIt is the most mature motion planning framework in the ROS ecosystem, and OMPL is its default planner backend; together they form the standard combination for the planning layer.
- `ent_software_pinocchio` — Pinocchio provides millisecond-level rigid-body dynamics computation, and OMPL supports integrating it as a kinematics backend; the two handle planning and dynamics computation respectively in the software stack.
- `ent_software_drake_systems_toolbox_2024` — Drake supports optimization-based control and offline verification, complementing OMPL's sampling-based planning—the former leans toward optimization, the latter toward search.
- `ent_software_ros_2_middleware_2024` — The ROS 2 computation graph is the carrier through which OMPL is embedded into robotic systems, invoked as a node or library via MoveIt.
- `ent_technology_ethercat_2024` — Fieldbuses such as EtherCAT carry 1 kHz-level joint closed loops, forming a frequency hierarchy with OMPL's planning layer (1–20 Hz), decoupled through state interfaces.

## 개요

OMPL(Open Motion Planning Library)은 RRT, RRT*, PRM, BIT* 등 샘플링 기반 운동 계획 알고리즘을 구현한 오픈소스 C++ 라이브러리로, ROS 생태계에서 MoveIt 프레임워크의 기본 플래너 백엔드입니다. 자체적으로 충돌 감지나 시각화 코드를 포함하지 않으며, 플러그인 인터페이스를 통해 외부 시스템과 통합되어 로봇 팔 및 휴머노이드 로봇의 전신 운동 계획에 널리 사용됩니다.

## 핵심 내용

### 무엇인가: 정확한 정의

OMPL은 **순수 알고리즘 라이브러리**로, 핵심 자산은 상태 공간(state space) 추상화 집합과 그 위에서 작동하는 샘플링 플래너 구현입니다. 로봇의 외형, 장애물 표현 방식, 경로 시각화 방법에는 관여하지 않습니다——이 모든 것은 통합 측에 맡겨집니다. 공식 문서에는 다음과 같이 명시되어 있습니다: "OMPL itself does not contain any code related to, e.g., collision checking or visualization. This is a deliberate design choice, so that OMPL is not tied to a particular collision checker or visualization front end."

이러한 포지셔닝은 MoveIt(완전한 계획 프레임워크) 및 Pinocchio(동역학 계산 라이브러리)와 차별화됩니다. OMPL이 해결하는 것은 **기하학적 경로 탐색** 문제입니다: 구성 공간 C-space에서 시작점과 목표가 주어졌을 때, 충돌 없는 연속 경로를 찾는 것입니다. 동역학적 실현 가능성은 담당하지 않습니다——이는 하위 제어기(예: WBC 또는 MPC)의 역할입니다.

### 왜 존재하는가: 문제점과 역사적 위치

OMPL이 등장하기 전에는 운동 계획 알고리즘 연구와 로봇 응용 사이에 큰 간극이 있었습니다. 연구자가 RRT 변형을 구현할 때는 충돌 감지, 모델 로딩, 시각화 등 알고리즘 자체와 무관한 엔지니어링 문제에 많은 시간을 쏟아야 했고, 응용 엔지니어가 최신 알고리즘을 사용하려 해도 통일된 인터페이스가 부재했습니다.

OMPL의 탄생은 바로 이 간극을 메우기 위한 것이었습니다: 알고리즘 계층과 시스템 계층을 완전히 분리하는 것입니다. 실제로 변화시킨 것은 특정 알고리즘이 아니라 **알고리즘 연구와 엔지니어링 배포 간의 협업 방식**입니다——연구자는 플래너 인터페이스만 구현하면 되고, 응용 측은 상태 공간과 충돌 감지 콜백만 제공하면 되며, 양측은 OMPL의 추상화 계층을 통해 연결되어 서로를 침범하지 않습니다.

휴머노이드 로봇 분야에서 이 문제점은 특히 심각합니다. 휴머노이드 로봇의 수십 개 액추에이터가 밀리초 주기로 폐루프를 형성하며, C-space 장애물을 명시적으로 표현하는 것은 계산적으로 불가능합니다(40+ 자유도의 구성 공간 차원이 매우 높음). 샘플링 방식 알고리즘의 확률적 완전성은 이를 가능하게 하는 몇 안 되는 대안 중 하나입니다. 따라서 OMPL은 MoveIt의 기본 플래너 백엔드가 되었고, NASA Robonaut2의 국제우주정거장 보행 계획과 같은 상징적인 응용을 지원했습니다.

### 원리 분석

**① 샘플링 기반 계획의 핵심 아이디어**

샘플링 기반 계획의 기본 아이디어는 구성 공간(configuration space, C-space)에서 무작위로 샘플링하고 국소적으로 연결하여 점진적으로 도달 가능한 경로 그래프나 트리를 구축함으로써, 고차원 공간의 장애물을 명시적으로 모델링하는 것을 회피하는 것입니다. 이는 40+ 자유도의 휴머노이드 로봇에 매우 중요합니다. C-space 장애물을 명시적으로 표현하는 것이 계산적으로 불가능하기 때문입니다.

**② 확률적 완전성**

샘플링 플래너가 샘플 수가 무한대로 갈 때 확률 1로(해가 존재한다면) 실현 가능한 해를 찾는 성질을 **확률적 완전성(probabilistic completeness)**이라고 합니다. 이는 OMPL의 RRT, PRM, BIT* 등 알고리즘의 이론적 기반입니다——유한 시간 내에 해를 찾는 것을 보장하지는 않지만, "충분히 많이 샘플링하면 해를 찾을 확률이 1에 수렴한다"는 것을 보장합니다.

**③ 알고리즘 계보**

OMPL은 세 가지 핵심 알고리즘을 포함합니다:

- **RRT(Rapidly-exploring Random Tree)**: 시작점에서 출발하여 무작위로 샘플링하고 트리를 점진적으로 확장하며, 미방문 영역을 탐색하는 데 치중합니다.
- **RRT\***: RRT에 재연결(rewiring) 메커니즘을 도입하여 점근적 최적성을 보장합니다——샘플 수가 증가함에 따라 해 경로가 최적에 수렴합니다.
- **PRM(Probabilistic Roadmap)**: C-space에서 많은 점을 무작위로 샘플링하고 인접 점을 연결하여 로드맵 그래프를 구성하며, 다중 쿼리 시나리오에 적합합니다.
- **BIT\***: 그래프 탐색과 샘플링을 결합하고 휴리스틱 정보를 활용하여 수렴을 가속화합니다.

**④ 충돌 감지와의 인터페이스**

OMPL은 `StateValidityChecker` 콜백 인터페이스를 통해 "특정 상태가 유효한지"를 질의하며, 통합 측이 구체적인 충돌 감지 로직을 구현합니다. 공식적으로 VAMP(SIMD 가속 충돌 감지 및 정기구학 라이브러리)를 기본 지원하여 계획 시간을 수 자릿수(several orders of magnitude) 단축할 수 있습니다; 또한 Pinocchio를 기구학 계산 백엔드로 지원합니다.

### 사용 사례·응용 사례

**① NASA Robonaut2(국제우주정거장)**

OMPL은 Robonaut2의 발걸음(footsteps) 계획에 사용되었습니다. 이는 OMPL의 우주 환경에서의 상징적인 응용입니다——미세 중력에서 로봇은 우주정거장 내를 이동하기 위해 복잡한 발 이동 시퀀스를 계획해야 합니다.

**② Amazon Picking Challenge(2016)**

델프트 공과대학 팀이 MoveIt 기반 맞춤형 운동 계획 파이프라인을 사용하여 대회에서 우승했으며, OMPL이 핵심 계획 작업을 담당했습니다. 이는 창고 피킹 시나리오에서 OMPL의 공학적 신뢰성을 검증했습니다.

**③ 다중 모드 운동 계획**

OMPL은 다중 모드 플래너에 사용되어 복잡한 로봇 동작을 구현합니다——예를 들어 퍼즐 상자에서 바벨 물체를 꺼내는 작업이 있습니다. 이러한 작업은 서로 다른 운동 모드(예: "밀기"와 "잡기")를 전환해야 하며, OMPL의 하위 계획 능력이 핵심 요소입니다.

**④ 제약 운동 계획**

OMPL은 기구학적 제약이 있는 로봇의 계획을 지원합니다. 공식 데모의 병렬 메커니즘은 150개 이상의 자유도를 가지지만, 실현 가능한 운동은 여전히 수 초 내에 계산될 수 있습니다——이는 제약 다양체 위의 샘플링 전략 덕분입니다.

**⑤ 휴머노이드 로봇 소프트웨어 스택**

휴머노이드 로봇에서 OMPL은 계획 계층(1–20 Hz, 지연 예산 수십 ms)에 위치하며, MoveIt과 협력하여 충돌 없는 기하학적 경로를 생성하고, 하위 제어기(WBC 또는 MPC)가 동역학적으로 실현 가능한 실시간 실행을 담당합니다. 공학적으로는 "거친 모델로 계획하고, 실행 시 온라인 장애물 회피"라는 2단계 구조를 흔히 사용하여 계획-실행 비동기 문제에 대응합니다.

### 한계와 경계

**① 동역학적 실현 가능성을 해결하지 않음**

OMPL이 생성하는 경로는 기하학적으로 충돌이 없지만, 동역학적 실현 가능성은 보장하지 않습니다——관절 속도, 가속도, 토크 제약은 모두 고려 범위에 없습니다. 공학적으로는 하위 제어기(WBC/MPC)가 경로에 대한 시간 파라미터화와 동역학 수정을 반드시 수행해야 합니다.

**② 확률적 완전성 ≠ 결정적 완전성**

OMPL의 알고리즘은 유한 시간 내에 해를 찾는 것을 보장하지 않으며, 해의 최적성도 보장하지 않습니다(RRT는 점근적 최적성조차 보장하지 않음). 좁은 통로(narrow passage) 시나리오에서는 샘플링 효율이 극도로 낮아질 수 있으며, 바이어스 샘플링이나 학습 사전 지식을 통해 가속화해야 합니다.

**③ 계획-실행 비동기 문제**

계획이 완료될 때 환경이 계획 가정에서 벗어나 궤적이 낡을 수 있습니다. 휴머노이드 로봇 시나리오에서는 전신 충돌 쌍이 많고(자체 충돌 포함), 균형 제약이 제어 계층과 조정되어야 하며, 이러한 문제는 OMPL 자체가 처리하지 않으므로 통합 측이 아키텍처 수준에서 해결해야 합니다.

**④ 인식 및 상태 추정을 포함하지 않음**

OMPL은 C-space의 장애물 분포가 알려져 있다고 가정하지만, 장애물이 어디서 오는지(인식, 매핑, 예측)는 전적으로 그 책임 범위 밖입니다. 실제로 변화시킨 것은 "로봇이 세상을 어떻게 인식하는가"가 아니라 "세계 모델이 주어졌을 때 어떻게 경로를 찾는가"입니다.

### 흔한 오해

1. **"OMPL이 곧 MoveIt이다"**——틀림. MoveIt은 완전한 계획 프레임워크이고, OMPL은 그 기본 플래너 백엔드일 뿐입니다. 팀은 MoveIt의 충돌 파이프라인만 재사용하고 자체 플래너를 개발할 수도 있고, 그 반대도 가능합니다. OMPL 자체에는 충돌 감지나 시각화 코드가 포함되어 있지 않습니다.

2. **"OMPL을 휴머노이드 로봇 전신 제어에 직접 사용할 수 있다"**——틀림. OMPL이 출력하는 것은 기하학적 경로이지 제어 명령이 아닙니다. 계획 계층(1–20 Hz)에 위치하며, 전신 제어(WBC)는 제어 계층(100–1000 Hz)에 위치하므로, 둘 사이에는 반드시 궤적 시간 파라미터화와 동역학 수정이 필요합니다.

3. **"RRT*가 반드시 RRT보다 낫다"**——아님. RRT*는 점근적 최적성을 보장하지만 계산 비용이 더 큽니다. 시간 제약이 엄격한 시나리오에서는 RRT가 실현 가능한 해를 더 빨리 찾을 수 있습니다. 공학적으로는 지연 예산(수십 ms 수준)에 따라权衡해야 합니다.

4. **"OMPL은 로봇 팔에만 사용된다"**——틀림. 공식 문서는 응용 범위에 (이동) 로봇 팔, 차량형 시스템, 드론 및 수중 항행체, 그리고 휴머노이드 로봇의 보행 계획이 포함된다고 명시합니다.

5. **"샘플링 플래너는 최적해를 찾을 수 있다"**——점근적 최적성만 있음. RRT*와 BIT*는 샘플 수가 무한대로 갈 때 최적해에 수렴하지만, 유한 시간 내에는 "충분히 좋은" 실현 가능한 해만 보장합니다.

### 관련 지식

- `ent_software_moveit_motion_planning_2024`` — MoveIt은 ROS 생태계에서 가장 성숙한 운동 계획 프레임워크이며, OMPL은 그 기본 플래너 백엔드로, 둘은 계획 계층의 표준 조합을 구성합니다.
- `ent_software_pinocchio` — Pinocchio는 밀리초급 강체 동역학 계산을 제공하며, OMPL은 이를 기구학 백엔드로 통합하는 것을 지원합니다. 둘은 소프트웨어 스택에서 각각 계획과 동역학 계산을 담당합니다.
- `ent_software_drake_systems_toolbox_2024`` — Drake는 최적화 기반 제어와 오프라인 검증을 지원하며, OMPL의 샘플링 계획과 상호 보완적입니다——전자는 최적화에, 후자는 탐색에 치중합니다.
- `ent_software_ros_2_middleware_2024`` — ROS 2 계산 그래프는 OMPL이 로봇 시스템에 내장되는 매개체이며, MoveIt을 통해 노드 또는 라이브러리로 호출됩니다.
- `ent_technology_ethercat_2024`` — EtherCAT 등 필드버스는 1 kHz급 관절 폐루프를 담당하며, OMPL이 위치한 계획 계층(1–20 Hz)과 주파수 계층을 구성하고, 둘은 상태 인터페이스를 통해 분리됩니다.
